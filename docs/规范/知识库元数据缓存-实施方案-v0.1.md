## 结论摘要（先给裁决）

1. **缓存边界**：进缓存的只有五个读路径元数据资源（库列表 / 库详情 / 文档列表（规范视图）/ 文档条目 / 库内目录）；**检索、入库、进度、时间线、正文一律不进**，且用"资源清单唯一一份 + 分类守卫用例"把它变成机械判据（§1）。
2. **缓存放哪一层**（最关键的分叉）：**放本机后端（SQLite），同时服务两个读面**——① `KnowledgeMetaReader` 与 HTTP 之间的 reader 面（M3 §2.4 的承诺，`stores.meta` 与 `services/` 一行不改）；② 新增只读端点族 `/api/v1/local/kb-cache/*` 给知识库页面"**先画快照**"用。**页面那条实时读一字不改**（仍是会话身份直连 NAS）。理由与两条候选路的代价对照见 §2。
3. **不能让页面改走"本机后端代理读 NAS"**：那会把页面身份（会话令牌：管理员/成员、KB 范围、`can_write`/`can_manage`）换成边车钥匙身份（`is_admin=false`、无范围限制，M3 §1.4），受限成员会**看到全部库**、管理员会**丢掉管理入口**——这是不可接受的一致性代价。
4. **NAS 侧不改一个字**：实测 `GET /knowledge-bases`、`/documents`、`/folders` **都没有** `ETag`/`Last-Modified`（全仓只有 `backend/app/api/v1/frontend.py:134` 与 `backend/app/services/connectors/base.py:112-140` 两处用 etag，都不是 KB 读端点；`backend/app/main.py:169-175` 只有 CORS 中间件）。所以 **etag / last_modified 两列照 v0.3 §6.3 建好但今天恒 NULL**，"变没变"的判据由**内容哈希版本戳**承担（§4）。
5. **本机库已发版**（M2 落地，用户机器上已有 v1 库）⇒ 缓存表只能走**增量迁移 v2**，`schema.sql` 基线冻结不动（与 PG 侧 `postgres_schema.sql:1-5` + `MIGRATIONS` 同一纪律）〔§3〕。

## 1. 缓存边界（问题 1）

### 1.1 进缓存（五个资源，正向清单只有一处）

| 资源 `resource` | NAS 端点 | `scope_key` | 为什么进 | 缓存里**必须剥掉**的字段 |
| --- | --- | --- | --- | --- |
| `kb_list` | `GET /knowledge-bases`（`api/v1/knowledge_bases.py:124-143`） | `''`（每个提供者一行） | v0.3 §6.3 点名的"库列表"；列表页与卡片/行两态的骨架 | `can_write` / `can_manage`（按调用者算，`:29-49`、`:52-67`） |
| `kb_detail` | `GET /knowledge-bases/{id}`（`:146-160`） | `kb_id` | "库详情"；且 reader 面每轮每库读的就是它（`chat.py:681-689`） | 同上 |
| `doc_list` | `GET /knowledge-bases/{id}/documents`（`frontend/src/api/documents.ts:112-125`） | `kb_id\|folder:<id\|root\|all>\|page:<n>\|size:<n>`，**只认规范视图**（无 `q` / `stage` / `source_kind`） | v0.3 §6.3 点名的"文档列表"；页面挂载那 3 次往返里最重的一次 | 每行的 `progress`（`DocumentProgressOut`，`schemas.py:218-240`）——**冻结的进度条是最糟的假象** |
| `document` | `GET /documents/{id}`（`documents.ts:139-140`） | `document_id` | "条目信息"；文档详情页 / 抽屉的入口帧 | 无 |
| `folders` | `GET /knowledge-bases/{id}/folders`（`features/knowledge/KnowledgeBaseView.tsx:305-313`） | `kb_id` | 与文档列表**同屏**的目录树；不做就是"半屏缓存" | 无 |

另：`loadCounts` 那次 `listDocuments(root:true, limit:1)`（`:316-323`）就落成 `doc_list` 的一个 scope（`size:1`），不必单开资源。

### 1.2 不进缓存（逐条给理由，写进模块常量）

| 不进的东西 | 理由 |
| --- | --- |
| `POST /search`（检索） | **v0.3 §6.3 定案**："轮次中的检索调用不缓存（正确性优先）"。它决定"这一轮依据了什么"，会进 `sources` 快照与 `[n]` 引用编号（M3 阶段 7 刚修好 `knowledge_base_id`）——缓存它等于让回答依据过期资料 |
| 入库 / 建库 / 改名 / 删库 / 目录 / 切块 / 分享 / Wiki 写操作 | §6.3 定案"写一律不进"；写成功后由页面自己那条链如实更新，**并且失效对应缓存键**（§3.4） |
| `/documents/{id}/timeline`、`progress`、租约/停滞 | 活数据；"看起来在动其实没动"是最坏的假象 |
| `/documents/{id}/parts` `/chunks` `/preview` `/download-url` `/content` | v0.3 §4"本地只留**元数据**缓存"，正文不是元数据，体积也不可控（§5.3 缓存严格可弃） |
| `/trash` `/api-keys` `/users` `/stats/*` `/tasks` `/maintenance/*` | 账号 / 后台 / 聚合，不属于"知识库读路径元数据" |
| `GET /provider/handshake` | 它是**状态**不是数据，已有自己的 30s 进程内缓存（`knowledge_provider.py:131-136`、`:340-356`）；M4 不落库 |

### 1.3 "检索与写一律不进"如何保证不被后来破坏（四道机械防线）

1. **清单唯一一份**：`services/kb_cache.py` 的 `CACHEABLE_RESOURCES`（正向）与 `NEVER_CACHED`（负向，逐条带理由）；**唯一写入口** `KbMetaCacheService` 只接受正向清单里的 `resource`（非法 resource 直接 `ValueError`）；
2. **分类守卫用例**（照 `IMPLEMENTED` / `LOCAL_METHODS` 那套"清单只有一份 + 逐名核对"）：枚举 `KnowledgeProviderClient` 的公开方法，**每个必须被分类**（`CACHE` 或 `NOT_CACHE` 映射表），出现新方法未分类即红；
3. **行为用例**：`retrieve_sources` / `submit` 前后 `kb_meta_cache` 行数不变（spy 断言）；
4. **端点面收窄**：`/local/kb-cache/*` 只有 `GET`（读快照）、`POST /revalidate`（**只读远端**，写的是本机那张表）、`DELETE`（只清本机）。

## 2. 缓存放哪一层（问题 2：最关键的分叉）

### 2.1 把现状摆到台面上

| 事实 | 落点 |
| --- | --- |
| 知识库页面（列表 / 详情 / Wiki / 文档详情）**直连 NAS**：`request()` → `/api/v1/...` → 壳把 `/api/**` 转发 NAS | `frontend/src/api/client.ts:11,88-94`；M3 §0.2 发现① |
| 本机后端**根本没有** KB 端点族（`local_router` 白名单不含 `/knowledge-bases`，M3 §9-1 明确不做） | `backend/app/api/v1/router.py:58-94` 与 `:133`；M3 方案 §9-1 |
| 本机后端**唯一**读 KB 元数据的地方是 `stores.meta.kb`（`RemoteMetaStore`）的 reader，今天只有 `ChatService._kb_prompt` 在用 | `remote_meta.py:96`、`chat.py:681-689` |

**⇒ 只在本机后端 reader 层加缓存，知识库页面一点也吃不到**（它的请求压根不经过本机后端）。v0.3 §9 M4 的验收（"二进知识库页秒开"）单靠 reader 层**做不到**。

### 2.2 两条候选路的对照

| | A. 只放本机后端 reader 层 | B. 只放前端（Webview 内存/localStorage） |
| --- | --- | --- |
| 页面秒开 | ✗ 吃不到（直连 NAS） | △ 同会话内可以（列表页今天已近似做到），**刷新/重启后归零**；持久化进 localStorage 违反 v0.3 §5.2「集合型数据禁入应用态小 JSON」（`:124-126`） |
| 设计条文 | ✓ 是 §6.3 要的"落本机 SQLite" | ✗ 做不到"SQLite + etag/last_modified 列" |
| 一致性代价 | 最小（调用方是提示词增强，`chat.py:684-686` 本来吞异常） | 中（前端要为每个视图自己实现 SWR/失效，且没有跨进程真相） |
| 改动面 | 3 处后端 + 组合根 | 4–6 个前端文件 |
| 能否独力满足 §9 M4 | **不能** | **不能** |

### 2.3 建议的形状：C = 后端缓存 + 页面"先画快照"（实时读一字不改）

```
① 页面进页面/换库时：requestLocal('/local/kb-cache/…')  ← 本机回环，个位数 ms，先画出内容
② 页面自己的实时读：request('/knowledge-bases…')        ← 会话身份、直连 NAS，与今天一字不差
③ 那次"读快照"顺带触发本机后端的后台再验证（钥匙身份）→ 更新本机 SQLite 的快照
```

- **为什么页面自己那条读不动**：身份。页面用**会话令牌**（管理员 / 成员 / 共享只读成员，`can_write` / `can_manage` / "看得见哪些库"都按它算，`knowledge_bases.py:29-67`）；边车用**长期钥匙**（`is_admin=false`、无范围限制，M3 §1.4）。让页面读后端代理 = 用钥匙的身份渲染页面：受限成员看到全部库（元信息泄露）、管理员丢掉管理入口、`can_write=true` 的入口点下去 403——**"如实"这条价值当场破功**。
- **为什么写者只有一个**（页面不回写缓存）：两个身份写同一行，"这份内容是谁看的"没有答案。**本机后端是唯一写者，页面是纯读者**；快照的新鲜度由本机后端自己的观察维持（读快照/读 reader 时判"该再验证了"就后台排一次）。
- **页面面剥权限位**是刻意的：缓存里的 `can_write`/`can_manage` 一律不落（§1.1），页面画快照时这两个位置为"未确认"→ 写/管理入口**晚一步出现**（实时读一落地就亮）。这就是"不许装成实时"的具体形态。
- **实时读的报错语义不变**：读失败照旧如实报（`KnowledgeBaseView.tsx:298-302`），只是内容不再因此消失——它已经在屏幕上了，顶上多一句"现在连不上，这是上次看到的内容（X）"。
- **离线快照的前提要说清**：整台 NAS 不可达时前端会被 `AuthGate` 拦回登录页（`frontend/src/app/App.tsx:81-105`），快照到不了眼前——**M4 的离线验收口径因此与 M3 一致**："配了 NAS（登录/会话仍在），但**知识库提供者**不可达或被关"（M3 §0.2 发现③）。"整台 NAS 不可达也能进去看"要等 M3 登记的 R13 前置小阶段（M3 方案 §6-R13、M3 验收记录 §10）。
- **明确不做**：不把 KB 读端点挂到本机档（那是 M3 §9-1 的既有裁定：重挂一遍等于在本机重造 KB 服务）。

## 3. 缓存 schema 与键（问题 3）

### 3.1 表（迁移 v2；**`schema.sql` 基线一个字不改**）

```sql
-- v2 增量迁移：知识库元数据缓存（M4 / v0.3 §6.3）
CREATE TABLE kb_meta_cache (
    provider        TEXT    NOT NULL,   -- 提供者地址（归一化：去尾斜杠）；键空间隔离靠它
    resource        TEXT    NOT NULL,   -- kb_list / kb_detail / doc_list / document / folders
    scope_key       TEXT    NOT NULL,   -- 资源内键：kb_id / document_id / 视图指纹；kb_list 用 ''
    payload         TEXT    NOT NULL CHECK (json_valid(payload)),  -- NAS 原样 JSON（权限位已剥）
    version         TEXT    NOT NULL,   -- 内容哈希（sha256:…）：变没变靠它（etag 缺席时的判据）
    etag            TEXT,               -- 服务端给的时候才有；今天恒 NULL（§4.1）
    last_modified   TEXT,               -- 同上
    source          TEXT    NOT NULL,   -- handshake / reader / revalidate：这行是怎么来的
    identity        TEXT    NOT NULL DEFAULT '',  -- api_key / session：**只作排障，不许当判据**
    fetched_at_ms   INTEGER NOT NULL,   -- 这份"内容"是什么时候看到的（界面那句"上次更新于 X"）
    checked_at_ms   INTEGER NOT NULL,   -- 最近一次**确认**（含"确认过没变"）
    stale           INTEGER NOT NULL DEFAULT 0 CHECK (stale IN (0, 1)),
    last_error      TEXT    NOT NULL DEFAULT '',
    PRIMARY KEY (provider, resource, scope_key)
) STRICT;
CREATE INDEX idx_kb_meta_cache_prune ON kb_meta_cache (fetched_at_ms);
CREATE INDEX idx_kb_meta_cache_scope ON kb_meta_cache (provider, resource);
```

要点：

- **键空间**：`(provider, resource, scope_key)` 三列主键。`provider` 用 `resolve_provider_target()` 解析出的 `base_url` 归一化（`knowledge_provider.py:209-240`）——**地址隔离**；`scope_key` 对 `kb_list` 是 `''`、对别的资源是 id 或视图指纹；
- **`fetched_at` 与 `checked_at` 分两列**（关键）：版本没变时只推进 `checked_at`（"确认过，还是那份"），界面那句"上次更新于 X"读的是 `fetched_at`——**两个时间戳不许混**（对应 M3 的 `checked_at` 是"上次确认连接"）；
- `kb_list` 那一次 revalidate 会**顺带派生**每库的 `kb_detail` 行（同一份 payload 拆开写），避免两处内容各自过期；
- 时间列带 `_ms` 且**不带 DEFAULT**（照 `schema.sql:16-34` 的类型映射纪律）；JSON 列带 `json_valid`（规范 1）。

### 3.4 失效与清理（四条规则）

1. **写后失效**：写类动作成功后（页面那条链自己知道），页面调 `DELETE /local/kb-cache?resource=…&kb_id=…` 就地失效；同时"**未确认前不画**"这条规则本身已经覆盖了大部分脏读窗口；
2. **条目上限 / 体积上限**（常量一处）：`MAX_ROWS_PER_PROVIDER = 500`、`MAX_PAYLOAD_BYTES = 2 MiB`（超了不缓存并如实记一条日志）、`MAX_TOTAL_BYTES = 64 MiB`；超限时按 `fetched_at_ms` 淘汰最旧（`idx_kb_meta_cache_prune`）；
3. **超龄丢弃**：`SNAPSHOT_MAX_AGE_SECONDS = 30 天`——超过就当作没有（`available:false`）。理由："更久以前的内容连看一眼的价值都抵不过误导风险"；
4. **清理粒度三档**：`DELETE /local/kb-cache`（全清 / `?provider=` 按地址清 / `?resource=&kb_id=` 按库清）；设置面板给一颗「清除」；`python -m app.storage.sqlite_impl.validate` 报出这张表的行数与字节数（`validate.py:105-111` 已有表/索引计数打印）。

## 4. SWR 流程（问题 4）

### 4.1 NAS 侧条件请求支持：逐个核实结论

| 端点 | `ETag` / `Last-Modified` | 证据 |
| --- | --- | --- |
| `GET /knowledge-bases`、`/{kb_id}` | **没有** | `api/v1/knowledge_bases.py:124-160` 直接回 pydantic 模型；`backend/app/main.py:169-175` 只挂了 CORS |
| `GET /knowledge-bases/{id}/documents`、`/folders`、`GET /documents/{id}` | **没有** | 同上（`Response(headers=…)` 只在下载/头像/前端包那几处出现，见 `documents.py:793-806`、`avatars.py:47-50`、`frontend.py:129-134`） |
| 全仓 etag 的既有两个落点 | 都不是 KB 读端点 | `services/connectors/base.py:112-140`（数据源条件 GET）、`api/v1/frontend.py:134`（前端包指纹） |
| 有没有更便宜的"变没变"探针？ | **没有** | 握手 `GET /provider/handshake` 内部就是 `list_all()` + `document_stats()` + `visible_kb_ids()`（`api/v1/provider.py:250-284`）——与列表端点**同价**，不构成廉价探针 |

**⇒ 判据定案**：M4 的"版本戳" = **内容哈希**（`sha256(canonical_json(payload))`，`sort_keys=True, separators=(',',':'), ensure_ascii=False`），再验证是"整取 + 比哈希"：哈希相同 ⇒ 只推进 `checked_at`，**不重写 payload、不通知界面**（"没变"就是"如实更新"的零变化）；哈希不同 ⇒ 整行替换、`fetched_at` 前进。
`etag` / `last_modified` 两列照样建好、照样写入（`response.headers.get('etag')`）——今天恒 NULL，将来 NAS 侧加上条件 GET 就自动生效（**M4 不改 NAS，一句都不改**）。这也是"不改壳"的理由：带 `If-None-Match` 的请求要过壳的转发与 304 空体处理，收益为 0（省的是带宽，不是 NAS 的 DB 计算）。

### 4.3 时序规则（前端，防"先画变成覆盖"）

1. 快照**只在"这个视图还没有实时结果"时画**（内存已有 → 跳过，连请求都不发）；
2. 实时结果**永远赢**：快照画的帧不许覆盖后到的实时结果（照 `api/provider.ts:340-354` 的"只有最新那次算数"水位写法）；
3. 画快照期间**不显示骨架屏**（内容已在），实时结果落地前 `store.fromSnapshot=true` 决定小字那一行；
4. 快照面的行**只读**：`can_write`/`can_manage` 置 false（§2.3），`doc_list` 行没有 `progress`（不画冻结的进度条）；
5. 轮询规则不变：只在 `hasActive || questionsPending` 时开表（`KnowledgeBaseView.tsx:408-416`）。

### 4.4 revalidate-on-focus 接哪

| 接点 | 谁触发 | 做什么 |
| --- | --- | --- |
| 窗口重新获得焦点 | **既有**：`api/provider.ts:479-495` 已 `refresh()` 强制重探握手 | 不动它 |
| 焦点 + 停留在 KB 页面 | **新增**：KB 两页挂一个 focus 监听 → `POST /local/kb-cache/revalidate {resource, kb_id…}`（当前视图） | 本机后端刷新那一键；页面随后自己再拉一次实时（可见更新） |
| 读快照那一刻 | 本机后端自己判 `now - checked_at >= 15s` | 排一次后台再验证（**SWR 的本义：读触发再验证**） |
| `state != ready` | 既有 30s 轮询（provider） | 不动；再验证失败进入 60s 退避 |

**防再验证风暴**：同一 `(provider, resource, scope)` 单飞（在飞就不再排）+ 每键最短间隔 15s + 失败退避 60s + 后台**一个**守护线程（照 `api/v1/local.py:475-485` 那条 `threading.Thread(daemon=True)` 的先例；`sqlite_impl/connection.py:64-76` 每线程一条连接，后台线程自带一条，无需加锁）。

### 4.5 失败时（NAS 断）

- **快照照旧可读**，`stale=1` + `last_error` 存着原因；
- 页面顶上一句如实说明（文案见 §7 阶段 6，**不许出现"缓存"二字**——`scripts/check_layering.py:622-629` 的 U2 是硬门禁，全仓现在零例外）：在线时"上次更新于 X"、断连时"现在连不上，这是上次看到的内容（X）"；
- 写/管理入口保持收起（未确认不画，§2.3）；
- **绝不**把快照当"实时"渲染进度/时间线；reader 面回快照时记一条日志（"读库元数据失败，用的是 X 分钟前的快照"，D-C）。

## 5. 与握手状态机的关系（问题 5）

| provider `state` | 导航组（M3） | 路由守卫 | 缓存怎么呈现 |
| --- | --- | --- | --- |
| `ready` | 在 | 放行 | 先画快照 + 实时读如实更新；顶上一句轻描淡写的"上次更新于 X" |
| `unavailable`（配了但连不上 / 凭据错） | **不在**（M3 规则不动） | **软化**（D-A）：本机有快照 → 放行、**只读**、顶部一条含原因与上次更新时间的说明；无快照 → 照旧重定向 `/chat` + toast（`ProviderRoute.tsx:47-72`） | 快照可读、`stale=1`；不改导航 |
| `unconfigured` / 还没探过 | 不在 / 按缺席 | 未探过 → 照旧"正在确认…"（`:62-70`）；`unconfigured` 同 `unavailable` 那一行 | 同上（`unconfigured` 时快照端点如实回 `available:false` + 原因） |

**地址改了（`base_url` 覆盖）**：**按地址隔离，不清旧行**。理由：① 同一台机器可能"家里的 NAS / 单位的 NAS"两个地址（M3 允许多地址但不做多凭据）；② 切回去还能秒开；③ 清理该由"上限 + 手动"决定，不该由"改了一个地址"隐式决定。切到新地址后的第一次进页面 = **没有快照**（`available:false`）→ 照旧骨架屏，这是如实的。

**两个时间戳不许混**：`checked_at`（握手：上次确认连接）与 `fetched_at`（快照：上次看到的内容）在界面上是两句话、两个字段，用例逐字钉住。

## 9. 明确不做 + 决策点（供架构师一句话确认）

**不做**：
1. **不改 NAS 一个字节**（不加 ETag/条件 GET、不加 `description` 到握手摘要）；"版本戳"由内容哈希承担（§4.1）；
2. **不改页面实时读的身份链**（不把 KB 读端点挂本机档、不做本机代理读）；
3. **不让页面回写缓存**（写者只有本机后端，避免两个身份覆盖同一行）；
4. **不缓存检索/写/进度/正文**（v0.3 §6.3 定案，四道防线守着）；
5. **不改前端登录门禁**（R13 仍是独立一小阶段；本方案的离线口径按 M3 的可执行定义）；
6. **不扩 `RemoteMetaStore.IMPLEMENTED`**——M4 只加缓存，不加映射（加行是另一件事）。

**决策点**：
- **D-A**：非 ready 时是否允许进 KB 页看快照。**建议：允许**（只读 + 如实标 + 顶栏给入口），否则 v0.3 §6.3 的"离线快照"永远看不见；
- **D-B**：快照里是否保留 `can_write`/`can_manage`。**建议：剥掉**（宁可晚一步出现，也不给一个点下去 403 的入口）；
- **D-C**：reader 面（`ChatService._kb_prompt`）远端失败时是否回快照。**建议：回快照 + 日志**（它是提示词增强；"恰好没有这个库"仍回 `None`）；若倾向 M3 的严格口径，把这条改成"抛"，一行之差，用例分开写；
- **D-D**：`doc_list` 只缓存规范视图（无搜索/无筛选）。**建议：是**（搜索结果是"这一问的答案"，过期即误导）；
- **D-E**：`MAX_ROWS/MAX_TOTAL/MAX_AGE` 三个数字。**建议：500 行 / 64 MiB / 30 天**（都在一处常量里，真机跑一轮再看要不要调）。
