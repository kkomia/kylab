## 1. 一张表：数据住在哪

| 数据 | 归属 | 能不能本地化 | 说明 |
| --- | --- | --- | --- |
| **账号 / 认证 / 配额 / 计费 / 模型 key** | **服务器 PG** | **不可本地化** | 授权、计费、密钥不下发。放本地等于把"谁能用什么"交给客户端自己声明 |
| **知识库**（文档 / 切块 / 向量 / 索引） | **知识库那一侧**（原先的服务器档已剥离到 kybase） | 不本地化 | 解析、切块、嵌入、检索、向量索引全在那边 |
| **会话与消息** | **服务器 PG 为权威** ＋ **本地 SQLite 副本** | 见 §3 | 本地**先写**、后台同步；本地那份是"离线能读 + 待上传队列" |
| **本机工作区文件** | **本地磁盘** | 始终本地 | **永不上传**，除非用户明确要求入库 |
| **工作区登记信息**（名字 / 根路径 / 绑定关系） | **服务器 PG**，但**按设备隔离**（v0.59） | 记录存服务器，可见性按设备 | 桌面壳转发时注入 `X-Kylab-Device` 头；无头（网页）只见 `device_id IS NULL` 的「服务器端」；别台设备的工作区 = 404。路径是机器本地的，别台机器看到也点不动——这是 2026-09-30 用户点名的（删旧电脑建的工作区报错那一单） |
| **技能库**（市场装的） | **本地** | 始终本地 | 技能是"装在这台机器上的说明书" |
| **技能市场目录元数据** | **服务器** | 不本地化 | 目录是产品内容，跟版本走 |
| **设置 / 偏好** | **服务器**（跟账号走）＋ **本地缓存** | 权威在服务器 | 本地那份是缓存，不是第二处真相 |
| **长期记忆** | **服务器** | 不本地化 | 与会话同一条信任边界 |

## 2. 分界线画在「API」，不画在「数据库」

**客户端只跟 API / 工具面说话，永远不直连 PG。**

两条理由，缺一不可：

1. **安全**：数据库凭据一旦下发，客户端就能绕过后端的所有判定（谁能读哪个库、
   哪条命令要不要问、配额还剩多少）——那些判定全在服务层；
2. **性能**：检索一次要碰几千个切块与向量（`kb_617a1ec9f798` 那个库是 21,580 段），
   跨公网直连库做这种活是灾难——而它在**同机**（后端 ↔ 库）跑就是一次本地查询。

推论：**数据库跟着后端走**。"后端在本地、库在远程"这种组合**不是**我们的目标——
那是把数据库当成一个跨公网接口在用，安全与性能两头都输。

## 3. 同步约定（会话）

- **每回合先本地落一条 → 再推服务器**：本地写是"这一轮已经发生"的事实，
  推失败不该把那句话弄丢（它在待上传队列里）；
- **客户端生成 id、幂等 upsert**：重推同一条不会写第二遍（网络重试是常态）；
- **会话按回合追加** ⇒ 冲突面极小：每条消息**最后写者胜**，没有合并地狱
  （不做 CRDT、不做字段级合并——那是在解决一个我们刻意不制造的问题）；
- **同一时刻只有一个活动回合**：沿用 `live_turns` 的语义
  （"这一段对话现在只有一个人在说"），跨设备也按这条走。

## 4. 两个明确不做

- **会话只存本地** ✗ —— 代价是砍掉网页端、跨设备与长期记忆
  （**记忆在服务器抽取**：会话只在本地 = 记忆永远是空的）；
- **账号本地** ✗ —— 等于放弃授权与计费。

## 5. 留到未来（现在是另一个产品级决定，不掺）

**隐私模式 = 「本地权威 + 端到端加密同步」**：服务器只存密文，密钥不离开用户设备。
它改变的是**信任模型**（服务器从"看得见"变成"看不见"），
与本文这套"服务器是权威"是两条路——**将来单独立项，不在本期掺进来**。

## 6. 现在的部署形态 vs 目标形态（别把「远程 PG」当成一个分离点）

用户问过一句话，容易理解偏：

> "就按你说的架构来。现在是不是相当于**前后端都跑在用户主机上**，
> 除了数据用的是**远程的 PG 数据库**存储？"

**不是。** 现在（Phase A，已实现）的实情是下面这两列：

| | **现在（Phase A）** | **目标终态（Phase B/C）** |
| --- | --- | --- |
| **界面** | **本地**（Tauri 从磁盘加载；88 个请求全打 `app.localhost`） | 本地（不变） |
| **API 服务 / agent 循环 / 工具 / 沙箱** | **服务器**（壳把 `/api/**` 转发到服务器；模型调用、循环、工具执行、隔离沙箱都在服务器） | **本地边车** |
| **知识库**（解析 / 切块 / 嵌入 / 向量 / 检索） | 服务器 | **服务器**（不变） |
| **账号 / 配额 / 模型 key / 模型代理** | 服务器 | **服务器**（不变） |
| **会话权威 + 长期记忆** | 服务器 | **服务器**（本地只是副本 + 待上传队列） |
| **PG 数据库** | 服务器（**一直是后端自己的库**） | 服务器（**不变**） |
| **工作区文件** | 服务器（沙箱目录里） | **本机** |

两句关键结论：

1. **分界线画在「API」，不画在「数据库」** —— 见 §2。数据库跟着后端走，
   所以"后端在本地、库在远程"**不是**目标形态；
2. **今天的"前端本地 + 后端远端 PG"不是三件事，是两件事** ——
   远程 PG 只是**后端自己的数据库**，它一直如此，**没有新增任何分离点**。
   真正的分离点是**界面搬到了本地**（Phase A）；
   而**执行面（循环 / 工具 / 沙箱 / 工作区）搬到本地**才是 Phase B ——
   那时才叫"**前端与 agent 运行时都在用户机器上，
   服务器只剩 KB + 模型代理 + 账号 + 会话权威**" = **数据面在服务器、执行面在本地**。
