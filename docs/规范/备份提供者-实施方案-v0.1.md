## 1. Q1 · 备份窄 API 的形状

### 1.1 两条路对照

| 维度 | **路 A**：本机后端拿 S3 凭据直写 MinIO | **路 B**：NAS 加 `/api/v1/backup/*`（服务端持 S3 凭据） |
| --- | --- | --- |
| 凭据下发面 | S3 的 access/secret（**等于整桶、含知识库原件**）要下发到每台桌面机并永久落盘 | 只多一次网络跳；客户端仍只有已用的那把 API Key（`kylab_sk_…`，`is_admin=false`） |
| 可达性 | NAS 上 MinIO 端口默认只绑 127.0.0.1（`deploy/docker-compose.yml:80-84`），要**新开一个局域网端口**（还有 TLS / 反向代理要处理） | 复用已有的 `:8080` nginx + 后端 |
| 校验 | 客户端自算自报，服务端无法证伪 | NAS 侧**边收边算 sha256**，不符即 400 且不落桶 |
| 配额 / 保留 | 客户端只能自报，服务端事后才知道 | NAS 侧算得出来（份数、字节、删除、GC 策略），握手就能如实回"配了多少、用了多少" |
| 幂等 | 靠 S3 PUT 覆盖语义，append-only 无保障 | 路径即幂等键 + `head_object` 先查：同内容 200 no-op、不同内容 409，绝不覆盖 |
| 实现量 | 后端要 import boto3（**闭包立刻爆**：客户端运行时红线，`core/storage.py:47-69`） | 后端一行 boto3 都不 import ✔ |
| 结论 | — | **建议路 B** |

> 路 A 的变体（NAS 签发**预签名 PUT/GET**、客户端直传）登记为将来优化：它同样不把 S3 凭据交出去，但需要 MinIO 在局域网可达 + 端口/TLS 决策 —— **M5 不做**。

### 1.2 桶布局与命名（append-only，一层不少）

```
桶：KYLAB_BACKUP_BUCKET（新，默认 kylab-backup；与知识库那个桶分开）
键：<KYLAB_S3_PREFIX><provider>/<device_id>/<snapshot_ts>-<hash8>/
        snapshot.tar.gz     ← 先传（大）
        manifest.json       ← 后传（小，**完成标记**）
   provider = "backup"（写死常量；将来别的提供者不混进来）
   device_id = 壳的 config.json.device_id（UUID v4，已有：config.rs:126-132）
   snapshot_ts = UTC "YYYY-MM-DDTHH-MM-SSZ"
   hash8 = 快照体 sha256 前 8 位（解决同秒冲突 + 天然幂等判据）
```

append-only 的四条硬规矩（**要写进契约与用例**）：
1. **不覆盖**：同路径同 sha256 → 201→200 no-op；同路径不同 sha256 → **409**（永不覆盖）；
2. **只能整份删**：删除的粒度是"一个恢复点"（两个对象一起删），没有"删某个对象"的入口；
3. **枚举只认有 manifest 的**：孤儿 blob（上传中断）留着不删（append-only），但枚举忽略——这同时满足"append-only"与"完整才可见"；
4. **服务端绝不替用户删**（保留份数超限时报错，不静默淘汰），删除永远是一次显式动作。

三条设计裁量（写进模块头）：
1. **不复用知识库的对象布局**：备份桶独立（v0.3 §7"落 MinIO 快照桶，不落知识库的 PG"），后端另起一个薄封装（见 §1.5）；
2. **握手独立、不并进 `knowledge` 那一段**：v0.3 §2 明写两个提供者可以指向不同 NAS —— 并进去就会出现"不配知识库就没法握手备份"的死角。协议版本各自一个整数；
3. **PUT 的路径本身就是幂等键**（append-only + 内容寻址），**不需要 `Idempotency-Key` 头**；这条新约定要手写进 `docs/规范/API-接口规范-v0.1.md` §1（新增 §1.13），并按 §4 的重跑 `scripts/gen_api_spec.py` 更新 §2 清单（`tests/unit/api/test_api_spec.py` 会核对）。

### 1.4 服务端状态（v0.3 §3.1 的"③ 状态 = 最近快照 + 配额"）

握手一次给全：`devices[]`（每台设备几份、多大、最近一份）+ `retention`（额度与已用）。**不另开端点**（与 KB 那条"库清单随握手回"同一口径）。

| 设置 | 库里的 `app_settings`（**判据见 2.4**：排除 `SECRET_KEYS` ∪ 三个前缀） | **必须** | 排除项在 manifest 的 `redacted` 段如实列出 |
| 会话档产物（大） | `data_dir/conversations/<会话>/<产物>.<后缀>`，按库里 `conversation_artifacts.storage='object'` 的记录取 | 选择性（默认全备，受额度约束） | 超限的在 `skipped` 段如实列 |
| 工作区档产物（大） | `storage='workspace'` 的记录指向的真实文件 | **默认不备** | 见 2.2 |
| 工作区里**其他**文件 | n/a | ✗ 永不 | v0.3 §4 |
| `originals/`/`markdown/`/`images/` 三目录 | n/a | ✗ | 本机档基本为空；真为空时跳过并在 manifest 记 `0` |
| **秘密** | n/a | ✗ **一律不进包** | §2.4 |

### 2.2 「工作区产物选择性备」怎么定义（三条判据，按优先级）

1. **位置判据（自动、无需用户勾）**：落在 `data_dir` 对象存储里的产物（`storage='object'`）→ **一律备**。它们是"这条会话的一部分"（会话删了就丢），且体积可控；
2. **工作区判据（默认关，用户显式打开）**：落在工作区真实目录里的产物（`storage='workspace'`）→ **默认不备**（工作区文件是用户的项目文件，v0.3 §4 "永不上传"）。给一个开关 `provider.backup.include_workspace`（默认 `0`）；打开后按第 3 条额度备。**明确不做**逐文件勾选（登记为不做）；
3. **额度判据（永远生效，超限如实报）**：单文件 ≤ `BACKUP_ARTIFACT_MAX_BYTES`（默认 64 MiB）、一次快照产物总量 ≤ `BACKUP_ARTIFACTS_TOTAL_BYTES`（默认 512 MiB）。超限项**逐条**进 manifest 的 `skipped`（`name` / `size_bytes` / `reason` ∈ `too_large` / `total_budget` / `workspace_not_included`），界面与恢复报告都能看到"哪些没备"。

### 2.3 打包格式：`snapshot.tar.gz`（stdlib `tarfile` + `gzip`）

成员顺序（**manifest 必须第一个**，便于将来流式读）：

```
manifest.json                 ← 第一成员（同时另传一份独立对象，作完成标记）
db/kylab.db                   ← 擦洗后的在线备份副本（单文件、无 -wal）
memory/<账号>/…               ← 记忆与人设
files/<对象 Key>              ← 会话档产物（按原 Key 落，恢复时按同一 Key 还原）
```

`manifest.json` 字段草案：

```json
{
  "format": "kylab-backup", "format_version": 1,
  "snapshot_id": "<device>-<ts>-<hash8>", "device_id": "…", "device_name": "…",
  "created_at": "2026-10-05T…Z", "kind": "manual|auto|pre_restore",
  "app_version": "0.1.1", "schema_version": 2, "platform": "windows",
  "blob": { "name": "snapshot.tar.gz", "bytes": 12345, "sha256": "…", "compression": "gzip" },
  "counts": { "conversations": 12, "messages": 340, "session_events": 900, "notes": 4,
              "workspaces": 2, "scheduled_tasks": 1, "artifacts": 7, "memory_files": 9 },
  "included": { "db": true, "memory": true, "settings": true,
                "artifacts_object": 7, "artifacts_workspace": 0 },
  "skipped": [ { "name": "项目/大报告.pptx", "size_bytes": 90000000,
                 "reason": "too_large" } ],
  "redacted": [ { "table": "model_providers", "column": "api_key", "rows": 3 },
                { "table": "app_settings", "key": "web.search_api_key", "rows": 1 },
```

**兼容判据**（不猜着读）：`format_version` 只增；`schema_version > 本机 SCHEMA_VERSION` → 拒绝恢复（照 `sqlite_impl/schema.py` 那条"不降级"纪律）；读的一方不认识某个版本**当场拒绝**。

### 2.4 擦洗：快照里绝不放秘密（**本方案最关键的一节**）

本机库确实有明文（`model_providers.api_key`、`mcp_servers.env/headers`、`app_settings` 的 SECRET_KEYS），**所以"打包"必须带一道擦洗**，否则"秘密只进钥匙串"这条纪律会被备份绕过去。

擦洗做在**副本**上（`sqlite3.Connection.backup()` 出来的临时文件），源库一个字节不动：

1. `PRAGMA secure_delete = ON`（副本连接）；
2. 白名单外的行删/清：
   - `model_providers.api_key` → `''`（恢复后需重配，见 §3.4 的报告）；
   - `mcp_servers.env` → `'{}'`、`mcp_servers.headers` → `'{}'`；
   - `app_settings` 里 **`runtime_config.SECRET_KEYS` ∪ 前缀 `provider.` / `model.` / `backup.`** 的键 → `DELETE`（判据**引用常量本身**，不手抄——将来新增 SECRET_KEY 自动被排除，机械防漂）；
3. `VACUUM`（**必须**：SQLite 的 UPDATE/DELETE 不会覆盖旧页内容，明文会残留在空闲页里；`secure_delete` + `VACUUM` 之后才真的洗掉）；
4. 副本不产生 `-wal`（新文件不带 WAL），打包前断言"目录里只有 `kylab.db`"。

**判据用例（最强的那个）**：造一份含哨兵串（`kylab_sk_SENTINEL…`、`tavily_SENTINEL…`）的本机库 → 打快照 → 在**包解开后的原始字节**里 `grep` 哨兵串 → 必须 0 命中。

### 2.5 加密与否：**不做应用层加密**（结论 + 理由 + 自描述）

理由三层：
1. **钥匙放哪没有诚实答案**：放本机 → 换了机器恢复不了（与"恢复到干净机器"这条验收直接冲突）；放 NAS → 服务端可解密（等于没加）；让用户另记一个备份口令 → 与自动快照/离线可用冲突，且多一个"口令丢了全丢"的失败模式；
2. **正确做法是"让快照里没有秘密"**：这正是"备份 + 钥匙串"是一件事的理由——先把明文凭据收编（§4）、再把凭据类内容从包里排除（§2.4），快照里就只剩"用户自己的数据"；
3. **残余风险如实说**：会话正文/笔记里用户自己粘的密码**洗不掉**（那是数据本身）。缓解=桶的访问控制（NAS 侧沿用现有鉴权，v0.3 §8-2）+ 在「备份」页面上写明"快照含全部会话与记忆"。

自描述字段 `"encryption": "none"` 先留着：将来若要加客户端加密，读的一方按它自识别（照 Kimi 调研 §5-照抄-3 那条"加密文件自描述"）。**M5 不做加密**（登记为不做 + 决策点 D2）。

## 3. Q3 · 断网入队与补传

### 3.1 队列形状：**本机库一张表**（目录即队列 ✗）

落 `migration v3`（`sqlite_impl/schema.py` 追加 `MIGRATION_V3_BACKUP_SNAPSHOTS`，`SCHEMA_VERSION` 1→2→**3**；基线 `schema.sql` 一个字不改——**本机库已经发过版**）：

```sql
CREATE TABLE backup_snapshots (
    id                 TEXT PRIMARY KEY,          -- <device_id>-<ts>-<hash8>
    created_at_ms      INTEGER NOT NULL,
    kind               TEXT NOT NULL CHECK (kind IN ('manual','auto','pre_restore')),
    state              TEXT NOT NULL CHECK (state IN ('pending','uploading','uploaded','failed','discarded')),
    blob_path          TEXT NOT NULL DEFAULT '',  -- <data_dir>/backup/pending/<id>.tar.gz
    blob_bytes         INTEGER NOT NULL DEFAULT 0,
    sha256             TEXT NOT NULL,
    manifest_json      TEXT NOT NULL DEFAULT '{}' CHECK (json_valid(manifest_json)),
    attempts           INTEGER NOT NULL DEFAULT 0,
    next_attempt_at_ms INTEGER,
    last_error         TEXT NOT NULL DEFAULT '',
    uploaded_at_ms     INTEGER,
    remote_device_id   TEXT,
    remote_snapshot_id TEXT
) STRICT;
CREATE INDEX idx_backup_snapshots_queue  ON backup_snapshots (state, next_attempt_at_ms);
CREATE INDEX idx_backup_snapshots_recent ON backup_snapshots (created_at_ms DESC);
```

为什么是库不是目录（四条）：① 队列项要有状态机/尝试次数/下次可试时间/原因 —— 目录名表达不了；② "断网入队、联网补传"要能**跨重启**继续（只有库有这份持久性）；③ 幂等判据（内容哈希）要落库；④ 与 M2 的 `imports/import_items` 台账同一套形态、同一个库、同一把写锁。

登记手法照 `LOCAL_LEDGER_METHODS` / `LOCAL_CACHE_METHODS` 那两块（`sqlite_impl/__init__.py:91-137`）：
- `LOCAL_BACKUP_METHODS`（新常量：`put_backup_snapshot` / `get_backup_snapshot` / `list_backup_snapshots` / `mark_backup_snapshot` / `reset_uploading_snapshots` 等）；
- `StoreBundle.backup_queue: BackupSnapshots | None`（`base.py:106-152` 那一段旁边加一段同样长的理由）；

> **字段名对齐（阶段 2 落地后回填，架构师改）**：`StoreBundle.snapshot` 与 `LOCAL_SNAPSHOT_METHODS`
> 这两个名字**已经给了阶段 2 的归档器**（`dump_scrubbed_db` / `read_snapshot_db` 两个方法，
> 与 `meta`/`ledger`/`kb_cache` 同一个实例），同一处不许两个东西撞名。所以**队列**改用
> `StoreBundle.backup_queue` 与 `LOCAL_BACKUP_METHODS`：前者的名字对着"打一份快照"这件事
> （归档器），后者对着"待传队列"这件事（`backup_snapshots` 那张表）。两条都只此一处定义。
- 接口协议 `BackupSnapshots` 落 `app/storage/base.py`。

### 3.2 快照生成时机与落点

- **手动**：界面「立即备份」→ `POST /local/backup/snapshots`；
- **自动**：默认 `provider.backup.every_hours = 24`（`0` = 关；决策点 D3）——判据"**距最近一条快照记录**（不论成败）超过 N 小时"，由补传线程的节拍顺带判（不另起计时器）；

  > **口径修正（阶段 3 落地后回填，架构师改）**：原文写的是"距最近一条 `uploaded|pending` 快照"。
  > 阶段 3 按字面实现之后，架构师用拨钟探针实测到一个真问题：**断网时每 5 分钟就重打一份快照**
  > （立即尝试失败 → 那一行变 `failed` → 下一轮判据看不见它 → 又算"到期"），半小时打 6 份、
  > 上限反复丢弃，CPU/磁盘白白空转，界面还会一路重复"有 N 份没备上去"。
  > 判据问的是"**这台机器上次打快照是多久以前**"，所以 `failed` 与 `discarded` 都算"打过一份"——
  > 它们不证明"我们有备份"（那件事由 `backlog` 如实报，一个字不改），只证明"最近打过"。
  > 于是断网窗口里**每个 N 小时最多打一份**，联网那一刻传上去的自然是最新的一份。
- **恢复前**：恢复动作前自动打一份 `kind='pre_restore'`（**只落本机、不入队上传**，落 `<data_dir>/restore-backup/<ts>/`），这是"误覆盖"的第一道兜底；
- 打包落在 `<data_dir>/backup/pending/<id>.tar.gz`；上传成功后**删掉本地包**（append-only 的保存处在远端，本机不留第二份明文副本）；
- **pending 上限**：默认 3 份 / 1 GiB；超限按最旧标 `discarded` + 删包 + `last_error='local_pending_cap'`（**如实报，不静默**），界面显示"有 N 份没备上去"。

### 3.3 重试与退避

| 事 | 落法 |
| --- | --- |
| 线程 | 一个 daemon 线程（名字 `backup-upload`），懒建、一个进程一个 —— 照 `services/kb_cache.py:888-903` 那一处的手法 |
| 节拍 | 5 分钟一次；**只有存在 `pending`/`failed` 且 `next_attempt_at_ms <= now` 的项才动**（没有待传项时零网络） |
| 立即触发 | `POST /local/backup/snapshots` 之后立刻试一次（不等 5 分钟） |
| 退避 | 60s → 2m → 5m → 15m → 1h（上限 1h，不放弃；每次失败把原因写 `last_error`） |
| 崩溃恢复 | 启动时把 `state='uploading'` 复位成 `pending`（进程被杀留下的半截），照 M2"未跑完的批次可续"同一句口径 |
| 上传顺序 | 先 `blob` 后 `manifest`（manifest 是完成标记）；两者都幂等，重试安全 |
| 成功 | 行置 `uploaded` + `uploaded_at_ms` + 删本地包 |
| 不做 | 并发上传（一张一张传，NAS 与网络都吃不下并发） |

### 3.4 恢复点枚举与「按点恢复」

枚举：`GET /local/backup/points`（本机端点透传 NAS `GET /backup/snapshots`，进程内缓存 30s，与提供者状态同一 TTL 口径）。

恢复流程（本机端点 + CLI 共用同一套服务）：

```
1. 选恢复点（device_id + snapshot_id）
2. （默认先）dry-run：下载 manifest → 报"会新建哪些会话 / 哪些跳过 / 哪些产物不在包里
   / 需要重配的凭据有几项" → 用户确认
3. 自动打一份 kind='pre_restore' 的快照（只落本机）
4. 下载 blob（流式）→ 校验 sha256（不符即中止，绝不落位）
5. 解包到 <data_dir>/restore-staging/<snapshot_id>/（校验每个成员路径不越界）
6. 打开 staging 里的 kylab.db（只读）→ 逐个会话构造 ConversationTransfer
7. **走 M2 的导入器**（同一套幂等键/覆盖规则/后台线程/台账）：
   source = "backup://<device_id>/<snapshot_id>"
   → 账写进 imports/import_items；进度查 GET /local/import/{batch_id}；
     回滚走 POST /local/import/{batch_id}/rollback（**这两个端点一行不改**）
8. 记忆：按 <账号>/<文件> 落位，**默认只补不覆盖**（本机已有 → skip 并如实报；勾选才覆盖）
9. 设置：只补本机没有的键（本机是权威）；SECRET_KEYS / provider.* / model.* / backup.* 一律不写
10. 产物字节：按 Key 写进 data_dir（同 Key 同内容 → skip；同 Key 不同内容 → **如实报冲突并跳过**，
    绝不静默覆盖，理由与 R5 同源）
11. 报告：新建/替换/跳过（含原因）/需要重配的凭据清单/未随包过来的工作区产物数
```

**会话冲突怎么办（三条规则，全部复用 M2 的）**：本机没有 → 建；本机有且是"我们导进来过、之后没动过" → 替换；本机有但动过、或根本不是我们导进来的 → **保留 + 如实报**（`local_newer` / `not_ours`）。在**干净机器**上这三条等价于全量重建 ✔ —— 这正是验收 B 要的那一档。

**"整机回滚到昨天"怎么办（明确不做整库替换）**：语义统一成"往一个库上补/合并"；真要整机换回，文档与 CLI `--help` 给一条干净的路：**停边车 → 把 `kylab.db*` 挪到 `restore-backup/<ts>/` → 再跑恢复**（此时库是空的 → 全量重建）。这条不需要额外代码，且避免了"在线替换 SQLite 文件"这个危险动作（进程持有连接、WAL 在飞）。

## 4. Q4 · 钥匙串收编

### 4.1 一处「秘密来源」接口

`backend/app/services/secrets.py`（新）：

```python
class SecretStore(Protocol):
    def available(self) -> bool: ...
    def get(self, name: str) -> str | None: ...      # None = 没配（含"钥匙串不可用"）
    def set(self, name: str, value: str) -> None: ... # 不可用时抛 SecretStoreUnavailable
    def delete(self, name: str) -> None: ...
```

三条口径（**写进模块头，用例逐条钉**）：
1. **读不到 = 没配**（不回退到别处读明文 —— 那样"收编"就白做了）；
2. **写不了 = 明确失败**（`SecretStoreUnavailable` → 端点 503 + 人话），**绝不静默写回明文**；
3. 实现三份：`WindowsCredentialStore`（ctypes，`os.name=='nt'`）、`NullSecretStore`（其余平台）、`InMemorySecretStore`（用例）。

**命名规范（唯一一份常量，壳与后端共用同一条规则）**：

```
TargetName = "kylab:<用途>:<对象 id>"      例：kylab:model_provider:mp_abc123
                                                kylab:setting:web.search_api_key
                                                kylab:nas_token:<origin>
UserName   = "kylab"（显示用）   Blob = UTF-8 秘密（≤2560 字节，超了如实拒，不截断）
```

两侧各自实现同一条规则，用一条真机用例钉住一致性（**壳写 → 后端读**、**后端写 → 壳读**）——否则会出现"壳写的钥匙后端读不到"这类最难查的问题。

### 4.2 逐个秘密的迁移路径

| 秘密 | 新家 | 读取路径统一 | 迁移动作 |
| --- | --- | --- | --- |
| 壳 `config.json.api_key`（#1） | Windows 凭据管理器 `kylab:nas_token:<origin>` | 壳启动时 `SecretStore.get`；`config.json` 里 `api_key` 保留字段但**恒空**（老配置读得出来 → 首次运行自动迁 + 清） | 壳侧一次性：读到明文 → 写钥匙串 → 清 `config.json` 那一栏 → 日志只记"已迁" |
| `model_providers.api_key`（#3） | `kylab:model_provider:<id>` | `services/model_registry.py` 读出记录后**由服务层填**（`ModelProviderRecord.api_key` 字段与 API 形状**零改动**，DB 列存空串）；写入路径改为"密钥落钥匙串、DB 存空" | 迁移器逐行：写钥匙串 → 清列；幂等（钥匙串已有同值或列已空 → skip） |

**过渡态与"两个真相源"的解法**：迁移完成前，"库里有值、钥匙串没有"是唯一允许的中间态，且**可被观测**：`GET /local/secrets` 回 `{"pending_migration": n, "store": "available|unavailable"}`；设置面板显示"发现 N 处明文凭据 → 「迁进系统钥匙串」"。**不静默迁移**（改用户的存储位置要有意识），但必须有一键入口。

### 4.3 旧明文清除策略

1. **写入路径先改**（新写的秘密只落钥匙串）；
2. **迁移器跑一次**（显式动作：端点 + 面板按钮 + CLI `python -m app.services.credentials migrate`）；
3. **清空后洗页**：迁移器最后在**源库**上执行 `PRAGMA secure_delete=ON` + 相关表的 `VACUUM`（不留空闲页残留）；
4. **判据**：用例在**库文件原始字节**里 grep 哨兵串 → 0 命中（与 §2.4 那条同一手法，两处共用）。
5. **失败处理**：某条写钥匙串失败 → **不清那一列的明文**（不清就不算迁完），如实报 `failed: [...]`，下次可重跑。

### 4.4 闭包影响实测预估

### 4.5 边界

- **CI / 无桌面环境**：`NullSecretStore` —— 读=没配、写=明确失败；用例覆盖两个实现分支（CI 上跑的就是 Null 那一支）；
- **服务器档（NAS 容器）**：库里那份凭据**不动**（Linux 容器没有系统钥匙串，它的边界是 NAS 的访问控制）—— 如实登记为边界，不假装收编了；
- **前端 localStorage 的会话令牌**：M5 不动（M3 R13 那一条仍是独立小阶段，"只在边界里提及"）。

## 8. 明确不做（M5 边界）与决策点

**不做**：
1. **不做应用层加密**（§2.5 的三层理由）；只留 `encryption` 自描述字段；
2. **不做整库在线替换恢复**（只做"合并/补全"；整机回滚走"先挪库再恢复"的文档路径）；
3. **不做工作区产物的逐文件勾选**（只给一个 `include_workspace` 开关 + 三条额度判据）；
4. **不做增量/去重快照**（每份都是全量；会话库小，产物受额度约束）——登记为"将来若体积成问题再做"；
5. **不做服务端（NAS）库内凭据的钥匙串化**（Linux 容器没有系统钥匙串，边界写清）；
6. **不收编 `mcp_servers.env/headers`**（本机档没接 MCP + 形态不友好 + 可能超 Blob 上限）；
7. **不动前端登录门禁**（M3 R13 那条独立小阶段）；
8. **不做预签名直传 MinIO**（需要有意识开端口，登记为将来优化）；
9. **不新建第三个提供者的抽象**（v0.3 §11-5）。

**决策点（建议已给，供架构师一句话确认）**：
- **D1**：路 B（NAS 端点族，客户端永不碰 S3 凭据）。建议：**按此**；
- **D2**：秘密**不进快照**（擦洗）→ 因此不做加密。建议：**按此**（若要"连会话正文也加密"，那是另一档，需要用户口令，与自动快照冲突）；
- **D3**：自动快照默认 **24h 开**（`provider.backup.every_hours=24`，0=关）。建议：**开**（"断网也不丢"是这条能力的价值；关掉就只剩手动）；
- **D4**：恢复默认"合并（缺就补、有就不动）"，不做整库替换。建议：**按此**；
- **D5**：钥匙串零新依赖（两侧直调 Windows 凭据管理器）。备选是 Python `keyring` 包（闭包 17→23+，判据要同步改）。建议：**零新依赖**；
- **D6**：不扩 `ObjectStore` 接口（它是 KB 的 5 方法面），备份桶另起薄封装。建议：**按此**。

## 改了口径的（原文 → 改成什么 → 为什么）

1. **§3.2 自动快照判据**（原文"距最近一条 `uploaded|pending` 快照超过 N 小时" → "距最近一条记录"）：
   按字面实现之后，拨钟探针实测到真问题——**断网时每 5 分钟重打一份整库快照**（立即尝试失败 →
   那一行变 `failed` → 下一轮判据看不见它 → 又算"到期"；六轮打 6 份、48 小时窗口能打 576 份）。
   定案：`failed` / `discarded` 也算"打过一份"，判据问的是"这台机器上次打快照是多久以前"；
   它们不证明"有备份"——那件事仍由 `backlog()` 如实报，一个字不改。原文那一节已回填引用块。
2. **§7 A 第一行的"`pending` 还是 `failed`"** → **两档都算入队成功**：原文一处写"入队落 `pending`"、
   另一处又说"端点若在请求线程里顺手试了一次上传，那一行是 `failed`"——两句自相矛盾。
   定案：`pending` = 还没试过、`failed` = 试过且失败，退避重试对两档一视同仁。
3. **§3.1 的命名收口**：`StoreBundle.snapshot` / `LOCAL_SNAPSHOT_METHODS` 已归阶段 2 的归档器，
   队列改用 **`StoreBundle.backup_queue` / `LOCAL_BACKUP_METHODS`**（前者的名字对着"打一份快照"这件事，
   后者对着"待传队列"这件事）——两条都只此一处定义，原文已回填引用块。
4. **阶段 7 的前端门控判据**："只在备份提供者 `ready` 时渲染" → **判据是本机档**（施工单明确要求）：
   "连不上"正是要看队列的时候；服务器档 `/local/backup` 404 → `unsupported` → 不渲染。
   随之 `SETTING_GROUPS` 里那个「备份」分组**撤掉**（照「知识库连接」先例：本机档前端自绘、
   读写走 `/local/backup`），`DEFAULTS` 保留。
5. **`provider` 块补三栏**（阶段 7 落地时如实登记"只写得进去读不回来"，两处收口补齐）：
   `GET /local/backup` 现在**永远给** `enabled` / `include_workspace` / `every_hours`
   （含 `unavailable` / `unconfigured` 两档——它们是配置事实，不是远端结论）；判据复用现成那三处
   （`backup_enabled()`、`BackupQueueService.every_hours()`、同一个键常量 + 同一个默认），
   前端改成直接读值、不再从后端那句人话反推；**读不到值时不摆开关**（摆 `checked=false` 等于把

6. **`_include_workspace()` 没提成模块级函数**：`backup_snapshot.py` 本轮禁改，等价做法

7. **阶段 4 的两处端点口径**：删除时"连不上"用 **502 `upstream_error`**（API 规范那张码表就是它，
   要 503 得新加异常类）；"没有设备身份"那条 **400 用 `BadRequestError`**（同 code 同消息，不改语义）。
   `/local/*` 不进服务器档 OpenAPI——所以 `schema.d.ts` 无改动（`gen_api_types --check` 过）。
8. **§4.2 的"`SECRET_KEYS` 一律走钥匙串"收窄**成"**已收编的那几个 + 钥匙串真的可用**"：
   否则只登记不迁的解析 token 会当场变成"没配"（静默丢凭据），服务器档也会读错
   （两份清单的一致性由用例钉，改一处不改另一处当场红）。
9. **§4.3-3 的洗页**：`PRAGMA secure_delete` 与 `wal_checkpoint(TRUNCATE)` 在 `services/` 够不到（L2）
   ——阶段 6 只做到"主库干净 + 进程退出后整目录干净"，**阶段 6·补**落成 storage 层的
   `Database.secure_erase()`（薄转发 + `LOCAL_ERASER_METHODS` + `StoreBundle.eraser`），
   判据提前到"**同一次运行、不重启**"；撞上读者时少量重试，仍不行如实抛（服务层翻成 409）。
10. **§5 R13 的现场形态**：`credentials_to_configure` 的判据（非空 + 含具体名字）成立，
    但真机上只有 NAS 钥匙一项——那台干净机器上本来就没有模型凭据 / 联网搜索 key 可列（擦洗后它们也不在包里）。
    报告是"按现场如实列"，不是照抄一句清单。
11. **§2.3 的 `blob.*` 字段**：指**快照体**摘要而不是归档自身（manifest-first 下自指算不出来）；
    归档自身那一对由 `SnapshotResult.blob_bytes / blob_sha256` 交给上传层。`skipped` 词表扩到 7 条
    （`missing` / `unsafe_location` / `unknown_storage` / `symlink` 都属如实报）。
12. **阶段 5 施工中抓到的两处**：① 发送层搬进 `HttpExportSource` 之后 `importer.transport = …`
    成了死字段（用例当场变成真网络请求）→ `LegacyImporter.transport` 做成透传到 reader 的 property；
    ② 导入器收尾先写 `done`，而那一刻 `restore` 段还没落（轮询的人读到"已完成但报告里没有 restore 段"）

13. **阶段 1 真机抓到的一个真 bug**：按设备前缀列举的解析错位 → **列一台设备永远空** →
    `keep` / `quota` 静默失效（超限该拒的没拒）；测试抓住、已修 + 回归。

## 没做的（明确不做 / 本轮没做）

1. **不做应用层加密**（§2.5 / §8-1）：`encryption:"none"` 自描述；秘密靠"收编 + 擦洗"清出去，
   包是"擦洗后的用户数据"（用户自己粘进正文的密码洗不掉，边界是桶的访问控制）；
2. **不做整库在线替换**（§3.4 / §8-2）：恢复是"合并 / 补全"（缺就补、有就不动、本机改过的保留）；
   真要整机回滚走文档那条"停边车 → 挪 `kylab.db*` → 再跑恢复"；
3. **不做工作区产物的逐文件勾选**（§2.2 / §8-3）：只有一个 `include_workspace` 开关 + 三条额度判据；
4. **不做增量 / 去重快照**（§8-4）：每份都是全量；**dry-run 的代价与真恢复差不多**
   （要下载并解包整包才能逐会话判定）——两件是同一个话题的两半；
5. **不做服务端（NAS）库内凭据的钥匙串化**（§4.5 / §8-5）：Linux 容器没有系统钥匙串，边界写清；
6. **不收编 `mcp_servers.env/headers`、`mineru.token`、`paddleocr.token`**（§4.2 表里那几行 / §8-6）：
   本机档没接 MCP、也不解析文档；任意键值对 + 可能超 Blob 上限。**只登记 + 快照排除**
   （只登记的三处在迁移现场**原样留着**，用例专门断言）；
7. **不动前端登录门禁**（§8-7 / R13）：整台 NAS 不可达时仍会被拦回登录页（M3 那条独立小阶段）；
8. **不做预签名直传 MinIO**（§8-8）：需要有意识开端口，登记为将来优化；
9. **不新建第三个提供者的抽象**（§8-9）；
10. **文档项（2026-10-02 补记录：已补，不再是缺口）**：`docs/规范/部署与运行-v0.3.md` §2.4 的
    「备份与恢复」小节（备份桶怎么建 / 备份页四个可改项与两个落点 / 恢复四步与整机回滚 / 钥匙串 /
    壳转发那条纪律）+ **常见问题三条** + §6 一句指路都已写；`docs/README.md` 的「计划与记录」
    索引也补了 M2–M5 四份验收记录的入口。**CHANGELOG 里「红字重复」那条已知限制按架构师指示
    留着不动**（等后端那条修复的提交落地后由架构师自己翻进「修复」）。
