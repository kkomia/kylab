## 2. 本地路线（已实测）

### 2.0 先备一个 PostgreSQL（必选）

自 v0.12 起 **PostgreSQL 是硬依赖**，没有可回退的本地实现；未配置 `KYLAB_DATABASE_URL`
时服务**启动即失败**（不是降级，是明确报错）。需要 **pgvector** 扩展。

```bash
docker run -d --name kylab-postgres -p 5432:5432 \
  -e POSTGRES_PASSWORD=kylab-dev-secret -e POSTGRES_DB=kylab \
  pgvector/pgvector:pg17-trixie
```

不想用 docker 也可以装本机 PostgreSQL + pgvector（版本 ≥ 0.7 即可用 HNSW）。
对象存储不强制：留空 `KYLAB_S3_*` 时原件落本地 `KYLAB_DATA_DIR`。

### 2.1 后端

```bash
cd backend
uv sync --all-extras                     # 注意 --all-extras，见下
cp .env.example .env                     # 至少填 KYLAB_DATABASE_URL；.env 不入库
uv run uvicorn app.main:app --reload     # http://127.0.0.1:8000
```

**为什么是 `--all-extras` 而不是裸 `uv sync`**（v0.1 这里写错了，照做会在
`import app.main` 时炸 `ModuleNotFoundError`）：`app/core/storage.py` 会**无条件**构造
DuckDB 表格副本，而 duckdb 在 `tabular` extra 里——它看着像可选项，其实是组合根的必需项。
`parsers` extra（pypdf / pymupdf / python-docx / openpyxl / pandas）
是上传→解析→入库主链路要用的，代码里惰性导入，缺了只是该功能不可用，
但**跑产品就该装上**。详见 `backend/README.md` 的「依赖分层」。
（`markdown-it-py` 原在这一组里，v0.47 起提为核心依赖：记忆召回也用它按 AST 切块。）

- 探针：`GET /api/v1/health` → `{"status":"ok",...,"version":"..."}`
- 接口文档：`/api/v1/docs`
- 首次启动**无需手工建库**：连接时自动跑迁移（`apply_migrations`），
  数据目录与对象存储子目录也会自动创建。

#### 日志在哪、怎么调（v0.21）

控制台一份 + **文件一份**（`data/logs/kylab.log`，滚动：5 MiB × 3 份）。
控制台那份活不过一次重启，而"昨晚那次对话为什么慢"只能从文件里翻，
所以文件这份是必须的。文件行里带**相对路径:行号**（`app/services/chat.py:1234`），
grep 出来的那一行能直接定位到代码。

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `KYLAB_LOG_LEVEL` | `INFO` | 控制台与文件的级别（两处共用一档，不分开配） |
| `KYLAB_LOG_MAX_SIZE` | `5mb` | 单个文件多大之后轮转（认 `512k` / `5mb` / `1g` / 纯字节数） |
| `KYLAB_LOG_MAX_BACKUPS` | `3` | 留几份备份 |

两条容易踩的：

- **写错的值回落到默认并留一条 warning**，不影响启动（`KYLAB_LOG_MAX_SIZE=5MBx`
  会打一行"用不了，改用默认值"）——静默用默认值会让"我设了没生效"变成一个
  没人能解释的现象；
- **Windows 上轮转失败不丢日志**：文件被日志查看器打开时 `os.rename` 抛
  `PermissionError`，原生实现会让这一条日志直接打不出来——而那正是最需要日志
  的时候。我们的处置是"这轮不轮转、接着写"。


### 2.2 前端

```bash
cd frontend
pnpm install
pnpm dev                                 # http://localhost:5173
```

开发服务器把 `/api` 代理到 `127.0.0.1:8000`，所以**同源、无跨域**。

**要从别的电脑访问（局域网 / VPN）**：`vite.config.ts` 里已经写了 `server.host: '0.0.0.0'`，
所以直接 `pnpm dev` 就同时监听所有网卡，启动日志会列出可用于其他机器的地址：

```
➜  Local:    http://localhost:5173/
➜  Network:  http://192.168.31.59:5173/      ← 别的电脑用这个
```

三个坑：

- **别加 `--host 127.0.0.1`**：命令行参数会**盖掉**配置里的 `0.0.0.0`，服务退回只监听本机——
  现象就是"本机能开、别的电脑连不上"。只想指定端口就写 `pnpm dev --port 5173`。
- **后端不用跟着暴露**：`/api` 是**开发服务器替浏览器**去请求后端的，
  后端留在 `127.0.0.1:8000` 也在同源之内；要放行的只有前端这个端口（5173）。
- **Windows 防火墙**：首次会弹询问，选"允许专用网络"。本项目实测已有入站放行
  （规则 `Node.js JavaScript Runtime`，Private/Public，TCP 任意端口）；
  换机器后如果本机打得开、外机连不上，先查这里。

### 2.3 内置消费线程

后端进程内会起一个消费协程（`KYLAB_RUN_WORKER=true` 时）。
**它是"上传之后文档会不会被处理"的关键**——关掉它，任务只会排队。

界面上「任务中心」的 `/tasks/health` 会直接告诉你它开没开
（`worker_enabled`），以及有没有任务卡住（见 §4）。

### 2.4 本机档（`KYLAB_DEPLOYMENT=local`）

上面三节讲的都是**服务器档**：库在 PostgreSQL、界面从 NAS 拉。桌面壳里跑的那一份是
**本机档**（M2「会话落本机」）——同一份后端代码、另一套装配。两者的差别：

| | 服务器档（默认） | 本机档 |
| --- | --- | --- |
| 环境变量 | 不设 `KYLAB_DEPLOYMENT`（或 `server`）+ `KYLAB_DATABASE_URL` | `KYLAB_DEPLOYMENT=local` + `KYLAB_DATA_DIR`（可选 `KYLAB_LOCAL_DB`）；**不许**配 `KYLAB_DATABASE_URL`（配了启动第一秒就报错：两个真相源） |
| 会话 / 消息 / 事件 / 产物 / 笔记 / 设置 / 模型凭据 / 工作区 / 定时任务 / MCP | PostgreSQL | `<data_dir>/kylab.db`（**SQLite 单库**，`-wal` / `-shm` 与它同目录） |
| 知识库（文档 / 解析 / 检索 / 向量） | 同一个库里 | **不在本机**：本机档不挂那些端点，它是那台 NAS 的**客户端**（M3「知识库提供者」）——地址与开关见下面「知识库提供者」 |
| 鉴权 | 一律要凭据 | 短路成"本机主人"（边车只监听 `127.0.0.1`，那一档没有账号体系） |
| 入口 | `uvicorn app.main:app` | `python -m app.sidecar --port 8765 --data-dir … --workspace … --server http://nas:8000/api/v1 --token …` |

**库在哪、怎么备份**

- 桌面壳把 `app_data_dir()` 作为 `--data-dir` 交给边车 →
  Windows 上就是 `%APPDATA%\com.kylab.desktop\kylab.db`（`KYLAB_LOCAL_DB` 可覆盖文件名与位置）；
- **整份备份 = 拷 `kylab.db`（连着同目录的 `-wal`）**：单文件、没有外部服务要停。
  更稳的做法是停掉边车再拷（WAL 下运行中拷出来的副本要靠 SQLite 自己恢复）；
- 迁移前**自动**备份：`<data_dir>/migration-backup/<UTC 时间戳>-v<from>→v<to>/kylab.db`
  （schema 版本从 `schema_metadata` 读，只升不降；版本高于应用会明确报错而不是降级跑）；
- 库文件要求 SQLite **≥ 3.37**（`STRICT` 表），启动时自检，不满足就明确报错；
- **库里有明文凭据**：`model_providers.api_key`、`mcp_servers.env/headers`（与服务器同口径，
  M5 才收编钥匙串）。NAS 的令牌**不落库**（只走命令行参数与请求头）；
- 库文件多大、WAL 积了多少、这一档接的是哪个 NAS：`GET /api/v1/local/status`
  （只读，库打不开时也答得上来）。

**旧会话导入与回滚**（从服务器档那台一次性搬过来）

```bash
# 界面那条路（本机后端在跑）：
curl -X POST http://127.0.0.1:8765/api/v1/local/import -d '{"dry_run":true}'   # 只看会怎么处理
curl -X POST http://127.0.0.1:8765/api/v1/local/import -d '{}'                 # 开一个批次（后台跑）
curl        http://127.0.0.1:8765/api/v1/local/import/<批次 id>                # 轮询进度
curl -X POST http://127.0.0.1:8765/api/v1/local/import/<批次 id>/rollback      # 回滚

# CLI 那条路（边车没跑也能导）：
cd backend && python -m app.services.legacy_import \
  --server http://nas:8000/api/v1 --token <令牌> --data-dir <数据目录> \
  [--since 2026-09-01] [--dry-run] [--rollback <批次 id>]
```

- 走**HTTP 导出流**（`GET /conversations/export`），不直连服务器库；
- **幂等**：键是 `(来源, 会话 id, 源端 updated_at)`，重跑同一批只会 `skipped`，一行不写；
- **覆盖策略**：本机这条在导入之后又被改过 → 跳过并如实列出（`local_newer`）；
  本机已有、但不是我们导进来的（`not_ours`）→ 也跳过；
- **回滚**：`created` 且本机没再动过 → 删；`replaced` → 用导入前的快照恢复；
  **本机改过的一律保留**并如实报数（回滚快照在 `<data_dir>/import-rollback/<批次>/`）；
- **文件本体不随导入**：产物与消息附件只搬记录（`location` 保着服务器上的 key），
  文件本身留在那台机器上——"未随导入的文件引用数"在 `/local/status` 与导入报告里如实报；
- **本机没有的工作区**（挂在服务器上的那些"项目"）**不搬**：导入时把会话的
  `workspace_id` 置空（那条路径在这台机器上没有意义），条数记在报告与台账的
  `unresolved_workspaces` 里。

**回退开关**（两条，都**可见**、不静默）

- `VITE_LOCAL_DATA=0`：界面这一侧把会话/笔记/设置这些**打回服务器**（排障/对比用）；
  顶栏那条状态会写明是哪个变量关的；
- `VITE_SIDECAR_TURNS=0`：**一轮对话**不走边车、回服务器那条链（两个开关互不牵连）；
- 反过来，边车没起来时**不会**替你回退：界面如实报
  「本机后端未启动：…；会话数据在本机，未回退服务器」——静默换源会让用户以为会话丢了。

**知识库提供者**（M3：本机档的知识库在 NAS 上，这里是它的客户端）

- **怎么配**：默认**不用配**——本机档直接继承壳的 `server` + `api_key`
  （`--server` / `--token`，也就是"这台机器连的那台 NAS"）。要指到**另一台** NAS 时两处入口：
  界面「设置 → 知识库连接」里的**地址**（写进本机库 `provider.knowledge.base_url`，留空 = 恢复默认），
  或排障用的环境变量 `KYLAB_KB_URL` / `KYLAB_KB_TOKEN`（对应 `--kb-url` / `--kb-token`）。
  **凭据只有引导级一个来源**（壳 / 环境变量），界面那一格是只读的——它不落本机库；
  改完地址**不用重启边车**，下一次调用与状态探测就生效（探测结论缓存 30 秒）；
- **怎么关**：「知识库连接」里的开关（`provider.knowledge.enabled=0`），或 `PATCH /api/v1/local/provider`
  发 `{"enabled": false}`。关掉之后：导航里没有「知识库」那一组、对话输入框不摆知识库开关、
  KB 工具（`search` / `attach_note_to_kb` / `ingest_file`）不摆给模型，而**本机那一半照常**
  （会话 / 笔记 / 记忆 / 设置都不受影响）；笔记「加入知识库」与产物「存进知识库」会如实 **503 + 原因**；
- **断了会怎样**：地址错 / NAS 不在 / 钥匙不对 / 协议版本比本机认识的新，都停在 `unavailable`
  并给一句人话 + 下一步（`/api/v1/local/provider` 的 `reason`）。此时知识库页面**不出现**
  （在 KB 页上会被守卫送回对话页，并弹一条含原因的提示），而**单次检索失败不改这个状态**
  ——一次超时不会让导航消失（状态只由握手探测的结论改）。**绝不回退到进程内检索**：
  本机没有那些表，回退只会得到假结果。状态恢复（NAS 回来了）后 30 秒内自己回来。

**常见问题**

| 症状 | 原因与处置 |
| --- | --- |
| 顶栏写「本机后端未启动」 | 边车进程没起来（壳里看壳的日志；手动起就照 §2.4 那条命令）。**它不会回退服务器**：会话数据在本机 |
| 会话列表空、库却很大 | 界面那一份连着**另一个**库：确认边车起的 `--data-dir` 与 `KYLAB_LOCAL_DB` |
| 知识库相关 404 / 503 | 本机档不挂那些端点（知识库在 NAS 上）。产物 / 笔记入库那条会如实 503 + 原因；**页面在不在**看「知识库连接」里的状态（见上面「知识库提供者」） |
| 导航里没有「知识库」这一组 | 提供者不是 `ready`：看「设置 → 知识库连接」里的状态与原因（地址错 / 连不上 / 钥匙不对）。恢复后 30 秒内自己回来，也可以点「测试连接」立刻重探 |
| 导入报「导出流里有一行不是 JSON」 | 2026-10-01 之前的老版本：读端按 `U+2028`/`U+2029` 断行（正文里带行分隔符就会中招），升级后已修 |
| 导入报 `FOREIGN KEY constraint failed` | 同一个老版本：会话挂着服务器上的工作区而本机没有那条记录；现已改成置空 + 如实报数 |
| 导入批次卡在 `running` | 上次没跑完（被杀/断电）：**重跑同一来源即可续上**（会话级幂等）；`/local/status` 的 `unfinished_imports` 数着它 |
| 两个进程开同一个库 | **两个边车实例**同库是禁止的（启动时探测并记日志）；边车与 CLI 导入同库是允许的（WAL + 写串行） |
| 断网时还能做什么 | 会话 / 笔记 / 设置 / 工作区 / 定时任务全可用；**模型与知识库**如实失败（它们在那台机器上） |

`app/docker-compose.yml` 不在就提示路径不对（2）、用不了 docker 就把 `sudo` 那一行打出来（3）；
构建走 npmmirror（这台机器到境外带宽不可用）。**部署后的 5 条核对与回滚**（回滚就是把
`frontend/` 换回旧提交那一份、只重建前端）见 [`deploy/nas/README.md`](../../deploy/nas/README.md)。

- 本文不声称容器路线整体可用，也不声称它对；
- 首次在有 docker 的机器上跑时，**预期的失败点**是：
  1. `uv sync` 在 `python:3.12-slim` 里可能缺少编译工具——
     若失败，给 builder 阶段加 `apt-get install -y build-essential`
     （**注意**：v0.1 把这条归因于 `sqlite-vec` 的原生扩展，该依赖已随 SQLite 删除，
     归因不再成立；保留这条是因为**没实测过**，而不是因为知道它还会失败）；
  2. 卷权限：容器内以 uid 10001 运行，宿主机 bind mount 时要 `chown 10001`；
  3. 首启健康检查有 20s 宽限（`start_period`），慢盘上可能不够。

### 3.1 架构上的三个决定

1. **不直接暴露后端端口。** 所有流量从 nginx 进，
   避免"一半请求带 `X-Forwarded-*`、一半不带"的排查噩梦。
   需要直连调试时取消 compose 里那两行注释。
2. **前端由 nginx 提供，并把 `/api` 反代到后端。** 同源就没有 CORS 问题——
   生产上配错 CORS 是"本机好用、部署后全 401"的常见来源。
3. **`/api/` 反代关掉了缓冲**（`proxy_buffering off`）。对话是 SSE 流式，
   缓冲会让用户等整段回答写完才看到第一个字（后端也发了
   `X-Accel-Buffering: no`，两边都要）。

## 4. 可观测性：怎么判断"卡住了"

`GET /api/v1/tasks/health` 给出运行态总览；任务列表里每一项也带 `health`。

| 判据 | 含义 | 怎么算 |
|------|------|--------|
| `running` | 正常执行中 | 状态 RUNNING 且**租约未过期** |
| `stalled` | **可能卡住了** | 状态 RUNNING 但租约已过期——没有 worker 在续约 |
| `overdue` | 该跑没跑 | PENDING 且 `next_run_at` 已过去 10 分钟以上 |
| `idle` | 排队中 | PENDING 且还在正常等待 |
| `done` | 已结束 | SUCCEEDED / FAILED / CANCELED |

**为什么用租约过期而不是耗时阈值**：租约是 worker 主动心跳续的，
过期就意味着"没人认领这个任务了"——这是**确定的事实**。
而"跑了超过 N 分钟"只是启发式：一份 500MB 的 PDF 解析半小时是正常的，
用耗时阈值会一直误报，误报多了用户就不看这个标记了。

### 4.1 常见症状与处置

| 症状 | 多半是什么 | 怎么办 |
|------|-----------|--------|
| 启动即失败、提示 `KYLAB_DATABASE_URL` | 没配 PostgreSQL 连接串 | 见 §2.0；这是必填项，没有降级路径 |
| 任务一直 `idle` 排队 | 消费线程没开 | 确认 `KYLAB_RUN_WORKER=true` 并重启 |
| 任务变 `stalled` | 进程崩过 / 被 OOM 杀 | 重启服务；租约过期后任务会被回收重跑 |
| 任务 `overdue` | 同上，或调度没起来 | 看 `/tasks/health` 的 `worker_enabled` |
| 任务反复失败 | 解析器或模型凭据问题 | 看任务详情里的 `error`（含阶段名） |

## 5. 容量与并发（T7.3：**未实测**）

计划里 T7.3 要求"至少两档内存配置实测数据"。**这一项没有完成**，
原因与容器路线相同：本机没有可做对照测试的环境，而编一张表出来
比不给更糟——用户会照着它做采购决定。

**可以确定的（来自架构与实测运行）**：

- 主服务常驻内存约 **300–500MB**（架构 §4.1 的量级，与本地运行观察一致）；
- **内存预算要把 PostgreSQL 算进来**（v0.12 起它是必选组件）：同机部署时
  PG 自身通常再要几百 MB，小内存机器上这是新的下限约束。
  v0.1 那句"纯云端解析路线 4GB 可跑"指的是**后端进程**，不含 PG；
- 摄入的主要开销在**向量化与解析**，不在这个进程本身——
  所以并发档位实际上受"云端配额"与"网络"约束，而不是本地 CPU。

**要拿到实测数据，需要做的对照**（留给有环境的机器）：

1. 同一批文档（建议 ≥200 份、含 10 份以上大文件）；
2. 两档内存（4GB / 16GB）各跑一遍，固定 `KYLAB_WORKER_LEASE_SECONDS`；
3. 记录：端到端耗时、峰值内存、失败率；
4. 结论写成"档位 → 推荐并发数"，写进本文件。

在此之前，**不要**给用户一个猜测的并发数。

## 6. 升级与备份

**v0.12 起数据分三处，备份要分别对待**（原先"拷一个目录"的做法已不适用）：

| 内容 | 位置 | 备份方式 |
|---|---|---|
| 元数据 + 向量 + 全文 | PostgreSQL | `pg_dump -Fc`（角色另用 `pg_dumpall --globals-only`） |
| 原件 / Markdown / 图片 | MinIO/S3 桶（或本地 `KYLAB_DATA_DIR`） | 对象的版本化/快照；本地实现则拷目录 |
| 表格副本 | `KYLAB_DATA_DIR/tabular.duckdb` | 拷文件（停服务后） |

- **schema 是应用拥有的**：启动时自动建/校验基线（`ensure_schema`），
  版本不符会拒绝启动而不是带着半截结构跑。
- **不要**直接拷运行中的 PG 数据目录——那是不一致的；用 `pg_dump` 或
  `pg_basebackup`（要 PITR 时再加 WAL 归档）。
- **回收站**：删除的文档原文保留 7 天（桶内 `.trash/<id>/`），
  到期由 worker 的空闲维护清理。**要立刻释放空间就手动清空该前缀**。
- **升级到 0.2.0**：存储层在 0.1.0 → 0.2.0 之间换过地基（SQLite → PostgreSQL），
  所以 **0.1.0 的 SQLite 数据没有迁移路径**——只能在 PG 上重新摄入。
  0.1.0 之后没有别的破坏性变更，同一大版本内的升级只需替换镜像/代码，schema 自动补齐。
