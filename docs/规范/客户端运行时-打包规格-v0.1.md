# 客户端运行时 打包规格 v0.1（P4-3）

- 日期：**2026-09-29**；范围：**客户端（壳 + 本地边车）那一个进程**的运行时怎么装、装多大、怎么重建。
- 结论一句话：**16.8 MB / 974 个文件**（目标 40–60 MB），`--help`、`/health`、一轮带工具的真烟测全部通过。

## 1. 为什么单独做一份运行时

前后端分离之后，"客户端"只跑 **agent 循环 + 工具 + 工作区 + 沙箱**；KB 解析、向量检索、
模型代理、账号与会话权威都在服务器。所以客户端**不需要**拖着服务器那套依赖走：

|                                      | 体量          | 里面是什么                                                                                                                                 |
| ------------------------------------ | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 服务器侧 dev venv（`backend\.venv`） | 约 **400 MB** | pymupdf 52.8 / jieba 40.9 / numpy 42.2 / pandas 40.6 / matplotlib 26.4 / botocore 20.6 / PIL 14.7 / cryptography 10.2 / psycopg_binary 8 … |
| **客户端运行时（本规格）**           | **16.8 MB**   | fastapi / uvicorn / httpx / pydantic + 传递依赖 + 我们自己的 `app\**`                                                                      |
| LibreOffice（用户裁定**不打包**）    | 约 700 MB     | 只做"本机装了就用它"                                                                                                                       |

## 2. 装什么 / 不装什么（及理由）

三段的完整清单与逐行理由在 `backend/requirements-sidecar.txt`（**该文件必须 UTF-8 带 BOM**：
pip 会按本机 locale 猜编码，无 BOM 时中文注释直接 `UnicodeDecodeError`，实测过一次）。

**装**：`fastapi`、`uvicorn`、`httpx`、`pydantic` 四个根 + 传递依赖（`starlette`/`pydantic_core`/
`pydantic-settings`/`python-dotenv`/`annotated-*`/`typing_*`/`anyio`/`idna`/`certifi`/`httpcore`/
`h11`/`click`/`python-multipart`/`markdown-it-py`/`mdurl`/`PyYAML`）+ 导入闭包带来的
`argon2-cffi` 链（`argon2-cffi-bindings`/`cffi`/`pycparser`）。

**不装**（每一条都有实测依据，见 §4）：

| 不装                                                                                     | 体量       | 为什么                                                                   |
| ---------------------------------------------------------------------------------------- | ---------- | ------------------------------------------------------------------------ |
| `psycopg` / `psycopg-binary` / `psycopg-pool`                                            | 约 9.5 MB  | 客户端**永不直连 PG**（服务器权威）；惰性化后也不在闭包里                |
| `boto3` / `botocore` / `s3transfer` / `jmespath` / `urllib3` / `six` / `python-dateutil` | 约 21.8 MB | 同上（对象存储在服务器）                                                 |
| `duckdb` / `_duckdb`                                                                     | 约 35.6 MB | 表格副本是服务器那条分析链                                               |
| `jieba`                                                                                  | 约 40.9 MB | 分词只服务服务器检索；四处模块级导入已惰性化                             |
| `pywin32` 全家                                                                           | 约 11.9 MB | **dev venv 的产物**（`pywin32.pth` 在 site 引导时 import），不是应用依赖 |
| `Pygments`                                                                               | 约 4.5 MB  | AST 扫描 126 个可达模块 **0 命中**；实测去掉照旧通过                     |
| LibreOffice                                                                              | 约 700 MB  | 用户裁定；本机装了**只检测后使用**                                       |
| dev venv 整体                                                                            | 约 400 MB  | 红线：绝不打包                                                           |

## 3. ⭐ 最重要的一课：**清单 ≠ 闭包**

"读代码看它 import 了什么"写出来的清单**不等于**真实依赖。实测被逐个逼出来的缺项：

1. `jieba`（模块级导入链）→ `ModuleNotFoundError: No module named 'jieba'`；
2. `_duckdb`（当时按"闭包建议"排除了它）→ 运行期才发现真的在链上；
3. `duckdb` 的 `.dist-info`（手工拷贝没带元数据）→ `PackageNotFoundError: duckdb`；
4. `typing_extensions`（**单文件 `.py`**，按目录拷必漏）；
5. `_cffi_backend`（**site-packages 根下的 `.pyd`**，同上）；
6. `psycopg` 的 `no pq wrapper available`（`psycopg_binary` 的 DLL/`.libs` 装不上）。

→ 所以口径固定为：**以 `import app.sidecar` 的实测 `sys.modules` 为准**，
工具是 `scripts/sidecar-closure.py`（**只读**：不装包、不打网络、不改运行时、不杀进程）。

**判据**（Phase B 验收就是它，别的都不算）：改完惰性导入之后**重跑闭包**，
期望被治掉的包从 `sys.modules` 里消失。"看代码觉得不该有"不是判据。

## 4. 体量：三个阶段与逐块拆解

| 阶段                    | 做法                                 | 体量                                                                |
| ----------------------- | ------------------------------------ | ------------------------------------------------------------------- |
| A（手工按闭包拷）       | 目录/单文件/根 `.pyd` 三种形态靠人记 | **156.6 MB / 5915 文件**（含 `_duckdb` 35.6 MB 与 botocore 等）     |
| B-1（离线按 RECORD 拷） | 惰性化 storage 后端之后              | **33.3 MB / 1940 文件**（清理掉 pip 本体与 pip 临时目录共 13.4 MB） |
| **B-2（最终）**         | 再去掉 `pywin32` 与 `Pygments`       | **16.8 MB / 974 文件**                                              |

最终拆解：

| 块                       | 体量                    | 说明                                                                                                                                        |
| ------------------------ | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `Lib\site-packages`      | **12.7 MB**             | 22 个发行包；最大的是 `pydantic_core` 5.3、`pydantic` 3.2、`fastapi` 1.3、`anyio` 0.9、`click` 0.8、`yaml` 0.7、`httpcore` 0.6、`httpx` 0.6 |
| `app\`（我们自己的代码） | **3.2 MB / 194 个文件** | 整份拷，不裁剪（红线）                                                                                                                      |
| `Scripts\`（解释器外壳） | 0.9 MB                  | venv 的启动器与 DLL 入口                                                                                                                    |
| 入口与清单               | < 0.1 MB                | `run-sidecar.cmd` / `run-sidecar.ps1` / `requirements-sidecar.txt`                                                                          |

**可删项（已经全删）**：pip 本体与 `setuptools`（约 13 MB，运行期不需要；"更新运行时"靠重跑脚本）、
pip 的临时目录（`pip-install-*`/`pip-unpack-*`/`pip-build-env-*` —— 中断的安装会留下几十 MB，
**体量读数就是被它带偏过一次**：91.8 MB 里有 54.9 MB 是临时目录）、`__pycache__`/`*.pyc`、
`*.chm`（pywin32 的 2.5 MB 帮助文件）。

## 5. ⭐ 惰性化那一招（Phase B 的核心）

**病灶**：`app.sidecar` 的**模块级**导入链会把服务器侧基础设施顺带拽进来 —— 客户端一次都用不到。

**这一刀落点**（唯一允许 import 具体后端的地方）：`backend/app/core/storage.py`

- 原本是模块级 `import` 三个后端（`postgres_impl` / `s3_impl` / `duckdb_impl`）；
- 现在改成**按需导入**：`build_stores()` / `_build_pg_stores()` / `_build_object_store()` 里才 import；
- 类型标注用 `TYPE_CHECKING` 挡住（`PgDatabase`）；
- **行为不变**：失败时机一样 —— 原先"导入模块时"缺包就炸，现在"调用 `build_stores()` 时"炸，
  而唯一的调用点就是服务器启动时的组合根。

**同一招的其他落点**（已由前一条 lane 完成，样板写法见 `services/retrieval/coverage.py::_jieba()`）：

- `app/storage/text.py`（`_jieba()`）与 `app/services/embedding/deterministic.py`（`_jieba()`）；
- `app/storage/postgres_impl/fulltext_store.py` 那处模块级 `import jieba` 现在**够不着**了 ——
  它是通过 storage 工厂才被导入的，工厂惰性之后整条链都不在客户端闭包里。

**适用面**：只治"**客户端永远不执行**的服务器侧路径"。判据是闭包复跑，不是手感。
反过来，**边车真会用到的东西不许惰性化**（例：`duckdb` 若将来被沙箱/表格用上，就要加回来并把理由写清）。

**反向验证（原文）**：

```
# 把模块级 import boto3 加回 storage.py：
boto3     boto3==1.43.93
botocore  botocore==1.43.93
合计 36 个顶层模块          ← 判据变红 ✓
# 恢复之后：
合计 28 个顶层模块          ← psycopg / duckdb / boto3 / botocore / jieba 全部不在 ✓
```

**注意**：闭包**只反映模块级导入** ✗ —— `uvicorn`、`httpcore`、`h11`、`certifi` 是
**函数内/运行期**导入的，闭包里看不到，但必须装在清单里（烟测证明：少了它们请求发不出去）。

## 6. 离线装配：按 RECORD 逐文件拷（五种形态都对）

`scripts/build-sidecar-runtime.ps1 -Offline` 不联网：`python -m venv` 建干净目录 →
从 `backend\.venv\Lib\site-packages` **按每个发行包的 `RECORD` 逐文件拷** → 拷 `backend\app\**` →
写 `run-sidecar.cmd` / `run-sidecar.ps1` → 清可删项 → **称重并出逐块明细**。

为什么按 RECORD 而不是"按目录名拷"：离线装配踩过五种形态 ——

1. **目录**（绝大多数包）；
2. **单文件 `.py`**（`typing_extensions.py`）；
3. **site-packages 根下的 `.pyd`**（`_cffi_backend.cp312-win_amd64.pyd`）；
4. **伴生目录**（`*.libs/`，重型二进制包才有）；
5. **`.dist-info/` 元数据**（少了它 `importlib.metadata` 会 `PackageNotFoundError`）。

`RECORD` 本身就是"这个包到底有哪些文件"的权威答案，所以按它拷一次就都对。

联网模式（`-IndexUrl https://pypi.org/simple`）保留作备用：**本机 pip 配置指向清华镜像时实测会卡住**
（十几分钟不动，被掐掉后还留下子进程占着目录），脚本因此做了"失败自动换官方源重试一次"。

## 7. 嵌入式 CPython 怎么接（只留接口）

**先说清自包含性**：venv **不带标准库** ✗ —— 实测 `dist\sidecar-runtime\Lib` 里只有 `site-packages`，
`pyvenv.cfg` 指向本机 `…\Programs\Python\Python312`。所以那 **16.8 MB 是"venv + 我们的代码"，
需要一台装了 Python 3.12 的机器**（或把嵌入式解释器放进去）。
按目标体量算：16.8 MB + 嵌入式 CPython 约 15–20 MB ⇒ **约 32–37 MB**（仍在 40–60 MB 目标内）。

目标形态是"客户端不依赖用户机器上的 Python"。脚本留了 `-EmbeddedPython <目录>` 参数：

- 给了：校验目录里有 `python.exe`，打印它的体量，并说明布局约定（解释器放 `runtime\python\`，
  入口指向它）；
- 没给：用 venv 自带的解释器外壳（`Scripts\` 0.9 MB），**不去下载几百 MB 的东西**。

本机没有嵌入式发行版，所以这一轮**只留接口不搬文件**（避免半成品）。

## 8. 红线

1. **绝不打包 dev venv**（`backend\.venv`，约 400 MB）；脚本里有守卫：产物目录落在它下面直接拒绝。
2. **绝不打包 LibreOffice**（约 700 MB）；本机装了**只检测后使用**（脚本会打印检测结果）。
3. **不裁 `backend\app` 的源码**（整份拷）。
4. 脚本**必须 UTF-8 带 BOM**（Windows PowerShell 5.1 无 BOM 会按 GBK 解码直接语法崩溃）；
   `requirements-sidecar.txt` 同理（pip 的编码猜错会 `UnicodeDecodeError`）。
5. 统计体量一律用**文件字节和**（`Length` 求和），不要用"占用空间"（两者差很多）。

## 9. 怎么重建（一次一条命令）

```powershell
# 离线（推荐）：从开发 venv 按 RECORD 拷，不打网络
powershell -ExecutionPolicy Bypass -File scripts\build-sidecar-runtime.ps1 -Offline

# 联网备用（本机镜像会卡，所以显式指官方源）
powershell -ExecutionPolicy Bypass -File scripts\build-sidecar-runtime.ps1 -IndexUrl https://pypi.org/simple
```

跑完会打印 **总大小 / 文件数 / 逐块明细 / 清理释放量 / LibreOffice 检测结果**。

**改完 `backend\app\**` 之后**：只要重跑上面那条命令即可（`app\` 是整份拷的）。
**改了依赖**之后：先 `cd backend`，跑
`..\.venv\Scripts\python.exe ..\scripts\sidecar-closure.py` 看真实闭包，
再按它的输出更新 `requirements-sidecar.txt`，然后重建。

**起边车**（用那份运行时）：

```powershell
dist\sidecar-runtime\run-sidecar.cmd --host 127.0.0.1 --port 8767 `
    --server http://127.0.0.1:8100/api/v1 --token <用户会话令牌> --workspace <可写工作区>
```

## 10. 验收（本轮的物证）

- `scripts/sidecar-closure.py` 复跑：**28 个顶层模块**，`psycopg`/`duckdb`/`boto3`/`botocore`/`jieba` 全不在；
- 体量：**16.8 MB / 974 文件**（阶段 A 156.6 MB → 阶段 B 16.8 MB）。
  ⚠️ 这 16.8 MB **不含标准库**（venv 不带）→ 独立分发要再加嵌入式解释器约 15–20 MB（合计约 32–37 MB）；
  ⚠️ **首次运行之后**会多出 `__pycache__`（Python 自己写的字节码缓存）：实测升到
  **24.4 MB / 1507 文件** ✓ —— 出厂状态是刚构建完的 16.8 MB（构建脚本会先删一遍缓存 ✓），
  跑起来变大是正常的，对启动速度有利；
- 真烟测（`python -m app.sidecar`，端口 8767，后端 8100）：
  `--help` ✓ → `/health`：`kb_reachable=true`、`model_reachable=true` ✓ →
  一轮"用 read_file 读 hello.txt"：`steps` 里 `tool="read_file"` **非空**、`args`/`result` 有内容 ✓、
  `recorded=true` ✓（证据：`.shots\sidecar-runtime-smoke.json`、`.shots\sidecar-runtime-smoke-stdout.log`）；
- 门禁：`ruff check app/ tests/` 全绿；`IMPORT_OK`；相关既有用例 **301 passed / 6 skipped**。

## 11. `httpx` 那条链：**已做完**（判据过了）

**病灶**：`httpx/__init__.py` 里有一句 `from ._main import main`（它自带的 CLI 入口）→
于是**任何** `import httpx` 都会把 `click` + `pygments` + `rich` 一起拖进导入闭包（约 5.5 MB），
而客户端（边车）只需要它"发请求"那一部分能力。

**做法**：新增 `backend/app/core/lazy_httpx.py` —— 一个**惰性代理**（真属性 + `__getattr__` 转发）：

```python
from app.core.lazy_httpx import httpx   # 全仓不再直接写 import httpx
httpx.Client(...)                        # 第一次访问属性时才真正 import httpx
```

- **调用点一个字都没改**（属性名照旧）；
- **行为不变**：缺包仍在**第一次访问那一刻**抛 `ModuleNotFoundError`（原先在导入模块那一刻抛）；
  `except httpx.HTTPError` / `isinstance(exc, httpx.TimeoutException)` 照旧（取到的是真类）；
- 为什么用"真属性 + 代理"而不是模块级 `__getattr__`：`from app.core.lazy_httpx import httpx`
  拿到的是**代理对象**本身（模块级 `__getattr__` 会在 `from ... import` 那一刻就把 httpx 拉进来）；
  代理类若塞进各文件的 import 块，还会让后面的 import 全吃 `E402`。

**改到的 13 个文件**：`app/core/http.py`（顺带把模块级的 `httpx.Limits` 改成惰性 `_limits()`）、
`app/services/{llm,web,model_registry,webhook,skill_sources}.py`、
`app/services/embedding/{openai_compat,wemm}.py`、`app/services/retrieval/rerank.py`、
`app/services/connectors/base.py`、`app/parsers/{mineru_cloud,paddleocr_api}.py`。

**判据（重跑闭包）**：**28 → 22** 个顶层模块，`httpx` / `click` / `pygments` / `rich`
**全部消失**（早先那轮只走到 26，去掉的是 `markdown_it` / `mdurl`）。

**用例的接缝也跟着换了**（这条经验值得记住）：`sidecar` 那 5 条写回用例原先
`monkeypatch.setattr(sidecar.httpx, "post", …)` —— 模块级名字没了，patch 就落空。
**没有把惰性化退回去**，而是给 `sidecar` 留了一个**明确的可注入接缝**
（`sidecar._httpx()`，测试 `monkeypatch.setattr(sidecar, "_httpx", lambda: fake)`），
语义没减弱："写回失败要如实进 notes 且不动 answer"这类真行为照样钉住。

**顺带一个实测结论**：`pygments` **不装也能跑**（httpx 对可选 CLI 依赖是容错的）——
它本来就不该出现在装配清单里（见 §2 与 `requirements-sidecar.txt` 第 4 节）。
