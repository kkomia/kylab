### 0.2 三个会决定形状的结构性发现

**发现 ①：前端的知识库页面今天已经能用，M3 不是"接一条新链"，而是"给这条链加握手与显隐"。**
`frontend/src/api/client.ts:88-94` 的 `request()` 打相对 `/api/v1`，桌面壳把 `/api/**` 转发到 NAS（`desktop/src-tauri/src/resources.rs:573-590`）；M2 §4.3 明写"知识库/账号面继续走壳转发到 NAS"（`docs/规范/会话落本机-实施方案-v0.1.md:307`）。所以 **NAS 现有的知识库 REST 族就是那个"提供者窄 API"**，M3 只需补握手，并把"页面在不在"接到握手上。

**发现 ②：本机档里 KB 域只剩两个真调用方，这一个数字决定 RemoteMetaStore 的边界。**
- `ChatService.kb_prompt` 读 `stores.meta.get_knowledge_base`（`backend/app/services/chat.py:683`）——今天被 `except` 吞成一句 warning（`:684-686`）；
- `notes` / `artifacts` **各自持有一份真 `IngestService`**（`backend/app/core/services.py:537`、`:667`）——`build_local_services` 用 `dataclasses.replace` 只换得到 `Services.ingest` 这个字段，**换不到这两个对象内部的引用**（`backend/app/sidecar.py:454-464`）。这就是 `attach_note_to_kb` 今天 503 的**真机制**：它走的是 `NotesService._ingest` = 真 `IngestService` → `stores.meta.create_document` → `UnavailableMetaStore` 抛"知识库在 NAS…"（`backend/tests/unit/test_sidecar.py:1187-1223` 抓到的正是这句）。
- 除此之外**没有任何**本机代码路径会碰 KB 域（`ChatService` 里另外两处 `stores.meta` 调用 `:487` `:867` 只在"没有 knowledge 客户端"的进程内检索分支上）。

**发现 ③：桌面壳在没有钥匙时根本不起边车。**
`Manager::ensure` 对空 token 直接报"还没有钥匙"（`desktop/src-tauri/src/sidecar.rs:474-488`）。因此 **"不配知识库"的可执行定义不能是"什么都没配"**，必须是：

> **配了 NAS（登录 + 领钥匙 + 模型代理可用），但知识库提供者被关掉或不可达。**

这条要写进验收口径（否则 M3 的两行验收在真机上不可执行）。

## 1. Q1 · 提供者窄 API 形状

### 1.1 结论：窄 API = NAS 现有知识库 REST 族 + **新增一个握手端点**；不新造一族

理由：现有端点族已经是"窄"的（只回检索原文与元信息、不做 LLM 预处理，`search.py:1-5`），而且**页面已经在用它**（发现①）。再造一层"提供者专属 API"只会得到第二份契约。

### 1.2 握手端点契约草案（唯一真正要新增的 NAS 端点）

**落点**：`backend/app/api/v1/provider.py`（新模块）
```python
router = APIRouter(prefix="/provider", tags=["provider"])

@router.get("/handshake", response_model=ProviderHandshakeOut, summary="知识库提供者握手（连通性 + 能力集 + 库清单）")
def handshake(services=Depends(get_services), caller: Caller = Depends(require_read)) -> ProviderHandshakeOut
```
挂载：`backend/app/api/v1/router.py` 的 `api_router.include_router(provider.router)`（`:57-105` 那一段）；**不进 `local_router`**（本机档没有知识库，本机侧是客户端角色）。

响应（`ProviderHandshakeOut` 加进 `backend/app/api/v1/schemas.py`，与 `KnowledgeBaseOut:170` 同一文件）：


**取值来源（全部复用现有读法，不新增存储方法）**：
- `knowledge_bases`：`services.knowledge_bases.list_all()`（`knowledge_bases.py:97`）+ `document_stats()`（`:104`）+ `services.api_keys.visible_kb_ids(caller)`（`:100`，**受限 key 只看到范围内的库**）+ `can_write`（`:57`）——即把 `GET /knowledge-bases` 那一段**换成同一个私有函数拼一次的 JSON**，字段名与 `KnowledgeBaseOut:170-201` 对齐；
- `capabilities.embedding`：`services.runtime.embedding().is_configured` + `services.embedder.model_id/dim/is_development`（与 `search.py:64-65` 同一读法）；
- `capabilities.ingest.extensions`：从 `app/parsers` 的注册表**机械导出**（不许手抄清单，与 `LOCAL_METHODS` 同一条纪律）；`max_bytes` 取 `documents.py:63` 的 `MAX_UPLOAD_BYTES` 常量本身；
- `capabilities.retrieval.modes`：`services/retrieval` 的 mode 枚举（`SearchRequest.mode` 默认 `hybrid`，`schemas.py:561`）。

**三条设计裁量（要写进模块头）**：
1. **不复用 `/health`**：health 是基础设施探针（不鉴权、容器编排用），握手要鉴权——"凭据错"本身就是握手结论的一部分；而且握手要带**能随调用者变的库清单**；
2. **必须鉴权**（`require_read`）：401/403 与"连不上"必须能被客户端分成两档（改钥匙 vs 改地址）；
3. **协议版本是整数且只增**：`protocol_version=1` 是 M3 的值；客户端规则——**不认识（>`本机所知`）即判不可用**，句子里带版本号，绝不硬试。

**权限模型映射（要写进《知识库连接》面板的注释里）**：
- **"本机主人"在 NAS 侧不是管理员**：`check_access` 只对 `is_admin` 短路（`api_key.py:229`），空范围 + readwrite 会让**所有知识库类端点**放行（`:261-275`），但 `require_admin` 的端点（`/settings`、`/api-keys`、`/users`、`/trash`、`/maintenance`、`/sandbox`）对这把钥匙是 **403**（`api/auth.py:120-132`、`lifecycle.py:42-51`）→ 所以窄 API 只用 `require_read`/`require_write` 那批；握手响应里 `caller.is_admin` 如实报 `false`，将来界面据此隐藏"回收站"这类入口（M3 只登记，不接线）。

**实现总数：2 个真映射 + 其余抛。** 这不是"半吊子"，而是把"能力在，才在"落到**方法级**：能映射的映射，映射不了的**如实抛**（v0.3 §3.1「"无"是一个合法实现」）。

### 2.2 检索不进 RemoteMetaStore 的两条理由（这是本节的结论，不留给 coder 再判）

1. `stores.meta.search` 的调用方是 `RetrievalService`（进程内混合检索：向量通道 + 全文通道 + 融合 + 重排 + `stats/mode/filtered_out`，`search.py:43-56`）。要让它走 NAS，就得在本机**再实现一遍"把一次混合检索拆成一次远端调用再拼回 `RetrievalResponse`"**，还得让 `stores.vectors`/`stores.fulltext` 装作存在——那是把服务器那个服务搬本机来套壳。
2. `ChatService` 早就在**更上一层的接缝**上（`retrieve_sources`，`chat.py:787`）整段委托，边车今天就是这么跑的。M3 只需把"那个委托对象"从 `RemoteKnowledgeClient` 换成提供者客户端。

**因此**：`stores.meta` 的 KB 半只补"本机服务层读得到的元数据"（2 个方法），检索/入库/进度/库清单统一进 `services/knowledge_provider.py`。

### 2.3 装配改动（三处，都是小改）

1. **新模块** `backend/app/storage/split_impl/remote_meta.py`：
   ```python
   IMPLEMENTED: frozenset[str] = frozenset({"get_knowledge_base", "list_knowledge_bases"})

   class KnowledgeMetaReader(Protocol):        # 只声明它要的两件事（storage 层不认识 HTTP/services）
       def get_knowledge_base(self, kb_id: str) -> dict[str, object] | None: ...
       def list_knowledge_bases(self) -> list[dict[str, object]]: ...

   RemoteMetaStore = _build_remote(...)        # 生成器与 UnavailableMetaStore 同一套（router.py:161-189）
   ```
   - 生成规则：`IMPLEMENTED` 里的名字走真实现（转 reader → 转成 `KnowledgeBaseRecord`），其余走 `_unavailable_method`（原句保留）；
   - `bind_reader(reader)`：**一次**注入（见下条，写清"为什么不是构造参数"）；
   - 未 `bind` 就调用 → 抛 `KnowledgeBaseUnavailable("知识库提供者还没接上（组合根未装配）")`，**不是 `AttributeError`**。
2. `backend/app/storage/split_impl/__init__.py`：导出 `RemoteMetaStore` / `KnowledgeMetaReader`。
3. `backend/app/core/storage.py::_build_local_stores`（`:157-210`）：`kb=RemoteMetaStore()` 替掉 `:203` 的 `UnavailableMetaStore()`；随后由**服务层装配那一步**接上 reader：
   ```python
   # core/services.py（本机档、provider 建好之后，一次）
   stores.meta.kb.bind_reader(provider.knowledge_meta())   # _Router.kb 是公开属性（split_impl/router.py:96）
   ```
   **为什么是"后挂"而不是构造参数**：层序决定了它——`core/storage.py` 先于 `core/services.py` 跑（`core/services.py:325` 的 `bundle = stores or build_stores(resolved)`），而 reader 需要"能随设置改地址"的能力（只有服务层有运行期配置）。这一处注入**只发生一次、只在装配期**，不动 `split_impl` 的"路由表构造时定下"那条纪律（`router.py:101-105`）。

**用例（照 `tests/unit/storage/test_split_impl.py:97-108` 那条的写法再加一条）**：
- `RemoteMetaStore` 的公开方法集合 **恰好等于** `REMOTE_METHODS`（一个不多一个不少）；
- `IMPLEMENTED` 之外的名字逐个调用 → 抛 `KnowledgeBaseUnavailable`；
- 未 bind 时两个已实现方法抛的是**那句中文**，不是 `AttributeError`；
- `bind` 之后按 reader 的返回映射成 `KnowledgeBaseRecord`，404（reader 给 `None`）→ 返回 `None`（契约：None = 没有这个库）。

### 2.4 与 M4 的接口（只写一句，别在本阶段做）

M4 的"读路径元数据缓存（etag + SWR）"就长在这个 reader 上：`RemoteMetaStore` 的调用点 = 本机服务层读 KB 元数据的唯一入口，缓存层插在 `KnowledgeMetaReader` 与 HTTP 之间，`stores.meta` 与 `services/` 一行不改。**M3 只把 `IMPLEMENTED` 定为这 2 个方法**，M4 再往这个集合里加（加行即扩展，有那条集合用例守着）。

## 3. Q3 · 页面激活规则

### 3.1 判定源与状态机

**唯一判定源**：本机档的 `GET /api/v1/local/provider`（新，落在 `backend/app/api/v1/local.py`，随 `local_router` 自动挂上、边车与 `create_app` 都挂，`app/main.py:180-183`、`sidecar.py:1079`）。

### 3.2 握手缓存、失效与降级

| 问题 | 落法 |
| --- | --- |
| 什么时候探？ | **不在启动时挡路**（v0.3 §6.1-1"模型连通性检查等放后台"同理）：首次被前端问到才探；进程内缓存 |

## 6. 风险清单（每条给缓解）

| # | 风险 | 缓解 |
| --- | --- | --- |
| R1 | **交互路径被握手拖慢**（每次切菜单都等一次 NAS 往返） | 握手只在后台/短超时（3s）+ 进程内缓存（TTL 30s）+ **前端不在渲染路径上等它**（未知按缺席渲染）；`ready` 时不轮询 |
| R2 | **页面显隐抖动**（网络一抖 KB 页就没） | ① 只以**握手**结论改状态，单次调用失败不改；② `unknown` 与 `unavailable` 分开（前者不闪）；③ 状态只在**变化时**广播 |
| R3 | **凭据落库/入日志**（把 NAS token 写进本机库或日志） | token 只从引导级来（壳 `config.json` / 环境变量）；`/local/provider` **只允许写 `base_url`/`enabled`**（白名单，键名写死）；设置面板只读显示。用例断言 `app_settings` 里不存在任何含 token 的键、日志里不出现明文（M5 才收钥匙串） |
| R4 | **库清单两处真相**（面板缓存 vs NAS） | 面板的库清单**只作状态展示**，不作权威：检索/建库/上传一律以 NAS 为准；M4 才做 SWR 缓存 |
| R5 | **回填的 NAS 文档 id 会失效**（NAS 重建/换实例） | `note.doc_id` / `artifact.document_id` 照旧回填；读到失效 id 时（`GET /documents/{id}` 404）**如实报"那篇文档不在这个提供者上了"**，不自动清理、不静默置空 |
| R6 | **影子引用没换干净**（发现②：`notes`/`artifacts` 各持一份真 ingest） | 组合根**一处**换线（§5.1）+ 那条"没有任何对象还指向真 `IngestService`"的守卫用例 |

## 9. 明确不做（M3 边界）与决策点

**不做**：
1. **不把知识库端点族挂到本机档**（`local_router` 白名单不动，`api/v1/router.py:113-137`）：页面经壳转发直连 NAS 是既有可用链，重挂等于在本机重造一遍 KB 服务；
2. **不搬向量化/嵌入/解析**（v0.3 §11-4）；本机不 import `psycopg`/`boto3`/`duckdb`/`jieba`；
3. **不做多 NAS 的凭据管理**（一个提供者 = 一处地址 + 壳里那把钥匙；覆盖地址时凭据仍来自壳）；
4. **不动前端登录门禁**（R13：本机档"无 NAS 也能进去"是独立一小阶段，M6 之前收）；
5. **不改 `session_events`**（§5.3）；
6. **M4 才做元数据缓存**（本阶段读数不落库、不做 etag/SWR）；
7. **不发 `protocol_version > 1`**（M3 = 1；升降级规则先落地，能力位先"如实报"再逐项消费）。

**决策点（建议已给，供架构师一句话确认）**：
- **D1**：把「概览」「任务中心」从侧栏「知识库」组里提出来（否则整组隐藏会连带两个与知识库无关的页面）。建议：**提出来**；
- **D2**：设置收编落成"壳的 server+key 是权威、本机库的 `base_url` 是覆盖"，凭据**不落本机库**。建议：**按此**（保住 M2 R6 那条纪律）；
- **D3**：提供者状态在顶栏的显示策略——"非 ready 才显示"。建议：**按此**（可用时长什么样由侧栏那组回答）。

### 偏离与决策点（逐条理由）

1. **`capabilities.ingest.extensions` 的"唯一权威来源"定在提供者模块的 `INGEST_EXTENSIONS` 常量**
   （原话：parser 探针链的声明可机械导出就用它）：审定前的核验②已经点明 `app/parsers` **没有**
   统一注册表（收不收由后缀 + MIME + 内容探测共同决定），机械导不出来。所以清单在
   `api/v1/provider.py` 模块头**集中定义一份**并注明"这是今后的唯一口径"——手抄第二份会漂，
   而这次是**唯一一份**；
2. **`KnowledgeBaseUnavailable` 搬到了接口层**（`storage/base.py`）再由 `split_impl` 与
   `services/knowledge_provider.py` 各自 import：抛出它的对象现在有"提供者客户端"这一侧的，
   而 services 层只允许 import 接口层（工程规范 §3.3 的 L2）。搬走不影响任何调用方（同名再导出），
   分层计数守住了 104；
3. **工具表门控在 `kb_ids` 为空时一次都不探提供者**（`Clients.tool_specs`）：那三个 KB 工具
   在没选库时本来就被库开关摘掉了，若还去探一次握手，**每一轮对话**都会多一次 NAS 往返
   ——R1 要的恰恰相反；
4. **`Clients` 的 `provider` 收成进程级单实例**（阶段 5）：`ChatService` 的检索、笔记/产物的
   入库网关、`Services.ingest`、`stores.meta.kb` 的 reader、`/local/provider` 端点与
   `Clients` 自己**全从 `Services.provider` 取同一个对象**。于是"端点说 `ready`、工具表说不 ready"
   这类不一致在结构上不可能出现（阶段 3 交接里登记过这条建议，阶段 5 落地）；
5. **`/local/provider` 不 ready 时那五段"根本不在响应里"**（不是 `null` / 空对象）：
   回了空对象，界面就得猜"是没探到还是真没有"；`response_model_exclude_unset` 让这个契约
   在 OpenAPI 与用例里都看得见；
6. **`PATCH /local/provider` 写完立刻重探并把整个最新状态回给前端**："保存地址 → 侧栏当场长出
   知识库组"是同一帧内的事（方案 §3.4）；空 body = 只重探一次（等价 `refresh=1`）；
7. **`GET /local/provider` 那个真 bug 顺手修了**（阶段 5 施工中抓到）：一个同名助手被后定义者
   覆盖，`GET` 曾回 `ImportBatchOut` 形状。加了用例（两个挂载面各钉一条），教训写进了 docstring；
8. **D1 按建议落地**：「概览」「任务中心」从「知识库」组里提进主导航——整组隐藏时不该把它们
   一起带走（真机物证：两态下这两项都在）；
9. **D3 按建议落地**：顶栏那条 provider 摘要**只在本机档且非 ready 时显示**（可用时长什么样
   由侧栏那组回答，而"数据在哪"那条必须常显是因为它说的是归属）；
10. **R8 只消费了"上传上限 + 格式提示"这一处**：`uploadLimits.ts` 改成握手优先、常量兜底
    （没探到结论时界面照旧能用）。能力集其余字段 M3 只在面板显示（不接线）；
11. **真机抓到的一个真缺口：本机档的 `sources` 事件从来没发过**（阶段 7 修）：
    本机这一侧的 SSE 只处理 `step`/`thinking`/`delta`/`approval`/`done`/`error`，**没收
    `SourcesEvent`**——M2 时本机档没有知识库可检索，它根本不会产生，所以少这一条没人看得出来；
