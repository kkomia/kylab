## 1. Q1 · 本机 SQLite 库怎么落

### 1.1 位置与文件

| 项 | 值 |
| --- | --- |
| 库文件 | `<data_dir>/kylab.db`（WAL：`kylab.db-wal` / `kylab.db-shm` 同目录） |
| 桌面端的实际落点 | 壳把 `app_data_dir()` 作为 `--data-dir` 传给边车（`desktop/src-tauri/src/main.rs:377,840-843`）→ `%APPDATA%\com.kylab.desktop\kylab.db` |
| 迁移自动备份 | `<data_dir>/migration-backup/<UTC 时间戳>-v<from>→v<to>/kylab.db` |
| 导入回滚快照 | `<data_dir>/import-rollback/<batch_id>/<conversation_id>.ndjson`（与导出同一套格式，一物两用） |
| 表结构定义 | `backend/app/storage/sqlite_impl/schema.sql`（基线） + `schema.py` 的 `MIGRATIONS`（增量），**与 PG 一样"DDL 的唯一属主是应用"** |

规范要求 `schema_metadata` 与迁移前自动备份（v0.3 §5.1-2、调研 §4），落法：
- `schema_metadata(key TEXT PRIMARY KEY, value TEXT NOT NULL)` 存 `version` / `created_at_ms` / `last_backup` / `migration_log`(JSON)。**不另外写 `PRAGMA user_version`**——那会变成第二处真相来源（与 `schema.py:427` 那段"不建分区登记表"同一条理由）。
- 迁移前用 `sqlite3.Connection.backup()`（在线备份 API，WAL 下安全、目标已存在也不怕）落一份整库副本，路径写回 `schema_metadata.last_backup`。
- 迁移**每条一个事务、版本号写在同一事务里**（照 `postgres_impl/schema.py:503 _apply_migrations` 的写法）；版本高于应用 → 报错，不降级。
- 启动自检：`sqlite3.sqlite_version_info >= (3, 37)`（`STRICT` 表的下限），不满足**明确报错**而不是降级成非 STRICT。

### 1.2 类型映射（逐表照搬时唯一要机械翻译的东西）

| PG | SQLite(STRICT) | 说明 |
| --- | --- | --- |
| `text` | `TEXT` | 照搬 |
| `boolean` | `INTEGER` + `CHECK (x IN (0,1))`；**可空的三态列仍是 `INTEGER`（NULL 合法）** | `thinking`/`pinned`/`enabled`/`disabled` |
| `timestamptz` | `INTEGER`（UTC 毫秒），列名加 `_ms` 后缀 | `_now()/_dump()/_load()` 三个helper与 PG 侧同名同形（`postgres_impl/meta_store.py:121,125,135`） |
| `jsonb` | `TEXT` + `CHECK (json_valid(x))` | 只整读整写，不做 JSON 内查询 |
| `bigserial` | `INTEGER PRIMARY KEY AUTOINCREMENT` | `session_events.id` |
| 外键 | 原样写，**但必须 `PRAGMA foreign_keys=ON`** | PG 版 `base.py:2384` 那条注释是 SQLite 老时代的（当时没开 PRAGMA），新实现要开，行为才与 PG 的 `ON DELETE CASCADE/SET NULL` 一致 |

**毫秒 + `MAX(旧值+1, now)`**：`touch_conversation` / `set_*` 这类"必须推进"的写，落值是 `max(now_ms, old_ms + 1)`。理由：毫秒精度下同一毫秒的两次推进会让"最近活动"排不出先后；这与 `session_events.seq` 是同一类问题的两种解法（一个用在追加表，一个用在原地更新表）。**要有一条用例钉住它。**

### 1.5 WAL 与并发口径（回答"边车与桌面壳会不会共写"）

- **同一时刻只有一个边车进程**（壳的 `sidecar::Manager` 保证；端口 8765-8769 `sidecar.rs:33`）。**壳本身不写库**——它只转发 HTTP。所以稳态是**单进程多线程**（Starlette 把同步端点丢进 40 个线程，见 `postgres_impl/connection.py:53-62` 的说明）。
- 单进程：**每线程一个 `sqlite3.Connection`**（`check_same_thread` 保持默认 True），`session()` 外面套一把进程级 `threading.RLock` → 写串行化，读并发（WAL 允许 1 写 N 读）。
- 跨进程（CLI 导入 + 边车同时写）：**WAL 本身支持**，加 `busy_timeout=5000` + `BEGIN IMMEDIATE`（拿写锁而非 deferred 升级，避免 `SQLITE_BUSY` 死锁循环）。**不禁止**（禁止会挡住"边车开着跑导入"这个必然场景），但**禁止两个边车实例开同一个库**（端口互斥已挡住大部分；启动时探测一次并如实记日志）。
- PRAGMA 口径：`journal_mode=WAL`（建库时设一次，持久属性）、`busy_timeout=5000`、`foreign_keys=ON`、`synchronous=NORMAL`、`wal_autocheckpoint=1000`。
  `synchronous=NORMAL` 的取舍要写在代码里：WAL 下崩溃可能丢最后几个**已提交**事务（不是库损坏），而"一轮对话 1ms 落盘"（v0.3 §6.1-④）要的就是这个；**导入是靠幂等重跑兜底**，不靠 fsync。
- **进程内两把锁的边界**：`session()` 拿写锁，`read()` 不拿。`append_turn` / `append_session_events` 在写事务里算 `max(seq)+1`，因为写锁是库级独占，**不需要 `FOR UPDATE`**（要删掉那句）。

## 2. Q2 · 存储抽象怎么改

### 2.1 结论：加**三层**，不动 `services/`（0 处改动）

```
services/  ──▶ StoreBundle.meta ──▶ RouterMetaStore ──┬──▶ SqliteMetaStore（本机域，新）
                                    （新，分流）        └──▶ UnavailableMetaStore / 将来 RemoteMetaStore（KB 域）
```

现有接口层**能直接加一个 SQLite 实现**吗？
- 对 `MetaStore` 这个 ABC：**不能直接整个实现**——本机档里知识库那半没有数据源（NAS 才是）。
- 但可以**分两步**：① `SqliteMetaStore` 只实现"本机域"（这是 200 来个方法里的约 100 个）；② `RouterMetaStore` 补全 `MetaStore` 的其余方法并转给"KB 侧实现"（M2 是 `UnavailableMetaStore`，M3 换成 `RemoteMetaStore`）。
- **域清单不许手抄**（两百来个方法手抄必漏）：从 `repositories.py` 已切好的协议**机械导出**：
  ```python
  LOCAL_PROTOCOLS = (ConversationRepo, NoteRepo, SettingsRepo, WorkspaceRepo,
                     ScheduleRepo, MCPServerRepo, ModelRegistryRepo, UsageRepo)
  LOCAL_EXTRA = frozenset({"storage_stats", "vacuum"})   # MaintenanceRepo 里属于本机的那两个
  LOCAL_METHODS = frozenset(从上面 8 个协议类体里取出的函数名) | LOCAL_EXTRA
  ```
  `MaintenanceRepo` 的第三个方法 `purge_stage_events` 归 KB 域；`IdentityRepo` 整个归 KB/不可用域（本机不设门禁）。
- `RouterMetaStore` 的构造方式（避免碰 `__abstractmethods__`）：
  ```python
  def _build_router() -> type:
      namespace = {name: _forwarder(name) for name in MetaStore.__abstractmethods__}
      namespace["__init__"] = _init
      return type("RouterMetaStore", (MetaStore,), namespace)
  ```
  用例断言 `RouterMetaStore.__abstractmethods__ == frozenset()` 且 `LOCAL_METHODS ∪ REMOTE_METHODS == MetaStore.__abstractmethods__`、两者不相交。

**为什么不改 `StoreBundle` 的字段/属性**：`services/` 里 346 处走 `stores.meta.*`，只有 12 处走窄视图；改属性层等于让 346 处里的一大半去改签名（且 `schedules.py` 那种窄视图用法还得一对一照顾）。分流放在 `meta` 上是**改动面最小**、且"哪些域本机"这个决定**只出现在一个文件里**。

## 3. Q3 · NAS 旧会话的一次性导入

### 3.1 一条硬纪律：**不直连 PG**（v0.3 §4 分界线、§8-3）

导入走 HTTP，不 dump 服务器库。所以**服务端要新增一个导出端点**（而不是让本机拼 `GET /conversations/{id}` + `/events` + `/artifacts` 三条——那丢 `context_summary`，也没有版本化契约）。

**服务端（NAS 那侧，新增，服务器档也照常跑）**
```
GET /api/v1/conversations/export?limit=200&offset=0&since=<ts>
  → 200 application/x-ndjson（流式）
  首行 {"type":"header","export_version":1,"generated_at":…,"count":N}
  每会话：{"type":"conversation","data":{…conversations 全列…}}
          {"type":"message","conversation_id":…,"data":{…}}
          {"type":"event",   "conversation_id":…,"data":{…}}
          {"type":"artifact","conversation_id":…,"data":{…}}
  末行 {"type":"footer","conversations":N,"messages":M,"events":E,"artifacts":A}
```
- 归属：管理员/本机主人视角导出自己可见的；成员通道只导自己的（复用 `conversations.py:88 _caller_owner` 与 `ConversationService.list(owner_id=…)`）。
- **不新增存储方法**：per-conversation 复用 `list_messages` / `list_session_events` / `list_artifacts` / `get_conversation_summary`。

**本机（导入器，纯接口调用，落在 services 层）**
```
backend/app/services/legacy_import.py      # 核心（CLI 与端点共用）
   class LegacyImporter:
       def plan() -> ImportPlan             # 拉源端清单 × 比对本机台账 → 新增/替换/跳过
       def run(progress=None) -> ImportReport
       def rollback(batch_id) -> ImportReport
backend/app/api/v1/local.py                # 端点：/local/import、/local/import/{batch}、/local/import/{batch}/rollback、/local/status
```
- 传输：`app.core.lazy_httpx`（既有代理，不用新依赖），用例用 `httpx.MockTransport` 打假 NAS（与 `tests/unit/services/test_remote_clients.py` 同一套手法）。
- **幂等**：`import_items(batch_id, conversation_id, source, source_updated_at_ms, outcome, local_updated_at_ms)`；键 `(source, conversation_id, source_updated_at_ms)`；重跑同一批 → 全部命中已导入 → 报告里 `skipped`，一行不写。
- **覆盖策略（明写一条，不许含糊）**：`replace_if_local_untouched`
  `本机该会话存在 && 本机 updated_at_ms > 导入时记下的值` → **跳过**并在报告里如实列出（"本机有更新的改动，没覆盖"）。绝不静默覆盖用户在本机说过的话。
- **可回滚**：导入前把被替换的会话按**同一套 NDJSON 格式**存进 `import-rollback/<batch>/`；
  `rollback` 的规则（两条都要写进 `ImportReport`）：`outcome=created` 且本机 `updated_at_ms == 导入后记下的值` → 删；`outcome=replaced` → 用快照恢复；**本机改过的一律保留并如实报数**。
- **进度反馈**：`imports.state`（`planned/running/done/failed/rolled_back`）+ `counts_json` + `GET /local/import/{batch_id}` 轮询（不选 SSE：断线无所谓、也少一条流式形状）。CLI 打同一批字段。
- **触发方式**（两条都给，共用同一个 importer）：
  1. CLI（在边车运行时里也能跑，不依赖边车进程）：`python -m app.services.legacy_import --server http://nas:8000/api/v1 --token … --data-dir … [--since …] [--dry-run]`（`-m` 跑 services 层模块**不违反 L6/L2**：它只用 `StoreBundle` 接口 + `lazy_httpx`）；
  2. 界面：`POST /api/v1/local/import`（本机后端）+ 进度条。
- **大 transcript 的落法**：源端并发 4 拉取；本机**每会话一个事务**、会话内 `executemany` 批插；进度按会话数报；目标 ≥1000 消息/秒（实测值写进物证）。
- **文件引用一致性（必须明写取舍）**：产物与附件指向 NAS 上的 key，**本体不随导入过来**。处置：产物记录照导入（"这条会话产出了什么"必须完整），`location` 保留原 key；导入报告与 `/local/status` 如实列出"未随导入的文件引用数"；界面按 `storage/location` 显示为"来源服务器（文件未随导入）"。**不下载文件本体**——体积不可控，且与"工作区文件永不上传"的对称纪律一致。

| R3 | **大 transcript 导入慢** | 源端并发 4、批 `executemany`、会话级事务、进度可查、`skipped` 短路；目标 ≥1000 消息/秒，实测值进物证 |
| R4 | **正文与文件引用一致性**（导入的产物/附件指向 NAS 上的 key，本机没有文件） | 不下载文件本体；`location` 保原样 + 报告与 `/local/status` 列出"未随导入的引用数"；界面上如实标"来源服务器（未随导入）"；产物可重新生成，成本低 |
| R5 | **两条数据源并存**（本机库 + 服务器库；回退开关打开时） | 默认开本机、回退必须显式且界面可见；**不做双向同步**（v0.3 §11 明确不做）；导入策略是"本机动过就不覆盖" |
| R6 | **本机库里的明文凭据**（`model_providers.api_key`、`mcp_servers.env/headers`） | 与服务器同口径（M5 才收编钥匙串），但**必须写进文档与库文件注释**；NAS token **绝不**落库（走命令行参数，M5 走钥匙串） |

   `import_items` / `schema_metadata`。写实的那一个；
2. **本机域方法 81 个**（本文估"约 100"）：从 `repositories.py` 的 8 个协议类体里机械导出
   （8 个协议 + `storage_stats` / `vacuum` 两个 `LOCAL_EXTRA`），数出来就是 81；
3. **`KYLAB_DATABASE_URL` 是"压成空串"而不是 `del env`**：开发机的 `.env` 里真的配了它，
   `delenv` 会让它从 `.env` 复活 → 本机档会去连服务器库（最糟的失败形态）；
4. **`attach_note_to_kb` 在本机档如实 503**：知识库在 NAS 上，本机没有那条链路。
   M3 的 `KnowledgeProvider` 是它的正式解（不是"忘了做"）；
5. **边车那一轮的 `session_events` 暂不写**：事件草稿链（`seq` 怎么发、`turn/start|complete`
   怎么配对）要先定，**先不写半套**——写半套会让"事件日志"这件事看着成立、实际断链；
6. **`LOCAL_PATHS` 里是 `/scheduled-tasks`**（本文 §4.3 写的是 `/schedules`）：
   实际端点前缀就是 `/scheduled-tasks`（`schedules.router` 的 prefix），界面也逐条用它。
   照本文写会让定时任务继续绕道 NAS；
7. **壳补了 PATCH/PUT/DELETE 白名单**：既有缺陷（只放行 GET/POST，本文 §0.3-② 已核实），
   阶段 4 顺手补 + 用例。本机权威面直连边车不走这条路，但**服务器面**（知识库/文档/技能）
   在壳里同样需要它们；
8. **旧笔记里的相对图址不改写**：笔记图片也在本机（`localizeUrl` 已经把相对签名链接贴到
   本机基址），改写正文里的相对地址规则要单独定，阶段 4 **如实登记**而没有顺手改；
9. **`/local/import*` 不进服务器档的 OpenAPI**：它们是"只在本机档成立"的端点
   （本机档才挂 `local_router`），而生成物是服务器档那一份契约。界面侧**手写类型**
   （`frontend/src/api/local.ts`，字段逐条对着 `LocalStatusOut` 抄，模块头写清出处）；
10. **导入跑在进程内后台线程**（不是队列、也不是 SSE）：几百条会话要走网络，
    按在请求上只会撞超时；进度写库（`imports` 表）→ CLI 与界面**同一份账**，
    轮询一条 `GET /local/import/{批次}` 就够（断线无所谓，也就不必多一条流式形状）；
11. **回滚的台账语义**：`rolled_back` **不算已导**、账也**不删**（回滚之后想再导一次是正当需求）。
    本条会话重导是**覆盖** `import_items` 那一行（幂等键就是主键）——真机实测：回滚 + 再导后
    `imports` 两行、`import_items` 仍是 302；
12. **真机导入验收用的"NAS"是临时起的服务器档实例（:8800）**：用户那个 `:8000`
    跑的是 **M2 之前的代码**（没有 `/conversations/export`、没有 `/local/*`），而按纪律不许动它。
    8800 与它同一个 PG、同一份当前代码、`KYLAB_RUN_WORKER=false`（不抢消费线程）；
13. **导入时"本机没有的工作区引用"置空 + 报数**（真机抓到的 bug ②）：
    `conversations.workspace_id` 在本机库上是外键，而工作区不随导入过来（本机档里它的含义是
    "这台机器上的一个路径"，`root_path` 又是 NOT NULL）→ 真机导到第 3 条整批
    `FOREIGN KEY constraint failed`。**不照搬工作区行**（那会建出一条点开必然报错的项目）、
    也**不静默丢**（计入 `counts.unresolved_workspaces`）；
14. **导出流由读端按字节切行**（真机抓到的 bug ①）：`httpx` 的 `LineDecoder` 按 W3C 换行口径
    把 `U+2028`/`U+2029` 也当换行，而这两个字符在 JSON 字符串里可以合法原样出现
    （真机 302 条里那条 24463 字符的行被切成 12543 + 11920）→ 导入当场失败。
    导出端一个字没改，读端（`legacy_import._raw_lines`）只认 ASCII `\n`；
15. **界面那三笔账放在顶栏状态条第二行**（本文给的是"`LocalDataStrip` 或设置页"二选一）：
    设置里那块「存储配置」报的是服务器档的存储构成（PostgreSQL / pgvector / MinIO），
    本机档三笔账放进去会与它自相矛盾；顶栏那条本来就是"我的数据在哪"的常驻落点；
16. **产物/附件的"来源服务器（文件未随导入）"写在卡片 `title` 上**：判据本该是
    `location`（导入过来的产物保着 NAS 上的 key），而它**不在** `ConversationArtifactOut` /
    `ArtifactService.describe()` 里；本阶段**不为界面一句提示扩契约**（那是 M3 导入向导那条线），
    措辞写成条件句（导入过来的…；本机新产出的在本机）；
17. **导入吞吐 65.4 消息/秒（端到端）**，低于 §5 R3 那个"≥1000 消息/秒"：
    这个数被**源端的导出流**卡着（单读一遍流 ≈15 s，与全程 17.8 s 同量级），
    本机写路径的判据由单测钉（`test_the_import_keeps_one_thousand_messages_per_second`）。
    如实记在验收记录里，不当成达标。
