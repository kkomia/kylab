# 桌面端：成员与钥匙 v0.1（2026-09-29）

**这份文档只回答一个问题**：成员（非管理员）怎么用桌面壳？以及为什么"给成员开一个自服务领钥匙的端点"这件事**不能照 60 行的规模去想**。

## 一、现状（实测代码，不是推测）

桌面壳需要一把**长期** key 才能让本地边车调服务器（网页用的是会话，会滑动过期；边车要的是不走浏览器的那把）。而今天唯一的签发口是：

```
POST /api/v1/api-keys        ← require_admin（管理员专用，故意如此）
```

`backend/app/api/v1/api_keys.py` 的模块注释把这条纪律写得很清楚：

> 能签发钥匙的接口如果也能被钥匙打开，那任何一把泄露的只读密钥都能给自己再发一把读写密钥——提权一步到位。

所以：**成员登录桌面壳没问题（`/auth/login` 走通），领钥匙会 403**。

## 二、为什么"再加一个自服务端点"不是小活（关键 ✗）

`ApiKeyService.create` 的形状是：

```python
def create(self, *, name: str, permission: ApiKeyPermission,
           knowledge_base_ids: list[str] | None = None) -> IssuedApiKey
```

注释里写明：**空列表 = 该凭据可访问全部知识库**（与"绑定到空集合"是两回事）。

而 `Caller` 上能拿到的只有：

| 属性 | 成员的会话 | 含义 |
| --- | --- | --- |
| `is_admin` | `False` | 不是管理员 |
| `api_key` | `None` | 会话通道，不是 key 通道 |
| `permission` | `None` | **`None` = 不受范围限制** |
| `knowledge_base_ids` | `()` | **空 = 不限范围** |
| `owner_id` | 自己的账号 id | 归属按**这个人**算 |

推论：如果照搬"把调用者自己的 `permission` / `knowledge_base_ids` 塞进新 key"，members 会拿到一把**不限知识库的 readwrite 钥匙**——而成员在网页里的可见范围是按 **`owner_id`（归属）** 算的，**两者并不等价**。也就是说，那样做的结果是**提权**，不是"自服务"。

**结论**：这个端点缺的不是 60 行路由代码，而是 **key 模型里少了"归属 / 可见范围"这一维**。要做就得动模型：

- **方案 A（彻底）**：给 key 记录加归属（如 `owner_user_id`），鉴权时把归属一并纳入 `check_access`；或强制自服务端点只接受**显式的** `knowledge_base_ids`，且服务端校验它 ⊆ 调用者可见集合。
- **方案 B（今天就能用 ✓）**：**由管理员签发一把带 `knowledge_base_ids` 限定的 key**，交给那位成员的桌面壳使用。模型早就支持（`ApiKeyCreateIn.knowledge_base_ids`），没有任何新代码。

## 三、建议的落地顺序

1. **现在**：走方案 B。管理员按设备发钥匙（命名建议 `桌面端 <主机名>`），`permission` 显式 `readwrite`，`knowledge_base_ids` 按该成员应有范围显式列出——这也是桌面壳 README 里"只给管理员用"那句话的**替代口径**；
2. **将来**：走方案 A 的自服务端点（`POST /api/v1/me/device-key`），但**前置条件是 key 带上归属或显式范围**，否则一定复现第二节那个提权问题；
3. 无论哪条路：**签发口都必须是会话**（不能用 API Key 给自己续命），撤销也只能撤自己名下的。

## 四、验收（将来做方案 A 时照抄）

```
成员调 POST /api/v1/me/device-key            → 201
拿到的 key 调 require_write 的端点           → 成功（成员本来就该能写）
拿到的 key 调 require_admin 的端点           → 403（这条就是"没提权"的物证）
拿到的 key 访问【不属于该成员】的知识库      → 被拒（这条是方案 A 的真正难点，必须有用例）
撤销自己 → 204 ；撤销别人的 → 拒绝（不泄露存在性）
无凭据 → 401
另：跑 scripts/gen_api_spec.py --write 更新 docs/规范/API-接口规范-v0.1.md（tests/unit/api/test_api_spec.py 在盯）
```

## 五、这份结论的来历

2026-09-29 的桌面端收尾里，"成员也能用桌面壳"被排成一条待办，起初按"~60 行 + 4 条回归"估。读全 `Caller` / `ApiKeyService.create` / `check_access` 之后发现上面那个**等价性问题**，于是**没有动代码**：写一个会提权的端点，比不写更糟。这份文档就是那次判断的留档。
