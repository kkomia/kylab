## 1. 两条路线，先选一条

| 路线 | 适合 | 验证状态 |
|------|------|---------|
| **本地 venv + 脚本** | 单机自用、开发调试 | ✅ **已实测** |
| **Docker Compose** | 交付给别人的机器、长期常驻 | ⚠️ **部分验证**：`postgres` 服务已在真实部署服务器上跑通（同一镜像、HNSW + KNN 实测可用），但整份 compose 未在干净机器上「一键起」 |

**为什么还留着本地路线**：容器是交付形态，但开发与排障几乎都在本地跑。
只有容器一条路的话，"到底是代码问题还是镜像问题"会变成一个很难回答的问题。

## 2. 本地路线（已实测）

### 2.0 先备一个 PostgreSQL（必选）

自 v0.12 起 **PostgreSQL 是硬依赖**，没有可回退的本地实现；未配置 `KYLAB_DATABASE_URL`
时服务**启动即失败**（不是降级，是明确报错）。需要 **pgvector** 扩展。

```bash
docker run -d --name kylab-postgres -p 5432:5432 \
  -e POSTGRES_PASSWORD=kylab-dev-secret -e POSTGRES_DB=kylab \
  pgvector/pgvector:pg17-trixie
```

不想用 docker 也可以装本机 PostgreSQL + pgvector（版本 ≥ 0.7 即可用 HNSW）。
对象存储不强制：留空 `KYLAB_S3_*` 时原件落本地 `KYLAB_DATA_DIR`。

### 2.1 后端

```bash
cd backend
uv sync --all-extras                     # 注意 --all-extras，见下
cp .env.example .env                     # 至少填 KYLAB_DATABASE_URL；.env 不入库
uv run uvicorn app.main:app --reload     # http://127.0.0.1:8000
```

**为什么是 `--all-extras` 而不是裸 `uv sync`**（v0.1 这里写错了，照做会在
`import app.main` 时炸 `ModuleNotFoundError`）：`app/core/storage.py` 会**无条件**构造
DuckDB 表格副本，而 duckdb 在 `tabular` extra 里——它看着像可选项，其实是组合根的必需项。
`parsers` extra（pypdf / pymupdf / python-docx / openpyxl / pandas / markdown-it-py）
是上传→解析→入库主链路要用的，代码里惰性导入，缺了只是该功能不可用，
但**跑产品就该装上**。详见 `backend/README.md` 的「依赖分层」。

- 探针：`GET /api/v1/health` → `{"status":"ok",...,"version":"..."}`
- 接口文档：`/api/v1/docs`
- 首次启动**无需手工建库**：连接时自动跑迁移（`apply_migrations`），
  数据目录与对象存储子目录也会自动创建。

#### 日志在哪、怎么调（v0.21）

控制台一份 + **文件一份**（`data/logs/kylab.log`，滚动：5 MiB × 3 份）。
控制台那份活不过一次重启，而"昨晚那次对话为什么慢"只能从文件里翻，
所以文件这份是必须的。文件行里带**相对路径:行号**（`app/services/chat.py:1234`），
grep 出来的那一行能直接定位到代码。

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `KYLAB_LOG_LEVEL` | `INFO` | 控制台与文件的级别（两处共用一档，不分开配） |
| `KYLAB_LOG_MAX_SIZE` | `5mb` | 单个文件多大之后轮转（认 `512k` / `5mb` / `1g` / 纯字节数） |
| `KYLAB_LOG_MAX_BACKUPS` | `3` | 留几份备份 |

两条容易踩的：

- **写错的值回落到默认并留一条 warning**，不影响启动（`KYLAB_LOG_MAX_SIZE=5MBx`
  会打一行"用不了，改用默认值"）——静默用默认值会让"我设了没生效"变成一个
  没人能解释的现象；
- **Windows 上轮转失败不丢日志**：文件被日志查看器打开时 `os.rename` 抛
  `PermissionError`，原生实现会让这一条日志直接打不出来——而那正是最需要日志
  的时候。我们的处置是"这轮不轮转、接着写"。


### 2.2 前端

```bash
cd frontend
pnpm install
pnpm dev                                 # http://localhost:5173
```

开发服务器把 `/api` 代理到 `127.0.0.1:8000`，所以**同源、无跨域**。

**要从别的电脑访问（局域网 / VPN）**：`vite.config.ts` 里已经写了 `server.host: '0.0.0.0'`，
所以直接 `pnpm dev` 就同时监听所有网卡，启动日志会列出可用于其他机器的地址：

```
➜  Local:    http://localhost:5173/
➜  Network:  http://192.168.31.59:5173/      ← 别的电脑用这个
```

三个坑：

- **别加 `--host 127.0.0.1`**：命令行参数会**盖掉**配置里的 `0.0.0.0`，服务退回只监听本机——
  现象就是"本机能开、别的电脑连不上"。只想指定端口就写 `pnpm dev --port 5173`。
- **后端不用跟着暴露**：`/api` 是**开发服务器替浏览器**去请求后端的，
  后端留在 `127.0.0.1:8000` 也在同源之内；要放行的只有前端这个端口（5173）。
- **Windows 防火墙**：首次会弹询问，选"允许专用网络"。本项目实测已有入站放行
  （规则 `Node.js JavaScript Runtime`，Private/Public，TCP 任意端口）；
  换机器后如果本机打得开、外机连不上，先查这里。

### 2.3 内置消费线程

后端进程内会起一个消费协程（`KYLAB_RUN_WORKER=true` 时）。
**它是"上传之后文档会不会被处理"的关键**——关掉它，任务只会排队。

界面上「任务中心」的 `/tasks/health` 会直接告诉你它开没开
（`worker_enabled`），以及有没有任务卡住（见 §4）。

## 3. 容器路线（部分验证，谨慎照抄）

```bash
export KYLAB_URL_SIGNING_SECRET=$(openssl rand -hex 24)
docker compose -f deploy/docker-compose.yml up -d
# 界面 http://localhost:8080 —— 首次打开会让你创建管理员账号
```

**2026-09-21 追加：应用层也真跑起来了。** NAS 上（前后端复用既有的 PG/MinIO，
部署定义见 [`deploy/nas/`](../../deploy/nas/README.md)）跑通了完整的一轮构建 + 启动 + 验证，
并且**踩到了下面三条里的第一条**（不同的根因，见《开发计划》§12.223 的四个真问题表）：
`pyproject.toml` 写着 `readme = "README.md"` 而 Dockerfile 没拷它，hatchling 装项目自身时
`OSError: Readme file does not exist`——已修。另外两条（bind mount 权限、慢盘上的
start_period）也各有了实测结论：权限那条在"镜像内 chmod + 以宿主 uid 运行"之后不再需要
`chown 10001`。**下面这段"未验证"的原文保留**，因为它是当时的真实状态：

**验证到什么程度**：compose 里的 **`postgres` 服务已按这份定义在真实部署服务器上跑通**
（`pgvector/pgvector:pg17-trixie`，PG 17.11 + pgvector 0.8.6，kylab-postgres 健康，
schema 由应用自检引导成功，HNSW + KNN 实测可用）。**没验证的是"整份 compose 在干净机器上一键起"**——
开发机没有 docker（计划 R9）。所以：

- 本文不声称容器路线整体可用，也不声称它对；
- 首次在有 docker 的机器上跑时，**预期的失败点**是：
  1. `uv sync` 在 `python:3.12-slim` 里可能缺少编译工具——
     若失败，给 builder 阶段加 `apt-get install -y build-essential`
     （**注意**：v0.1 把这条归因于 `sqlite-vec` 的原生扩展，该依赖已随 SQLite 删除，
     归因不再成立；保留这条是因为**没实测过**，而不是因为知道它还会失败）；
  2. 卷权限：容器内以 uid 10001 运行，宿主机 bind mount 时要 `chown 10001`；
  3. 首启健康检查有 20s 宽限（`start_period`），慢盘上可能不够。

### 3.1 架构上的三个决定

1. **不直接暴露后端端口。** 所有流量从 nginx 进，
   避免"一半请求带 `X-Forwarded-*`、一半不带"的排查噩梦。
   需要直连调试时取消 compose 里那两行注释。
2. **前端由 nginx 提供，并把 `/api` 反代到后端。** 同源就没有 CORS 问题——
   生产上配错 CORS 是"本机好用、部署后全 401"的常见来源。
3. **`/api/` 反代关掉了缓冲**（`proxy_buffering off`）。对话是 SSE 流式，
   缓冲会让用户等整段回答写完才看到第一个字（后端也发了
   `X-Accel-Buffering: no`，两边都要）。

## 4. 可观测性：怎么判断"卡住了"

`GET /api/v1/tasks/health` 给出运行态总览；任务列表里每一项也带 `health`。

| 判据 | 含义 | 怎么算 |
|------|------|--------|
| `running` | 正常执行中 | 状态 RUNNING 且**租约未过期** |
| `stalled` | **可能卡住了** | 状态 RUNNING 但租约已过期——没有 worker 在续约 |
| `overdue` | 该跑没跑 | PENDING 且 `next_run_at` 已过去 10 分钟以上 |
| `idle` | 排队中 | PENDING 且还在正常等待 |
| `done` | 已结束 | SUCCEEDED / FAILED / CANCELED |

**为什么用租约过期而不是耗时阈值**：租约是 worker 主动心跳续的，
过期就意味着"没人认领这个任务了"——这是**确定的事实**。
而"跑了超过 N 分钟"只是启发式：一份 500MB 的 PDF 解析半小时是正常的，
用耗时阈值会一直误报，误报多了用户就不看这个标记了。

### 4.1 常见症状与处置

| 症状 | 多半是什么 | 怎么办 |
|------|-----------|--------|
| 启动即失败、提示 `KYLAB_DATABASE_URL` | 没配 PostgreSQL 连接串 | 见 §2.0；这是必填项，没有降级路径 |
| 任务一直 `idle` 排队 | 消费线程没开 | 确认 `KYLAB_RUN_WORKER=true` 并重启 |
| 任务变 `stalled` | 进程崩过 / 被 OOM 杀 | 重启服务；租约过期后任务会被回收重跑 |
| 任务 `overdue` | 同上，或调度没起来 | 看 `/tasks/health` 的 `worker_enabled` |
| 任务反复失败 | 解析器或模型凭据问题 | 看任务详情里的 `error`（含阶段名） |

## 5. 容量与并发（T7.3：**未实测**）

计划里 T7.3 要求"至少两档内存配置实测数据"。**这一项没有完成**，
原因与容器路线相同：本机没有可做对照测试的环境，而编一张表出来
比不给更糟——用户会照着它做采购决定。

**可以确定的（来自架构与实测运行）**：

- 主服务常驻内存约 **300–500MB**（架构 §4.1 的量级，与本地运行观察一致）；
- **内存预算要把 PostgreSQL 算进来**（v0.12 起它是必选组件）：同机部署时
  PG 自身通常再要几百 MB，小内存机器上这是新的下限约束。
  v0.1 那句"纯云端解析路线 4GB 可跑"指的是**后端进程**，不含 PG；
- 摄入的主要开销在**向量化与解析**，不在这个进程本身——
  所以并发档位实际上受"云端配额"与"网络"约束，而不是本地 CPU。

**要拿到实测数据，需要做的对照**（留给有环境的机器）：

1. 同一批文档（建议 ≥200 份、含 10 份以上大文件）；
2. 两档内存（4GB / 16GB）各跑一遍，固定 `KYLAB_WORKER_LEASE_SECONDS`；
3. 记录：端到端耗时、峰值内存、失败率；
4. 结论写成"档位 → 推荐并发数"，写进本文件。

在此之前，**不要**给用户一个猜测的并发数。

## 6. 升级与备份

**v0.12 起数据分三处，备份要分别对待**（原先"拷一个目录"的做法已不适用）：

| 内容 | 位置 | 备份方式 |
|---|---|---|
| 元数据 + 向量 + 全文 | PostgreSQL | `pg_dump -Fc`（角色另用 `pg_dumpall --globals-only`） |
| 原件 / Markdown / 图片 | MinIO/S3 桶（或本地 `KYLAB_DATA_DIR`） | 对象的版本化/快照；本地实现则拷目录 |
| 表格副本 | `KYLAB_DATA_DIR/tabular.duckdb` | 拷文件（停服务后） |

- **schema 是应用拥有的**：启动时自动建/校验基线（`ensure_schema`），
  版本不符会拒绝启动而不是带着半截结构跑。
- **不要**直接拷运行中的 PG 数据目录——那是不一致的；用 `pg_dump` 或
  `pg_basebackup`（要 PITR 时再加 WAL 归档）。
- **回收站**：删除的文档原文保留 7 天（桶内 `.trash/<id>/`），
  到期由 worker 的空闲维护清理。**要立刻释放空间就手动清空该前缀**。
- **升级到 0.2.0**：存储层在 0.1.0 → 0.2.0 之间换过地基（SQLite → PostgreSQL），
  所以 **0.1.0 的 SQLite 数据没有迁移路径**——只能在 PG 上重新摄入。
  0.1.0 之后没有别的破坏性变更，同一大版本内的升级只需替换镜像/代码，schema 自动补齐。
