## 2. 设计文档规范（docs/）

| 项 | 规范 |
|----|------|
| 存放 | 一律放 `docs/`，按主题单文件 |
| 命名 | `<主题><类型>-v<主.次>.md`，主题与类型连写不加分隔符，如 `架构设计-v0.2.md`、`前端设计规范-v0.4.md`、`项目工程规范-v0.3.md`、`开发计划-v0.1.md` |
| 版本 | **已提交即冻结**：一旦某个版本进入 git，任何实质改动一律升次版本（v0.1→v0.2→v0.3），新文件替代，旧版本**保留不删**；定稿冻结为 v1.0 |
| 头部 | 必须含：版本号、日期、状态（讨论稿/基线/冻结）、变更摘要 |
| 语言 | 中文为主；代码标识符、接口名、路径保持英文原样 |

### 2.1 已提交即冻结（本条的由来）

判断标准是**是否已经 commit**，不是**是否已冻结为 v1.0**。已经进过 git 的文档，
其正文、条款、示例、表格与表头一律不得在原文件上修改——**改错了就升下一个版本改回来，
错的那一版留在历史里**，不要在旧文件上抹掉痕迹。

> 教训来源：2026-09-10 前端设计规范 v0.2 提交后被发现就地修改了内容（既改错了方向，
> 又在回退时直接改了原文件）。评审定案：此后一律升版本，不得就地改已提交内容。

### 2.2 可就地修改的例外

以下三类不影响规范含义的编辑，可直接改原文件、不升版本：

1. **补全缺失的头部字段**（版本/日期/状态/变更摘要）；
2. **回填进度与偏差**（开发计划类文档在每个里程碑收口更新）；
3. **给已被取代的存档版本标注状态**（如把「基线」改为「已被 vX.Y 取代（保留存档）」）。

除这三类外，如需改动已提交的文档，一律走 §2.1 的升版流程。

当前文档清单：`架构设计`、`前端设计规范`、`项目工程规范`、`开发计划`。
后续新增：`API 接口规范`、`解析插件开发指南`、`部署与容量`。

## 3. 后端代码规范（backend/）

### 3.1 目录结构

```
backend/
├── app/
│   ├── main.py                # FastAPI 入口
│   ├── api/                   # REST 路由层（协议适配，无业务逻辑）
│   │   └── v1/                # API 版本化，路径即版本
│   ├── mcp_server/            # MCP Server（stdio / streamable HTTP）
│   ├── core/                  # 配置、日志、鉴权、异常
│   ├── services/              # 业务服务：kb / ingest / retrieval / connector
│   ├── pipeline/              # 摄入流水线状态机
│   ├── parsers/               # ParserProvider 接口与各实现
│   │   ├── base.py            # ParserProvider 协议
│   │   ├── probe.py           # 文件探测（文本层覆盖率判定）
│   │   ├── mineru_cloud.py
│   │   ├── mineru_local.py
│   │   ├── paddleocr_api.py
│   │   └── office.py          # pandas/openpyxl/python-docx 系
│   ├── storage/               # Repository 抽象 + SQLite 实现
│   │   ├── base.py            # VectorStore / MetaStore 接口
│   │   └── sqlite_impl/       # 唯一实现；PG 实现未来平级新增
│   ├── models/                # Pydantic / ORM 模型
│   └── workers/               # asyncio 任务队列与消费者
├── tests/                     # 后端测试（见第 5 节）
├── pyproject.toml
└── README.md
```

### 3.2 命名

| 对象 | 规则 | 示例 |
|------|------|------|
| 文件名 | snake_case | `mineru_cloud.py` |
| 类 | PascalCase | `MinerUCloudParser` |
| 函数/变量 | snake_case | `probe_text_coverage()` |
| 常量 | UPPER_SNAKE | `MAX_SINGLE_PARSE_PAGES = 1000` |
| API 路径 | kebab-case，带版本 | `/api/v1/knowledge-bases/{id}/documents` |
| MCP 工具 | snake_case 动词开头 | `upload_document`、`get_document_status` |
| 解析器实现类 | `<引擎><节点>Parser` | `PaddleOCRApiParser` |
| 数据库表 | snake_case 复数 | `knowledge_bases`、`document_parts`、`chunks` |
| 数据库字段 | snake_case | `created_at`、`content_hash` |
| 外键字段 | `<引用表单数>_id` | `knowledge_base_id`、`document_id` |

**常量必与架构契约对齐**：解析切分阈值取《架构设计 v0.2》§4.2 的 1000 页，
即 `MAX_SINGLE_PARSE_PAGES = 1000`；子文件切分粒度 `SPLIT_PART_PAGES = 200`
（与 MinerU 单文件 200 页上限对齐）。v0.1 曾以 `MAX_SPLIT_PAGES = 150` 作示例，与架构阈值冲突，已修正。

### 3.3 分层纪律

- `api/` 和 `mcp_server/` 只做协议适配，**禁止写业务逻辑**——两种接入共用 `services/`；
- `services/` **禁止直接写 SQL**，必须经 `storage/` 的 Repository 接口；
  **只允许 import `storage/base.py` 的接口，禁止 import `storage/sqlite_impl/`**——这是 PG 迁移后门的保险费；
- `parsers/` 各实现只依赖 `base.py` 的 `ParseResult` 中间产物，互不引用
  （`base.py` 与 `probe.py` 为共享契约，可被引用）。

以上三条加上"测试文件不得进源码目录"（§5.1），由 `scripts/check_layering.py` 机械核查并接入 CI，
不依赖 review 记忆。规则编号：`L1`（协议层越界）、`L2`（业务层直连数据库/SQL 字面量）、
`L3`（解析器互引）、`T1`（测试位置）。

### 4.3 风格纪律（引自《前端设计规范》，此处为工程约束）

## 5. 测试规范（重点）

### 5.1 测试文件存放位置

| 测试类型 | 位置 | 说明 |
|----------|------|------|
| 后端单元测试 | `backend/tests/unit/` | 与被测模块**镜像同构**：`app/parsers/probe.py` → `tests/unit/parsers/test_probe.py` |
| 后端集成测试 | `backend/tests/integration/` | 跨模块：流水线状态机、存储层、API 端到端 |
| 后端测试夹具 | `backend/tests/fixtures/` | 样例 PDF/DOC/MD/CSV、mock 的 MinerU 响应等 |
| 前端组件测试 | `frontend/tests/unit/` | 与 `src/` 镜像同构 |
| E2E 测试 | `<repo-root>/tests/e2e/` | 跨前后端全链路（Playwright），放仓库根级 `tests/` |
| 性能/容量基准 | `backend/tests/bench/` | 向量检索延迟、批量摄入吞吐（如 45 万 chunk 刻度验证） |

**铁律**：

1. 测试代码**绝不进入** `app/` 或 `src/` 源码目录（不散落 `__tests__`、不混放 `test_*.py`）；
   由 `scripts/check_layering.py` 的 `T1` 规则核查；
2. 测试文件命名 = `test_` + 被测文件名（后端）/ `<组件名>.test.ts`（前端）；
3. 夹具文件用真实小样本，禁止把大文件（>5MB）提交进仓库，大样本放 `fixtures/README.md` 指明的下载方式。

### 5.2 测试执行位置

| 场景 | 命令 | 执行位置 |
|------|------|----------|
| 后端单元+集成 | `cd backend && pytest tests/ -m "not bench and not cloud"` | 本地开发 & CI 每次提交 |
| 后端基准 | `cd backend && pytest tests/bench/` | 手动触发 & 发布前 |
| 前端组件 | `cd frontend && pnpm test` | 本地开发 & CI 每次提交 |
| E2E | `pnpm --dir tests/e2e test`（先起本地服务） | CI 主分支 & 发布前 |
| 覆盖率 | `pytest --cov=app` / `vitest --coverage` | CI 产出报告 |

- **CI 是最终裁判**：本地通过不算数，PR 合并前 CI 全绿；
- 云端解析类测试（MinerU/PaddleOCR 真实 API）一律打 `cloud` 标记，CI 默认跳过
  （用 fixtures 里的 mock 响应），避免消耗免费额度与网络抖动导致红 CI；
- 集成测试使用**独立临时 SQLite 文件**（tmp 目录），禁止触碰开发库。

### 5.3 验收关联

架构文档中的关键承诺**每条对应至少一个集成测试用例**，共 7 条：

| # | 架构承诺（来源） | 兜底测试 |
|---|------------------|----------|
| 1 | >1000 页强制切分；200–1000 页优先 PaddleOCR 渠道（§4.2） | `tests/integration/pipeline/test_large_pdf_split.py` |
| 2 | 逐文件探测路由，路由决策写入任务记录（§4.1） | `tests/unit/parsers/test_probe.py` + `tests/integration/pipeline/test_routing_decision.py` |
| 3 | embedding 模型切换校验：仅允许同模型 ID 换 endpoint，维度相同但模型不同须拒绝（§6.4） | `tests/integration/services/test_embedding_model_lock.py` |
| 4 | 文件 hash 去重："检测到相同文件"提醒（§6.3） | `tests/integration/services/test_dedup.py` |
| 5 | 级联删除：先返回影响清单，确认后执行；原文 7 天回收站、向量立即删（§6.2） | `tests/integration/services/test_cascade_delete.py` |
| 6 | chunk 级增量更新按位置对齐，PDF 走"位置 + 相似度兜底"（§6.1） | `tests/unit/services/test_chunk_alignment.py` |
| 7 | 流水线各状态可重试、断点续跑，解析失败可降级备选节点（§4） | `tests/integration/pipeline/test_retry_resume.py` |

## 6. 其他工程规范

| 项 | 规范 |
|----|------|
| 配置文件 | 后端 `backend/.env.example`（提交模板，密钥不入库）；用户配置运行期落 SQLite |
| 密钥 | 任何 token/API key 禁止提交；`.gitignore` 必须含 `.env`、`*.db`、`data/` |
| 脚本 | 开发/部署脚本统一放 `scripts/`，命名 `<动词>-<对象>.sh/.ps1`（双平台各一份） |
| 部署产物 | `deploy/docker-compose.yml`，镜像标签与版本号一致 |
| 提交信息 | `<类型>: <简述>`，类型限 `feat/fix/docs/test/refactor/chore` |
| Lint | 后端 ruff；前端 eslint + prettier + **自定义 no-emoji 规则** |
| 依赖 | 后端 `pyproject.toml`（uv 锁定，`uv.lock` 提交）；前端 `pnpm` + `pnpm-lock.yaml` 必须提交 |
| 前端构建脚本放行 | pnpm 10+ 默认拦截依赖构建脚本，放行名单写在 `frontend/pnpm-workspace.yaml` 的 `allowBuilds`，变更用 `pnpm approve-builds` |
| 运行时数据 | 开发期数据目录 `data/`（SQLite、上传文件、Markdown 产物），已在 `.gitignore` |

### 6.1 分支模型

| 分支 | 角色 | 规则 |
|------|------|------|
| `main` | 可发布分支 | **受保护**，只接受经 CI 全绿的合并；每次发布打标签 |
| `develop` | 集成分支 | 功能分支的合并目标；主分支发布时从 `develop` 合入 |
| `feat/<简述>` | 功能分支 | 自 `develop` 切出，完成后回合 `develop` |
| `fix/<简述>` | 修复分支 | 同 `feat/`，紧急线上修复可从 `main` 切出并双向回合 |

> 仓库历史上的默认分支名为 `master`，已按本规范改为 `main`；远端默认分支需在托管平台同步设置。

### 6.2 CI 承载

- 门禁内容以 `scripts/lint.*` 与 `scripts/ci.*` 为准，**与承载平台解耦**；
- `.github/workflows/ci.yml` 已提供 GitHub Actions 版本；若继续托管在 Gitee，该文件不会执行，
  需接入 Gitee Go 或自建 runner，并复用同一组脚本；
- 承载方式为待决事项（见《开发计划 v0.1》§8 D3），决策前以本地 `scripts/ci.ps1` / `ci.sh` 为日常门禁。

### 6.3 顶层交付物目录：`skills/`（v0.3 增补，解 D8）

除 `backend/` 与 `frontend/` 外，仓库根还有一类**交付给别人安装**的产物：

```
skills/
└── kylab-knowledge-base/      # 官方 Skill（架构 §5：MCP + Skill 两种对外形态）
    ├── SKILL.md               # frontmatter（name/description）+ 用法说明——平台识别它的唯一依据
    ├── README.md              # 给人看的快速上手与排障
    └── scripts/               # 调用脚本（给不会说 MCP 的运行环境用）
```

判定规则（与 §3.1 同一套思路）：**它是不是"被安装到别处、而不是在本机运行"的东西？**
是 → 放 `skills/`。这与 `backend/`（本机服务）、`frontend/`（本机界面）是三种不同的
生命周期：Skill 产出后被复制到别人的 Agent 里，本仓库只负责它的**源码与版本**。

约束：`skills/` 下的脚本**不得 import `app/`**——它是独立交付物，会脱离本仓库运行。
需要调用服务时走 HTTP 或 MCP（见该 Skill 的两条接入路径）。

## 7. 新增文件的决策树

```
要写一个新文件？
├─ 是设计/规范文档？ → docs/，按 §2 命名
├─ 是 Python 源码？   → backend/app/ 下按分层归属（§3.1），禁止放别处

├─ 是测试？           → 按 §5.1 表格对号入座，镜像同构
├─ 是脚本？           → scripts/
├─ 是部署配置？       → deploy/
└─ 以上都不是？       → 先想清楚该不该存在，再在工程规范里补一类
```

## 8. 质量门禁自动化清单

三级门禁（详见《开发计划 v0.1》§6.3），全部命令与脚本一一对应：

| 级别 | 内容 | 入口 |
|------|------|------|
| 提交级 | ruff、emoji 扫描、分层纪律、eslint+prettier、pytest、vitest | `scripts/lint.ps1` / `lint.sh` |
| 里程碑级 | 提交级 + 该里程碑集成测试 + 全量质检 | `scripts/ci.ps1` / `ci.sh` + `code-quality-check` |
| 发布级 | 里程碑级 + E2E + bench + 质检报告归档 | 发布清单（M7 产出） |

脚本与规则的对应关系：

| 脚本 | 核查内容 | 依据 |
|------|----------|------|
| `scripts/check_layering.py` | 分层纪律 `L1/L2/L3`、测试位置 `T1` | §3.3、§5.1 |
| `scripts/scan_emoji.py` | 源码 emoji 禁令（与前端 lint 规则同区段） | §4.3、《前端设计规范》§3 |
| `scripts/lint.ps1` / `lint.sh` | 上述两项 + ruff + eslint + prettier | §6 |
| `scripts/ci.ps1` / `ci.sh` | lint + 后端测试 + 前端测试 | §5.2 |
