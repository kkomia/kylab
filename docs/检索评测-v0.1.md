# 检索质量评测 v0.1

- 日期：2026-09-12
- 目的：让"切块大小 / rerank / 混合权重 / 查询改写"这类改动的效果**可量化**，而不是"感觉更好了"
- 位置：指标口径 `backend/app/services/retrieval_eval.py`，跑分脚本 `scripts/eval_retrieval.py`

---

## 1. 为什么必须有它

调研报告把"建金标评测集"列为"只做三件事"之一，理由是：检索参数一改，
**没有数字就无法判断是不是真的变好，更发现不了悄悄变差的那部分**。
典型场景——把块长从 512 调到 256，短问答的召回上去了，但需要跨段推理的问题
开始漏；只看几条抽样会得出"变好了"，跑一遍金标集才知道整体是平的。

## 2. 指标口径（三条，够用且好解释）

| 指标 | 定义 | 什么时候看它 |
|---|---|---|
| `hit@k` | 前 k 条里**有没有**期望文档 | 最粗的一档，直接对应"用户能不能找到" |
| `recall@k` | 期望文档**被找到的比例** | 一条金标写了多个期望文档时才有区别；只填一个时它等于 hit |
| `MRR` | 第一个期望文档名次的倒数（第 1 名 1.0、第 2 名 0.5…） | 惩罚"找是找到了，但排在第 9 条"——在对话里那常常等于没找到 |

口径写在 `app/services/retrieval_eval.py` 里，并有单测钉住（`tests/unit/services/test_retrieval_eval.py`）：
**指标一改，历史跑分就不可比**，而"上次 0.62、这次 0.58"这种对比正是调参唯一的依据。

`--compare` 会把 **hybrid / vector / fulltext** 三种模式各跑一遍并排成一张表。
这张表本身就是最有用的诊断：全文强而向量弱 → 嵌入模型或中文分词的锅；
反过来 → 语料里的措辞与提问差异大（该考虑查询改写了）。

## 3. 怎么用

```bash
cd backend

# 1) 生成金标集草稿：问题由已配置的对话模型按语料提出，"应该命中谁"留空等人填
uv run python ../scripts/eval_retrieval.py suggest --kb kb_xxx --token "$KYLAB_TOKEN" -o golden.jsonl

# 2) 人工补 expect（只填问题不填 expect 的条目按满分计，填完再跑）
# 3) 打分
uv run python ../scripts/eval_retrieval.py run golden.jsonl --kb kb_xxx --token "$KYLAB_TOKEN" --compare -v
```

- 令牌从 `--token` 或环境变量 `KYLAB_TOKEN` 取，**不写进任何文件**。
- 走 HTTP（不是进程内直连）：进程内要占 DuckDB 的文件锁，服务在跑时根本起不来；
  HTTP 版本还能对着远程实例复测同一份金标集。
- `-v` 打印逐条明细，包括**漏掉了哪一份文档**——那才是"接下来改什么"的线索。
- `--min-hit 0.8` 可让脚本在低于阈值时返回非 0，便于接进流水线。

## 4. 金标集 JSONL 格式

一行一条：

```json
{"query": "眼轴长度在近视防控中的应用", "expect": ["眼轴长度"], "note": "同一主题的专家共识"}
```

- `query`：必填。
- `expect`：期望命中的**文档名里的一段有辨识度的文字**（忽略大小写与空白）。
  **不要写 `.pdf` 这种谁都有的一截，也不要写全名**——全名会在改名后失效。
  留空 = 只记录问题、暂不评分（方便先把问题攒起来）。
- `note`：给自己看的备注（为什么这条期望是它）。

## 5. 第一次跑分的结果与它的局限（重要）

2026-09-12 在真实实例上跑，两个库的小样本（5 条查询，逐条见下）**三种模式全部满分**：

| 库 | 规模 | hit@8 | recall@8 | MRR |
|---|---|---|---|---|
| RSS 订阅测试（3 篇 Markdown） | 40 块 | 100% | 1.000 | 1.000 |
| 眼科指南（2 篇 PDF） | 126 块 | 100% | 1.000 | 1.000 |

**但这说明不了检索有多好**：那 5 条查询几乎是从文档里照抄的词，属于最容易的一档。
它证明的是**工具链路是通的**（三种模式都能跑、指标能算、逐条能定位），
以及"随手写的金标集会什么都通过"。

所以真正的工作量在**写有区分度的问题**上，建议的目标是 20–50 条，覆盖：

1. **改写式提问**：不用原文措辞（"孩子眼轴长得快怎么办"而不是"眼轴长度监测"）；
2. **多期望**：一个问题有三处相关，检查 `recall` 而不只是 `hit`；
3. **该漏的**：语料里确实没有的问题，期望为空——**但此时要看的是它不该乱答**，
   这一项由对话层的人工检查覆盖，检索指标管不了；
4. **易混文档**：同一主题的几份文件，看能不能排对（这才是 MRR 的用武之地）；
5. **长文档跨段**：答案分散在两处，检查切块是否把它切断了。

拿到 20–50 题之后再谈调参：先跑基线，每改一处（块长 / rerank / 权重）跑一次，
**只有三项指标同时不退化才合并**。
