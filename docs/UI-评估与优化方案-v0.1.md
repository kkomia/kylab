# UI 评估与优化方案 v0.1

> 覆盖范围：性能（后端接口 + 前端渲染）、各页面与弹窗的美术/布局评估、以及与
> Dify / MaxKB / WeKnora 的功能对比与补齐计划。
>
> **评估方法的局限**：性能部分有实测数字与代码证据；美术部分基于组件与样式代码
> 通读 + 已有页面截图，**未逐屏截图核对**（浏览器自动点击在本机不可靠）。
> 因此美术评分里带 ⚠ 的条目表示"从代码看有问题，但需要一次人工目视确认"。

## 1. 性能审计与优化

### 1.1 已定位并修复

| # | 问题 | 证据 | 处理 | 效果 |
|---|------|------|------|------|
| 1 | 侧栏启动时**逐库拉一次文档列表**只为数出文档数 | `SideNav.onMounted → store.loadSummaries()`，内部对每个 KB 调 `listDocuments` | 后端 `document_stats_by_kbs()` 一条 `GROUP BY` 把每库文档数+最近更新时间随 `GET /knowledge-bases` 返回；前端 `summaries` 由列表结果构造 | 启动请求数 **O(库数) → 1**；上传/删除后的刷新同理 |
| 2 | 任务列表按可见库过滤时**逐条 `get_document`** | `DocumentService.list_tasks` 循环内查库 | 新增 `get_documents_by_ids`（分片 `IN`，500/批），一次批量取回 | N+1 → 1（每 500 条 1 次） |
| 3 | 对话渲染**每次重渲染都重解析全部历史消息** | `v-html="renderAnswerMarkdown(m.text)"` 逐条内联 | `renderAnswerMarkdown` 按文本缓存（上限 300 条） | 流式期间总解析量 **O(消息数×token) → O(消息数 + token)** |
| 4 | 驾驶舱一次性加载 **595KB**（ECharts 打进路由 chunk） | `DashboardView` 静态引 `EChart`；`ActivityHeatmap` 又静态引一次，导致异步化失效 | 两处都改 `defineAsyncComponent` | 驾驶舱 chunk **595KB → 11KB**，ECharts 独立 584KB 按需加载 |
| 5 | 大库文档列表**一次挂上全部行** | 每行都是带状态标签/菜单/复选框的组件 | 先渲染 100 行，其余"显示更多"按需追加；筛选条件变化时重置 | 首屏与轮询刷新的渲染量有上界 |

门禁：后端 1255 passed、前端 165 passed，全部全绿。

### 1.2 仍存在（已排期，未做）

- **驾驶舱聚合在 Python 里做**：`StatsService.dashboard` 把全量文档与任务读进内存再分组
  （`stats.py` 顶部注释已自陈）。库级增长到几万文档时会明显变慢。
  正确做法是在 storage 加"按日聚合"的仓储方法（分层纪律不允许 services 写 SQL）。
- **知识库详情页轮询 2s**：只在有文档处于活动阶段时轮询（已收口），但每次都会拉全量
  文档列表。可改为"只拉有变化的行"或退化为拉计数 + 变化时全量。
- **主包 213KB**：已可接受；若继续增大再考虑细分 vendor。

## 2. 各页面 / 弹窗美术评估

评分口径（1–5）：**布局合理性**（信息是否在正确的位置、留白是否成立）、
**组件一致性**（是否复用同一套控件与间距）、**层级与可读性**（主次是否分明）、
**反馈完整性**（空/载/错/危险确认是否齐）。取四项均值作总分。

| 页面 / 弹窗 | 布局 | 一致 | 层级 | 反馈 | 均分 | 主要问题 |
|---|---|---|---|---|---|---|
| 登录 LoginView | 4 | 4 | 5 | 4 | **4.3** | 单卡片形态克制；缺"忘记密码"的指引文案（本地部署情有可原） |
| 概览 DashboardView | 4 | 4 | 4 | 3 | **3.8** | 图表区在数据为空时是整块空白；缺"最近文档/失败任务"这类可点击的下一步 |
| 对话 ChatView | 5 | 4 | 5 | 4 | **4.5** | 布局（960 居中、无页头）已是全站最好；引用展示可再收紧 |
| 知识库列表 | 4 | 4 | 4 | 4 | **4.0** | 卡片/行两套形态并存（>12 切行）逻辑正确，但**两套的视觉密度差异大** ⚠ |
| 知识库详情 | 4 | 4 | 4 | 4 | **4.0** | 目录树+列表两栏已成立；工具栏与列表的横向对齐在窄窗口会折行 ⚠ |
| 文档详情 DocumentView | 3 | 3 | 3 | 3 | **3.0** | 信息最杂的一页：阅读/切块/元信息三块并列，缺分区导航；切块编辑是行内表单，视觉上与阅读冲突 ⚠ |
| 任务中心 TasksView | 4 | 4 | 4 | 3 | **3.8** | 表格式展示清楚；缺"按库/状态"筛选，任务多了以后不可用 |
| 上传弹窗 | 5 | 5 | 5 | 5 | **5.0** | 本轮刚收敛过；三种入口 → 两个入口、文案只讲类型与上限 |
| 分享弹窗 ShareDialog | 4 | 4 | 4 | 4 | **4.0** | 清楚；成员列表为空时缺引导 |
| 设置弹窗 SettingsModal | 3 | 4 | 3 | 3 | **3.3** | **1708 行单文件**，分区多但缺左侧导航（长滚动）⚠ |
| 模型注册面板 | 3 | 4 | 3 | 4 | **3.5** | 供应商 + 模型两级列表挤在一屏，探测结果与手填混在一起 ⚠ |
| 库内检索面板 KbSearchPanel | 4 | 4 | 4 | 4 | **4.0** | 通道/排名/原始分齐全，是我们相对三家的优势项 |
| 数据源面板 SourcePanel | 4 | 4 | 4 | 4 | **4.0** | 说明文案偏多，但都在讲"下一步做什么"，可接受 |
| 知识库设置弹窗 | 4 | 5 | 4 | 4 | **4.3** | 基本信息 + 库信息 + 危险区分段清楚；危险区与信息区之间可再加一条更强的分隔 |
| 危险操作确认 | 3 | 2 | 4 | 3 | **3.0** | **7 处用 `window.confirm`**（删目录/删文档/删数据源/删供应商…），与"影响清单 + AppModal"的既有做法**两套并存** |

**跨页面的共性问题**

1. **危险确认两套做法**（P0）：文档/知识库删除走"影响清单 + AppModal"，
   而删目录、删数据源、删供应商、取消解析走浏览器原生 `window.confirm`。
   原生弹窗样式不可控、无法承载"还有 N 篇"这类说明，也打断了产品观感。
2. **105 处硬编码 px**（P2）：多数是 `1px` 边框与图标尺寸（合理），
   但 `KnowledgeBaseView` 一处就有 20 处，其中行高/列宽这类**应当走 token**。
3. **超长单文件**（P2）：`KnowledgeBaseView` 1782 行、`SettingsModal` 1708 行。
   不是美术问题，但直接影响"改一处会不会碰坏另一处"的成本。
4. **空状态的下一步**（P2）：概览与任务中心在无数据时只给"还没有…"，
   没有"去上传/去建库"的入口（知识库列表与文档列表已有）。

## 3. 优化方案（按优先级）

### P0（建议立即做）

1. **统一危险确认**：把 7 处 `window.confirm` 换成统一的
   `ConfirmDialog`（AppModal + 一句后果说明 + 危险按钮），能带影响清单的就带。
   收益：观感统一 + 破坏性动作有可读后果。
2. **任务中心加筛选**：按知识库 / 状态 / 健康度过滤（后端已在任务响应里给了健康判据）。

### P1

3. **文档详情分区**：阅读 / 切块 / 元信息 用子标签收起（与知识库详情的次级菜单同构），
   一屏只看一件事。
4. **设置弹窗加左侧分区导航**：现在是一个长滚动，分区多了以后找不到。
5. **概览空状态给下一步**：无数据时给「新建知识库」「上传文档」入口。

### P2

6. 把行高/列宽类硬编码 px 收敛到 token；拆分 `KnowledgeBaseView` 与 `SettingsModal`。
7. 窄窗口下工具栏的折行策略（现在是 `flex-wrap` 自然折，按钮会换到第二行）。

## 4. 与 Dify / MaxKB / WeKnora 的功能对比

调研来源：三家官方文档与仓库（Dify `knowledge/*`、MaxKB `user_manual/dataset/*`、
WeKnora README/CHANGELOG）。

| 能力 | Dify | MaxKB | WeKnora | 我们 |
|---|---|---|---|---|
| 文档目录 | 无 | 仅知识库分层 | 有（树、可改归属） | **有**（单层，v13） |
| 文档标签 / 元数据 | 元数据 + 过滤 | 标签（多值） | 多标签 + 自动打标 | **无** |
| 文档级启用/停用 | 有 | 有 | 无 | **无**（切块级有） |
| 切块管理（增删改/启停） | 有 | 有 | 有（带版本回滚） | **有** |
| 批量操作 | 部分 | 有（导出/移动/打标） | 有（框选批量） | **有**（删除/重建/移动） |
| 重新解析 / 重建索引 | 有 | 有 | 有（可带参数） | **有**（重新摄入） |
| 切块参数可视化 / 预览 | 有（预览） | 有（分段预览） | 有（实时预览） | **无**（参数是库级、建库时定） |
| 父文档-子块 | 有 | 无 | 有 | 无 |
| 检索模式 | 向量/全文/混合 | 向量/全文/混合 | BM25/稠密/混合/GraphRAG | **混合 + rerank** |
| 库内检索测试 | 有 | 有 | 有 | **有**（通道/排名/原始分） |
| 引用展示 | 有 | 有 | 有（引用抽屉） | **有** |
| FAQ / 关联问题 | 部分 | 有 | 有（FAQ 库） | **无** |
| 中文分词词典 | 无 | 有 | 无 | **无** |
| API / 作用域密钥 | 有 | 有 | 有（按库限制） | **有** |
| 权限 / 分享 | 工作区成员 | 角色授权 | 四级 RBAC + 审计 | **有**（owner/admin/成员 + 读/写分享） |
| 审计日志 | 应用日志 | 操作日志 | 有 | 无 |
| 评测指标（召回/BLEU） | 无（外接） | 无 | 有 | 无 |
| Webhook | 无 | 无 | 无 | **有**（我们领先） |
| 回收站 | 无 | 无 | 无 | **有**（我们领先） |

### 必要缺口（≥2/3 家都有，且我们确实没有）与补齐顺序

1. **文档级启用 / 停用**（Dify、MaxKB 有）——P0。
   价值：不想让某份文档参与检索时，不必删掉它（删了就进回收站、切块与向量全丢）。
   设计：迁移 v14 给 `documents` 加 `enabled`（默认 1）；检索两条通道
   （全文 `fulltext_store.search` 与向量 `vector_store.search`）加同一条件的过滤；
   `PATCH /documents/{id}/enabled`；列表行显示"已停用"标签 + 行菜单开关；
   批量动作加 `enable` / `disable`。
   注意：**必须两条通道一起改**——只改一条会出现"全文搜得到、向量搜不到"的静默不一致。

2. **文档标签 / 元数据 + 检索时过滤**（三家都有）——P1。
   价值：目录是一棵树，一份文档只能属于一个位置；标签是多对多，能表达
   "合同 + 2026 + 已完成"这类交叉维度，也是检索收窄最常用的手段。
   设计：迁移 v15 建 `documents.tags`（JSON 数组即可，避免多对多表）+
   `knowledge_bases` 不需要额外表；列表筛选加 `tag` 参数；检索请求加 `tags` 过滤；
   行菜单"编辑标签"，批量"加标签"。

3. **FAQ / 关联问题**（MaxKB、WeKnora 有）——P2。
   价值：把"用户会怎么问"与"文档里怎么写的"分开维护，命中 FAQ 优先于切块，
   显著提升短问句的命中率。这是一块独立功能（新表 + 命中路径 + 管理界面），
   建议单独一轮。

4. **中文分词词典**（MaxKB 有）——P2。我们已用 FTS5，但中文默认按字符切；
   允许用户维护一个自定义词典能改善全文通道的召回。属于调优项。

**明确不做**（本轮判断）：父文档-子块、GraphRAG、审计日志、评测指标——
三家只有 1 家覆盖，且都要动数据模型与检索链路，收益相对成本不划算。
