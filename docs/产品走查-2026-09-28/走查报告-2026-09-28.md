## 一、走查概况

**方法**：不是"看代码猜问题"，而是用 Playwright 驱动真实 Edge（1440×900，中文环境）登录后
**真发消息、真让 agent 干活**，把每一步的 DOM 状态、控制台告警、网络失败、
滚动几何量都落了数据；共 21 个脚本、40+ 轮真实模型调用。

**覆盖**：用户给的 7 个模块 31 项，逐项实际执行。下面每条问题都带可复现的步骤与本机实测数值。

**走查分两轮**：第一轮覆盖 7 个模块主干；第二轮补做第一轮留白的项——
审批与人工干预（已实测）、非文本文件上传与预览、异常流（网络中断 / HTTP 500）、
翻译 / 计划规划 / 数据分析三类任务、单会话 31 轮的长上下文召回，
以及一次**工具崩溃的定位**（D33，本轮最高价值发现）。

**未覆盖（本次没做，别当"已通过"）**：
单条 >10 万字的消息、上传 >200MB 与断点续传、
多用户/成员身份下的权限行为（全程只用 admin 一个身份）、
真·长上下文压缩（要堆到 70 万 tokens 才会触发，见 D37）。

**样本说明**：模型是 DeepSeek Flash，回答风格（短、爱追问称呼）属模型行为，下面不计为产品缺陷。

## 二、总体结论

**主链路是通的，而且端到端闭环已经能跑**。本次实测走完了一条完整链路：

> 上传 `走查样例.md` → agent `list_conversation_files` 看到 1 项 →
> `read_conversation_file` 读了 20 行 → 正确回答"样本量 128" →
> 另一轮里检索知识库 3 次、引用 10 段/6 篇文档 → `export_document` 生成 `eye.md`（10.9 KB）
> → 产物卡片挂在会话里、可预览。

这一步是很多同类产品做不到的，值得肯定。

**但"成熟度"的差距不在能力，在四个地方**：

| 差距面 | 表现 | 典型条目 |
| --- | --- | --- |
| **状态可靠性** | 一次网络抖动就把用户踢回登录页并**删掉令牌**；React 无限更新告警间歇出现 | D02、D14 |
| **渲染正确性** | 数学公式排版塌陷（用了 KaTeX，但 KaTeX 的内联样式被丢掉） | D01 |
| **信息架构** | 上下文用量、压缩、文件、能力被塞进"模型"浮层之类的次级入口；常驻区看不到关键状态 | D05、D15 |
| **默认该有的功能** | 没有编辑重发/删除/反馈、没有会话分享、没有骨架屏、窄屏直接崩 | D07、D10、D13、D03 |

**分级统计**：P0 **0 项**（没有发现让主流程走不下去的问题）／**P1 4 项**／**P2 17 项**／**P3 15 项**，

在"没挂项目的会话"里，列文件工具是 100% 崩的，而且这是用户最常处在的状态。

#### D01　数学公式渲染塌陷，`E=mc²` 的指数掉到下一行

- **所属模块**：一 · Chat UI（清单第 2 项 Markdown/公式）
- **严重度**：**P1**
- **复现步骤**：
  1. 新建会话，发送："请只输出一份 Markdown 渲染自检样例……包含一个行内公式 `$E = mc^2$`、一个块级公式 `$$\int_0^1 x^2\,dx = \frac{1}{3}$$`"
  2. 等回答结束，滚到公式那一段
- **期望（对标 Kimi Work / DeepSeek Harness）**：行内公式与正文同基线，指数在右上角；
  块级公式居中、积分上下限在积分号上下、分式上下叠放。
- **实际表现**：指数 `2` 掉到下一行且是正常字号；块级公式散成
  `∫ 0 1 𝑥 2 dx= 1 3` 的多行碎片。截图：[`shots/40-math-zoom.png`](shots/40-math-zoom.png)、
  [`shots/21-thread-mid.png`](shots/21-thread-mid.png)
- **根因（已定位到具体环节）**：KaTeX 本身工作正常（`.katex` / `.katex-html` / `.katex-mathml`
  都在，CSS 0.18.7 规则已加载），但 **KaTeX 输出的内联 `style` 属性在渲染链路上被丢掉了**：

  ```
  实测：.katex-html 内 19 个节点，带 style 属性的 = 0
  正常 KaTeX 应有：<span class="vlist" style="height:0.8141em">
  实测拿到的是：  <span class="vlist">            ← 高度丢了
  .vlist 计算高度 = 0
  ```

  KaTeX 的纵向排版完全靠这些 `style` 里的 `height/top/margin` 撑起来，丢了就整体塌成一行。
  另外单独验证过：把段落的 `white-space` 从 `pre-wrap` 改回 `normal` **不能**修复
  （前后高度都是 21px），所以不是 `white-space` 的锅。
- **改进建议**：
  1. 查 `frontend/src/features/chat/model/markdown.tsx:1045-1072` 的 rehype 链——
     链尾是 `rehypeKatex`，但中间几个自研插件（`rehypeTrimBlocks` / `rehypeCodeText` /
     `rehypeMathSpacing`）会重建 hast 节点，检查是否有"重建 `element` 时只复制
     `className/children`、丢掉 `properties.style`"的写法（KaTeX 在最后，但它上游的通用
     walk 函数可能对所有节点都跑过一遍）。
  2. 若确认是 `react-markdown` 的 `components` 映射吞了 `style`，在 `span` 上显式透传 `style`。
  3. 补一条回归用例：渲染 `$a^2$` 后断言 `.katex .vlist` 的 `getBoundingClientRect().height > 0`——
     这类问题用快照测文本是测不出来的。

#### D02　输入框不随内容增高，6400 字挤在 44px 的盒子里滚

- **所属模块**：一 · Chat UI（清单第 1 项 超长文本输入）
- **严重度**：**P2**
- **复现步骤**：
  1. 新建会话，在输入框粘贴/输入一段 6400 字的长文本（或 30 行带换行的文本）
  2. 量输入框高度
- **期望**：输入框随内容增高到上限（如 8–10 行）后再内部滚动——Kimi Work、DeepSeek Harness
  都是这个行为。
- **实际表现**：高度**恒为 44px**，内容在 44px 的盒子里滚：

  ```
  6400 字：height=44px, scrollHeight=2954px, overflow-y=auto
  222 字 ：height=44.09px
  30 行  ：height=44px, scrollHeight=661px
  ```

  截图：[`shots/51-long-input.png`](shots/51-long-input.png)、[`shots/60-longinput-multiline.png`](shots/60-longinput-multiline.png)
- **根因**：`frontend/src/features/chat/ui/Composer.tsx:599-601` 只有
  `rows={2}` + `max-h-[240px] min-h-[44px] resize-none`，**全仓没有基于 `scrollHeight`
  的自增高逻辑**，`max-h-[240px]` 是从没被触发的死 CSS。
- **改进建议**：加一个 `useLayoutEffect`：`el.style.height='auto'; el.style.height=Math.min(el.scrollHeight,240)+'px'`，
  并在内容清空后复位。注意与 `rows={2}` 的最小高度配合。

#### D07　一次网络波动就把用户强制登出，并且**删掉了本地令牌**

- **所属模块**：二 · 上下文管理（清单第 12 项 会话恢复）+ 三 · 对话管理（清单第 15 项）
- **严重度**：**P1**（会丢正在进行的输入，且用户无法理解为什么被踢）
- **复现步骤**：
  1. 正常登录并进入 `/chat`
  2. 让页面加载期间的 `GET /api/v1/auth/me` 失败一次——最容易触发的现实场景是
     **后端 `uvicorn --reload` 重载的瞬间**（交接说明 §5.3 明确说这是常态）、
     网络抖动、或请求被导航中断
  3. 再看页面
- **期望（对标 Kimi Work / DeepSeek Harness）**：只有**服务端明确回 401/403**
  才清凭据跳登录页；网络错误/请求中断应当**保留令牌 + 重试 + 顶部提示"连接中断"**。
  这是成熟产品的通行口径，用户不该为一次抖动重新输密码。
- **实际表现**：被重定向到 `/login?redirect=...`，且 `localStorage['kylab-session-token']` 已被删除。
  **拿到了确切的调用栈**（在页面里 patch `Storage.prototype.removeItem` 抓的）：

  ```
  fetchreject  /api/v1/auth/me   "Failed to fetch"
  removeItem   kylab-session-token
  stack: setSessionToken (session.ts:36)
      <- clearSessionToken (session.ts:41)
      <- restoreSession (sessionActions.ts:54)      ← catch 里无条件 clear
      <- async App.tsx:92                            ← AuthGate
  ```

  截图：[`shots/116-load-60ms.png`](shots/116-load-60ms.png)（空白首屏）
- **根因**：`frontend/src/lib/sessionActions.ts:74-83`：

  ```ts
  export async function restoreSession(): Promise<boolean> {
    if (!useSessionStore.getState().token) return false
    try { ... return true }
    catch { clearSessionToken(); return false }   // ← 任何异常都当"凭据失效"
  }
  ```

  `catch` 没有区分「401（令牌真的无效）」与「网络失败/超时/被 abort」。
- **改进建议**：
  1. `catch (e)` 里判断 `e.status === 401 || e.status === 403` 才 `clearSessionToken()`；
     其余情况保留令牌，返回"暂时不可用"，由 `AuthGate` 放行并显示离线提示。
  2. 顺手把 `/auth/me` 的失败重试一次（现有 react-query 的 `retry:2` 没覆盖到这条手写请求）。
  3. 加一条用例：mock `me()` 抛 `TypeError: Failed to fetch`，断言令牌仍在。

#### D08　上下文用量与压缩入口埋在「模型」浮层里，常驻区看不到任何占用读数

- **所属模块**：二 · 上下文管理（清单第 10 项 上下文查看）

- **实际表现**：数据本身**很齐全**（点开模型浮层能看到）：

  明细留在浮层里。这一颗的成本已经被上一版验证过是放得下的。

#### D09　"本轮注入了什么"没有内容级视图

- **所属模块**：二 · 上下文管理（清单第 10 项）
- **严重度**：**P2**
- **期望（对标）**：能展开看**这一轮实际注入了什么内容**——系统提示词全文、
  注入的文件正文、命中的检索片段全文、工具结果——这是排查"为什么它答错了"的唯一手段。
- **实际表现**：

#### D37　压缩阈值按"窗口比例"算，在 1M 窗口的模型上实际不会触发

- **所属模块**：二 · 上下文管理（清单第 9、10 项）
- **严重度**：**P3**（产品策略问题，不是实现错误）
- **实际表现**：模型浮层里显示"到 **70%** 会自动压缩"，而当前模型是
  DeepSeek Flash（1,000,000 tokens 窗口）——阈值 = **70 万 tokens**。
  **实测数据（31 轮对话之后）**：

  ```
  已用 11,735 / 1,000,000 tokens（1.2%）
  消息 721 · 系统提示词 1,378 · 技能目录 544 · 工具定义 6,603 · 记忆与人设 2,169 · 其它 320
  ```

  两个结论：
  1. **固定开销（11,014）占了 93.9%，真实对话只占 6%**——其中**工具定义一项 6,603
     就是总量的一半以上**（56%）。才 5 个技能加若干内置工具就这样，工具面一扩，
     这是每轮都付的固定成本。
  2. 31 轮才 1.2%，**离 70% 的压缩阈值差两个数量级**。也就是说"上下文管理"在长窗口
     模型上基本处于未激活状态，用户不会看到压缩发生；真正会动历史的只有"剪旧工具结果"
     那一级（`services/chat.py:93-103`，保留最近 5 条）。后果是用户**只会在某一次
     突然失败/被截断时才发现上下文爆了**，而不是被提前告知。

  截图：[`shots/191-longcontext-usage.png`](shots/191-longcontext-usage.png)、
  [`shots/81-model-menu-context.png`](shots/81-model-menu-context.png)
- **改进建议**：
  1. 阈值不该只按窗口比例。建议同时给一条**绝对值**上限
     （例如"无论窗口多大，超过 120k tokens 就压缩"），因为成本与延迟随 token 线性上升，
     而"窗口够大"不等于"该让它一直涨"；
  2. **工具定义按需加载**——6,603 tokens 的固定开销是眼下最值得砍的一块

## 五、布局与动效专项小结

**做得好的**
- 输入框胶囊收成 `+ 权限 知识库 …… 模型 发送` 五格，1440 下单行放下，比上一版干净；
- 消息操作 hover 出现（`opacity-0 → group-hover:opacity-100`），不打扰阅读；
- 深色模式是**真的做完整了**：`data-theme` 切换正常，深色底 `rgb(24,24,23)`，
  高亮色在深色下有覆盖（`chat.css:385-386`）。截图 [`shots/111-dark-mode.png`](shots/111-dark-mode.png)
- 空态（"让你的知识触手可及" + 5 条示例问题 + 换一批）方向对，示例问题按知识库生成；
- 首字之前的等待有过程面板在动，不是死的。

**不合理的地方（按影响排序）**
1. **窄屏无断点**（D29）——这是唯一"看一眼就知道不行"的布局问题。
2. **上下文读数的位置**（D08）——把"还能问多长"藏进"模型"浮层，是信息架构问题：
   它和模型不属于同一类问题（一个是"怎么生成"，一个是"还剩多少额度"）。
3. **过程面板与正文同列上下堆叠**：长任务（3 次检索 + 导出）时，
   过程占满整个视口，正文被推到首屏之外，用户要先滚过一堆步骤才看到答案。
   交接说明 §4.4 里"右侧栏 + tab 注册表"的方案正是解这个的，建议按那个方案推进
   （P1 把「产物与文件」搬进右侧栏）。
4. **出处 chip 内联插入正文**：实测某次回答读起来是被切碎的
   （`…检索到（命中 10 段）眼科手册 、眼眶海绵状静脉畸形 ×× 28眼科学 第10版 …、颈动脉海绵窦瘘 …，共 10 处出处`）。
   建议出处收成正文末尾的编号列表，或右侧栏统一的"来源"tab——内联 chip 只留角标数字。
5. **侧栏信息密度**："项目"节里会话是第二层折叠，超过 5 条收起；
   侧栏行没有时间。会话一多，找一条要点两次展开。
6. **"更多 / 浏览市场 / 设置"的层级**：能力页头部同时有 `设置`、`浏览市场`、`更多` 三个入口，
   `设置` 又和左下角账号菜单里的 `设置` 是两个东西（账号菜单那个打开的是
   一个十页签的大弹窗：模型注册/向量化/对话模型/服务配置/存储配置/检索/用户/系统与安全/外观/快捷键，
   见 [`shots/140-settings-modal.png`](shots/140-settings-modal.png)）。同名不同物，容易点错。
