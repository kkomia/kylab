## 0. 结论摘要

界面整体已有一套克制的设计系统（灰阶 + 品牌色只用于动作、四级圆角、可调字阶、
实测对比度）。**问题不在审美方向，而在"同一件事被实现了很多遍"**：
下拉框 5 套、表单标签 6 套、小字说明 15 个局部类名、间距偶有手写 px。
它们各自都"还行"，摆在一起就是不齐——而用户扫视时看的正是这些对齐线。

| 区域 | 问题 | 级别 |
|------|------|------|
| 下拉框 | 5 处原生 `<select>` 各写一套：高度 24 vs 32、边框 strong vs hairline、字号 meta vs inherit | P1 |
| 表单标签 | 6 处 `.field-label`：字号 micro vs meta、颜色 secondary vs tertiary、字重 500 vs 默认 | P1 |
| 小字说明 | 15 个 note/muted 局部类，字号与灰阶混用 | P2 |
| 间距 | 少数手写 `2px` 未走 `--space-pair` | P2 |
| 按钮 | 本身一致；但"危险动作"的视觉重量在弹窗里偏轻、缺 block 能力 | P3 |
| 图标 | 手绘 1.5px 线稿 26 枚，与用户提供的 Remix 集合（69 枚，Apache-2.0）未统一 | P2 |

## 1. 下拉框样式（用户点名）

### 现状：同一个控件，五套实现

| 位置 | 类名 | 高度 | 边框 | 字号 | 颜色 |
|------|------|------|------|------|------|
| `components/knowledge/SourcePanel.vue:288` | `.field-select` | `--hit-target` (24) | `--border-strong` | `--text-meta-size` | primary |
| `components/settings/ModelRegistryPanel.vue:758` | `.field-input` | 24 | strong | meta | primary |
| `components/settings/ModelRegistryPanel.vue:611` | `.slot-select` | 24 | strong | meta | primary |
| `components/search/KbSearchPanel.vue:337` | `.select` | 32 | strong | inherit | primary |
| `components/layout/SideNav.vue:459` | `.identity-select` | 24 | **hairline** | meta | **secondary** |

**为什么这是问题**：同一屏里出现 24 与 32 两种高度的下拉（设置弹窗左表单 vs 右侧
slot 行），视觉上像两种控件；`hairline` 与 `strong` 的边框差异让"可点"的信号强弱不一。
更要紧的是**每新增一个下拉就再抄一遍**——这正是它已经漂成五套的原因。

### 计划（P1，本轮执行）

1. 保留并强化 `components/ui/AppSelect.vue` 为**唯一**下拉实现：
   - 高度 32（与 `AppInput`、`AppButton md` 同基线）；
   - `1px --border-strong`，聚焦 `--text-secondary`；
   - `font: inherit`（跟随可调字阶，不再写死 meta）；
   - `width: 100%`（由父容器的 grid/flex 决定宽度，行为可预测）。
2. 五处原生 `<select>` 全部迁到 `AppSelect`，删除各自的局部样式。
3. 例外只允许一种：需要**富内容选项**时（目前没有）才另起组件。

**验收**：`grep -rn "<select" src/` 只剩 `AppSelect.vue` 一处；
设置弹窗里"表单控件"与"slot 行"的下拉同高同边。

## 2. 表单标签与小字说明（用户点名）

### 2.1 表单标签：六套 `.field-label`

| 位置 | 字号 | 颜色 | 字重 | 布局 |
|------|------|------|------|------|
| `KbSearchPanel.vue:330` | micro | secondary | 默认 | block + margin-bottom |
| `SourcePanel.vue:283` | micro | **tertiary** | 默认 | 行内 |
| `ModelRegistryPanel.vue:753` | micro | **tertiary** | 默认 | 行内 |
| `KnowledgeBasesView.vue:444` | **meta** | secondary | 默认 | block + margin-bottom |
| `LoginView.vue:223` | micro | secondary | **500** | 行内 |
| `SettingsModal.vue:1352` | micro | secondary | **500** | + margin-top |

**判定**：标签是"这个控件填什么"的说明，属于**次要信息但必须可读**——
规范 §4.2 把注释定在 12–13px 且三级灰需过 AA。这里 micro/secondary/500 是正确取值；
`tertiary` 与 `meta` 两处是偏离，`KbSearchPanel` 的 block+margin 与其余的行内写法也不统一。

### 2.2 小字说明：15 个局部类

`.row-note` `.section-note` `.share-note` `.delete-note` `.readonly-note` `.muted`(×3)
`.side-note` `.usage-note` `.scope-note` `.summary-note` `.preview-note` `.prompt-note`
`.figure-note` `.bar-note` `.empty-note`

它们做的是同一件事：**在主内容下面补一句灰字**。但取值散在
micro/secondary、micro/tertiary、meta/secondary 三种之间，行高也各写。

### 计划（P1/P2，本轮执行）

1. `assets/base.css` 增加三个**全局**工具类，作为唯一口径：
   ```
   .field      → flex column, gap --space-1   （标签 + 控件的成组容器）
   .field-label→ micro / 500 / secondary
   .field-optional → micro / 400 / tertiary   （"可选"这类后缀）
   .text-note  → micro / secondary / 1.7      （引导、说明：需要被读到）
   .text-hint  → micro / tertiary / 1.7       （脚注、次要提示：可以弱）
   ```
2. 六个局部 `.field-label` 删除，改引全局类；`LoginView` / `SettingsModal`
   的表单改用 `.field` 成组（间距由容器 `gap` 定，不再靠 `margin-top`）。
3. 局部 note 类按语义归并到 `.text-note` / `.text-hint`，保留极少数确有特殊
   排版需求的（如 `KnowledgeBaseView` 的只读说明条需要底色，保留容器样式但
   文本取值引用同一口径）。

**验收**：`grep -rn "^\.field-label" src/` 为 0；note/muted 类名显著收敛，
同一屏内的说明文字字号与灰阶一致。

## 3. 按钮样式（用户点名）

### 现状

`AppButton` 本身是好的：三档 variant（primary/secondary/danger）+ 两档 size（28/32），
主按钮用品牌色、禁用态用实色（规范 §2 已修）。问题在**使用面**：

1. `.slot-select` 旁边的 `测试` 按钮与输入不同高（行控件混排）；
2. 弹窗里"破坏性动作"（删除用户/删除文档）与普通按钮同尺寸，只靠红字区分——
   在弹窗 footer 里两颗按钮等宽等高，扫视时容易点错；
3. 没有 `block`（占满整行）能力，登录页靠局部 CSS `width:100%` 硬撑。

### 计划（P3，本轮只做低风险项）

- 给 `AppButton` 增加 `block` 属性，替换登录页的私有 CSS；
- `danger` 在**确认弹窗 footer** 里保持"红字 + 浅红底 hover"，但**不**改成实心红：
  实心红会让它成为弹窗里最显眼的按钮，而它恰恰是最不该被顺手点的（规范 §7 的解释）。
  改为在文案上更强（如"删除并移入回收站"），而不是加颜色重量；
- 表单行内控件统一 32px 基线（随 §1 的下拉统一一起达成）。

## 4. 排版与间距（用户点名）

### 现状

- 页标题 28px / 小节 16px / 正文 15px / 注释 13–14px 的阶梯已落地，方向正确；
- 间距基本走 `--space-*`，但仍有手写值：
  `TasksView.vue:394` `gap: 2px`、`TasksView.vue:432` `margin: 2px 0 0`
  应为 `--space-pair`（base.css 已为"成对文本"定义了该令牌）；
- 结构常量（行高 36/44、进度条 6px、状态胶囊 22px）不属间距节奏，保留。

### 计划（P2，本轮执行）

- 手写 `2px` 改 `--space-pair`；
- 复核所有 `padding/margin/gap` 的 px 字面量，仅允许结构常量。

## 5. 图标（用户提供的 Remix 集合）

### 现状

- 现用图标：`components/icons/` 手绘 1.5px 描边线稿 26 枚（`IconBase` 统一）；
- 用户提供的资产：**Remix 图标集合（69 枚，24×24 网格，Apache-2.0，可商用）**，
  清单见《知识库UI图标选型清单》，每枚带建议用途。Remix 的 "line" 系列是
  **以填充路径绘制线稿**（视觉仍是线性单色），与本项目"单色线性、currentColor"一致。

### 问题

1. 两套图标并存会破坏"统一一套不混用"（规范 §3）；
2. Remix 集合覆盖的是**知识库语义**（文档/检索/任务/分享…），
   不含少数**界面 chrome**：关闭、对勾、折叠箭头、+、太阳/月亮、状态点、品牌标。
   这几枚需从 Remix 同库补齐（同网格同重量），而不是继续手绘另一套。

### 计划（P2，本轮执行）

1. 取用户提供的 69 枚 + 同库补齐的 chrome 图标，**统一为一套 Remix 基线**；
2. `IconBase` 渲染方式从描边改为填充（`fill="currentColor"`，24 网格），
   现有 `Icon<Name>.vue` 组件名与 `size` API 不变——调用方零改动；
3. 语义映射沿用现有组件名（如 `IconLibrary` ← `book-2-line`、
   `IconTasks` ← `task-line`、`IconSearch` ← `search-line`、`IconTrash` ← `delete-bin-line`…），
   新增图标按需落地（`IconShare`、`IconUser`、`IconLogout` 等）；
4. **规范影响**：规范 §3 现写"基准库 Lucide、1.5px 描边"。改为 Remix 填充式线稿
   属规范级变更，按"已提交即冻结"须**升版到 v0.5** 并写明理由，不在 v0.4 原地改。

**验收**：全仓图标均出自同一集合、同一网格、同一 `currentColor`；
16/20/24 三档下视觉重量一致（截图目视 + 与侧栏文字并列检查）。
