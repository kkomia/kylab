- 日期：2026-09-12
- 范围：UI、功能、布局、文档清洗、前后端运行效率，共五块
- 目的：**给"要不要开发、先开发什么"提供判断依据**，不是一份功能清单

## 0. 一页结论

**产品目前的位置**：一个"工程完整度明显高于功能广度"的单机知识库。异步流水线（租约/退避/断点续跑/取消）、双云端解析引擎的路由与探测、页级引用、思考方言适配、MCP/Webhook/API Key 这些**底座**做得比多数开源同类扎实；而**广度**（图片理解、图表结构、工作流 Agent、图谱、评测集）基本是空的。

**三条最重要的结论**：

1. **有一批"小而致命"的存量缺口，代价极低但持续伤用户**。最有代表性的是切块参数：接口和界面都保存了 `chunk_size/chunk_overlap/chunk_strategy`，摄入却永远用硬编码的 512/64——**这是一个 no-op 的承诺**。同类还有：删库不清理向量分区表、DB 空闲页不回收（实测 19%）、上传 `.html` 不剥标签、会话重命名/删除有 API 没界面。这些加起来约 **5–8 人日**，是本次调研里性价比最高的一批。
2. **真正的能力差距集中在"解析深度"与"检索质量"两处，不在 UI**。UI/布局经过最近几轮改造（对话页时间线 + 行内引用、设置弹窗、文档抽屉）已经追到开源同类的水平线上；但对标产品在**图片理解**（RAGFlow 的多模态图片描述、WeKnora 的 VLM 图片描述）、**表格结构识别**（RAGFlow 的 TSR）、**切块模板与父子块**（RAGFlow 十种模板、WeKnora 三级自适应 + 父子块默认开）上是成体系的投入，我们是"透传上游结果 + 固定长度切块"。**如果要继续投入，这里才是主战场。**
3. **单机零依赖不是短板，是差异点，不要拆掉**。RAGFlow 最低 4C/16G/50G + ES/MySQL/Redis/MinIO，Dify 一套 compose 起 15 个组件，FastGPT 要 Mongo+pgvector+Redis+对象存储；我们和 WeKnora Lite、AnythingLLM 站在同一路线（SQLite 单文件 + 嵌入式向量）。sqlite-vec 官方明确在 **100 万向量以内**够用（暴力检索，无 ANN），这对自托管知识库是合理区间。**建议明确把"零中间件"写进定位**，而不是补中间件去"对齐"。

**如果只做三件事**：① 把切块参数接线（或从界面撤掉）；② 建一个 20–50 题的金标评测集；③ 本地 PDF/Office 直提兜底。前两件是"让后续每一次优化可验证"的前提，第三件是"没有云端 token 时产品还活着"的底线。

## 1. 方法与取证口径

本报告的每条判断分三类，正文里都标了记号：

| 记号 | 含义 | 来源 |
|---|---|---|
| `[实测]` | 在真实运行的实例上量出来的数字 | 本机运行中的后端 8000 / 前端 5173 + 生产构建产物 |
| `[代码]` | 从仓库源码读出来的事实（带文件与行号） | E:\gitlab\kylab |
| `[公开]` | 对标产品的公开资料 | 官方文档 / GitHub README（2026-09 抓取），文末有链接 |

**实测的样本量提醒**：当前库内只有 **8 份文档 / 169 个切块 / 4 个知识库**（`[实测]`）。所以：

- **时延、体积、吞吐**这类"与数据量弱相关"的数字可直接采信；
- **"能撑多大规模"**这类结论本报告**不给数字**，因为样本量不足以外推。需要规模结论时先补压力测试。

另外区分两类问题，优先级完全不同：

- **存量缺陷**：已经承诺/已经实现但坏了或不生效 → **必须修，代价小**；
- **能力缺口**：对标产品有、我们没有 → **可选，代价中到大，看产品方向**。

## 2. 现状盘点（五个维度）

### 2.1 UI 与交互

`[代码]` 已具备：

- 预览：PDF 走原生 iframe（`#page=N` 跳页）、图片、Markdown/文本、Office 三件套懒加载（`OfficePreview.vue`）。

### 2.2 功能

`[代码]` 有且完整：知识库/文档全生命周期、混合检索（向量 + 全文 + RRF(k=60) + 可选 rerank + 文档级过滤 + 相对阈值 + 分路统计）、对话（多轮/引用快照/示例问题/标题生成/请求-会话-全局三级模型与思考选择）、**思考方言适配 8 家**（DeepSeek/Qwen/GLM/Kimi/OpenAI/Gemini/Anthropic/generic，三档强度）、异步队列（原子领取/租约心跳/指数退避/断点续跑/协作取消）、模型注册三层 + 探活、账号体系（argon2 + 会话滑动续期 + 登录限流）、API Key 范围控制、库分享两档、MCP 双传输 7 工具、Webhook 签名重试、用量统计、迁移 v16、健康探针。约 70 个端点。

`[代码]` 有但很浅：数据源仅 RSS/HTML（无 WebDAV/网盘，无调度器）；切分仅固定长度；检索无查询改写/HyDE/同义词；对话无服务端停止端点（靠断开 SSE）；权限仅 owner/member 两档；无全局限流/配额；**检索调用不落库**（`stats.py` 注释明确），所以驾驶舱看不到检索量。

`[代码]` 完全没有：工具调用 / Agent / 工作流 / 联网搜索 / 多模态图片问答；图谱与实体抽取（`ENRICH` 只有枚举与状态机占位）；OpenAI 兼容**服务端**接口；SDK/CLI；多租户/审计/配额。

### 2.3 布局与信息架构

`[代码]` 页面收敛为 5 页 + 登录（概览 / 知识库 / 对话 / 任务 / 文档抽屉），全部路由懒加载，**会话与抽屉状态放在路径参数里**（可收藏、可后退）；侧栏 4 项导航 + 会话区 + 账号二级菜单；检索收进库详情页；设置收进弹窗。这个收敛度是对标产品里少见的（Dify/FastGPT 的菜单元件数量高一个量级），**是优点，不要为了"功能多"把它撑开**。

`[代码]` 问题：知识库详情页单文件 1960 行、知识库列表 604 行、对话页 1507 行，样式与逻辑同文件；文档列表**分页是客户端"显示更多"（每次 100 行），接口一次回全量**——文档上千条时首屏会明显变慢。

### 2.4 文档清洗

`[代码]` 唯一"超出开源同类"的地方是**逐文件探测 + 逐文件路由**：抽样 5 页、单页 ≥20 字符算有文本层、覆盖率 ≥0.8 判 TEXT / ≤0.2 判 SCANNED / 中间 MIXED，结论与理由（`route_reason`、`sampled_pages`、`pages_with_text`）全部落库可回看（`parsers/probe.py:43-122`，`parse_results.probe_meta` 实测样例可读）。页标记 `<!-- page:N -->` 写读共用一份定义、页码贯穿到 chunk、标记不进正文——**页级引用可核查性做得比多数同类扎实**。

`[代码]` 明显落后：

- **没有本地 PDF 文本层直提**：`pypdf` 只用于探测，文字型 PDF 也必须上 MinerU；**MinerU token 未配置时所有 PDF/Office/图片直接不可用**（`parser_router.py:94-97` 抛"暂不支持"）。对标里 AnythingLLM 有本地 PDFLoader + tesseract 回退，FastGPT 有 pdfjs 本地解析。
- **没有本地 docx/pptx 解析**，同样完全依赖云端。
- **图片管道形同虚设**：云端明明抽出了图片字节，但 `ParseResult.image_ids` 之后没有被持久化——`[实测]` `images` 表 0 行、`chunk_images` 0 行、`data/images` 0 个文件；`caption` 恒为 None，切块器从不设置 `image_ids`。**"多模态"目前是注释里的预留位。**
- **无表格结构还原**：MinerU 的 HTML 表格原样透传，本地 CSV/Excel 渲染成"列名=值"的逐行文本，HTML 连接器把 `td/th` 压成单行。
- **上传 `.html` 走纯文本直通，不剥标签**：`.html` 不在 `TEXT_EXTENSIONS` 里，是**靠"声明的 MIME 是 `text/*`"兜底**落进纯文本直通（`parsers/plain_text.py:48`），导航与脚本会进检索索引。剥标签的逻辑只存在于连接器路径（`connectors/html_reader.py`），上传路径没有复用。
- **切块参数是 no-op**（见 §0 结论 1）。
- **无父子块、无 chunk 级去重、无页眉页脚去除**。
- **两引擎无故障自动降级**：路由是静态选择，MinerU 单点失败不会自动切 PaddleOCR。

`[实测]` 切分性能不是瓶颈：44 KB markdown → 119 块耗时 **0.69 ms**（约 65 MB/s 文本吞吐）；169 块平均 434 字符、p50 479、上限 512。也就是说**切块算法的算力成本可以忽略，问题全在"切得好不好"**。

### 2.5 前后端运行效率

`[实测]` 后端时延（直连 `127.0.0.1:8000`，本机，避免开发代理干扰）：

| 接口 | p50 | 说明 |
|---|---|---|
| `GET /health` | **1 ms** | 框架固定开销可忽略 |
| `GET /knowledge-bases` | 9 ms | |
| `POST /search` mode=fulltext | **19 ms** | jieba 预切词 + FTS5 + JOIN；8 并发总 124 ms，**无串行化问题** |
| `POST /search` mode=vector | **422 ms** | 其中约 400 ms 是查询嵌入的网络往返 |
| `POST /search` mode=hybrid | ~440 ms | ≈ 全文 + 向量 |
| 对话：检索完成 | ~0.42 s | 与混合检索一致，前后互验 |
| 对话：**首字** | ~2.5 s | DeepSeek 思考模式；扣掉开发代理的 ~0.25 s（原始读数 2.76 s） |
| 对话：整段（117 字） | ~2.7 s | 原始读数 2.996 s，扣代理 |

`[实测]` 嵌入：单条 **~400 ms**，32 条一批 **同量级（~400 ms）** → 批处理有效，约 **80 块/秒**；`usage_events` 里 embedding 的 duration p50 = 405 ms，与实测吻合。**结论：时延被供应商网络往返主导，不是本地计算问题。**

`[实测]` 解析：`tasks` 表 parse 平均 **6.12 s**、最大 18.3 s（含云端往返），7 次全部一次成功。

`[实测]` **重要澄清**：在浏览器里经 Vite 开发服务器测，每个接口都会平白多出 **~250 ms**（静态资源 2 ms、被代理的 `/health` 248 ms，呈现 60/250 ms 交替）。**这是开发代理的产物，不是后端问题**——早期我差点把它当成"后端慢"写进报告。后端直连健康检查是 1 ms。任何"接口慢"的判断都必须绕过开发代理再下。

`[实测]` 前端生产构建的首屏下载（起一个静态服务托管 `dist/` 并代理 API）：

| 路由 | JS | CSS | 主要构成 |
|---|---|---|---|
| `/`（概览） | **866 KB** | 41 KB | 入口 279 + **EChart 571** + 视图 12 |
| `/kb/:id` | 361 KB | 66 KB | 入口 279 + 视图 57 + 弹窗 14 |
| `/chat` | 309 KB | 50 KB | 入口 279 + 视图 27 |

- gzip 口径（构建输出）：入口 286 KB → **103 KB gz**；EChart 585 KB → **199 KB gz**；概览页合计约 **302 KB gz**。对照公开建议的 170 KB 量级，**概览页偏重**。需要说清楚的是：ECharts **已经按需引入**（`components/charts/EChart.vue:17-30` 只注册了 Bar/Heatmap/Line 三种图表 + Canvas 渲染器，走 `echarts/core`），**不是"整个库引了进来"**——是 `echarts/core` 本身就有这个量级。真要瘦身得换更轻的绘图方案，或把概览页的图表改成"点开才加载"。
- 懒加载块：`docx-preview` 175 KB（52 gz）；两个 1.35 MB（431 gz）/ 1.68 MB（504 gz）的块含 `@vue-office` + ExcelJS，只在预览 Office 时加载。`[实测]` 概览页与 PDF 预览都不会加载它们，懒加载是有效的。
- `[代码]` `vite.config.ts` **没有 `manualChunks`**，分包完全靠路由懒加载。
  > **2026-09-12 更正**：本节初稿写过「构建产物里 `echarts` 同时出现在 `EChart-*.js`
  > 与含 `vue-office` 的 1.35MB 块里，说明自动分包把不相关的库搅在一起」。那句是
  > **按子串搜索**得出的，不成立：把 echarts 单独命名成 `vendor-echarts` 之后，
  > 那个 1.35MB 块的大小一个字节都没变（1,348.42 kB → 1,348.42 kB），说明里面的
  > `echarts` 只是别的库（ExcelJS / vue-office）里的字符串，不是 echarts 的代码。
  > 实测结论：ECharts 本来就自成一个懒加载块，概览页只下它；**不存在「两个不相干的
  > 库被搅在一起」的问题**。手动 `manualChunks` 试过两次都无收益，已回退
  > （详见《开发计划》§12.75）。

`[实测]` 存储现状（这是最容易看到"工程细节债"的地方）：

| 事实 | 数字 | 解读 |
|---|---|---|
| DB 文件 | **21.1 MB** | 8 文档 / 169 块 / 4 库 |
| 其中空闲页 | **4.05 MB（19%）** | 删除后不回收；无 VACUUM 入口 |
| sqlite-vec 向量分区 | **有向量的 4 个分区各占一个 4,194,304 字节的固定块** | 只要库里有**第一条**向量就预分配 4 MB；4 个非空库 = 16 MB（第 5 个空表 0 字节） |
| 孤儿向量分区 | `vec_kb_2319aa4125df`（无对应知识库） | **删库不清理向量表** |
| FTS 索引 | 134 KB / 169 块 | 合理 |
| 图片对象存储 | **0 文件** | 图片管道未落盘（同 §2.4） |

即：**在这个样本上，DB 的 21 MB 里约 20 MB 是"固定 4 MB 向量块 × 非空库数"和空闲页，真正的数据不到 1 MB。** 这个开销与文档量无关，只与知识库数量有关。

`[公开]` 对话/引用 UX 基准（商业产品）：

- **NotebookLM**：引用是 `[N]` 行内标记 + 悬停锚定，数据模型带 `cited_text` 与**源文档字符区间**（可精确定位并高亮原文）；Studio 衍生音频/思维导图/报告/闪卡。
- **Perplexity**：引用默认开启 + 回答下方 Follow-ups 追问区。
- **RAGFlow**：会话搜索/多选删除/Stop/Thinking 开关；`Show citations` 与 `Show chunk metadata` 开关；文档未体现检索步骤时间线。
- **Dify**：来源引用可点；每条回答有 Copy / Like / Dislike；自动生成 3 条 follow-up；会话说置顶/删除；界面**自适应移动端**；开场白消除空状态。
- **FastGPT（Chunk Reader）**：点引用**弹窗显示完整原文并高亮被引段落**，多引用可导航（7/10），引用带相关度评分，匿名分享可限制"仅引用片段"。
- **WeKnora**：行内引用 popover + 右侧 references drawer（区分 Web/知识库）；聊天内展示**分阶段 RAG 流水线进度**；会话按来源分组、标题行内重命名、置顶与搜索、一键导出 Markdown。

**我们对话页的位置**：过程时间线 + 行内徽标已对齐 WeKnora 的做法；缺的是 WeKnora 的**会话级管理**（改名/置顶/搜索/分组/导出）、FastGPT 的**引用原文弹窗高亮**、Dify 的**消息级操作**。

## 5. 明确不建议做的事

1. **不要为了"对齐"去堆中间件。** RAGFlow 要 16 GB 内存起、Dify 一套 15 个组件、FastGPT 要 Mongo+pgvector+Redis+对象存储。我们"一个进程 + 三个文件"（SQLite/DuckDB/对象目录）是**自托管用户真正在乎的差异点**，也是 WeKnora Lite 和 AnythingLLM 走的同一条路。要补的是这条路上的短板（本地解析兜底、规模上限的明确说法），不是拆掉它。
2. **不要自研版面分析与 OCR。** RAGFlow 的 DeepDoc 是长期积累；WeKnora 的选择是"引擎可插拔"（PaddleOCR-VL/OpenDataLoader/anydoc）。我们已经在双云端引擎 + 逐文件探测上走对了，**继续沿"可插拔 + 探测可解释"走**，而不是从零训练版面模型。
3. **不要先做多模态全家桶**（音频概览、思维导图、视频）。这些是 NotebookLM 的差异化，不是知识库的必需品。**先把已经抽出图片却没落盘这条断链接通**，收益更大也更便宜。
4. **不要在没有评测集的情况下调检索参数。** 改 chunk size、开 rerank、加查询改写都会"看起来更好"，但没有金标集就无法判断是否真的更好，也无法发现回归。**先做第 8 项。**
5. **不要追求"供应商 20+"式的广度。** 我们的差异在**思考方言适配做到了 8 家 + 三档强度**（含实测发现 DeepSeek 会静默忽略 `enable_thinking` 这类细节）。把 3–5 家做深，比铺 20 家的列表更有价值。
6. **不要把信息架构撑开。** 现在 5 个页面 + 弹窗收得很紧，是对标里少见的清爽。加功能时优先"收进已有页面/弹窗"，而不是新增顶级导航项。

## 6. 如果只做三件事

1. **切块参数接线（或撤掉）** —— 半天到一天，消除一个不成立的承诺。
2. **金标评测集 20–50 题** —— 一到两天，从此每次优化都可验证、可回归。
3. **本地 PDF/Office 直提兜底** —— 两到三天，让产品在没有云端 token 时仍然可用。

三件事合计 **约 4–6 人日**，做完之后再决定要不要进 P1（图片管道 / 父子块 / 表格结构）这条"解析深度"的主线。

## 附录 A：实测数据与复现方法

**环境**：`[实测]` 后端 uvicorn `127.0.0.1:8000`（**未开 `--reload`**，Python 3.12 / venv），前端 Vite `localhost:5173`；样本 8 文档 / 169 块 / 4 库。时延取 6–12 次的中位数。

**时延**：直连后端用 `node:http` 打点（绕开开发代理）；浏览器侧用 `performance.now()`。
**体积**：生产构建后用静态服务托管 `dist/`（并把 `/api` 代理到后端）逐路由读 `performance.getEntriesByType('resource').encodedBodySize`。
**存储**：`sqlite3` 只读连接（`mode=ro`）读 `page_count` / `freelist_count` / `sqlite_master`，向量分区用 `sqlite_vec.load()` 后查 `vec_*`。
**切分吞吐**：直接调用纯函数 `chunk_markdown()` 跑真实 markdown，5 次取均值。
**嵌入时延**：`usage_events` 里 embedding 事件（72 条）的 `duration_ms` 分布，与供应商实测交叉验证。

**两个测量陷阱（留给以后做性能结论时避坑）**：
1. **开发代理会凭空加 ~250 ms**（静态资源 2 ms vs 被代理的 `/health` 248 ms）。判后端快慢必须绕过它。
2. **样本量小**：所有"规模/上限"结论都不应从这份数据外推。
