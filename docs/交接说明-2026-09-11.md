## 1. 这是什么项目

**kylab**：本地优先（不依赖云、数据不出机器）的知识库 RAG 系统。
把 PDF / Office / Markdown / 表格 / 图片 / 网页 / RSS 摄入进来，
解析成统一 Markdown，切块、向量化，提供混合检索，
并通过 **REST / MCP / 官方 Skill 三条通道**对外服务。

### 目录结构

```
backend/      Python FastAPI（app/ 分层：api → services → storage/parsers）
frontend/     Vue 3 + Vite + TS + Pinia
docs/         全部设计文档（见 §4，**这是本项目的核心资产**）
scripts/      ci.ps1 / lint.sh / check_layering.py / scan_emoji.py / gen_api_spec.py
tests/        e2e
skills/       官方 MCP Skill 产物
deploy/       容器编排（**未实测**，见 §7）
.shots/       开发期的验证探针与截图（**不入库**，.gitignore 里有）
```

### 技术栈的关键选择

| 部分 | 选型 | 为什么 |
| --- | --- | --- |
| 元数据 | SQLite（WAL） | 单文件、可备份、不需要额外服务 |
| 向量 | sqlite-vec，**按知识库分区** | 跨库不串味；分区也让删除是整表操作 |
| 全文 | FTS5 + jieba | 中文查询可用；RRF 与向量通道融合 |
| 表格副本 | DuckDB | 行文本进向量库，结构化副本另存一份供取数 |
| 解析 | 插件式 `ParserProvider` | 逐文件探测路由（文字型/扫描型/混合型） |
| 云端解析 | MinerU / PaddleOCR | 版面还原与 OCR；**凭据可选，没有也能跑通全链路** |

### 分层纪律（**会被 CI 拦**）

```
L1  app/api/ + app/mcp_server/   只做参数处理与转发，**不放业务逻辑**
L2  app/services/                只许 import storage/base.py（抽象接口）
L3  app/parsers/                 解析器之间**不许互相引用**
L4  app/storage/                 具体实现，只被组合根装配
T1  测试目录与 app/ 镜像同构
```

`scripts/check_layering.py` 会检查。**这不是形式主义**：
L2 不许 import 具体存储实现，是"换存储不用改业务代码"的唯一保证。

## 5. 必须遵守的纪律（这些不是建议）

### 5.1 环境与命令

1. **用 Git Bash，不要用 PowerShell 跑 shell 命令。**
   `C:\Program Files\Git\bin\bash.exe`。Git Bash 里有 `curl`/`node`/`python`/`git`，
   **没有 `jq`/`bc`**——解析 JSON 用 `node -e`。
2. **`uv` 与 `pnpm` 不在 bash 默认 PATH 上。**
   `corepack enable` 会失败（`EPERM: operation not permitted, open 'C:\Program Files\nodejs\pnpm'`，需要管理员）。
   可用方案：`$env:TEMP\kylab-shim` 里放一个 `pnpm.cmd`（内容是 `@corepack pnpm %*`），
   跑门禁前 `$env:PATH = "$env:TEMP\kylab-shim;$env:PATH"`。
3. **MinGW 下内联中文会被 bash 弄坏。**
   写带中文的 curl 请求体时：先 `printf '%s' '...' > /tmp/body` 再 `curl --data-binary @/tmp/body`。
4. **Windows 沙箱下 `pwsh` 用管道捕获子进程输出可能报 EPERM**。
   这是已知边界，不要绕，改用 `stdio: inherit` 或换别的写法。

## 6. 会反复踩的坑（血泪清单）

这些每一条都真的发生过，而且**症状都指向错误的地方**：

### 后端

- **`FileResponse` 需要路径**，不能塞 bytes——要返回内存内容用 `Response`。
- **`model_dump()` 入存储前要 `mode="json"`**，否则 `datetime` 会炸。
- **`_json(None)` 得到字符串 `"null"`**，不是 SQL NULL。
- **pymupdf：出了 `with` 块再读 `document.page_count` 会抛 `ValueError: document closed`**。
- **`RepeatedCode` / 辅助函数定义在 `if __name__ == "__main__":` 之后** →
  `python -m` 会 `NameError` 而 `import` 正常。有用例守着这条（AST 检查）。
- **UTC 与本地时区做日期分桶会错**。全项目时间戳统一 UTC 存储。
- **`INSERT` 遇到重跑会撞主键**。可重入的路径要用 `INSERT OR REPLACE`
  （子文件记录就是这么修的：id 由 `document_id + 段序号` 派生，**不能用随机值**——
  否则失败重跑会让界面上子文件树越跑越长）。
- **回退"用更严的限制判要不要做、又用它当参数"**：切分器的第一版把 `limit`
  既当"要不要切"的判据又当段长，于是 201 页被切成**一段 201 页**，
  提交上去照样超限，**等于没切**。判据与参数要分开。

### 前端

- **Vue 会静默跳过未 import 的组件**（渲染成未知元素，不报错）。
  而且 `innerText()` 对隐藏元素**照样返回文本**——所以探针可能"看起来通过"。
  两者合起来能骗过所有检查：`AppModal` 没 import 时弹窗根本不出现，但探针是绿的。
- **`<dialog>` 的 `display` 必须只写在 `[open]` 上**。
  给 `.modal` 直接写 `display: flex` 会让**未打开的弹窗也渲染出来**，
  而 DOM 查询 `dialog[open]` 数量是 0——只有看截图或量 rect 才发现。
- **`const x = someFunction` 绑的是函数不是 ref**（下拉框刷新后空的元凶）。
  要 `export const x = ref(...)`。
- **Vue 3 的 `ref([])` 里对象属性变更**：`items.value[i].status = x` 是响应式的，
  但要在 `map` 里造新对象时注意别丢响应性。

### 探针/测试（**这一类最误导人**）

- **Playwright 的 `addInitScript` 在同一 context 里会累积**——
  多场景要用**新的 context**。
- **`route` 的 glob 会连别的方法一起拦**。本次就吃过：
  拦 `**/api/v1/knowledge-bases/*/documents` 时把"列出文档"的 GET 也喂成了
  上传响应体，于是 `documents.value` 变成 `undefined`、页面当场抛错、
  弹窗根本打不开——**看着像弹窗坏了，实际是探针把数据打断了**。
  拦端点要连方法一起确认，非目标方法 `route.continue()`。
- **用固定 `sleep` 等界面 → 探针自己制造 flaky**。
  第一版上传弹窗探针报了两次假失败（"弹窗没开"、"按钮不可见"），
  人工复查 4/4 都正常。**等待一律改成显式条件轮询**。
- **测"按页切了"却喂假字节** → 测的其实是报错分支。
  夹具要真：切分用例第一版传 `b"x"`，7 个用例全在断言"打不开 PDF"。
- **断言写下标而不是按名字核对**：中间做过"移除再加回"，
  加回的文件排在末尾，位置和初始列表已经不一样，于是"顺序"全错。
- **测试太慢就没人跑**：切分用例第一版造 1200 页真 PDF，整套 23 秒。
  改成每段 6 页后 **2 秒**——要验的是"切了几段、顺序对不对"，与每段多长无关。

### 教训的共同点

上面标"探针/测试"的那些，**症状全都指向应用代码，实际是测试自己错了**。
所以：**测试红了先怀疑测试**。特别是"失败得很整齐"（7 个一起红）的时候，
几乎一定是夹具而不是实现。

## 8. 与用户协作的方式

这位用户的要求很具体，值得先读一遍：

- **对页面美观程度十分看重**。每个界面改动后要**截图判断**，
  并与主流开源项目（RAGFlow / MaxKB / Dify）比对找差距、努力克服。
  本次做上传弹窗时就对照 MaxKB 的文档补了格式清单与大小/数量上限。
- **每个模块完成后要做该模块的 review，然后提交，再做下一个**。
  review **只 review 这个模块**，不用全量。
- **参考开源项目的成熟实现**（ragflow / wekaora / maxkb / dify），
  不要闭门造车。
- **大模型 API**：DeepSeek 的 key 只在本机 SQLite 的 `app_settings` 里
  （`base_url=https://api.deepseek.com`、`model_id=deepseek-chat`），
  **不在任何入库文件里**（`git grep sk-` 是干净的）。要用自己去设置页配。
- **持续开发，不要偷懒**。做完一个做下一个。

### 沟通上的两个偏好

1. **说清楚"为什么"**：本项目所有非显然的决定都在代码注释与计划 §12.x 里
   写了理由。写代码时请保持这个习惯——**注释要解释"为什么"，
   而不是复述"做了什么"**。
2. **诚实**：做不到的、没验证的，明确标出来（比如 `deploy/` 那份文档里
   如实写着"未验证"）。**文档撒谎比没有文档更糟**——
   这是外部监测报告连着几轮提的意见，也是这个项目最在意的东西。
