> 移进 `归档/`，并在它的文件头标注了取代关系）。

## 1. 定位与目标

### 1.1 唯一目标【已定】

**干正事的时候，用户不用复述大的背景。**

场景是工作场景：写论文、做 PPT、写报告、做调研。这些活都有同一段前期成本——
每次开口都要先说一遍"我这个项目是什么、给谁看、有什么约束、我习惯怎么看东西"。
档案就是替用户省掉这段复述的那份东西。

所以档案**不是**"记住我们聊过什么"，而是**用户画像**三件事：

- **用户是谁**：称呼、角色、语言、所在环境；
- **用户长期在意什么**：偏好、**雷点**（否定式偏好）、正在推进的项目及其目标与约束、
  已经定下的决定与理由；
- **用户手上有什么**：工具、机器、路径、常用链路。

判据落在"**下次对话仍然成立**"这条线上：一次性的任务细节、今天的进展、临时的分工，
一律不进档案。**明确不要"鸡毛蒜皮都记"**——档案每轮进上下文，写进去的每一条都在
向未来每一次对话收税。

### 1.2 为什么是"重新设计"而不是"精简"

这一点要先说清，否则后面的取舍会被读成"砍功能省 token"。

旧架构的对象是**流水**：捕获把对话变成 `daily/` 的现场，整理把现场归并成 `digest/`
的长期知识，召回从这两层里按需取片段。它回答的问题是"这件事以前是怎么说的"。

新架构的对象是**档案**：一份固定分区的画像，全量注入，冲突即顶替。它回答的问题是
"这个人是谁、他在做什么、他要什么"。

三个维度同时换了，所以不是同一个东西变小：

| | 流水制（旧） | 档案制（新） |
| --- | --- | --- |
| 对象 | 多份按时间与主题分散的文件 | **一份**四区档案 |
| 量级 | 几份到几百份、几百 KB | 几十条、**几千字** |
| 生长方式 | 定期捕获、事后整理、只增不并 | **三条写入路**，冲突即顶替 |
| 生效方式 | 注入（核心文件）+ 召回（流水文件） | **全量注入**；召回降级为查证 |
| 时间轴 | `daily/` 就是时间轴 | 档案**没有时间轴**，历史在变更流里 |
| 主要失败模式 | 越攒越多、越召越偏 | 写得太满、把噪音当画像 |

**"没有时间轴"是这次换对象的核心**：档案只描述**现在成立的**画像。一条偏好改了，
档案里就必须只剩新的那一条——这正是 §3.4 的替换语义。旧设计的"结论可变、现场不可变"
解决的是同一件事，但代价是两套文件与一个整理动作；档案制直接把"现场"这一层去掉。

会话历史**不是**记忆：想找回"上次那段原文"，那是会话记录的事（会话落本机已经在做）。
把会话塞进记忆，得到的是"记得很多、但画像很脏"，正好背离 §1.1。

### 1.3 不做什么：显式退场的概念【已定】

下面这些是旧架构的构件。写在这里是为了让"退场"是一次有据可查的决定，而不是
下一轮实现时被顺手留下来：

| 退场 | 它原先服务什么 | 现在的处置 |
| --- | --- | --- |
| `daily/` 会话现场、当天索引页 | 捕获的落点，只增不并 | 不再写入、不再注入、不再召回；历史文件保留在磁盘上 |
| `digest/{personal,procedure,wiki}` | 整理产出的长期知识（三桶） | 同上；内容在迁移时折叠进档案（§8） |
| Auto-Dream / `dream` 四动作 | 把现场归并成长期知识 | 整条机制退场：档案不需要跨时间整理，它只有"这个值对不对" |
| wikilink 图谱、Auto-Link 补链 | 记忆之间的关联 | 退场。**一条条目与另一条条目的"关系"如果重要，就该写成一句话进档案** |
| 图谱界面、`GET /memory/graph` | 看结构 | 下线（§6.3） |
| 定时 / 节流捕获（每 5 回合） | 自动沉淀 | 换成 §4.1 的信号触发；默认关 |
| 向量那一路（本地小索引 + RRF） | 同义召回 | 退场：它服务的召回池（流水）也没有了 |
| BM25 + jieba 分块 + markdown-it AST 分块 | 在几百 KB 里排准序 | 退场：档案几十条，排序用的判据退回到纯字面（§5.3） |
| `MEMORY.md`「核心长期记忆」一节 | `remember` 的落点 | 内容折叠进档案；文件退场（§7.2） |
| 记忆页的"文件 / 图谱 / 召回"三分段 | 浏览结构 | 换成档案卡 + 变更流（§6） |
| "待整合 / 已整合"标记 | 表示现场有没有被整理 | 退场：没有整理这一步了 |

两条**不退场**、且本文不动的东西：**两池红线**（§7.1）与 **`SOUL.md`/`AGENTS.md`
的只读现状**（§7.2）。

## 2. 调研与依据

### 2.1 开源社区：没有哪一个比自己写更轻

2026-10-03 把 mem0、Graphiti、Letta、cognee、Memobase、MemOS、memU、EverOS 等
二十余个项目逐个核过**活跃度与依赖面**（不是读 README 的自我描述）。结论只有一句：

**没有一个比我们自研更轻。** 理由集中在两条，两条都跟我们的硬约束（§2.3）正面对撞：

1. **语义层基本都要 embeddings**。它们把"记住"建模成向量 + 图 + 分层摘要，
   于是 numpy/lancedb/onnx 之类必然进依赖树。而我们的判据是"闭包不许涨"，
   任何模块级引入这类包的方案直接出局；
2. **服务形态基本都带第二个进程**（自带 HTTP/MCP 服务端）。这正是 v0.46 明确否掉的
   形态——记忆是本地的一路读写，没有第二个进程可连。

唯一一个**纯画像型**（不做向量、不做图，就是一份 profile）的是 **Memobase**，
而它已经停更约九个月。也就是说：**我们想要的那种东西，社区里没有现成且健康的**。

这条结论只影响一件事：不要把"接入某个开源记忆框架"当成备选方案（旧设计里 ReMe
那一轮已经走过一次，代价与结论见《记忆层设计 v0.1》§3.5.1）。逐项目核实的原始清单
按 §2.3 应落 `归档/调研/`，本篇只留结论。

### 2.2 标杆 Kimi 记忆的五条抽象

五条都是对 Kimi 记忆功能核对/实测之后抽出来的模型，本文逐条给了我们的落地位置——
抄的是**模型**，不是它的界面：

| # | Kimi 的做法 | 我们的落地 |
| --- | --- | --- |
| 1 | **硬预算**：≤ 50 条、每条 ≤ 500 字符，两个上限都在 | §3.3：条数 + 字数双硬顶，超顶不允许追加 |
| 2 | 写入判据是**画像双问**（用户是谁 / 在意什么），且由**专门模型**判定 | §4.2 判据 + 可绑定的捕获模型（`memory.capture_model`） |
| 3 | 显式「记住」是**一等公民**，且与自动记忆**共用同一份清单** | §4.1 三条路写的是同一份档案，不是两套存储 |
| 4 | **注入而非召回** | §5.1 档案全量进 system prompt；§5.3 recall 降级为查证 |
| 5 | **更新 = 替换**；隐私默认不记、用户可控 | §3.4 替换与变更流；§4.5 敏感信息否决项；§7.3 开关 |

第 3 条最容易被忽略、但对我们最关键：如果显式「记住」写进 `MEMORY.md`、自动捕获写进
`daily/`，用户就会面对**两份清单**，而且只有其中一份每轮生效。档案制把这条路堵死——
只有一个对象、一个预算、一个界面。

### 2.3 硬约束：闭包不许涨

《[客户端运行时 打包规格 v0.1](../规范/客户端运行时-打包规格-v0.1.md)》§3 定了口径：
**判据是 `scripts/sidecar-closure.py` 的实测输出**，不是"看代码觉得该有/不该有"。
本篇写作时复跑（`cd backend && .venv/Scripts/python.exe ../scripts/sidecar-closure.py --json`，
venv 在 `backend/.venv`）：

```
dists: 17 个发行包      count: 22 个顶层模块
```

**这两个数不许涨。** 由它推出的三条设计纪律，本文每条机制都必须满足：

1. **自研、进程内**：没有第二个进程、没有服务地址、没有连通性可查；
2. **纯文件**：档案与变更流都是工作区里的普通 Markdown，读写用标准库；
3. **零强制新包**：解析只用字符串与正则——连 `markdown-it-py` 都不必碰（它在旧实现里
   是惰性导入的，本来就不在闭包里；档案是固定分区 + `- ` 条目，按行解析足够）。

向量、图、嵌入、以及任何"聪明的相似度"都不在这条线上，所以 §3.4 的判据只能做成
**机械的字面判据**（可用 `re` 与 `difflib` 之类的标准库）。

## 3. 数据模型：一份档案

### 3.1 分区：四个，固定【已定】

| 分区 | 装什么 | 例 |
| --- | --- | --- |
| **身份与称呼** | 用户是谁：称呼、代词、语言、角色、所在团队或单位 | 用户叫小又，称呼「小又」；中文沟通。 |
| **长期偏好与风格** | 输出风格与格式习惯，**含否定式偏好（雷点）** | 用户要求先给结论再列依据；用户不看客套话与"好问题"式开场。 |
| **进行中的项目** | 每件正事一组：目标、背景约束、关键决定（含理由）、产出规范 | 见下 |
| **工具与环境** | 机器、系统、路径、常用工具链（**不含凭据**） | 用户的内网有一台 Windows Server 2019 配一张 L20，用来跑模型。 |

三条关于分区的约定：

1. **分区清单是固定的**。条目不能新开分区：新开就等于给"流水"留了个后门，而每轮注入
   的成本会随分区数无上限地长。**一条东西如果放不进这四区，多半本来就不属于档案**
   （长文写进 `AGENTS.md`，资料写进知识库，一次性的进笔记）；【建议】未知分区不报错，
   但计入预算并在界面上标"分区不认识"（§3.5 第 4 条）。
2. **进行中的项目**用 `### <项目名>` 分组，组内是条目行。这是"每件正事一段"的字面落点，
   也是"不复述大背景"最直接受益的一区。项目组标题本身也是可顶替的对象（改名 = 一次顶替，
   旧名进变更流）。
3. **否定式偏好优先级更高**：雷点排在偏好区靠前的位置，且**同一主题下"不要什么"与
   "要什么"同时存在时，两条都留**——它们说的是两件事（"不要客套"≠"要简短"）。

### 3.2 条目形态【已定】

每条**一句话**，四条硬性写法：

- **主语是用户**，不是助手、不是"我们"。写"用户要求先给结论"，不写"我会先给结论"；
- **自足**：单看这一条就能懂，不出现"这个""那个""上次那个"这类依赖上下文的指代；
- **不带时间戳**：档案没有时间轴（§1.2）。时间信息属于变更流，不属于档案；
- **不写"用户说"**这类外框：档案整体就是"用户说过的"，加外框是噪音。

### 3.3 预算：条数与字数双硬顶【已定：必须有硬顶；数值【建议】】

| 项 | 建议值 | 一句理由 | |
| --- | --- | --- | --- |
| 单条字符上限 | **120 字** | 一句话说清不了一件事，说明它该被拆成两条或降级成 `AGENTS.md` 里的一段 | 可调 |
| 全档案条数上限 | **60 条** | 挡"碎"：把 20 个项目各写 5 条碎事实，加起来的注入成本与 3 个项目写清目标一样贵，但换来的判断力差得多 | 可调 |
| 全档案字数上限 | **4000 字** | 挡"长"：这是每轮固定的上下文成本，需要一个定价；按中文 1 字≈1 token 粗估是 3–4k token 一档 | 可调 |
| 每区条数 | 身份 10 / 偏好 20 / 项目 8 组（每组 8 条）/ 工具 12 | 分区的软约束，防止某一区吃光全局预算 | 可调 |
| 注入硬顶 | **6000 字** | 兜住"用户在外部编辑器里把档案改超了"这一态（§5.2） | 可调 |

两个全局上限是**互补**的：条数挡"碎"，字数挡"长"，先到的那一个生效。Kimi 是
50 条 × 500 字符，我们是 60 条 × 120 字——**条数接近、单条更严**，因为中文一句话的
信息密度更高，而 500 字符的条目在注入模型里更像"一小段散文"，那正是档案要避免的形状。

**超限时的行为**（这条是设计的一部分，不是错误处理）：

- **不允许追加**：越线的写请求被**拒绝**，档案文件逐字节不变；
- **允许顶替**：判据是**净额**（新条目字符数 − 被顶替条目字符数），净增为正且会越线时
  同样拒绝；
- **回执必须给两条出路**："这一区满了。要我先删一条，还是顶替某一条？"——拒绝而不给
  出路，模型会反复重试同一条（§4.4）。

### 3.4 替换与变更流【已定】

**冲突即顶替**，旧值**不删除**，进"变更流"（changelog）。变更流**不参与注入**，
只服务三件事：界面上看得见"改过什么"、用户可以一键还原、recall 能回答"这条以前是什么"。

为什么旧值不直接删（这决定了整套判据的松紧）：

> 判错"这两条是同一件事"的代价，从**静默丢掉一条真事实**降级为**一次看得见、可还原的顶替**。

这是相比旧设计的一个实质改进：旧口径里"像就跳过"（`_similar` → dedupe），判错的代价是
一条真事实永远进不了记忆；现在判错的代价是变更流里多一条记录 + 界面上一次点击。
【建议】所以机械判据可以比旧设计**更敢顶替**（§4.3），但"数字不同就不是同一件事"
这条否决必须保留。

**变更流的记录形态**（`changes.md`，末尾追加，界面倒序显示）：

```markdown
- 2026-10-03 14:22 · 顶替 · 长期偏好与风格 · 来源：显式
  - 旧：用户要求回答简短。
  - 新：用户要求回答先给结论、再列依据，不写客套话。
```

两处刻意的写法：

1. **旧值与新值各占一行**，不用分隔符拼成一行。还原要的是**逐字节的旧文本**，
   而条目正文里完全可能出现任何标点——拼行就还原不回去了；
2. **动作只有五种**：`新增 / 顶替 / 忘掉 / 还原 / 撤回`（"撤回"= 一次被拒绝的写入，
   也记一条，因为它解释了"我说过要记住，怎么没记上"）。

【建议】变更流保留**最近 300 条**，超出从最旧开始丢。它服务的是近因问题（"我刚改了什么"），
不是审计日志；而它是备份与同步的一部分，不该无上限地长。**可调。**

### 3.5 落点与格式【建议】

档案与变更流都住在既有的记忆工作区里（`data/memory/<user_id>/`，按账号分桶不变）：

```
data/memory/<user_id>/
├── SOUL.md          # 人格（只读，不变）
├── PROFILE.md       # ← 档案（四个固定分区）
├── AGENTS.md        # 规程（只读，不变）
├── changes.md       # 变更流（不入注入）
└── import-draft.md  # 迁移时没挤进档案的旧条目（§8，只在迁移后存在）
```

档案文件形态（**四区顺序固定**，注入时按这个顺序）：

```markdown
---
updated: 2026-10-03
---

# 用户档案

## 身份与称呼

- 用户叫小又，称呼「小又」即可。

## 长期偏好与风格

- 用户要求回答先给结论，再列依据。
- 用户不看客套话，不要用「好问题」这类开场。

## 进行中的项目

### 内网知识库部署

- 用户的目标是把知识库与 Agent 都放在内网，不出公网。
- 用户已决定用 PostgreSQL + pgvector，理由是元数据与向量要同库查。

## 工具与环境

- 用户的内网有一台 Windows Server 2019 配一张 L20，用来跑模型。
```

四条格式决定：

1. **frontmatter 只放 `updated`**（整份最后写入时间）。它给界面与备份用，不进注入块；
2. **条目不携带显式 id**。内部标识用 `(分区, 归一化文本)` 的短哈希，**只用于变更流记账**，
   不写进正文，也没有跨编辑的稳定性承诺——档案是用户会拿别的编辑器改的普通 Markdown，
   往正文里塞 id 会把每一条都弄脏；
3. **写文件要写字节**（`write_bytes`），不用 `Path.write_text`：Windows 上会把 `\n`
   翻成 `\r\n`，已有 `\r\n` 时每存一次长一个 `\r`。这条是旧设计踩过的实测坑，继续有效；
4. **文件级白名单不变，文件内分区不静默丢**。`memory_files.CORE_FILES` 那套"只有白名单
   里的文件能进系统提示词"照旧；但**档案文件内部**出现不认识的 `## 某区` 时，正文**照注入**
   （计入预算，界面标"分区不认识"）——用户写在自己档案里的东西被静默丢掉，比多花几十个
   token 糟糕得多，而 §3.3 的字数硬顶已经兜住了无上限增长。

**代码落点**【建议】：新增 `app/services/archive.py`（分区、条目、预算、顶替与变更流）
与 `app/services/archive_files.py`（解析与写字节，按行、无第三方依赖）；
`app/services/memory.py` 收薄成门面（开关、注入块、工具接线），
`memory_files.py` 里的检索/图谱/整理部分在期五删除。

## 4. 写入路径

### 4.1 三条路【已定】

| 路 | 触发 | 模型调用 | 判据 | 默认 |
| --- | --- | --- | --- | --- |
| ① 显式 | 用户说「记住 / 忘掉 / 更正」，或模型调工具 | **零额外**（就在当轮工具循环里） | 用户说了算；只做 §4.3 的机械定位 | **开** |
| ② 项目级信号 | 新项目 / 重大背景 / 长期约束 / 明确偏好或纠正 | **一次**（唯一的自动调用点） | §4.2 画像双问 | **关**【建议】 |
| ③ 界面直改 | 用户在档案卡上改一条 | 零 | 人自己改，算数 | **开** |

三条路**写的是同一份档案、走同一个服务、受同一套预算**（Kimi 第 3 条）。区别只在
"谁判定"和"花不花钱"。

**① 显式是一等公民**，四条具体化：

- **零额外调用**：判定与写入都是机械的（定位目标条目 + 预算检查 + 落盘 + 变更流），
  模型的那一轮输出本来就在发生；
- **共用同一预算**：显式「记住」**不豁免**上限。豁免一次，档案就会在每个"就这一条"里长胖；
- **回执先说**：写成功、写不进、已存在，三种都要回一句（§4.4）；
- **更正一次完成**：模型可以带 `replaces` 指认要顶替的那条，于是"不是 A，是 B"是**一次**
  工具调用，而不是"先删再记"两次。

**② 项目级信号触发**（不是定时轮询）——这一路是"隐式"的全部实现，四个信号：

| 信号 | 例 | 落区 |
| --- | --- | --- |
| 新项目出现 | "我最近在做一个 XX" | 进行中的项目（新建一组） |
| 重大背景 / 长期约束 | "这个必须过等保三级""交付时间定在 11 月" | 项目组 / 工具与环境 |
| 明确偏好或纠正 | "以后都先给结论""别给我列那么多选项" | 长期偏好与风格 |
| 关键决定 | "已经定了用 A 不用 B，因为…" | 项目组 |

**它不是定时器**：旧设计的"每 5 个用户回合判一次"退场（它花的是固定节奏的钱，
换来的是一堆"值得记但不该进档案"的东西）。这里只在**信号出现的那一轮**判定，
"宁可漏不可滥"是明确取向——漏一条，用户下次张口说一句「记住」即可；滥一条，
每轮都在付它的上下文成本，而且用户很难发现。

**默认关**【建议】，三条理由：

1. 它是这条链路上**唯一会自动花钱**的地方，与本项目「凡是会花钱的都默认关」
   这条口径一致（旧设计里捕获与向量各自的默认值就是这么定的）；
2. 默认关之后，"**默认配置下每轮零额外模型调用**"这条判据才成立（§9.2）——
   档案制的目标不靠它也能达成（显式 + 界面两条路是完整的，不是降级）；
3. 产品的画像本来就是"少的、稳的"：开着一开始就自动写，最容易写进一堆噪音。

打开之后再加一道**零成本的机械前置筛**【建议】：只有用户消息里出现强信号词
（"记住""以后""下次都""每次都""别""不要""我们的项目""目标是""必须是""已决定"
"不用…了"）时，才发起那一次判定。词表必然脆，但它的代价只是**漏**（下次用户说
「记住」就补上了），方向与"宁可漏不可滥"一致。**这是全篇唯一一处词表，也是最该被
真实使用推翻的一处**（§10 第 5 条）。

**③ 界面直改**：档案卡上的每一次编辑都是一次"顶替"（旧值进变更流），走的是同一个
服务。**不提供整份覆盖入口**——那等于给预算与变更流开后门。用户仍可用外部编辑器改
磁盘上那份 Markdown（这是"记忆是普通文件"这条承诺的一部分），改完由读侧校验并如实报告
（§3.5 第 4 条、§5.2）。

### 4.2 判据：画像双问【已定】

对候选条目问两句话，**两问皆否就不写**：

1. **这句说的是"用户是谁"吗？**（称呼、角色、语言、环境、拥有什么）
2. **这句说的是"用户长期在意什么"吗？**（偏好、雷点、项目目标与约束、已定的决定与理由、
   产出规范）

再加三条**否决项**（不是第三问，是否决）：

- **下次对话仍成立**吗？只对今天有效的，不写；
- **是用户说的**吗？模型推断出来的一律不写；
- **不含敏感信息**吗？密码、令牌、密钥、证件号、私密标识——**绝不写**，哪怕用户直接
  粘贴过来（这条原先是 `MEMORY.md` 模板里的一句约定，现在更重：档案每轮进上下文）。

**裁决规则：拿不准就不写。** 判据要的不是召回率，是精确率。

**由专门模型判定**【已定】——落成配置项 `memory.capture_model`【建议】：
**默认留空 = 用运行期配置里绑定给「对话生成」的那个模型**（记忆是对话的副产品，
没理由另配一个必须存在的模型），允许绑一个更便宜的模型来做判定。默认留空的理由：
不引入新的必填配置，也不引入"没配记忆模型 → 记忆功能不可用"这种半死状态。

### 4.3 机械判据：新增还是顶替【建议】

在**同一份档案**的范围内（跨分区也要查，见第 5 条）：

| 情况 | 动作 |
| --- | --- |
| 归一化后完全一致（去空白、统一全角半角标点） | **不写**，回执"档案里已经有了" |
| 包含关系且**数字集合相同**，差值 ≤ 6 字 | **顶替**（留下更完整的那一条） |
| 字符二元组重合度 ≥ 0.7 且**数字集合相同** | **顶替** |
| **数字不同**（版本号、地址、数量、日期） | **不顶替**：是另一件事 |
| 其余 | **新增** |

这套判据与阈值直接沿用旧设计（`_similar` / `DUP_SIMILARITY = 0.7` /
`CONTAINMENT_SLACK = 6` / `_DIGIT_RUN`），**动作从"跳过"改成"顶替"**。两条本地约束：

1. **模型可以在同一次调用里直接给出顶替目标**（它看得到整份档案，只有几十条）。
   模型的显式判定优先于机械判据，机械判据是兜底；
2. **跨分区也查**：同一句话不能同时出现在两个分区。跨分区命中时顶替，并把条目归到
   新分区（这条治的是"偏好从项目段漂到偏好段"这类迁移）。

【建议】机械判据**比旧设计敢顶替**的边界就在这里：旧设计"像就跳过"是因为判错的代价
是丢掉真事实；现在判错的代价是变更流里的一条 + 界面上一次点击（§3.4）。但"数字不同
不顶替"这条**一个字都不放松**——它是唯一能机械区分"同一个东西"与"两个东西"的证据。

### 4.4 显式回执【已定】

每一次写入都要有一句回执，**三条路共用同一份文案来源**（否则模型从工具听到的与人在
界面上看到的会是两种说法——旧设计里 `RECALL_NOTE` 那条纪律继续有效）。四种形态：

| 结果 | 回执 |
| --- | --- |
| 新增 | 「记下了：……」（来自档案的那一条原文，不是改写过的转述） |
| 顶替 | 「改成：……（旧的已留档，可还原）」 |
| 已存在 | 「档案里已经有了：……」 |
| 被拒（超预算） | 「这一区满了（20/20 条）。要我删一条，还是顶替哪一条？」 |

两条纪律：

- **回执不能只说"好"**：没有回执，用户无法判断"我说了记住，到底记没记"——而事后
  发现没记的成本，比当时多一句话高得多；
- **被拒时不要重试**：给模型的指引里要写死这条。反复重试同一条超限写入，既写不进，
  又会占掉工具循环的轮次。

### 4.5 什么进不了档案

- 一次性的任务细节（"帮我把这段改短一点"）；
- 模型推断出来的（"他大概偏好简洁"）——**只能写用户说过的**；
- 敏感信息：密码、令牌、密钥、证件号、私密标识（否决项，§4.2）；
- 文献里的事实——那是知识库（两池红线，§7.1）；
- 超过单条上限的长内容——写进笔记或 `AGENTS.md`，档案只装一句话；
- 有保质期的状态（"今天在改 X"）。**例外**：如果它是一条长期约束（"这个项目 11 月交付"），
  那它进的是项目段，不是流水。

## 5. 注入与召回

### 5.1 注入【已定】

**档案全量进 system prompt，不挑选、不摘要、不排序。**

- **位置**：挂在人设那一档（`prompt.py` 的 `PRIORITY_PERSONA`，与 `SOUL.md`/`AGENTS.md`
  同一档）——它与那两份是同一类东西：每轮都该在场的设定。但它是**独立的一个贡献者**：
  自己的配置项（`memory.enabled`）、自己的开关语义，不与人设共用一份配置（§7.2）；
- **形态**：**原文照进**（分区标题 + 条目行），前面加一句极短的边界说明：
  "以下是用户档案：说的是用户是谁、他在意什么，不是文献依据；与当前问题无关时不要
  主动提它。"——旧设计的 `MEMORY_GUIDANCE` 正是干这件事的，继续保留并改写；
- **不挑选**是这条设计的要点：挑选会引入一个"这一轮该看哪几条"的判定，那既费模型，
  又让用户无法预测助手到底知道什么。档案小到可以全给，就把"挑选"这件事直接取消。

**首次引导保留**（`bootstrap_block` / `profile_is_untouched`）：它就是档案的初稿入口，
而且**正好问的就是档案的三区内容**——怎么称呼（身份与称呼）、最近在忙什么（进行中的项目）、
希望怎么说话（长期偏好与风格）。三件事问完，用户答完，档案就有了第一版；
引导块在档案非空之后自己消失，这条闭环不变。

### 5.2 预算与截断【建议】

- 注入块的硬顶是 **6000 字**（§3.3）。**正常路径下永远碰不到它**——写入侧在 4000 字就
  开始拒绝了；它只兜一种情况：用户在外部编辑器里把档案改超了；
- **截断必须在提示词里说出来**："（档案超出上限，以下为前 N 条；请到记忆页整理）"。
  静默截断是不可接受的：用户会以为助手看到了整份档案；
- 正常态下**不截断**：多花 token 好过"我写了它没看到"；
- 界面顶部常驻一条读数（`32/60 条 · 1840/4000 字`），接近上限时变色——预算**必须可见**，
  否则"写不进去"会变成一次莫名的失败。

### 5.3 recall 的新定位【已定：保留但降级】

**保留工具，语义降级为"查证"。** 具体三件事：

1. **档案本身不进召回池**——它已经全量注入，再召回一次就是把同一段内容进两次上下文
   （旧设计里"核心文件不进召回池"那条口径继续成立）；
2. **池子只剩变更流**（默认口径下），所以 recall 回答的是：**"这条以前是什么、什么时候改的"**。
   这正是"上次那个"最常指的两种意思里的第一种，而且它是零新增机制——变更流本来就要读；
3. **若采纳 §10 第 3 条的"项目段按活跃会话裁剪"**，recall 顺带承担"把没注入的项目段找回来"。
   【建议】先不裁（§10），所以现在不用为这条留复杂度。

**"上次那个方案"里那些内容在哪**：在会话历史、笔记、知识库里——不在记忆里。把它们并进
recall，等于把"记忆"变成"历史对话检索"，那是另一个池子、另一套索引（也违背 §2.3），
本文不做。

**实现口径**：档案与变更流都是几十条到几百条，排序用**纯字面判据**就够——归一化子串
命中数 + 二元组覆盖率（不依赖分词，`jieba` 本来就不在闭包里）。**不上 BM25、不上 AST 分块、
不建索引**：旧实现的那一整套是为几百 KB 的流水文件准备的，池子变小之后它是纯粹的复杂度。
"没搜到"仍然只有一个含义：这两份文件里确实没有相关的话（这条性质比排序精度更重要）。

## 6. 界面

### 6.1 档案卡（主视图）【已定方向 + 建议细节】

记忆页从"文件 / 图谱 / 召回"三分段换成**一页两块**：档案卡 + 变更流。

档案卡：

- **四个分区纵向排列**，顺序与注入顺序一致（用户看到的顺序 = 模型看到的顺序）；
- **每区标题右侧是读数**（`7/20 条 · 320/800 字`），顶部一条全局读数
  （`32/60 条 · 1840/4000 字`），接近上限变色；
- **条目行内编辑**：点一下变 `textarea`，失焦保存 = 一次顶替，旧值自动进变更流；
- **行尾两个动作**：删除（= 忘掉）、加一条（分区底部）；
- **项目段分组显示**，组标题可改名、可折叠；
- 【建议】每条行尾一个**来源小字**（"来自会话 …" / "你在这里改的"），点击跳到变更流
  对应记录——它让"这条是什么时候来的"可见，而这是"它到底对不对"最便宜的线索；
- 右下角一个**「原文」**链接：只读展示这份 Markdown 的全文与它在磁盘上的路径。
  保留它不是为了让用户在这里编辑（编辑在卡片里），而是让"记忆是磁盘上一份普通
  Markdown、可备份可迁移"这件事仍然看得见。

**不出现实现细节**（`check_layering.py` 的 U2 规则）：不解释分区是干什么的、不说
"档案会被注入提示词"、不显示 token 数——**只给读数与事实**（条数、字数、路径、时间）。

**开关关着时**：档案卡与变更流照旧可用（编辑不依赖开关，旧纪律"关了也能改自己的东西"
保留），只有**注入与 recall** 停下（§7.3）。

### 6.2 变更流【已定方向 + 建议细节】

倒序时间线，每条记录显示：**时间 · 动作 · 分区 · 旧值 → 新值 · 来源**（显式 / 隐式 / 界面）。
每条带一个**「还原」**：把旧值写回档案，新值作为一次新的顶替进流。

还原存在的理由是 §3.4 那条代价分析——顶替判错只值一次点击，那这个点击必须在手边。
【建议】变更流的每一条都**不可编辑、不可删除**（它是记录，不是第二个可写清单）；
超出保留条数时从最旧开始丢。

### 6.3 下线的东西

文件列表与整份文件的编辑（`PUT`/`DELETE /memory/files/{path}`）、图谱页
（`MemoryGraph.tsx` / `GET /memory/graph`）、召回试验框、"待整合 / 已整合"标记、
新建记忆文件。文件级写入端点**必须删**——留在那里就是一个绕过预算与变更流的后门；
只读的 `GET /memory/files/{path}` 保留，供"原文"视图与迁移草稿查看。

## 7. 与既有系统的关系

### 7.1 两池红线不动【已定】

记忆与文档知识库仍然是**两个池子**，绝不混检索（旧设计 §2.1 原样有效）：

| | 记忆（档案 / recall） | 文档知识库（search） |
| --- | --- | --- |
| 谁说的 | **你说的** | 文献说的 |
| 出处 | 无（来源是某次对话） | 有（文档、页码、章节） |
| 可变性 | 高频顶替、用户随时改 | 低频、不改 |
| 检索口径 | 找回"我知道什么" | 找回"原文怎么写的" |

档案制让这条红线更硬：档案住在工作区的普通文件里，**不 import 检索服务、不碰
pgvector、不建任何索引**。盯这条红线的用例继续保留
（`test_recall_never_returns_document_pool_content`）。

### 7.2 人设文件【已定：`SOUL.md`/`AGENTS.md` 不动；`PROFILE.md`/`MEMORY.md` 的处置见 §10】

- **`SOUL.md`（人格）与 `AGENTS.md`（规程）**：只读现状不动——Agent 不能自己改写，
  用户想改自己动手或让 Agent 起草（v0.52 口径）。它们每轮整份进 system prompt，
  **与记忆开关无关**，本文一个字不改；
- **`PROFILE.md`**：【建议】**它就是档案**。三条理由：名字本来就对（profile = 画像）；
  它已经是"每轮注入 + 不进检索"的那一份；首次引导的 `profile_is_untouched()` 判的
  正是"档案还没写"。它的正文从散文改成四区条目，迁移时把现有散文折叠进「身份与称呼」。
  它的注入由 `memory.enabled` 管，**不进 `memory.persona_files` 那一项**——那一项只管
  人设的取舍与顺序，而把档案也挂上去的后果是：用户从那一行里删掉一个文件名，
  档案就静默停止注入；
- **`MEMORY.md`**：【建议】**退场**。内容是"已知的事实"，正是画像的另一半，迁移时折叠
  进档案；文件留在磁盘上（用户数据不删），只是不再注入、不再写入、也不再出现在
  人设配置里。界面上它显示为"旧记忆（只读）"，供用户自己确认折叠结果。
  **替代方案与确认项见 §10 第 2 条。**
- **想每轮都在的长文本写哪里**：写 `AGENTS.md`。那是"这类活怎么干"的正当落点，
  档案只装一句话条目——这条边界要说给用户听，否则他们会在档案里写小作文。

### 7.3 开关与配置项（旧 → 新）【建议】

**基调：默认全程零额外模型调用。** 默认配置下，档案的注入、显式写入、界面编辑、
recall 全部不产生任何额外的模型调用——花的只有"档案进了这一轮上下文"的固定 token。
唯一会自动花钱的是隐式捕获，而它默认关。

| 配置项 | 旧 | 新 | 说明 |
| --- | --- | --- | --- |
| `memory.enabled` | bool，默认 **false** | bool，默认 **true**（§10 第 4 条） | 管**档案注入与 recall**；档案编辑与文件读写不看它；`SOUL.md`/`AGENTS.md` 的注入也不看它 |
| `memory.capture` | —（旧为 `capture_every`） | bool，默认 **false** | 隐式捕获总开关，唯一的自动模型调用点 |
| `memory.capture_model` | — | 空 = 用对话模型 | §4.2 的判据模型绑定 |
| `memory.capture_every` | 5（每 5 个用户回合） | **删** | 定时轮询退场 |
| `memory.dream_after_hours` | 0（不整理） | **删** | 整理退场 |
| `memory.vector_enabled` / `memory.vector_min_score` | false / 0.45 | **删** | 向量那一路退场 |
| `memory.persona_files` | `SOUL,PROFILE,AGENTS,MEMORY` | `SOUL.md,AGENTS.md` | 只管两份人设的取舍与顺序；档案（`PROFILE.md`）不挂在这里（§7.2） |
| `memory.workspace` | 工作区目录 | 不变 | 按账号分桶不变 |

`memory.enabled` 从 false 改 true 是**行为变更**，理由与确认项见 §10 第 4 条：
旧设计默认关，是因为打开它会启动定期捕获（会花钱）；档案制把那一项拆成独立开关之后，
"默认关"就成了"这个功能默认不存在"。

### 7.4 工具面（旧 → 新）【建议】

| 工具 | 处置 | 说明 |
| --- | --- | --- |
| `recall(query)` | **保留**，池子改为变更流（§5.3） | 语义从"召回记忆"降级为"查证以前那条" |
| `remember(content, replaces?)` | **保留**，语义改为"新增或顶替" | `replaces` 让"更正"一次调用完成 |
| `forget(topic)` | **新增** | 定位并删除，变更流留痕、可还原 |
| `read_memory()` | 保留 | 读全档案，供模型自查它写进去的是什么 |
| `write_memory(...)` | **退场** | 整份覆盖与条目级预算/变更流不相容；`SOUL.md`/`AGENTS.md` 的只读现状不变 |
| REST `POST /memory/remember` | 保留，返回体加 `action` 与 `receipt` | `added` / `replaced` / `existing` / `rejected` |
| REST `PUT`/`DELETE /memory/files/{path}` | **删** | §6.3：绕过预算与变更流的后门 |
| REST `GET /memory/graph` | **删** | 图谱退场 |

`skills/kylab-memory/SKILL.md` 那段指引需要在期五改写：它现在教模型"新旧两条都会留着，
让用户自己删"（与替换语义相反），也还在描述旧的两池检索口径。

## 8. 迁移方案：从旧数据折叠出档案初稿【已定方向 + 建议细则】

一次性、可重跑、**只读旧文件、只写新文件**。

### 8.1 折叠来源与落区

| 来源 | 折叠进 | 为什么 |
| --- | --- | --- |
| `PROFILE.md` 的散文 | 身份与称呼（拆出的偏好进偏好区） | 它本来就是"对方是谁" |
| `MEMORY.md` 的条目 | 偏好 / 工具与环境 / 项目段（按内容归） | `remember` 写的那一节，是最干净的结论层 |
| `digest/personal/*` | 长期偏好与风格 | 个人类长期知识 |
| `digest/procedure/*` | 工具与环境 / 项目段的产出规范 | 做法类 |
| `digest/wiki/*` | 默认**不折叠** | 概念类内容更可能属于知识库，交用户逐条决定 |
| `daily/**` | **不折叠** | **现场是流水**，正是这次要丢掉的那一层 |

### 8.2 丢弃噪音的原则（写清楚，因为这是最容易做错的一步）

丢弃与降级分四类，每类的**处理与条数**都要进迁移报告（只有第 2 类的明细不进，理由见下），
让"丢了什么"是可见的：

1. **定级丢弃**：`daily/**` 整层不进候选（它是时间轴，不是画像）；
2. **记录丢弃**：命中敏感信息形状的（`key`/`token`/`密码`/`私钥`/证件号），
   **直接丢且不进报告明细**（只报条数）——旧约定是"绝不记录敏感信息"，迁移不该成为例外；
3. **降级不丢**：超过单条上限的长条目搬进 `import-draft.md`（人可读），界面提示
   "还有 N 条旧条目没进档案"，由用户逐条收录或放弃；
4. **裁剪不丢**：折叠结果超出预算时，按 **项目段 > 偏好（含雷点）> 身份 > 工具** 的顺序保留，
   落选的进 `import-draft.md`。这个优先级的理由就是 §1.1 的目标本身——
   "不用复述大背景"最直接的受益者是项目段。

### 8.3 改写：默认机械，模型整理是可选项【建议】

- **默认机械折叠（零模型调用）**：按来源归区、逐条**原样搬**（只做归一化去重与预算裁剪，
  不改写文字）。代价是语气不统一（有的条目主语不是用户），
  但它**事实齐全、零成本、可重跑**，而且是初稿；
- **可选的一次模型整理**：界面上给一个"整理初稿"按钮，跑一次模型把条目改写成
  "主语是用户"的一句话、合并同义、剔除噪音。**由用户显式触发**，符合"会花钱的默认关"。

### 8.4 幂等、回退、不删任何东西

- **水位**：`mem_metadata/archive-migration.json` 记源文件指纹 + 已折叠条目的指纹，
  重跑不重复搬；**新写入的档案条目不会被二次折叠覆盖**（迁移只 add / 只顶替它自己搬进去的）；
- **幂等判据**：连跑两次，第二次对档案的净改动为零（§9.2 有用例钉着）；
- **回退**：迁移**不改动、不删除任何旧文件**。所以"迁移做错了"的止损是——
  删掉档案文件重跑（源还在），或把内容手工贴回去。**旧文件的 md5 在迁移前后必须一致**；
- **迁移报告**：折叠了几条、丢弃几条（分类计数）、降级几条、裁剪几条、超预算情况，
  一次性展示在界面上，之后留在变更流的第一条里。

## 9. 分期与验收

### 9.1 分期

| 期 | 内容 | 验收 |
| --- | --- | --- |
| **一** | 数据模型与服务：`archive.py` + `archive_files.py`（分区解析、预算、机械顶替、变更流），迁移脚本（机械折叠）。界面不动 | 单测钉住预算闸、顶替进流、幂等、旧文件不动；真实工作区跑一遍迁移，报告数字与人工抽样对得上 |
| **二** | 接线：档案块进 system prompt（含超限声明）、工具面换成 §7.4 那四个、`write_memory` 与文件级写端点退场 | 真模型一轮"记住…"→ 档案变 → 下一轮不追问背景即可引用（这就是 §1.1 的目标本身） |
| **三** | 界面：档案卡 + 变更流时间线，旧页（文件 / 图谱 / 召回）下线 | 改一条 → 下一次注入里是新值、变更流里是旧值、还原可用 |
| **四** | 隐式捕获（默认关）：机械前置筛 + 画像双问 + 捕获模型绑定 | 关着时一次都不调；开着时真模型跑一轮"我以后都要…"能被捕获、有回执、超限被拒时回执给出路 |
| **五** | 退场清理：`daily`/`digest` 的检索与整理、向量那一路、图谱、旧配置项、`SKILL.md` 文案；旧设计文档移入 `归档/`、`docs/README.md` 与工程规范 §2.3 的清单同步 | 闭包仍是 22 模块 / 17 发行包；全量回归绿 |

### 9.2 验收判据（机械可查）

每条写成"用例名 + 它钉住什么"。第 1–11 条与第 13 条是单测/集成用例，第 12 条走门禁脚本口径。

1. `test_default_config_makes_zero_extra_model_calls_per_turn` —— 默认配置下，一轮对话的
   模型调用次数与记忆无关（注入、显式写入、recall 都不新增调用）；
2. `test_archive_is_injected_whole_in_system_prompt` —— 档案每个条目都出现在注入块里
   （逐条比对，不做抽样）；
3. `test_over_budget_append_is_rejected_not_truncated` —— 越线写入被拒，且**档案文件逐字节未变**；
4. `test_replace_moves_old_value_to_changelog` —— 顶替后：档案里是新值、查不到旧值、
   变更流里旧值逐字节可找回；
5. `test_restore_from_changelog_round_trips` —— 还原后档案文本与顶替前逐字节相等；
6. `test_forget_removes_entry_and_keeps_history` —— 忘掉 = 从档案删除 + 变更流留痕 + 可还原；
7. `test_recall_pool_excludes_archive_entries_already_injected` —— 已注入的条目不再被召回返回；
8. `test_recall_never_returns_document_pool_content` —— 两池红线（旧用例，改口径后继续存在）；
9. `test_implicit_capture_off_by_default` —— `memory.capture=false` 时捕获路径一次模型都不调；
10. `test_migration_is_idempotent` / `test_migration_keeps_source_files_byte_identical` ——
    重跑净改动为零；旧文件 md5 不变；
11. `test_sensitive_entries_never_reach_archive` —— 迁移与三条写入路都挡住敏感信息；
12. `test_sidecar_closure_unchanged` —— `scripts/sidecar-closure.py` 仍是 **22 个顶层模块 /
    17 个发行包**（门禁脚本口径）；
13. `test_unknown_section_is_injected_and_reported` —— 用户在外部编辑器加的未知分区
    照注入、计入预算、界面如实报"分区不认识"（§3.5 第 4 条）。

门禁命令沿用仓库既有入口：`scripts/check-backend.sh`、`scripts/check-frontend.sh`、
`scripts/lint.sh`（含 U1/U2 界面文案检查）；收尾按《项目工程规范 v0.6》§5.2.1 跑全量。

### 9.3 真跑验收（产品级，人工）

这条不能用单测替代，因为它是 §1.1 的目标本身：

> 新账号 → 首次引导问三件事（怎么称呼 / 最近在忙什么 / 希望怎么说话）→ 用户照常回答 →
> 档案里出现对应三区条目 → **换一个会话**，用户直接说"帮我把这个项目的方案过一遍"，
> 助手**不追问"哪个项目""给谁看""有什么约束"**，而是带着项目段的约束直接开工。

跑法照旧：数据目录指到临时目录（不碰用户的真实记忆）、真模型、真工具循环。

## 10. 开放问题（留给产品负责人拍板）

每条都给本文的倾向与理由，默认值是"先按建议落地，拍板改数即可"。

1. **预算参数定多少？**（§3.3）建议 120 字/条、60 条、4000 字、每区 10/20/8×8/12。
   理由是"条数挡碎、字数挡长"。这几组数**全部可调**，但要一次定下来——
   预算写在文档里、也写在界面上，改它要同时改两处。
2. **档案是复用 `PROFILE.md` 还是新开一份？** 本文倾向**复用 `PROFILE.md` 并让
   `MEMORY.md` 退场**（理由见 §7.2）。另一条路是新开 `ARCHIVE.md`，把四份人设文件与
   档案彻底分开——好处是人设的"散文"性质不受影响，代价是"身份与称呼"会与 `PROFILE.md`
   重复，用户要维护两处。
3. **项目段是否按"活跃会话"裁剪注入？** 例如只注入最近 30 天内出现过的项目组，
   其余的靠 `recall` 找。省 token，但引入了"助手看不见某个在做的项目"这一新失败模式。
   **本文倾向先不裁**：先看真实账单价，再决定要不要用可见性换钱。若采纳，
   §5.3 第 3 条要把裁剪部分接回 recall。
4. **`memory.enabled` 的默认值改成 true 吗？**（§7.3）档案制下它不再花钱，
   默认关等于"这个功能默认不存在"；但它是**行为变更**（老用户升级后行为会变）。
   本文倾向 **true**，并保留"关掉后档案仍可编辑"这条。
5. **隐式捕获的机械前置筛用哪几个词？**（§4.1）这是全篇唯一一处词表，也是最容易做成
   "看起来很聪明、实际很脆"的地方。备选是**不加词表、打开开关就每轮判定**
   （更贵但更简单，也不会漏）。倾向先用一个窄词表，用真实使用去删改它。
6. **变更流保留多少条？**（§3.4）建议 300，超出丢最旧。它同时是备份体量的一部分，
   所以要定一个数。
7. **迁移里要不要提供"模型整理初稿"这一次调用？**（§8.3）提供了初稿读起来更顺，
   但要花一次钱、且它会把机械折叠的结果**改写**（改写就有失真）。倾向提供、由用户点。
