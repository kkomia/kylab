# Agent 工作区与能力层设计 v0.1

> 本轮的目标是把产品从"知识库问答"推到"**带工作区的个人 Agent**"：左侧信息架构重排、
> Agent 按账号隔离、引入工作区（项目）概念、把知识库与 Agent 天生融合，
> 并把能力层（技能 + MCP）做出来，同时把**会话沙箱**与**工作区**这两件常被混为一谈
> 的事分清楚。
>
> 先调研（§1）、再定设计（§2–§6）、最后是落地清单（§7）。**一次只加一层，每层可验收**。

## 1. 调研：QwenPaw 与 Kimi Work 各自给了什么

**QwenPaw（`agentscope-ai/QwenPaw`，3.5 万 star）** 的文档里有一张很清楚的图，
是它对自己的定位——"Agent OS"，**每个 Agent 一个工作区，由三根柱子撑起来**：

| 柱子 | 它管什么 | 我们的对应 |
| --- | --- | --- |
| **Resources** | 透明在磁盘上的文件与目录 | 工作区的 `root_path` |
| **Governance** | allow / deny / ask / sandbox 的准入策略 | 工具准入策略（§4） |
| **Sandbox** | 内核级执行隔离（Seatbelt / Bubblewrap+Landlock / AppContainer） | 会话沙箱目录 + 策略层（§4） |

它另外两处值得直接抄：

- **Drivers**：协议中立的连接层（MCP / A2A / ACP），**凭据加密 + 每次调用过策略闸**。
  这解决的是"接了一堆外部工具之后，谁在什么条件下能调用什么"——见 §6。
- **Skills 的分层**：`SKILL.md` 是**索引**（`name` + `description` 决定何时被激活），
  详细材料放在 `references/*.md` 里**按需读**（渐进式展开）。它的 `description` 写法
  是"先走章节索引、再下钻正文页"这种**动作描述**，而不是"这个技能是什么"的名词描述
  ——因为那句话是模型的**触发条件**，动词才管用。
  仓库里 5974 个文件里有多份 `SKILL.md` 实例，格式与 Claude Code 的 Agent Skills 一致。

**还有一条重要的现实感**：它的 Roadmap 里 **"Multiple workspaces" 标着 In Progress**
——也就是说"多工作区"在成熟产品里也还在做。我们不必做得比它更花，先把
"**一个账号一个 Agent + 若干工作区 + 会话挂在工作区下**"这条主干走通、走对。

**Kimi Work** 那侧（前几轮已调研过它的界面与 token）：项目/工作区是**左侧第一等公民**，
文件树、会话、产物都挂在项目里；会话列表在项目之外单独有一栏"最近"。
这正好回答本轮的菜单问题（§2）。

## 2. 信息架构：左侧栏重排

### 2.1 现在的问题

侧栏是：`新对话` → `对话 / 概览 / 知识库 / 笔记 / 记忆 / 任务中心` → `对话列表`。
两个毛病：

1. **知识库是"一个入口"，但它的内容（每个库）没有位置**。要进某个库必须先点"知识库"
   再在页面里找——侧栏这一格占着一个顶级位置，却没承担它该承担的导航；
2. **会话是产品的核心工作区，却挤在导航下面当一个扁平列表**。会话多了以后，
   它们和导航项抢同一块纵向空间，而且**没有归属**——分不清哪些是"这个项目的"。

### 2.2 侧栏：导航 + 两节清单（v0.22，照 Kimi Work）

```
[字标]
[新会话]                                ← 最高频动作，常驻最上（不变）

导航
  笔记 / 记忆 / 能力
  知识库 ▸                              ← 可折叠子菜单（v0.15 起）
  ──────────────
  项目 ⌄                      [＋]      ← 默认展开；悬停出现"新建项目"
    📁 项目 A                           ← 点它进项目页（`?focus=<id>`）
       会话 1                           ← 它下面的会话，缩进一级
       会话 2
       展开（还有 N 条）                 ← 一屏放不下的收在这里
    全部项目                            ← 清单末尾，进项目页
  对话 ⌄                      [＋]      ← 默认展开；悬停出现"新建会话"
    会话 x / 会话 y / …                  ← 没归项目的（已归档的不在这里）
    查看全部会话                         ← 打开搜索菜单（搜索 + 全部 / 已归档）

[账号 / 设置]
```

**这一版是照用户给的 Kimi Work 截图来的**（前两版都不对，原因记在下面）：

- **节标题是 `项目 ⌄`**：箭头**紧跟文字**，表示"这一节能收起来"。
  `›`（点进去）与 `⌄`（就地展开）是两个意思，同一栏里混用会让人分不清点下去
  会不会把东西撑开。
- **标题右侧默认什么都不摆**，鼠标移上来才出现一个"新建"图标
  （项目是带加号的文件夹 `IconFolderPlus`、对话是新建会话）——
  常驻的话两节各挂一个加号，读起来像"这两行各有一个主要动作"，
  而它们的主语其实是下面那份清单。
- **两节默认都展开**，清单直接铺在标题下面。
- **每一行铺满侧栏宽度**：上一版的行是行内元素，只有文字那么宽（实测 87px / 240px），
  悬停高亮只覆盖一小块——用户的原话是"你这个标签没有铺满这个侧边栏"。

前两版的错法记在这里，免得再来第三次：

1. 把「项目」做成**点开才出现的菜单**（`项目 ›` + 弹出项目列表）——Kimi 那里它是
   就地展开的一节，清单和标题是一体的；
2. 更早一版把「项目」做成常驻展开的**分组 + 旁边一个「管理」菜单**，还给「对话」
   配了独立节结构（条数 + 搜索标记）——那是把两个简单的节搞成了三层结构。

其余三条与 v0.16 的差别：

- **项目排在对话之前**（用户指定）：项目是"在哪儿干活"（会一直用下去），
  对话是"刚刚问了什么"（临时的）。
- **「未归档会话」那一栏没有了**（用户指定）：它铺的全是随手问的"你好"
  （用户实例上 9 条里 6 条）。顺带清掉一个**同名歧义**——「未归档」以前兼着
  "不属于任何项目"与"没归档"两层意思，界面上现在只留后者：归档过的会话
  本来就不进侧栏（`setArchived` 把它从清单里摘掉），要去「查看全部会话」的
  「已归档」视图看。
- **项目的增删查**：新增在节标题右侧那个悬停出现的图标里，改名/路径/绑定知识库
  在项目页（点项目名或「全部项目」进去）。

## 3. 数据模型：一个账号一个 Agent，若干工作区

### 3.1 Agent = 四条轴的交点

"一个用户一个 Agent"不是一张表，而是**四条已有/新增的归属轴都按账号收口**：

| 轴 | 落点 | 现状 |
| --- | --- | --- |
| **记忆与人格** | `data/memory/<user_id>/`（`MEMORY.md` / `SOUL.md`） | 原先是**全部署共用一份**（旧 §5 的已知边界），本轮改成分账号 |
| **工作区** | `workspaces` 表（`owner_id`） | 本轮新增 |
| **会话** | `conversations.owner_id` + `workspace_id` | 归属已有，**工作区归属本轮新增** |
| **能力**（技能 / MCP） | 技能=磁盘上的 `SKILL.md`；MCP 服务按账号存 | 本轮新增 |

于是"这个 Agent 是谁"= 它的 `SOUL.md`（人格）+ `MEMORY.md`（长期记忆）
+ 它能碰的工作区 + 它能用的技能与 MCP 服务。**没有第五个地方**。

### 3.2 `workspaces` 表

```
id, owner_id, name, root_path, description, kb_ids jsonb, created_at, updated_at
```

三个字段的取舍：

- **`root_path` 由用户指定**（这是"可以指定路径作为工作区"的直接落点）。
  存绝对路径，创建时**校验存在且是目录**，并且**拒绝指向数据目录自身或系统根**
  ——否则"把工作区设成 `/`"就等于把整台机器交给 Agent。
- **`kb_ids`**：工作区自带一份知识库清单。这就是"知识库与 Agent 天生融合"的落点
  （§5）——不是让模型自己去挑库，而是**进入工作区就已经带上这个项目的资料范围**。
- **没有 `sandbox_path`**：沙箱不是工作区的一个字段，它是另一个概念（§4）。

### 3.3 会话归属

`conversations.workspace_id`，**可空**：
- 有值 = 属于某个工作区，侧栏挂在该工作区下；
- `NULL` = 未归档，侧栏单独一栏按序排列。

外键 `ON DELETE SET NULL`：删工作区**不该删掉里面的会话**——那是用户问过的内容，
只是失去了归属。这比级联删除安全得多（会话里有消息，误删无法恢复）。

## 4. 会话沙箱 ≠ 工作区（这一节是本设计的核心区分）

两件事经常被混着说，其实回答的是不同问题：

| | 工作区（Workspace） | 会话沙箱（Sandbox） |
| --- | --- | --- |
| 回答的问题 | "**在哪干活**" | "**试错的地方在哪**" |
| 生命周期 | 长期，用户拥有，`root_path` 是他自己的目录 | 一次会话，可随时丢弃 |
| 位置 | 用户指定的路径 | `data/sandbox/<conversation_id>/` |
| 内容 | 真实的代码 / 文档 / 项目文件 | 临时脚本、下载、中间产物 |
| 谁清理 | 用户自己 | 会话结束或超期后自动回收 |
| 可否被引用 | 是（产物就落在这里） | 否（只许诺"会话期间有效"） |

**为什么必须有沙箱**：Agent 要跑命令、试脚本、下东西。如果这些都直接bundle在
用户的工作区里，那么一次失败的尝试会在他的真实项目里留下垃圾——而"我什么都没做，
它自己多了一堆文件"是最让人不敢再用一个 Agent 的原因。沙箱把**探索的痕迹**与
**真实的产物**分开：想留下的，由用户（或 Agent 明确地）从沙箱挪进工作区。

### 4.1 产物（v0.26）：文件的第一身份是"文件"，不是"库里的一份文档"

上面那张表里有一行"可否被引用：工作区是（产物就落在这里）"——但**没有工作区时它落哪儿，
设计里是空的**。那个空档出过一次事故：用户让 Agent 导出一份 docx，那条会话没挂工作区，
而导出工具当时的实现是"直接当一次入库提交"（`knowledge_base_id` 必填），
模型只好**替用户挑了一个语义最顺手的库**塞进去，并在回答里说明
"你这边没有专门的工作区，我就选了最顺手的那个"。

补上第三档落点，填的正是那个空档：

| | 工作区 | 未挂工作区（v0.26 补） | 沙箱（§4 上半） |
| --- | --- | --- | --- |
| 位置 | 用户指定的 `root_path` | 对象存储 `conversations/<会话 id>/<产物 id>.<后缀>` | `data/sandbox/<会话 id>/` |
| 谁创建 | 用户建工作区 | 服务端，随会话 | 服务端，随会话 |
| 生命周期 | 用户自己管 | **随会话**：删会话时清掉 | 超期回收 |
| 可见性 | 他打开项目就看得见 | 对话里的文件卡片（可下载） | 不可见（只许诺会话期间有效） |
| 与知识库 | **默认不入库** | **默认不入库** | 不入库 |

三条纪律（都写在 `app/services/artifacts.py` 的模块头里）：

1. **入库是显式动作**。文件不是天生要入库的；"这条会话做出来的东西"与"我资料库里的一份"
   是两个身份。入库的入口有两个，都是用户本人的意思：跟它说一句（`ingest_artifact`），
   或者点卡片上的「存进知识库」。
2. **工作区里的那份是用户的文件**。删会话**不动它**——顺手删掉别人项目里的 docx，
   是最不该有的"贴心"。
3. **落点不可预期是最大的问题**。所以工作区目录不存在时**明确报错**，
   不悄悄改落到临时区；同名文件退到 `报告 (2).docx`，不覆盖。

**Governance（准入策略）**分两层，都是照成熟方案抄的（v0.17 补）：

1. **总开关**（QwenPaw 的四档词表）：`allow` / `ask` / `deny` / `sandbox`；
2. **规则清单**（**Claude Code 的权限模型**）：三张清单 + `Tool(specifier)` 语法
   （`Bash(git status:*)`），**优先级 deny > ask > allow**，
   **`:*` 只在词边界生效**（`git status:*` 匹配 `git status --short`、
   不匹配 `git statuses`），没命中就回总开关那一档。规则比总开关更具体，所以命中时规则说了算。

两条必须照抄的理由：

- **deny 永远优先**：少了它，一条更宽的 allow 会把用户的 deny 静默盖掉，
  而用户以为自己已经禁掉了；
- **默认不放行**（这里是 ask，与 Claude Code 的默认模式一致）：
  预置一张"看起来安全"的只读命令表是危险的，因为**只读不等于无害**——
  `cat /etc/passwd` 是只读的，而它能读到工作区外面的东西。

**后一条同时说明了内核隔离为什么不能只做写**：最初的 bwrap 参数是
`--ro-bind / /`（整个根只读）+ 工作区与沙箱挂读写。命令一定跑得起来，
但 `/etc/passwd`、`~/.ssh` 都**还在视野里**，只是不能写——而读走凭据不需要写权限。
现在改成 **restricted filesystem view**（QwenPaw 的说法）：**只挂运行所需的目录**
（`/usr` `/bin` `/lib*` `/etc/ssl` 等），没挂上的路径在沙箱里**根本不存在**。
代价是可能缺某个工具要的文件，那时命令跑不起来——**两害相权，取"跑不起来"**。
清单可用 `sandbox.bind_ro` 显式扩展，但**不提供"挂整个 /"这个选项**：
需要时请把具体目录加进来，那是一次看得见的放权。

## 5. 知识库与 Agent 的融合

融合不是"在对话页加一个库选择框"（那已经有了），而是三件事：

1. **工作区自带库**（§3.2 的 `kb_ids`）：进入工作区，资料范围就定了。
   新会话的 `kb_ids` **默认继承工作区的库**，用户不必每次勾一遍。
2. **两池仍然分开**：知识库是"文献说的"（有出处、只读），记忆是"你说的"（无出处、可改）。
   工作区只是把**前者的范围**绑给了项目，**不把两者混进同一次检索**（《记忆层设计》§2.1）。
3. **Agent 的工具面按工作区收口**：`search` 默认只搜这个工作区绑定的库
   （不填 `kb_ids` 时），越权的库直接 403——与既有的 `check_kb_scope` 同一套判定。
4. **关掉知识库开关 = 知识库那一侧的工具整个不出现**（v0.27）。在此之前只是
   "检索会被拒绝"：工具照给，于是模型每轮都先 `list_knowledge_bases` 看一眼、
   再 `search` 一次拿到一句"这一轮没有可查的知识库"——两个来回白花
   （用户报的现象："没开知识库，但每轮都去知识库检索"）。**给了又拒，不如不给。**
   边界画在知识库上：记忆（`recall` / `remember`）与笔记（`create_note` / `list_notes`）
   不属于这一侧，照旧可用；而"把笔记加入知识库"「把产物存进知识库」**算**这一侧
   （它们动的是知识库）。收起来的同时提示词里追加一句说明（`chat.NO_KB_NOTE`）：
   第 1 条写着"问对方自己的东西 → 查 search / recall"，而表里没有 `search`——
   不说清楚，模型会去试一个不存在的工具。

## 6. 能力层：技能与 MCP

### 6.1 技能（Skills）

**形态**：磁盘上的目录，每个一个 `SKILL.md`（与 QwenPaw / Claude Code 同格式）：
frontmatter 的 `name` + `description`，正文是流程与索引，细节放 `references/`。

**加载是两段的**（这是它省 token 的关键）：
1. **目录注入**：把所有技能的 `name` + `description` 拼进 system prompt
   ——模型据此知道"**有哪些能力、什么时候该用**"，成本是每个技能一行；
2. **按需展开**：模型决定用某个技能时，调 `use_skill(name)` 把正文读进来。
   正文里指向的 `references/*.md` 再按需读。

**来源目录**（按优先级合并，同名后者不覆盖前者）：
- 仓库自带 `skills/`（随代码发布，如 `kylab-knowledge-base`）；
- 数据目录 `data/skills/`（用户自己放，或从市场安装）。

**扫描要防注入**：QwenPaw 有 Skill Scanner（检测提示注入、硬编码密钥、外传数据）。
本轮做**最小必要**的两条：技能描述里的可疑指令（"忽略之前的指令"这类）在注入前
标出来并**降级为不可见**；技能只提供**文本与流程**，不能凭自己获得工具权限。

#### 6.1.1 从线上源安装（v0.27，调研见《技能仓库与技能市场调研-v0.1》）

调研的第一条结论就是"**没有统一的市场协议**"：`SKILL.md` 是事实标准，但分发各家
一台自己的插件市场，目录约定也不同（Anthropic 在 `skills/`、Microsoft 在
`.github/skills/`、Google 是多级嵌套）。所以这里**不做"市场适配器列表"**，
而是把"一个源"定义成"**一个 GitHub 仓库**"，浏览 = 递归找仓库里所有 `SKILL.md`。
副产品是：任意合规仓库都能用（用户粘一个 `owner/repo` 就行），不必等谁去适配。

四步流程，每一步都有它挡的东西：

| 步 | 做什么 | 为什么 |
| --- | --- | --- |
| **浏览** | 一次仓库信息 + 一次 commit + 一次递归文件树（`git/trees/{sha}?recursive=1`），再并行取每个 `SKILL.md` 的 frontmatter | 只解析 `name`/`description`（那是模型判断"何时该用"的依据），正文与附件等用户点了再拉——渐进式加载的天然对应。结果**带 TTL 落盘缓存**：GitHub 匿名配额 60 次/小时/IP，重启就清零的缓存等于没缓存 |
| **看清单** | `inspect` 给出文件清单（路径、大小、`doc`/`code`/`asset`）、总体积、commit SHA | 调研 §4.6 的硬要求：`scripts/` 是**会被执行的代码**，用户在看到清单之前没有别的地方能判断"我在装什么"。代码文件在界面上单独标出来并单独提示 |
| **取文件** | 按**同一个 SHA** 逐文件取，三条路按序退：jsDelivr → GitHub contents 接口 → raw | 按 SHA 而不是分支：分支会在"用户点安装"和"我们下载"之间变 |
| **落盘** | 交给 `services/skill_market.py`：白名单后缀、扫描、失败清干净、**记版本锁** | 锁里既有 commit SHA（上游那一版）也有逐文件 hash（我们磁盘上这一份）——"commit 没变但本地被改过"是另一件要答得出来的事 |

**三条取文件的路是这台机器的网络逼出来的**（实测 2026-09-19）：
`raw.githubusercontent.com` 多数请求被重置或七八十秒超时；jsDelivr 快，
**但它对没缓存的文件会 301 回 raw**（4 个文件里 3 个如此）；GitHub 的 contents 接口
（`Accept: application/vnd.github.raw`）8 个文件并发 0.8 秒全成。所以顺序是
CDN → contents → raw，**跨主机的跳转不跟**（跟过去等于又卡一次），
而 contents 那条会花 API 配额——撞上时的报错直接告诉用户配 `KYLAB_GITHUB_TOKEN`。

**安装期跟着改掉的一条老规矩**：白名单从"只收文本"放宽到"文本 + 脚本 + 资源"
（仍然不收二进制）。理由是真实的技能包 `scripts/` 是常态——Anthropic 官方的
docx/pdf 技能就带着 Python——而"只收 Markdown"等于把最有用的一批挡在门外。
换来的是三条更实在的防护：装之前必须把清单摊给用户看、落盘前扫描、**绝不自动执行**。

**三种入口，同一个写入**（v0.28）：① 线上源（浏览 → 看清单 → 按 SHA 装）、
② 本机上传（选文件夹或选 `.zip`）、③ 目录 / zip / catalog.json 的接口调用。
三者最后都落到 ``skill_market.install_files``——**白名单、扫描、失败清干净只有一处实现**，
上传不是"信得过的后门"：它恰恰是别人给的包最常见的到达方式。
技能名取 ``SKILL.md`` 的 ``name``（规范里它等于目录名），取不到才退到顶层目录名。

**中文简介**（v0.28）：技能生态里绝大多数描述是英文，而这一页是给中文用户看的。
浏览一个源时**一次调用**把这一批的（名字, 描述）翻成中文（不是 20 次调用），
结果写进源缓存；安装时那一行跟着记进安装清单，能力页的卡片与详情都显示它。
**原始英文一个字都不改**：``description`` 是模型判断"何时该用"的触发文本
（见 ``services/skills.py``），改写它有真实的功能风险；中文只是给人看的那一行，
在详情里仍以"原文"的形式留在中文下面。翻不成（没配模型 / 模型报错）就退回英文。

**权限与边界**：浏览要登录，安装/卸载/上传要管理员（与 MCP 那一侧同一档）；
**只写 `data/skills/`**，仓库自带的技能卸不掉（那是"我们审过的那个版本"）；
前端永远不直接打 GitHub（匿名配额一分钟就能打爆）。

**这一版没做**：`npx skills` / `giget`（要 Node、行为不由我们控制）、skills.sh 榜单
（强制认证）、SkillsMP 全文检索（口径误导，见调研 §3.4）、签名与评分（没有真市场，
做了也没人验）、自动更新（更新应当是显式动作）。

### 6.2 MCP（外部工具）

现状：KYLAB **只做 MCP 服务端**（把知识库能力暴露给外部 Agent）。
本轮补上**客户端**：连外部 MCP 服务、发现工具、在对话里调用。

- **连接方式**：`stdio`（本地进程）与 `streamable-http`（远端服务）两档；
- **凭据**：与设置页其它密钥同等对待——**按账号存、接口只回显"是否已配置"**
  （绝不回显明文），这是既有做法（模型注册表的 api_key 就是这样）；
- **每次调用过策略闸**：`allow` / `ask` / `deny` 三档；
- **命名冲突**：外部工具名一律加前缀 `mcp__<server>__<tool>`，避免与内置工具撞名
  （Anthropic 的 MCP 约定也是这个）。

#### 6.2.1 工具怎么进对话（v0.21 落地）

外部服务的工具**与内置工具一起进模型那张工具表**（`agent_tools.tool_specs` 的第三段），
模型像用内置工具一样用它们。三处值得记下来：

1. **工具清单要缓存**（成功 5 分钟 / 失败 1 分钟）。取清单 = 连一次那个服务
   （stdio 还要起子进程），而工具表是**每一轮都要**的——不缓存的话，
   问一句话的成本会变成"起子进程 + 握手"乘上服务数。失败也缓存、但更短：
   不缓存会让一个挂掉的服务在每轮对话里白等一个超时。
   能力页的「测试连接」即刷新缓存，与对话读到的是同一份。
2. **判定只有一处**（`MCPClientService.decide`）。顺序是：
   服务策略为 `deny` → 拒（**硬停**，命中的放行规则也掀不开它）；
   有命中的规则 → 按规则；没命中 → 回服务那一档。
   规则比服务那一栏更具体，所以命中时它说了算——这允许"只放开某一个工具"，
   而不必把整台服务放开（最小权限的用法）。没命中规则时**看的是"真的命中了吗"
   而不是规则集的默认档**：那个默认档也是 `ask`，把它当规则用会让
   "服务设成允许、清单一个字没写"这个最常见的部署变成每次都要求确认。
3. **`ask` 档不进对话执行**（默认档就是它）。原因在链路形状上：对话是一个
   **拉取式**的事件生成器，而"停下来问用户"要求先把已经发生的事件送出去、
   再阻塞等一个回答——拉取式做不到（阻塞发生在 yield 之前，界面根本收不到那个
   询问，两边一起等）。要支持它得先改成推送式事件流，那是一次协议层改造。
   于是取舍是：**宁可"这轮用不了、并说清怎么打开"，也不要静默执行**。
   模型收到的是"这一轮没有执行 + 请如实告诉对方怎么放开"，
   并带上可以直接粘进放行清单的那一行（`mcp__<服务>__<工具>`）。
   REST 端点那条路**不受此限**：它有"确认后带 `approved=true` 重调"的往返
   （409 → 确认 → 再调），界面上那个确认框是真的。

### 6.3 Office 四件套：读写都是纯 Python（v0.21）

"个人 agent 得有处理这四种文档的能力"这件事，拆成两半看，**读的那一半早就有了**：

| 方向 | 谁在做 | 形态 |
| --- | --- | --- |
| **读** docx / pptx | `parsers/local_office.py` | 纯本地（zip + XML），不需要任何凭据 |
| **读** xlsx / csv | `TabularParser` | 解析 + 结构化副本（DuckDB，可查列） |
| **读** pdf | `parsers/local_pdf.py` → 云端 MinerU | 文字型本地直提；扫描件走云端 |
| **写** docx / xlsx | `services/office.py` | python-docx / openpyxl |
| **写** pptx / pdf | `services/office.py` | python-pptx / reportlab（本层唯一两个新依赖） |

所以缺的只是**产出**：对话里整理出的结论要能变成一份能发给别人的文件。

**方案 A：纯 Python 库，不装 LibreOffice / Pandoc。** 理由与代价：

- LibreOffice 是几百 MB 的安装包，Pandoc + Poppler 还要另外配路径，而它们能做的事里
  我们真正需要的（读写这四种格式）纯 Python 库都能做；
- **代价写在明处：不保证版式好看**。这套东西只保证"结构正确、内容完整、
  能被 Word / Excel / PowerPoint / 阅读器打开"。所以 `services/office.py`
  **不做任何"版式检查"**——没有渲染引擎时那种检查只能是假的
  （要么恒真，要么在猜）。需要真排版那一步是方案 B（装 LibreOffice），
  那是一次显式的部署选择，不是这里偷偷假装的事。

**三个工具，一种形态一个**（不是四个：`.pdf` 与 `.docx` 是同一个"读的东西"的两种封装）：

| 工具 | 产出 | 按什么选 |
| --- | --- | --- |
| `export_document` | `.docx` / `.pdf` | 结果是"要读、要转发"的（报告、说明） |
| `export_table` | `.xlsx` | 结果是"行列"（清单、对照、逐项统计） |
| `export_deck` | `.pptx` | 结果是"要讲一遍"的（汇报、方案、提纲） |

三条实现上的选择：

1. **产出走入库**（`ingest.submit` + `enqueue_ingest`），不另开一条"写文档"的通道。
   于是交付物与手动上传的文件是**同一种东西**：在文档列表里看得见、能下载、
   能检索、能删，也能走回收站。另开一条通道的话，库里会出现两种来源、两种格式，
   而"这份文件是怎么来的"就再也说不清了。
2. **格式由扩展名决定，不猜**。给 `export_document` 一个 `.xlsx` 名字就当场报错
   并告诉它该用哪个工具——猜的话，模型会以为自己导出了一张表，实际拿到一份文档。
3. **依赖是可选 extra**（`office`），缺了报"装什么、怎么装"，不抛 `ImportError`。
   工具报错是给模型读的：它需要的是"这件事现在做不到、原因是这个"，
   而不是让它换个参数反复重试同一条走不通的路。

**技能与工具的分工**：三个工具进工具表（模型得知道它们存在），
而"什么时候该用哪一个、内容怎么组织"写在 `skills/kylab-office-export/SKILL.md` 里
——那是流程性的东西，占的是目录里的一行，按需才展开。

**边界**（同一份技能里也写给模型看了）：不改已有文件（每次是新文档）、
不做格式互转（读那种文件走入库管线）、不渲染检查版式。

### 6.4 联网（v0.22）：让"查一下"真的能查

**这一节回答的是一个实测报过来的现象**：用户问"帮我查下今天的热点新闻"，
面板里出现的是 `查看知识库 → 查看文档列表 ×2 → 回忆`，最后答"你的库里没有"。
看起来像"还是检索框架"，但根因不是框架——**是它没有别的事可做**：
在那之前，Agent 的工具面只有知识库那一侧（检索、文档、笔记、记忆、导出）。
任何问题都只能往库里找，找不到就回一句"库里没有"。

补的是两家共识的两项（《预装技能选型》§2 的 P0 第 3、4 项）：

| 工具 | 做什么 | 要不要密钥 |
| --- | --- | --- |
| `web_search` | 搜一次网，回**带编号**的结果（标题 / 网址 / 摘要） | **要**（见下） |
| `web_fetch` | 抓一个网页、抽出正文（复用入库管线那个 HTML 正文提取器） | 不要 |

三条决定：

1. **抓取必须挡内网**（`services/web.py::check_public_url`）。URL 是**模型给的**，
   而模型可能正被一段网页内容牵着走（提示注入的常见目标就是"让它去访问某个地址"）。
   只允许 http/https 不够：`http://192.168.31.18:54321/` 是这台机器上的 PG，
   `http://127.0.0.1:8000/api/v1/…` 是 KYLAB 自己的管理接口。
   所以**解析主机名、拒绝环回/私有/链路本地/保留地址**，
   并且**每一跳重定向之后重判**（不用 `follow_redirects=True`，那样没有"每一跳"这个位置）。
   域名解析出多个地址时**全都得是公网**——只查第一个的话，内网地址放在第二条 A 记录上就能过。
   **没覆盖 DNS rebinding**，写在那个函数上：要堵死得把连接钉在已校验的 IP 上，
   代价是 TLS SNI 与 Host 头都要自己处理，在当前形态下不值得，但必须写出来。
2. **搜索需要一个供应商**（设置里新增「联网」一组：供应商 + 密钥，密钥只回显掩码）。
   没有免密钥又稳定的通用搜索接口，所以它是一项配置；**没配就说清去哪配**，
   不返回空结果——空结果会被模型读成"网上没有这件事"。
3. **抓回来的正文当资料用，不进知识库**：入库是另一个动作（`upload_document` / 数据源）。
   把"看过一眼"与"收进库里"分开，否则库会被一次点击攒下的东西占满。

**提示词那一层同时改了措辞**（`AGENT_SYSTEM_PROMPT` 规则 1、6）：原文只说
"涉及对方资料时先检索"，没有说"外面正在发生的事该去哪"，也没有说
"资料不够而上网能补上时要去联网"。现在第一条是**先判断信息源**：
外部正在发生的事 → 联网；对方自己的东西 → 本地的 search/recall；常识与写作 → 直接答。

### 6.5 预装技能包与门控（v0.22）

《预装技能选型》给的是一张 20 项的清单，但那张清单里**绝大多数是能力**，
不是文档：`shell` / `file-ops` / `browser` / `cron` / `email` / `tts` / `vision` …
写一份说明书很容易，**但没有对应的能力时，那份说明书只会让模型照它做然后失败**。
所以落地的顺序是"先有capability，再有技能"，而这一轮先做的是**门控机制**，
它保证这件事不会做反：

**`requires` 门控**（`services/skills.py`，抄调研 §4.2 的字段）：

```yaml
requires:
  config: [web.search_api_key]   # 运行期配置里有值
  binaries: [gh, git]            # PATH 上有
  env: [SOME_VAR]
  os: [linux, darwin]
```

不满足的技能**不进模型目录**（= 预装 ≠ 默认开启），但在能力页里
**照样列出来并说明差什么**（"需要先配置：「设置 → 联网」里的「搜索 API 密钥」"）。
理由与"疑似注入"那条处置完全一致：静默藏掉会让用户以为技能装失败了。
拼错的键（`bins:` / `require:`）会**报出来**——不报的话那个条件等于没写，
而写它的人以为已经门控住了。

落到今天的能力面上，能诚实预装的是五项（其余等能力到位）：

| 技能 | 覆盖调研的哪一项 | 靠什么工具 |
| --- | --- | --- |
| `kylab-knowledge-base` | 笔记 / 知识库（2/3） | `search` / `list_documents` / `create_note` … |
| `kylab-web` | `web-search` + `web-fetch`（3/3） | `web_search` / `web_fetch` |
| `kylab-memory` | `memory`（3/3） | `recall` / `remember` |
| `kylab-delegate` | `delegate`（3/3） | `spawn_subagent` |
| `kylab-office-export` | `doc-*`（3/3） | `export_document` / `export_table` / `export_deck` |

**还没能力做的**（每一项都写清卡在哪，而不是"以后再说"）：

| 调研项 | 卡在哪 |
| --- | --- |
| ~~`shell` / `exec` `file-ops`~~ | **v0.33 已做**（见 §6.6）：`run_command` + 文件三件套。执行仍然**要内核隔离**，所以在这台开发机上 `detect()` 报 `none` 时它会如实拒绝——那是纪律，不是缺陷 |
| ~~`cron` / `todo`~~ | **v0.33 已做**（见 §6.6）：定时任务（`scheduled_tasks` + 任务中心里的一个分段）。`todo` 那半边（清单）没做——它不是"到点跑"，而是一份要持久化的待办，属于另一个产品面 |
| `browser` | 需要无头浏览器（几十 MB 的运行时 + 一个真正的网络出口） |
| `ask-user` | 对话是拉取式事件流，"停下来问一句"要先改成推送式（见 §6.2.1 第 3 条） |
| `email` / `tts` / `vision` / `diagram` / `github` / `coding-cli` | 各自要一个外部依赖或凭据，属于"用到才装" |

**描述长度**（v0.43 改口径）：照抄 ZCode 的渐进披露——**每个请求注入一份目录**
（`- 名字: 描述（何时用：…）(file: 路径)`），单条描述截断 **250 字符**、
整段预算 **20000 字符**，正文只在 `read_skill` 时加载。
所以"长描述"不再进提示词：写技能的人在 `description`/`when_to_use` 里
**把触发词放在前 250 字内**就行（仓库自带的 5 个技能都在前 250 字里）。
调研 §5 那条"超过 20 个再改短描述"的结论已经被这个机制吸收：目录本身就是分层。

### 6.6 这台机器上的能力：文件 / 执行 / 表格 / 定时任务（v0.33）

**这一节的起因是"工具面盘点"**：把我们的 22 个工具对《国内 Agent 默认搭载工具盘点》
那 12 类原语逐条比，排除掉我们明确不做的（图片 / 视频生成、语音、GUI 操作）之后，
缺口集中在四处——**能写不能读**（导出 docx / xlsx / pptx 都行，但工作区里已有的
文件模型看不见）、**不能跑**（`POST /sandbox/exec` 早就在，却没有给模型的工具）、
**不能算**（表格副本写进 DuckDB 了，但只有"按文档读第 N 行"这一条受控查询，
答不了"这个月一共花了多少"）、**不会到点自己做事**（只有数据源拉取与入库维护，
两者都是知识库的维护）。这一轮把这四处补上，工具面从 22 个变成 30 个。

四项共用的三条纪律：

1. **只在对话这条门里**（与技能工具同一档）。它们的共同点是**依赖这一轮的上下文**：
   工作区（会话挂的那个目录）、沙箱（这条会话的试错目录）、会话上选定的库范围。
   外部 MCP 客户端这三样都给不出——给它一个凭据不明的根，比不给更糟；
2. **路径一律过 `resolve_in`**：相对路径、不许 `..`、不许碰凭据文件、解析后必须在根内。
   模型写的路径是"它推测这个项目的结构"，会写出 `../../backend/.env`——
   **不是恶意，是它在猜**（`sandbox.py` 模块头那段说明仍然成立）；
3. **越界与拒绝要说得比"不合法"更多**：模型据此才改得动。所以报错里带着"能查的是哪些表"、
   "要放开执行该改设置里的哪一项"、"这条命令被哪条规则拦下"。

#### 文件：两个根、三种动作

| 工具 | 做什么 |
| --- | --- |
| `list_files` | 列目录（默认跳过 `node_modules` / `.git` / `__pycache__`，并如实说跳了几个） |
| `read_file` | 按行分页读文本；二进制**明确拒绝**（读半屏乱码比读不了更糟）；告诉它还剩多少行 |
| `search_files` | 按正则搜内容，回"哪个文件第几行"——**比逐个读省得多** |

两个根就是 §4 那两个概念的直接落地：**工作区**（用户的真实项目）与**沙箱**（试错的产物）。
`where` 不给时有工作区就用工作区、没有就用沙箱（写死成工作区会让没挂工作区的会话白撞一次错）。
**这一层没有任何写接口**：写由 `export_*`（产出文件）与 `run_command`（执行）承担——
把读写混在一个工具里，等于开出一条我们没设计过、也没审过的写路径。

#### 执行：三道闸 + ask 在这条路上的形态

`run_command` 把 `POST /sandbox/exec` 的那套闸原样搬到工具上：**管理员专属**
（它按设计就是"在你的机器上执行东西"，与设置页同一档）、**策略闸**（`command_policy`
的规则 + `sandbox.exec_policy` 总开关，deny 永远优先，命中规则时规则说了算）、
**内核隔离**（没有可用后端就拒绝，**不回退成裸跑**）。

与端点唯一实质的差别：**`ask` 这一档在这里是"拒绝并说清"，不是"停下来问用户"**。
对话是一条拉取式生成器——"问用户"要求先把已发生的事件送出去、再阻塞等人回答，
而阻塞发生在 `yield` 之前，界面根本收不到那个询问（实测过那个死锁的形状）。
所以取舍与外部工具那层一致：宁可"这轮用不了、并说清怎么打开"，也不要静默执行。
默认档就是 `ask`，所以"接上就能跑命令"这件事不会发生。

**挂载与断网**：cwd 是这条会话的沙箱目录，工作区挂成读写，**默认断网**
（`allow_network` 要模型显式要）。没挂工作区时"工作区根"取沙箱自己——
端点的默认值是 `data/sandbox` 那一层，而那里装着**其它会话**的沙箱。

#### 表格：一条受控的只读 SQL

`list_tables`（有哪些表格、列名是什么、多少行）+ `query_table`（只读 SQL）。
三条硬约束，都不靠"自觉"：

1. **单条只读语句**：白名单起始关键字（SELECT / WITH / DESCRIBE / SHOW / EXPLAIN…），
   写语句与 DDL 一律拒；
2. **不许碰外部世界**：`read_csv` / `ATTACH` / `COPY` / `INSTALL` 这类能读写文件、
   装扩展、连别的库的一律拒——DuckDB 的能力远不止查表，这是它与 SQLite 最不一样的地方；
3. **表名必须在范围里**：把 SQL 里的标识符与**库里真实存在的表名**取交集，
   交出来的必须全在"这一轮允许的库"里。不做 SQL 解析（半吊子解析器给出的"安全"是假的），
   而"标识符里出现过真实表名"是一条不会漏的判据——不出现表名就查不到它的数据。

判定跑在**剥掉字符串与注释之后的骨架**上（`SELECT 'DROP'` 里那个 DROP 只是数据），
而执行的是原文。结果外面再包一层 `LIMIT`：模型写的聚合查询常常没有 LIMIT，
而"把整张表捞进内存再丢掉"是白付的代价。架构 §5.2 的 D5 没有被推翻——
用户仍然没有"自定义 SQL 的开放入口"，这一条是**给模型用的受控通路**，
它的表范围就是"越权读表"的答案。

#### 定时任务：结果落进一条会话

**"到点替我做事"**：每天早晨把昨天的日志汇总、每周一把周报底稿准备好。
表在 `scheduled_tasks`，两种时间形态（`cron` 五字段 / 一次性 `run_at`），
**按服务器本地时间解释**（部署里显式设了 `TZ`，接口把当前时区回给界面显示——
"每天 9 点"是哪个 9 点必须让人看得见）。

三处刻意的形状：

- **每次运行就是那条会话里的一轮问答**：于是"上周它都跑了什么、结论是什么"
  就是翻会话记录——不另造一套"运行历史"的存储与界面。会话首次运行时才建；
- **执行走任务队列**（`TaskKind.SCHEDULED`）：调度侧只做"到点把活放进队列"
  （一条带索引的 SELECT + 一次 CAS），真正的问答由 worker 跑——
  租约、心跳、失败重试、进程崩溃后回收**全部复用已有那一套**，
  而且"跑得慢"不会把下一次到点也堵住；
- **认领是 CAS**：多个 worker 会同时扫到同一条到点的任务，而"跑两次"的代价不是
  重复一次查询，是重复**一整轮问答与工具调用**（真花钱）。判据落在一条
  `UPDATE … WHERE next_run_at = 期望值` 上，让数据库裁决谁先。

界面上它是**任务中心里的一个分段**（"正在跑的事"与"到点要跑的事"是同一件事的
两个时间态，分成两页会让"我那个定时任务跑了吗"变成要跳页找的问题），
并提供**「立即跑一次」**：挂完一条"每天 9 点"的任务，最想确认的是"它会跑成什么样"，
等到明天早上才知道太晚了。

### 7.1 后续四项的落地情况（v0.16）

主干跑顺之后补的四项，**只留下 A2A / ACP 不做**：

| 项 | 落地形态 | 关键决定与实测 |
| --- | --- | --- |
| **内核级沙箱** | `services/isolation.py`：bwrap（Linux）/ sandbox-exec（macOS）/ docker（任意平台）三后端 + 能力探测 | **探测而不是假设**：真去盘上找可执行文件，并问一次 docker daemon（装了 CLI 但 daemon 没起是最常见的假阳性）。**没有隔离时拒绝执行**，不回退成裸跑——回退会把"我们以为它在沙箱里"变成一个静默的假象。实测这台 Windows 机器上没有 docker，`detect()` 如实报 `none`，`exec` 返回可读的拒绝理由 |
| **技能市场** | `services/skill_market.py`：索引 / 安装 / 卸载，三种源形态（目录、zip、catalog.json，本地或 URL） | **安装前扫描**（与扫描磁盘上已有技能同一套规则）：命中注入特征当场拒绝并清掉半成品——与"标注已有技能"不同，安装是主动引入。**zip slip 整包拒绝**（不是跳过那条）、符号链接拒绝、大小与条目数上限、非文本文件拒绝。**只写 `data/skills/`**：仓库自带的技能卸不掉 |
| **子 Agent 派生** | `services/subagent.py` + `ChatService.run_subagent`，决策里多一个 `{"action":"spawn","task":"…"}` | **深度只能是 1**（子 Agent 的工具面里没有派生，不是"检查 depth 然后继续"）；轮次/时限/检索次数三道闸；**范围只继承不扩**（`kb_ids` 由父任务复制）；停下来的原因如实带回（`budget` / `timeout` / `error`），不把"没查完"说成"查完了" |
| **A2A / ACP** | **不做** | 它们是"Agent 之间互相发现与编排"的协议；单机单 Agent 的形态下没有对手方。等真有第二个 Agent 要对接时再说——先做等于给一个不存在的场景写代码 |

四项都有单测（隔离 15 条、市场 31 条、子 Agent 14 条、沙箱端点 7 条），
外加真机验证：MCP 探活真连上 KYLAB 自己的 MCP 服务端（13 个工具）、
沙箱在没有隔离的机器上如实拒绝执行。
