# 记忆层设计 v0.1

> 本轮（v0.12/v0.13）的开发方案里，"记忆层"一直标着"等前五步落地后再细化"。
> 前五步已完成，本文把那一阶段定清楚：先讲调研结论，再讲设计，最后给分期与验收。

## 1. 调研：QwenPaw 与 ReMe 怎么做的

（详细归纳见 `docs/调研/Kimi-设计token对照表.md` 之外的调研笔记与 `ReMe` 仓库 README；
这里只留与我们的设计直接相关的结论。）

**ReMe 的定位**：`local-first, self-evolving personal knowledge base`。
核心主张是 **Memory as File, File as Memory**——持久记忆就是带 frontmatter 与
wikilink 的普通 Markdown，用户可读、可改、可备份、可迁移。

**它的文件分层**（这是最值得抄的部分）：

| 层 | 内容 | 谁改 |
| --- | --- | --- |
| `MEMORY.md` | 少量稳定的核心长期记忆（偏好、长期约定、工具设置） | 用户与主 Agent，**不由自动流程覆盖** |
| `memory/YYYY-MM-DD/` | 每日现场：一个 session 一条记忆笔记 | Auto-Memory 自动生成，**永不被改写** |
| `digest/{personal,procedure,wiki}/` | 跨时间整理后的长期知识 | Auto-Dream 持续改写 |
| `mem_session/` `resource/` `mem_metadata/` | 原始对话、外部资料、可重建索引 | 只读 / 派生 |

**那条铁律**：结论可变、**现场不可变**。Auto-Dream 只写 `digest/`，从不回头改 `memory/`
——所以长期记忆可以一直修正而不丢历史。

**四个机制**：Auto-Memory（捕获，默认每 5 个用户回合一次，只留"以后仍可能有用"的）、
Auto-Index（Markdown AST 分块 + BM25 + 可选向量 + wikilink 图谱）、
Auto-Dream（整合，`CREATE/CORROBORATE/REFINE/CORRECT` 四选一）、
Memory Search（BM25 → 向量 → RRF → 附出边/入边，**返回片段与行号，再按需展开**）。

**它的服务形态**（调研 PyPI 得到，决定了我们怎么接）：
`reme-ai` 0.4.1.12，`requires-python >=3.11`，**核心依赖里没有 agentscope**
（agentscope 是可选的 `as` extra），而 **`fastapi` 与 `fastmcp` 在核心依赖里**。
也就是说它本来就设计成"跑成一个本地服务，用 HTTP 或 MCP 对外"。
这一点很关键：它不需要和我们同一个 venv，**因此不会与我们的 `mcp>=2` 冲突**。

## 2. 设计

### 2.1 一条红线：记忆与文档知识库是**两个池子**

| | 记忆 | 文档知识库 |
| --- | --- | --- |
| 谁说的 | **你说的** | 文献说的 |
| 出处 | 无（来源是"某次对话"） | 有（文档、页码、章节） |
| 可变性 | 高频写入、用户随时改 | 低频、不该被改 |
| 检索口径 | 找回"我知道什么" | 找回"原文怎么写的" |

**绝不能混进同一次检索**：混了之后引用会脏（一段没有出处的结论和一段有出处的原文
并列返回）、溯源会断。所以 `search`（文档）与 `recall`（记忆）是**两个工具、
两条路径**，结果永不合并。

### 2.2 分工：谁存、谁整理

> **v0.46 起这一节已经作废，改法见 §3.5**：ReMe 不再参与，捕获/召回/文件都在
> KYLAB 自己的进程里。下面这一段保留着，是为了记清"当初为什么是那样分工"，
> 以及那些约束是怎么消失的。

- **ReMe 负责**：文件管理、捕获（Auto-Memory）、整合（Auto-Dream 四动作 + 三类记忆 +
  wikilink 图谱）、它自己的检索。
- **KYLAB 负责**：
  1. **门面**：对外暴露 `recall` / `remember` 两个 MCP 工具与两个 REST 端点，
     让 agent 不必知道 ReMe 的存在（也不必各自配一遍 ReMe 的地址与凭据）；
  2. **注入**：把 `MEMORY.md` 与 `SOUL.md` 读进对话的 system prompt；
  3. **界面**：浏览/编辑记忆文件、看记忆图谱。
- **数据落点**：ReMe 的 workspace 放在 KYLAB 的 `data/memory/` 下，
  与其它数据一起备份/迁移（一个部署只有一处要备份）。

> 关于"KYLAB 检索"：本轮**不**把记忆文件塞进 KYLAB 的 pgvector 索引。
> 理由是口径不同（记忆靠关键词 + wikilink 更准，文档才需要向量），
> 而且塞进去就破坏了 2.1 的两池隔离。记忆的召回统一走 ReMe 的
> `memory_search`，KYLAB 只做转发与呈现。**这是一个明确的取舍**，
> 若以后证明记忆也需要语义召回，再单独给记忆池开一路向量索引（不共用文档池）。
>
> （**v0.46 仍然不走向量**，理由改成了"规模上不值得 + 会破坏两池隔离"，
> 见 §3.5 的三条。这条取舍本身没变。）

### 2.3 开关与降级

**开关在界面上**：「设置 → 长期记忆 → 启用长期记忆」（运行期配置 `memory.enabled`，
落库、改完即刻生效）。`KYLAB_MEMORY_ENABLED` 只是它在环境变量那一层的引导值，
**不是另一套开关**——`RuntimeConfigService` 的取值顺序是"数据库 > .env 引导值 > 代码默认值"。
（v0.46 起这一组里**没有"服务地址"**了，见 §3.5。）

- **默认关**：捕获会用模型（每 N 个回合一次），升级之后默默开始烧 token
  是最不该有的默认——与"推荐问题"当初的取舍一致。
- **关着时**：`recall` 明确报"未启用记忆"，而不是返回空。
  返回空会让模型以为"没有相关记忆"，然后基于错误前提继续推理。
  反之，**开着而真的没搜到**时返回空是诚实的：那时检索确实在本地跑过一遍了。
- **`remember` 与那四份人设文件不看这个开关**（v0.21 起）：它们是磁盘上的普通文件，
  由我们直接读写（`_read_entries` / `write_bytes`），**关着也能记住、也能读到人设**。
  这个开关管的是另一半——过去的对话会不会被召回、会不会自动沉淀。
  原先人设也挂在这道闸上，结果用户的实例（记忆关着）里人设整个是死的，
  界面上还写着"没启用"。
- **没有"连不上"这一态了**（v0.46）：记忆是我们自己进程里的一路本地检索，
  没有第二个进程可连，所以没有中间态要处理。

**ReMe 的启动前提（当时实测，保留备查）**：它**必须**有
`LLM_API_KEY` 与 `LLM_BASE_URL` 才起得来——`reme/config/default.yaml` 里
`api_key: ${LLM_API_KEY:-}` 的默认值是空串，而启动时就会构造 `openai.AsyncClient`，
于是抛 "Missing credentials. Application startup failed. Exiting."
即使只想用它的文件操作与 BM25（README 说这些不需要凭据），**服务本身仍要一把可用的 Key**。
另外 `EMBEDDING_*` 在默认配置里是**注释掉的**，也就是默认只走 BM25——这与我们的设计相符
（记忆召回靠关键词 + wikilink，不需要向量）。

> 当年这条被写进部署文档的理由是"启用记忆 = 多一个进程 + 一把 LLM Key"。
> **v0.46 之后不再成立**：现在启用记忆 = 打开一个开关（要用的模型就是对话模型那一个）。

### 2.4 捕获怎么接进来

> **v0.46 改法见 §3.5**：捕获的**接入点与三条约束一字未变**，变的只是
> "谁来挑值得记的东西"——从 ReMe 的 Auto-Memory 换成我们自己的模型调用。
> 所以这一节仍然有效，只把"交给 ReMe"读成"交给 `MemoryService.capture`"。

ReMe 的 `auto_memory` 需要拿到对话回合。我们的接入点是**对话链路**：
一轮问答结束（`answer_agent_stream` 收尾）之后，把这一轮的用户问题与回答
交给 ReMe。三个约束：

1. **异步、best-effort**：记忆写入失败不该让一次问答失败（与 webhook 同口径）；
2. **不能阻塞响应**：放进队列（复用 `tasks` 表，新增 `TaskKind.MEMORY`），
   而不是在请求里同步调用；
3. **只送"值得记"的东西**：由 ReMe 的 Auto-Memory 判断，我们不在这里做二次筛选——
   但要把**已经召回过的内容**标出来（否则会把"刚找回的记忆"当成"用户新说的事实"，
   ReMe 自己也有这条纪律）。

### 2.5 SOUL.md

与记忆并列的第二类持久文件，性质不同：`MEMORY.md` 记事实与偏好，`SOUL.md` 定"你是谁"。
两条约定照抄 QwenPaw：

- **由 Agent 自己进化**（了解自己是谁之后更新它）；
- **改动要告知用户**——"这是你的灵魂，他们该知道"。

实现上它是一个受管的 Markdown 文件（与笔记同一套编辑器与存储），
注入位置在 system prompt 的前部，**不进任何检索**。

#### 2.5.1 人设文件是一组四份，模板照抄 QwenPaw（v0.21）

一个账号一个 Agent，它的人设是**四份并列的文件**（`services/memory.py` 的
`PERSONA_FILES`），按这个顺序注入：`SOUL.md`（人格）→ `PROFILE.md`（我是谁/对方是谁）
→ `AGENTS.md`（这类活怎么干）→ `MEMORY.md`（已知的事实）。越靠前越像"身份"，
越靠后越像"数据"。

**模板直接抄 QwenPaw 的 `md_files/zh/`**，理由是这一层的价值全在"写什么"上：
它那几份写的是**行为约束**而不是自我介绍（"真心帮忙，别演""先自己想办法"
"对内大胆、对外谨慎""你是客人"），每一条都能落成具体动作；而空标题的骨架
（`## 我是谁` / `## 我的准则`）只会让新 Agent 先猜"这里该写什么"。

抄的时候改了三处，都是"照抄会出错"的地方：

1. **emoji 全部剥掉**（这个项目禁 emoji）。它有一整节讲在 Discord/Slack 上
   用表情回应——那部分**整节删掉**：我们没有那种通道，写进去等于让模型
   去等一件不会发生的事；
2. **`Heartbeat` 那一节删掉**：那是它的心跳轮询机制，KYLAB 没有这个机制。
   在给模型看的文件里描述一个不存在的机制，比不写更糟；
3. **"工具"那一节按我们的现实改写**：技能在它那里是"去看 `SKILL.md` 文件"，
   在我们这里是 `list_skills` / `read_skill` 两个工具。**写成真实的工具名**
   ——描述里给一个不存在的能力，模型只会去试、然后失败。

`MEMORY.md` 只改了一处：它那四条"该记什么"的例子是列表项，而我们这个文件里的
列表项**就是记忆条目本身**（`_read_entries` 按 `- ` 认条目），照抄的话那四条
会在下一次 `remember` 时被当成四条已存在的记忆。改成一句散文，意思不变。

**顺带修掉一个静默删除**：`_write_entries` 原先替换「核心长期记忆」那一节的
整段正文，而模板那段"记什么、别记什么"的说明正好在那一节里——第一条记忆落盘时
它会被悄悄删掉，其中包含"**除非明确要求，不要记录密码、令牌或其他敏感信息**"
这条安全约定。现在只替换 `- ` 条目行，散文与其余小节一并保留。

## 3. 分期与验收

| 期 | 内容 | 验收 |
| --- | --- | --- |
| **一** | 配置 + 服务连通性检查；`recall` / `remember` 两个工具与端点；关着时明确报错 | 关着 → 明确报错；开着 → 能召回 ReMe 里手写的记忆 |
| **二** | `MEMORY.md` / `SOUL.md` 注入 system prompt；对话收尾入队 `TaskKind.MEMORY` 交给 ReMe 捕获 | 注入生效（提示词里能看到）；一轮问答后记忆文件出现新条目 |
| **三** | 记忆页：浏览/编辑 Markdown、查看图谱、显示"哪些还没被整合" | 能改一条记忆并在下一轮对话里被召回 |

三期**已完成**。落地时的三个决定与 §3.1 的接口普查有关，写在 §3.3。

**一期那两行的措辞已经过时**（"需要一个能跑起来的 ReMe 服务""服务连通性检查"）：
v0.46 起记忆并进了我们自己的进程，没有第二个服务、也没有连通性可查，见 §3.5。

**一期的前置**：需要一个能跑起来的 ReMe 服务。第一期**不引入 `reme-ai` 依赖**，
只按它的接口对接（它本身就是服务），这样 KYLAB 的依赖树不变，
本地没装/没起 ReMe 时一切照旧。若以后要把 ReMe 嵌进同一个进程，再评估 extra。

### 3.1 接口面（ReMe 时代的实测记录，v0.46 起不再使用）

> **这一节与下一节是历史资料**（当时把 ReMe 的接口钉死用的）。v0.46 起我们不调它了
> ——为什么还留着：迁移、排查"当年为什么这么设计"时，它们是唯一的一手记录，
> 而且**若哪天要重新评估 ReMe**（比如它的依赖冲突解决了），这里省掉一整轮调研。
> 现在真正在跑的接口面见 §3.5。

调研阶段把它当成未完成项，后来装了一遍 + 读了源码，现在是确凿的：

**HTTP 面**：`reme/components/service/http_service.py` 的 `_add_json_job` 写道
`self.service.post(f"/{job.name}", …)`——也就是**每个 job 就是 `POST /<job 名>`，
请求体是 JSON**。所以：

```
POST http://127.0.0.1:2333/search        {"query": "...", "limit": 10}
POST http://127.0.0.1:2333/read          {"path": "digest/wiki/x.md", "start_line": 1, "end_line": 80}
POST http://127.0.0.1:2333/health_check  {}
POST http://127.0.0.1:2333/auto_memory   {...}
```

**端口是 2333**（`reme/constants.py` 的 `REME_DEFAULT_PORT`）——这里原先写 8181
是照文档抄的，而 `memory.base_url` 的默认值也跟着抄错了，照它配永远连不上。
真机联调时才发现（见 §3.4）。

job 名从 CLI 就能列出来（`reme help`；CLI 与 HTTP 共用同一批 job）：
`search` / `read` / `health_check` / `auto_memory` / `reindex` / `find_reme` 等。
MCP 面是同一批 job 注册成工具，路径可配（`mcp_path`，默认形如 `/mcp`）。

**两条实测得出的接入注意**（都写在文档里免得重踩）：

1. **`reme-ai` 的依赖声明不完整**：核心依赖里没有 `agentscope`，但
   `reme/steps/base_step.py` 直接 `from agentscope.model import ChatModelBase`——
   只装 `reme-ai` 会在 import 时就炸。必须装 **`reme-ai[as]`**（实测装完是
   `agentscope 2.0.7.post1`）。
2. 而 agentscope 2.0.7.post1 **钉 `mcp<2.0.0`**，与我们的 `mcp>=2` 互斥。
   所以"记忆服务独立进程/独立 venv"不是可选项而是**必须**——
   好在它本来就是服务形态，两种传输（HTTP／MCP）都对外。

**给一期用 HTTP 而不是 MCP 的理由**：HTTP 是一行 `httpx.post`，
不需要在 KYLAB 里新引一个 MCP 客户端依赖；而且 `POST /<job>` 的返回是纯 JSON，
比 JSON-RPC 少一层。等 ReMe 的 MCP 面稳定且我们确实要复用时再换。

**端点普查（实测：装好并起服务后读 `/openapi.json`，共 33 个）**：

| 类别 | 端点 |
| --- | --- |
| 我们要用的 | `search`（召回）、`auto_memory`（捕获）、`health_check`、`status` |
| 三期（记忆页）会用 | `list` `read` `load` `write` `save` `edit` `move` `delete` `stat` `frontmatter_read` `frontmatter_update` `frontmatter_delete` `list_tags` |
| 图谱 | `graph_snapshot`（整体）`traverse`（按节点展开） |
| 整理与维护 | `auto_dream` `auto_resource` `reindex` `daily_reindex` `daily_list` `daily_write` |
| 其它 | `app_config` `chat`（它自带一个只读 agent）`help` `version` `node_search` `proactive_read` `auto_memory_cc` `read_image` |

`POST /help` 是它**自带的说明书**（返回每个 job 的参数与默认值），
比读 OpenAPI 更省事——OpenAPI 里只有一个 `additionalProperties: true` 的通用信封。

### 3.2 两个关键契约（ReMe 时代的实测记录，同上）

**召回 `POST /search`**

```jsonc
// 请求
{"query": "锂价下跌对利润的影响", "limit": 3}   // 也支持 min_score / tags / start_date / end_date
// 响应
{"answer": "…给人读的文本，带行号与 score…", "success": true,
 "metadata": {
   "results": [{"id": "…", "text": "片段原文",
                "path": "digest/wiki/锂价敏感性.md",
                "start_line": 5, "end_line": 9,
                "scores": {"keyword": 2.72, "score": 2.72}}],
   "link_expansion": {"<命中路径>": {"outlinks": [{"path": "…", "meta": {"name": "…"}}],
                                   "inlinks":  [ … ]}}}}
```

**两个位置我们第一版都猜错了**：结果列表在 `metadata.results`（不在顶层），
分数在 `scores.score`（不是顶层 `score`）。第一版的容错解析在这份真实数据上会
直接报"认不出结构"——是**真跑了一遍服务**才纠正的，现在测试里存着这份原始返回。

`link_expansion` 是**免费附带的图谱**：召回片段的同时给出出边/入边，
所以"先给片段、不够再顺着链接走"这条渐进式召回不需要第二次请求。

**捕获 `POST /auto_memory`**

```jsonc
// 请求
{"messages": [{"role": "user", "name": "用户", "content": "以后简短点"},
              {"role": "assistant", "name": "助手", "content": "好"}],
 "session_id": "conv_xxx"}     // 也支持 date / memory_hint
// 响应
{"answer": "Created `2026-09-16/xxx.md`, recording …", "success": true,
 "metadata": {"date": "…", "path": "daily/2026-09-16/xxx.md",
              "created": true, "modified": true, "n_messages": 2,
              "source_conversation": "[[session/dialog/conv_xxx.jsonl]]", "index": {…}}}
```

**每条消息必须带 `name`**：ReMe 那侧收的是 agentscope 的 `Msg`，缺 `name` 会被它
自己的校验拒掉（实测报 `1 validation error for Msg / name Field required`）。
`name` 就是"谁说的"——所以我们在自己这边就拦住，而不是替它编一个。

`created: false` 表示这次对话没有值得记的新内容（ReMe 不会产生空记忆），
调用方据此不必报告"记下了"。

**两个字段的分工**：`answer` 是给人读的一句话，`metadata` 才是结构化数据。
**永远读 `metadata`，不要去解析 `answer`**——那是渲染给人看的文本，格式随时会变。

**已实测跑通的闭环**：`auto_memory` 写入 → 索引 → `search` 把它召回
（实测里那条"用户偏好简短回答"确实被搜出来了）。

### 3.3 三期落地时改掉的两个判断（读源码得出，不是猜的）

三期的记忆页要"改一条记忆，然后在下一轮对话里被召回"，所以必须搞清一件事：
**我们改了文件之后，ReMe 的索引什么时候跟上。** 我原先的设计是"每次保存后
调一次 `reindex`"，读完它的 `config/default.yaml` 与 `steps/index/*.py` 之后
推翻了——两处都错：

1. **它自己有一组文件守护，不需要我们管**。`index_update_loop` 的
   `watch_dirs: [daily_dir, digest_dir]`、`watch_suffixes: [md]`、
   `force_polling: true` + **5 秒 debounce**（`DEFAULT_WATCH_DEBOUNCE_MS = 5_000`，
   step 1 秒、poll 5 秒）。文件一改，它自己重新分块入库。
2. **`reindex` 看不见新文件**。它 job 的说明是
   *rebuild BM25, embedding, and/or tag indexes **without rescanning workspace files***，
   参数是 `scope: all|bm25|embedding|tag`（默认 `all`）——也就是"只重建已入库分片的
   索引"。所以每次保存后调它**既多余、又解决不了新文件的问题**。

于是实现改成：**保存路径上什么都不做**（`MemoryService.write_file` 不调 `reindex`），
`POST /memory/reindex` 只留作手动兜底（服务当时没起、之后才拉起来这类情况）。

**同一份配置还划出了一条界**：只有 `daily/` 与 `digest/` 在 `watch_dirs` 里，
也就是说**只有这两个目录会被召回**；`MEMORY.md` / `SOUL.md` 靠**注入**生效
（每轮整份进 system prompt）、本来就不参与检索，其余位置的文件既不召回也不注入。
这条事实由 `MemoryFile.retrievable` / `.injected` 带到界面上——不写清楚的话，
用户改完一个不参与检索的文件却搜不到，会以为是索引坏了。

**另外两件事记在这里，免得下一个人重踩**：

- **浏览与编辑走本地目录，不转发 ReMe 的 `list`/`read`/`write`**。这个工作区是
  我们自己的（`data/memory/`，§2.2 的数据落点），`remember` / `core_text` 早就直接
  读写它；转发一圈的代价是"读自己的文本文件还得先有另一个进程活着"。所以记忆页的
  文件浏览与编辑**在 `memory.enabled=false` 时也能用**——界面上明说哪一半还能用。
- **写文件要写字节，不能写文本**。`Path.write_text` 在 Windows 上会把 `\n` 翻成
  `\r\n`，文件里本来就有 `\r\n` 时结果是 `\r\r\n`——每存一次长一个 `\r`（实测：
  往返一趟就不再逐字相等）。记忆文件是用户也会用别的编辑器改的东西，
  我们只能原样存回。

### 3.4 真机联调（2026-09，真后端 + 真 PG + 真 ReMe + 真文件系统）

三期的验收是"能改一条记忆并在下一轮对话里被召回"。上面那些是读源码与单测得出的，
真正把 ReMe 起起来、把文件写进工作区、从浏览器点一遍之后，又抓到三件事——
**都是只有真跑一遍才会出现的**：

1. **默认端口写错了：ReMe 是 2333，不是 8181。** `reme/constants.py` 里写着
   `REME_DEFAULT_PORT = 2333`，`reme start` 起来后日志打的是
   `REME_SERVICE_INFO={"host": "127.0.0.1", "port": 2333}`。
   `memory.base_url` 的默认值原先照文档抄了 8181，**照它配就永远连不上**，
   而界面上只表现为一句"连不上"——很难看出是端口抄错。已改成 2333。
2. **`probe` 在"启用且服务活着"这条路径上 500。** 它用
   `MemoryStatus(**{**base.__dict__, ...})` 拼返回值，而 `MemoryStatus` 是
   `slots=True` 的记录、**没有 `__dict__`**。修法是 `dataclasses.replace`。
   值得记的是它为什么能活到真机才炸：唯一沾到 probe 的接口用例断言的是
   "成员访问被拒"（403），压根走不到实现；单测又只覆盖了"关着"那条 early return。
   **"只测失败分支"会让整条成功路径无人看守**，现在三条分支都有用例。
3. **`GET /memory` 返回 `reachable: false`，而服务其实是健康的。** 那个端点故意
   不打远端（界面每次渲染都调它），却把 `reachable` 填成了布尔 `False`，
   于是页头常挂"记忆服务未连接"的警示——**而那时根本没有谁去连过**。
   改成三态：`None` = 这次没探测，只有 `probe` 才给 `True`/`False`。
   界面因此只说"已启用"，不说"未连接"。

**三条实测的旁证**（顺手确认了前面的设计判断）：

- ReMe 启动时的 `[InitChangesStep] scan file_store` 报 **`added: 4`** ——
  正是 `daily/` 与 `digest/` 下那 4 个文件；根下的 `MEMORY.md` / `SOUL.md`
  **不在其中**。这就是 §3.3 那条"只有 daily/digest 会被召回"的直接证据。
- 它启动后打印 `Watching: [daily, digest] step=1000ms debounce=5000ms`，
  与 §3.3 从配置里读出的 5 秒 debounce 一致。
- **Auto-Dream 真的会改写 `digest/` 下的文件**：我们写进去的那份
  `digest/procedure/跑后端门禁.md` 被它重排成"触发 / 前置输入 / 步骤 /
  失败模式 / Sources"的结构，并回链到当日笔记，同时生成了 `daily/2026-09-16.md`
  当日索引。于是 `MemoryFile.consolidated`（靠回链判定）在真数据上确实为真——
  这条启发式不是纸面上的。

联调覆盖的路径：真实会话登录 → 文件列表（7 份，含 ReMe 生成的当日索引）→
读/写往返（浏览器里改一份，磁盘上 md5 与内容都对得上）→ 图谱（真 wikilink 与
悬空链接）→ 召回（真命中，带行号 L5-10 / L11-22 与融合分数 6.33 / 5.74）。
页面无 console 报错、无 4xx/5xx。


### 3.5 v0.46：记忆并进我们自己的进程（ReMe 退出）

**用户的话**：「reme那个 我觉得就不应该单独起一个端口来接收。他应该跟我们的后端是绑定到一起的。」

#### 3.5.1 先复核前提：嵌不了，冲突还在

§3.1 记着一条实测结论（"必须装 `reme-ai[as]` → agentscope 2.0.7.post1 → 钉 `mcp<2.0.0`"）。
动手之前重跑了一遍，**冲突仍然成立**（2026-09-24，`backend/` 下）：

```
$ cd backend && uv pip install --dry-run "reme-ai[as]"
Resolved 135 packages in 94ms
 + agentscope==2.0.7.post1
 + fastmcp==3.4.7
 - mcp==2.2.0
 + mcp==1.30.0
 + reme-ai==0.4.1.12
```

`- mcp==2.2.0 / + mcp==1.30.0` 就是那次降级：把 ReMe 当库 import 进同一个进程，
代价是**把我们自己的 MCP 接入层从 2.x 降到 1.x**（而 `mcp_server/server.py` 用的是
2.x 才有的 `MCPServer.add_tool`）。拿工具层换记忆层不划算，所以
**同一进程 import 这条路是关着的**；而"用户不该多起一个端口"这条要求本身是对的
——于是正确的解法不是"把 ReMe 塞进来"，而是**我们不再需要它**。

#### 3.5.2 改法：三件事都 native，服务面全删

| 能力 | 原先 | 现在 |
| --- | --- | --- |
| 召回 `recall` | `POST {base_url}/search` | `memory_files.search`：在本工作区的 Markdown 上按块打分（本地，无索引，无第二个进程） |
| 捕获 `capture` | `POST {base_url}/auto_memory` | `MemoryService.capture`：问一次对话模型挑条目 → 去重 → 追加到当天的 `daily/` 文件 |
| 状态 `status` | 本地字段 + `reachable` 三态 + `/memory/probe` | **纯本地数字**：几份文件、几份可召回、可召回几条、上次更新 |
| `reindex` | 请 ReMe 重建索引 | **端点删掉**：每次按需扫工作区，没有索引要重建 |
| 设置项 | 开关 / **服务地址** / 工作区 / 节流 / 服务所属账号 | 开关 / 工作区 / 节流 |

**`memory.base_url` 删了**（运行期配置 + `.env` 引导 + 设置页字段），
`memory.service_scope` 也删了：那一项存在的唯一理由是"一个 ReMe 实例只能盯一份
工作区"，而 native 之后按账号分目录天然就是精确隔离的——留着它反而能让管理员配出一个
把自己锁死的值（"服务盯的是 u1，你去查共享桶"）。**`POST /memory/probe` 也删了**：
它本来就是"打一次那个可配置地址"，本地实现里没有可打的东西。

**两池隔离仍然是第一条纪律**（§2.1）：记忆召回**连索引都不与文档共用**，
它读的就是 `data/memory/` 下的 Markdown，不 import 检索服务、不碰 pgvector。
测试里有一条盯着这件事（`test_recall_never_returns_document_pool_content`）。

#### 3.5.3 召回怎么打分（口径写在这里，免得下一个人猜）

**为什么不上向量**：这一池子是"个人长期记忆"，量级是几份到几百份文件、几百 KB；
词面命中已经够用，而向量要么进文档池（破坏两池隔离）、要么为记忆单开一路索引
与一份 embedding 账单。**在证明"规模上值得"之前不付这个代价**——
这仍然是 §2.2 那条取舍，只是理由从"ReMe 有 BM25"换成了"规模上不值得"。

- **切块**（`memory_files._split_blocks`）：空行分段；**顶格的标题或列表项另起一块**
  （日笔记里一条 `- ` 就是一条记忆，粘成一整块就分不清命中哪一条）；缩进的列表项不切开；
  超长块按行数再切。行号是**文件里的真实行号**（frontmatter 的几行要算进去，
  否则用户按行号去编辑器里找会找错地方）。
- **打分**（只用于排序）：`Σ(证据权重 × (1 + ln 频次))`，权重 = `ln(1 + 块数/(1+出现块数))`
  （一份日笔记里到处都是「用户」，「用户」就不该和「锂价」一样重）；
  命中的证据出现在**标题/路径/摘要**里时整块乘 1.5；查询原样出现再加 2.0。
- **命中判据**（不看分数，**两条证据通道任一条通过**即可）：

  | 通道 | 单位 | 判据 |
  | --- | --- | --- |
  | 实词 | jieba 切出来的词（≥2 字），**剔掉疑问词** | 至少 2 个命中（单位不足 3 个时按 1 个）**且**覆盖 ≥ 1/3 |
  | 相邻字对 | 去空格后的滑动二元组（不依赖分词） | 同上 |

  覆盖率是归一化的量、跨查询可比，所以"没召回任何东西"永远只有一个含义：
  这几份记忆里确实没有相关的话。取值比文档检索那边的 0.5 松，是因为记忆的块
  往往只有一句话（实测：拿 0.5 去卡，界面输入框里那句示例提示词什么都搜不出来）。

  **两条"实测逼出来的"规则**：

  1. **疑问词不算证据**（`_FILLER_WORDS`：什么/怎么/为什么/多少/是否…）。
     它们描述"我要问什么"，不是"这段记忆在说什么"。不剔掉的两种坏法各一例：
     「复盘什么时候做」在写着「复盘固定每周五下午做」的记忆上被判成不相关
     （"什么时候"没命中）；而「用户的时间安排」会靠蹭上「用户」更像命中。
  2. **字对那条通道**：分词是 jieba 做的，它的切法与正文写法可能对不上——
     实测「发布前要先跑什么」被切成 `发布 / 前要 / 什么`，而正文写的是
     「发布前必须先跑一遍后端门禁脚本」：`前要` 在正文里永远找不到。
     字对（`发布 / 布前 / 先跑`）不依赖分词，正是为这类情况留的。
     两条通道**分开算覆盖率**（不混在一张表里数）：混着数会把正常提问的覆盖率
     压到线下——这条也实测过。
- **每份文件最多 3 条**：没有这条限制，一次召回会被某一份长日笔记占满，
  而召回的价值恰恰在于从多个文件里凑线索。
- **顺链的邻接边照旧免费**：命中文件的 wikilink 解析出来后给出（入链/出链各一步），
  不需要第二次检索。

**召回池的边界没变**：只有 `daily/` 与 `digest/` 参与召回；`MEMORY.md` / `SOUL.md`
那几份每轮整份注入，再召回一遍就是同一段内容进两次上下文。这条界原先是从 ReMe 的
`watch_dirs` 读出来的（§3.3），现在由我们自己的 `_INDEXED_KINDS` 定——
**用户看到的行为一字未变**，界面上的 `retrievable` 标记与那句"搜不到是位置决定的"
说明继续成立。

#### 3.5.4 捕获怎么落（沿用队列与重试，落 daily）

链路一字未改：对话收尾 → `MemoryService.enqueue_capture`（每 5 个用户回合一次）
→ 入队 `TaskKind.MEMORY` → worker 调 `MemoryService.capture` → 失败按队列的
重试语义走（不吞异常：吞掉的话"记忆开着却什么都没记住"会变成查不出原因的现象）。

捕获本身三步：

1. **问一次对话模型**：用运行期配置里绑定给「对话生成」的那个模型（记忆是对话的
   副产品，没理由用别的模型）。提示词里留着 ReMe/QwenPaw 那份"什么值得记"的清单
   （稳定偏好、项目背景与长期约束、已确认的决定及原因、当前进展与阻塞、可复用的做法），
   并且**把已经记过的条目给模型看一份**（最近 60 条）——这是我们能做的最省的去重；
   最后两条是安全与卫生：**敏感信息不进记忆**（这条规矩原本只写在 `MEMORY.md`
   模板里，而捕获是我们唯一会"自动写入"的入口）。
2. **解析 + 去重**：只认带项目符号/编号的行（模型回一句散文时结果就是"没有新条目"，
   不会把一句说明写进记忆）；每条上限 500 字、一次最多 5 条；
   去重三条判据 + 两条否决，见下。
3. **落盘**：追加到**当天的 `daily/YYYY-MM-DD.md`**（本地日期：这是给人看的
   "今天的现场"，用 UTC 会让东八区早上 8 点前的对话记到"昨天"）。
   来源会话写成一行 HTML 注释 `<!-- 来源会话 conv_x -->`：渲染出来看不见，
   又能回答"这条是哪次对话来的"；**不写成 wikilink**——那会连到不存在的文件上，
   把图谱的悬空链接数弄脏。

**为什么落 daily 而不是 `MEMORY.md`**（这是 §1 两层分工的直接推论）：
`MEMORY.md` 是每轮**整份注入上下文**的核心文件，自动沉淀直接写进去等于机器替人决定
"什么该长期占着上下文窗口"；daily 是按需召回的现场，只增不并，由人（或以后的整理机制）
再决定哪几条值得升进核心。

**去重判据**（`_similar`）：指纹相同（只差标点空白）→ 整段包含且只多出几个字
（`CONTAINMENT_SLACK = 6`）→ 字符二元组重合度 ≥ 0.7。两条**否决**：数字不同就不是
同一件事（版本号、地址、数量、日期都是数字，"codelab → codelab2"不能被当成重复）；
其中一条为空则不算。

**为什么阈值偏高、且包含关系只允许差几个字**：漏过一条重复是看得见的（用户扫一眼
文件就能删），而误判"新事实 = 旧条目"会**静默丢掉一条真事实**——尤其在这一轮
**没有整理机制**的前提下（没有 Auto-Dream 去合并），拦下来就等于丢了。
两者不对等，所以宁可少拦。

**这一层拦得住什么、拦不住什么**（实测）：

| 情况 | 结果 |
| --- | --- |
| 同一句、只差标点空白 | 拦（指纹相同） |
| 语序调换的同一句 | 拦（二元组重合度 0.8） |
| 同一句补几个字（≤ 6 字，数字不变） | 拦（整段包含） |
| 数字变了（版本号 / 地址 / 数量） | **不拦**（是另一件事） |
| 补了半句的新信息 | **不拦**（没有整理机制去合并，拦下就是丢信息） |
| **换了说法的同一件事** | **不拦**——实测「发布顺序固定为：先跑门禁 → 再打标签 → 最后推镜像。」与「发布顺序是门禁、打标签、推镜像」判不出来 |

最后一行那种情况靠的是**提示词那一侧的纪律**（把已有条目给模型看，让它自己别重复，
实测第二轮返回 `created: false`），以及以后若做了整理机制由它去合并。
机械化地判"两句话说的是不是一回事"要的是语义，不是字面——那是这一层不做的事。

#### 3.5.5 这一轮**没做**的（以及没做会发生什么）

1. **Auto-Dream 四动作整合（CREATE/CORROBORATE/REFINE/CORRECT）——不做。**
   后果是**记忆只增不并**：捕获进来的条目会一直躺在 `daily/` 里，不会自动折叠进
   `digest/`、不会与旧条目合并、也不会被修正。界面上那枚「待整合」标记因此会
   长期为真——它是**如实**的（没有回链就是没被整合），但用户要自己动手，
   或者接受"日笔记越攒越多"。要做的话，落点很明确：读一批 daily 条目 +
   已有 digest，让模型产出"新增/佐证/精炼/纠正"四类动作，**只写 digest/**
   （那条铁律：结论可变、现场不可变）。
2. **ReMe 的 BM25 检索质量——不追。** 我们只做词面命中 + 标题加权 + 整串加分
   （§3.5.3）。它没有同义词、没有词干化、没有相对文档长度的归一化（BM25 的那套
   参数）；换来的是零依赖、零索引、可测（纯函数）。**规模变大时第一个该回来看的
   是这里**：如果哪天记忆变成上万条、词面命中开始不够用，先考虑"给记忆池单独开一路
   向量索引"（不共用文档池），而不是把 ReMe 请回来。
3. **响应里不再有 `answer` 那样"给人读的一段话"。** ReMe 的返回里有
   `answer` 字段（带行号与分数的可读文本），我们只给结构化的命中列表——
   界面自己拼显示，模型那边由 MCP 工具自己格式化。少一处"文本格式随时会变"的依赖。
4. **`reindex` 端点与界面上那颗「重建索引」按钮删了。** 本地检索没有索引，
   留着它就是一个点了什么也不发生的按钮。

#### 3.5.6 实测验收（2026-09-24）

- **召回**：在工作区里手写三条记忆（digest 一份、daily 一份、核心 `MEMORY.md` 一份），

#### 3.5.7 顺带修掉的一件事：界面上不该出现实现细节

## 5. 已知边界（做完了，但要说清）

**"一个账号一个工作区"现在是精确的**（v0.15 落的目录分桶，v0.46 之后由 native 实现保证）。

历史：v0.15 之前记忆只有一份共享工作区；ReMe 时代的"按账号隔离"受制于它的
`workspace_dir` 是**进程级**配置（一个实例只能盯一份工作区），所以"每个账号一份"
意味着"每个账号跑一个 ReMe"。native 之后这条限制**消失了**：`workspace_for(user_id)`
决定扫哪个目录，召回与捕获都按它取——隔离是代码里的一个路径，不是进程数。

当前形态：

- 普通成员 → `data/memory/<user_id>/`（各自的人格、长期记忆、日笔记，互不可见）；
- 管理员网页会话与 API Key 通道 → `data/memory/`（**共享桶**，也是单用户部署下的老路径）；
- 这个分桶与知识库/会话/笔记的归属口径一致，见 `api/v1/memory.py` 的 `_scope`。

仍然要记住的两条：

1. **共享桶是"无账号归属"的那一份**（管理员与 API Key 共用），
   不是"所有人的公共池"——普通成员看不到它，也写不进它；
2. 界面上显示的那行工作区路径就是**当前这一份的落点**，页面不另做隔离判断
   （分桶由后端的登录令牌决定）。
