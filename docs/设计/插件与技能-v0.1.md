# 插件与技能设计 v0.1

> 实现开发计划 §12.225 的 **P1-4（插件包与本地市场）**。
> 格式与语义照三家（ZCode / DeepSeek Harness / QwenPaw）的交集抄，
> 逐条对照见 [Agent-与对话架构对标调研 v0.1](../调研/Agent-与对话架构对标调研-v0.1.md) §2.4。
>
> **这一版只做本地**：没有在线市场、没有下载、没有来源与版本锁。
> 能力面四类**都还没接执行**——哪一类到了哪一步，§3 写明。

## 1. 两档能力：技能与插件

| | 技能（v0.15） | 插件包（本版） |
| --- | --- | --- |
| 磁盘形态 | 一个目录 + `SKILL.md` | 一个目录 + `plugin.json`（+ 按约定摆的组件） |
| 是什么 | **写给模型看的流程与索引** | **一个能力包**：里面可以装技能、命令、钩子、工具 |
| 校验 | 缺 `description` 不进提示词（标出来） | 缺 `name` / 名字不合法 / 组件路径越界 → **整条不加载**（标出来） |
| 发现源 | 仓库 `skills/` → `data/skills/`（内置优先） | `data/plugins/` → 仓库 `plugins/`（**用户优先**） |
| 状态 | 无（在目录里就是生效） | `app_settings` 里的启停与屏蔽 |
| 清单文件 | `SKILL.md` 的 frontmatter | `plugin.json` |

**为什么要有第二档**：技能只能装"文本流程"，谁也没法把一个带命令、带钩子的包交给它。
而这三家都有插件这一档，且都把它**收窄**了：ZCode 的组件靠目录约定发现、
QwenPaw 的能力面只有四类、DSH 用有序层栈表达"谁覆盖谁"。
我们照它们交集最小的那一份做——**能跑通的最小形态是一个只有 `plugin.json` 的目录**。

## 2. 格式与目录约定

### 2.1 `plugin.json`

```json
{
  "name": "demo-pack",
  "version": "0.1.0",
  "description": "这个包干什么（一行）",
  "author": "谁写的",
  "homepage": "https://example.com",
  "userConfig": [{ "name": "token" }],
  "tools": [{ "name": "导出", "description": "导出文档", "entry": "src/export.py" }]
}
```

- **只有 `name` 必填**（照 ZCode）。它同时是插件的标识符、接口路径参数与设置键的一部分
  （`plugins.enabled.<name>`），所以形状必须可猜：`^[a-z0-9][a-z0-9._-]{0,127}$`。
- `version` 缺省 `0.0.0`（照 ZCode）。
- `userConfig` 与 `tools` 是**声明**：前者是"这个包有哪些可配项"，后者是它提供的工具。
- **组件不写路径**（照 ZCode）：技能/命令/钩子靠目录约定发现（§2.2），
  只有 `tools[].entry` 是路径——那本来就要指向一段代码。
- 形状不对（不是 JSON 对象、`tools` 不是列表、某项缺 `name`）→ **整条拒载并给出原因**。
  静默当没有会让写它的人以为声明生效了。

### 2.2 组件靠目录约定

| 能力面 | 约定位置 | 识别方式 |
| --- | --- | --- |
| skill | `skills/<技能>/SKILL.md`（也认 `skills/<组>/<技能>/SKILL.md`） | 与技能那一档同一份 frontmatter（名字、描述） |
| command | `commands/*.md` | 文件名即命令名，`description` 取 frontmatter |
| hook | `hooks/hooks.json` | 事件名 + 每条事件的条数 |
| tool | manifest 的 `tools[]` | 名字、描述、`entry` |

**只看一层（技能两层）**：再深就是"把别人的仓库整个拷进来"，扫描会变成遍历。

**没有 `.mcp.json` 这一条**：计划 P1-4 那一行提到过它（照 ZCode 的约定），但本轮按
四类能力面收窄，插件里"要连的外部服务"与 `tools` 是同一类**声明**，
而这一类只列出、不注册（§3）；MCP 服务的登记仍然走能力页第二栏那条路。

### 2.3 发现源与优先级

固定两条、**first match wins**：`<data_dir>/plugins/`（用户放的）→ 仓库自带 `plugins/`
（内置；**没有这个目录就跳过**，不是错误）。同名时以**用户目录那份**为准——
它是"他现在要的这个版本"，内置那份是随代码发布的兜底。
（注意这条与技能那一档（内置优先）**正好相反**，是本版按用户指定的 ZCode 顺序做的。）

隐藏目录（`.` 开头）与 `_` 开头的目录不算插件：那是用户的杂物，不是"加载失败的插件"。
一个目录里**没有 `plugin.json`** 则算一条加载失败（带着原因），
因为"我放进去了它却不出现"必须有答案。

### 2.4 校验失败的插件照样在列表里

照 DSH 的"失败的 preset 也列出"。失败的判据：

1. 没有 `plugin.json`；2. 不是合法 JSON；3. 缺 `name`；4. `name` 形状不合法；
5. **组件路径逃逸插件根**——`tools[].entry` 指到外面（`../../.ssh/id_rsa`、
   绝对路径指到别处），或 `skills/` 下有一条指到插件根外的符号链接。

逃逸一律**整条拒载**而不是"只跳过越界那一个"：只跳一个的话，列表上看起来一切正常，
而少了一个组件没人会发现。

坏掉的 `hooks/hooks.json` **不拒载整个插件**：manifest 是好的，坏的是它的一个组件，
而"这个组件坏了"本身就是要在界面上说出来的一件事（那一行里写着读不出来的原因）。

状态（启停）从不算加载成功与否：内容坏与状态是两件事，
用户把 manifest 改好之后点一下"重新扫描"，它该还是原来那个状态。

## 3. 四类能力面：现在到了哪一步

照 QwenPaw 的 `register(api)` 四类（provider / 生命周期 hook / 控制命令 / 工具配置）收窄。
**做不到的要说"未实现"，不假装支持**——每一类的状态由后端给出、界面原样显示：

| 能力面 | 状态 | 说明 |
| --- | --- | --- |
| skill | 已发现 | **未接入**：技能的装载仍走 `skills/` 那两条来源（仓库 + 数据目录），插件内的技能还没并进去 |
| command | 只列出 | 未实现：本轮只列出，不执行 |
| hook | 只列出 | 未实现：本轮只列出，不触发 |
| tool | 只列出 | 未实现：本轮只列出，不注册成工具 |

**为什么技能没有一起接上**：技能的装载在 `services/skills.py`，而那一档同时在做
"目录注入 + 校验前置"（P0-3）；两处同时改同一份发现逻辑必然打架。
下一轮把它接上时的做法是明确的：`skills.py` 的发现源加一层"启用的插件根"
（照 ZCode 的第六层发现：显式根 → 用户 → `~/.agents` → 工作区逐级上溯 → 插件根），
插件只在**启用时**贡献那一层。

## 4. 状态与内容分离

插件目录**只读**——服务层一个字节都不写它。状态写 `app_settings`：

| 键 | 含义 |
| --- | --- |
| `plugins.enabled.<name>` | `true` / `false`。没写过 = 启用（把它放进目录本身就是"我要用它"） |
| `plugins.blocked.<name>` | **屏蔽标记**：内置插件被用户停用时的记录，值是它的版本号 |

三条理由（照 ZCode）：

1. **重新扫描永远安全**：列表是只读的，扫描不产生副作用；
2. 插件目录可以交给 git / 同步盘 / 手工管理，我们不去改它；
3. 停用**可逆**：想回来点一下启用即可，而"卸载"是用户在文件系统里的事。

**内置插件的"物化"我们没做拷贝**。ZCode 是把内置插件拷进用户目录、版本变了才刷新；
KYLAB 的内置插件与技能一样是**仓库里那一份**（部署时只读），发现顺序已经覆盖了它，
再拷一份进数据目录只会产生两个真相（改哪一份生效？）。所以照抄的是它**能观察到的
两条语义**：① 扫描是幂等的，内置插件每次都以同样的一条记录出现；
② 被用户停用的内置插件记一条**屏蔽**而不是从磁盘上抹掉——"伪装卸载"，
但它仍然在列表里看得见（标着「已屏蔽」）。启用的动作会清掉这条标记。

## 5. 配置项（密管）与本轮的边界

调研 §2.4 把 ZCode 的 `userConfig.sensitive` 无法在 UI 录入列为**反面教材**，
并要求"先把密管做出来再谈插件市场"。本轮的落点：

- 插件目录**绝不存值**（凭据不进插件目录，这一条已经由 §4 的状态与内容分离保证）；
- `userConfig` 里的字段名**登记在列表接口里**（界面显示「配置项 N」），
  值将来的落点是 `app_settings` 的 `plugins.config.<name>.<键>`；
- **录入的端点与界面还没做**：所以界面上只显示"声明了几个配置项"，
  不提供输入框——一个录不进去的入口就是 ZCode 那个反面教材。

**明确没做的**（写在这里，免得被当成漏了）：

1. 在线市场（下载、来源、版本锁、跨源依赖）——技能侧已有
   （`services/skill_market.py` / `skill_sources.py`），插件侧要等"插件里的代码怎么过闸"
   这个问题答完；本轮**目录即市场**；
2. 插件配置项的录入端点与界面；
3. 四类能力面的执行（见 §3）；
4. 用户自己新增/删除插件目录——那是文件系统里的事，界面只读、只启停。
