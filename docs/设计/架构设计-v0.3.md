## 1. 路线修正：为什么改

v0.2 时代的隐含形态是"后端（含会话、知识库）集中在局域网服务器，各机器用 Web UI /
桌面壳远程访问"。这条路线在真实使用中暴露出两个结构性问题：

1. **Agent 与工作区绑定 = 与机器绑定**。工作区是一组机器语义（绝对路径、沙箱执行、
   文件监听、Office 导出、产物落盘），跨机器没有可移植性。产品的核心场景
   （写论文、做 PPT、处理文档）摸的必须是用户眼前这台机器的文件系统；
2. **按 loopback 写出来的薄客户端，跨机器就原形毕露**。界面从服务器加载、
   每次点击一串同步 XHR——localhost 上被 0 延迟掩盖，跨机器后首屏慢、
   切菜单卡。归因不是"数据在远端"，而是**交互路径上存在"一次点击 = 一次同步远端往返"**。

修正后的形态一句话：**Agent 本机优先（界面、运行时、数据全部在本机循环），
知识库与备份作为可插拔提供者经局域网接入，缺失即降级。**

两条推论，以后不必再讨论：

- **NAS 不可达 ≠ 不能用**。本机运行时不设门禁——这是用户自己的机器，信任边界就是
  机器本身；NAS 凭据只在真正调知识库/备份时才需要。登录是提供者那半边的事，
  不是 Agent 的入场券；
- **模型凭据走本机**（取代《数据归属与同步 v0.1》"模型 key 不可本地化"一条），
  离线时对话照跑。

## 2. 总体形态

```
┌───────────────────────── 用户主机（本地优先） ─────────────────────────┐
│  桌面壳（Tauri）                                                      │
│  ├─ 前端产物：**打包在壳内**（自定义协议本地读出，不做远程加载）        │
│  ├─ 本地后端（边车演进而来）：轮次执行 + 会话/产物/笔记/设置 全本地存储   │
│  └─ 提供者注册表：握手成功的提供者，其页面才激活（§3）                  │
└───────────────┬──────────────────────────────┬──────────────────────┘
                │ 窄 API（握手 + 检索/入库）      │ 窄 API（握手 + 快照/恢复）
┌───────────────▼────────────────┐  ┌───────────▼─────────────────────┐
│  知识库服务（NAS）              │  │  备份桶（NAS MinIO）             │
│  PG(pgvector/tsvector) + MinIO │  │  append-only 快照（§7）          │
│  + 可选独立管理台（另一个应用）  │  │                                 │
└─────────────────────────────────┘  └─────────────────────────────────┘
```

- 两个提供者可以指向同一台 NAS，也可以各自独立；不配知识库，备份照样能配；
- **知识库的独立管理台**（浏览器直连 NAS 用的完整管理界面）允许存在，
  但它是"另一个独立应用"，**不是嵌进 Agent 的插件**（§3.3）。

## 3. 提供者模型（可插拔的唯一概念）

Agent 内核只有一种扩展概念：**提供者（Provider）**。当前定义两个，第三个要等
真出现再加，不提前抽象。

### 3.1 接口三件套

每个提供者实现三件事：

| 提供者 | ① 握手 | ② 主能力 | ③ 状态 |
| --- | --- | --- | --- |
| `KnowledgeProvider` | 连通性 + **能力集**（检索模式/入库格式/协议版本） | 检索（轮次中）、入库（上传/跟踪） | 连接状态、库清单 |
| `BackupProvider` | 连通性 + 能力集（快照格式/恢复点枚举） | 快照上传、按点恢复 | 最近快照、配额 |

- **版本契约长在握手上**：交换的是能力集，不是干巴巴的版本号；
- **"无"是一个合法实现**（断连/未配置时的空实现）——离线降级由此自然成立，
  内核不需要到处写 `if (在线)`；
- 多机并发使用同一个 NAS 知识库的三条规则（家庭/单人多机场景，不建 ACL）：
  **按内容哈希去重、last-writer-wins、库归账户一份不分命名空间**——写进 API 契约。

### 3.2 页面激活规则

**能力在，页面在；能力缺席，页面不存在。**

- 知识库页面、备份页面的**代码随 Agent 前端打包**，平时休眠；
  对应提供者握手成功才注册进导航。断连/未配置时导航里就没有那几项——
  而不是几个点进去报错的死页面；
- 知识库的设置 UI 收归「知识库连接」一处（连哪个库、什么凭据、什么状态），
  不再散在 Agent 设置里。

### 3.3 插件插的是能力，不是网页

**不做"知识库页面由知识库服务远程提供、嵌进 Agent"**（iframe 路线）。理由：
跨框的 token 递送、双设计系统、浮层裁剪、拖拽入库，以及最要命的跨框交互
（`[n]` 引用开出处抽屉、产物卡「存进知识库」、输入框知识库开关）需要发明一套
postMessage RPC——UI 级契约比数据 API 脆得多。页面归属决定体验归属。

## 4. 数据住在哪（v0.3 版归属表）

**本表取代《数据归属与同步 v0.1》§1 与之冲突的行。**

| 数据 | 归属 | 说明 |
| --- | --- | --- |
| 会话 / 轮次 / 步骤 / 产物引用 | **本机 SQLite**（唯一权威） | 每台机器的会话归每台机器——产物路径是机器本地的，漫游过去也是死链；**跨机流动走备份恢复（§7），不建同步引擎** |
| 本机工作区文件 | 本地磁盘 | 永不上传，除非用户显式入库（沿用旧约） |
| 笔记 / 长期记忆 / 设置 | 本机存储 | 随备份快照走（§7） |
| 知识库（文档/切块/向量/索引） | **NAS**（PG + MinIO） | 解析、嵌入、检索、向量索引全在服务端；本地只留**元数据缓存**（§6.3） |
| 账号 / 认证 | 本机运行时**不设门禁**；NAS 侧账号仅用于知识库/备份 API | 模型 key、NAS token 都在本机钥匙串（§5.5） |
| 技能库（市场装的） | 本地 | 沿用旧约 |
| 分界线 | **画在 API，不画在数据库** | 沿用《数据归属与同步 v0.1》§2：客户端永不直连 PG；"后端在本地、库在远程"不是目标形态 |

## 5. 本地存储分层

实证依据见《Kimi桌面端-本地存储调研 v0.1》；下表"依据"列指该文档的条目。

### 5.1 结构化数据 → 单 SQLite 库（WAL）

五条规范（照抄 Kimi daimon 侧 `conversations.sqlite` 的满分作业，调研 §4）：

1. `STRICT` 表；
2. `schema_metadata` 表存版本与迁移日志，**每次迁移前自动备份**到
   `migration-backup/<时间戳>/`；
3. 列表查询全部走 `(…, updated_at_ms DESC)` 最近序覆盖索引，列表页零排序扫描；
4. 列表预览字段（标题/状态/首轮摘要）与正文分离，正文/大字段按路径引用外部文件；
5. 单库文件：`kylab.db`（+ `-wal`），位置固定、可直接备份。

### 5.2 应用态小 JSON（受控使用）

只管"一文件一关注点、坏了重建也不疼"的：窗口几何、界面偏好、最近打开的会话。
**原子写（临时文件 + 改名）；集合型数据禁入**（写放大是反面教材，调研 §4）。

### 5.3 文件类 → 目录分片

原件/产物/附件按实体分目录（每个实体自成一个小目录），SQLite 里存引用；
**缓存目录严格可弃**——删了只丢速度不丢数据。

### 5.4 日志

文本 20 MiB 硬上限滚动（`main.log` + 单个 `.old`，日志目录永 ≤26 MB、可直接 grep）
+ 需要结构化查询时按天 SQLite 索引。（整套照抄，调研 §5-4。）

### 5.5 秘密 → 系统钥匙串

NAS token、模型 key **一律进系统钥匙串**（Windows DPAPI / `keyring` crate）；
落盘的加密文件带 `encryption:` 自描述字段。**三处凭据三种待遇是反着抄的**
（调研 §5-不抄-5）；config.json / webview 存储 / 明文 TOML 一律不许放秘密。

## 6. 性能契约

用户拍板的预算：**启动可以慢（给进度条），启动之后不许卡。**
（"切换菜单、切换会话出现卡顿"是不可接受的。）

### 6.1 四条设计铁律

1. **启动期一次性付清**：开库、读会话索引进内存、加载设置、读知识库目录的
   本地缓存——全走本地磁盘，进度条如实报阶段；模型连通性检查等放后台，不挡首屏；
2. **交互路径零网络**：切菜单/切会话/发消息只读内存与 SQLite（预算 <50 ms）；
   远端调用（检索、备份、刷新、快照）永远在后台，失败不堵交互；
3. **切会话 = 磁盘命中**：当前会话正文从本地库出，最近 N 个会话预载内存；
4. **写操作乐观化**：界面先动，落盘异步（WAL 单次写入 ~1 ms）。

### 6.2 前端进壳

前端产物**打包进桌面壳**、经自定义协议本地读出——首屏不付任何网络代价
（Kimi 的 Code Cache 证据：壳与字节码落盘是流畅感最大单一来源，调研 §2）。
壳更新走内置 updater，**更新器只留一份回滚包**（不抄 866 MB 堆积）。
实施规格已有：《[Tauri-壳资源分离与前端热更新-实现规格 v0.1](../规范/Tauri-壳资源分离与前端热更新-实现规格-v0.1.md)》——按它落地，本文不再复述。

### 6.3 知识库元数据缓存

知识库的**读路径元数据**（库列表、文档列表、条目信息）落本机 SQLite 缓存：
带 `etag` / `last_modified` 列，**stale-while-revalidate**（先画缓存、后台再验证）。
**轮次中的检索调用不缓存**（正确性优先；它是"每轮几次"不是"每点一次"，
局域网延迟可忍）。**一致性靠再验证（revalidate-on-focus + 版本戳），
不靠 TTL 猜**——多机改同一个库，TTL 一定会脏。

## 7. 备份与恢复

**备份落 MinIO 快照桶，不落知识库的 PG。** 知识库的 PG 是其生产库、schema 归
知识库服务独有；备份写进去等于两套生命周期住进一个库（迁移互相砸、恢复要先装
知识库）。备份要的是又笨又稳的东西：

- 本机导出快照（SQLite 备份 + 记忆/设置文件打包）→ 上传 MinIO 独立桶，
  **append-only、带时间戳、可校验、按点恢复**；
- 备份内容分两类：会话/记忆/设置（小、必须备）与工作区产物（大、选择性备）；
- 恢复还有个隐藏红利：**在另一台机器上恢复一次，就是将来的"会话漫游"**——
  今天不建同步引擎，明天也有退路。

## 8. 安全边界

1. 本机运行时不设门禁（§1 推论）；**Auth 只存在于两个边界**：模型 API、
   提供者 API，凭据全在钥匙串（§5.5）；
2. NAS 侧的知识库/备份 API 沿用现有鉴权（api key），token 由壳在握手时递送，
   不进日志、不进 webview 存储；
3. 客户端永不直连 PG（沿用，§4 分界线）。

## 9. 迁移阶段

每阶段独立可验收，**顺序不许倒**（4、5 先做就是给烂地基刷漆）。

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| **M1** 前端进壳 | 按《壳资源分离与前端热更新-实现规格 v0.1》落地：产物打包/热更、自定义协议、updater | 断网（除模型/KB API）首屏秒开；打开不再从 NAS 拉 UI |
| **M2** 会话落本机 | 本地后端接管会话/轮次/产物/笔记/设置：§5 存储分层落地（SQLite 单库 + 五条规范），现有 NAS 会话提供一次性导入 | 断 NAS 时对话全流程可用；切会话 <50 ms；旧会话导入可回滚 |
| **M3** KnowledgeProvider | 知识库抽成提供者接口（握手/检索/入库）+ 页面激活规则 + 设置收归一处 | 不配知识库时导航无知识库页、Agent 全流程不受影响；配上后页面出现、检索入库正常 |
| **M4** 知识库元数据缓存 | §6.3（SQLite + etag + SWR） | 二进知识库页秒开（先画缓存）；后台再验证后列表如实更新 |
| **M5** BackupProvider + 钥匙串收编 | §7 快照/恢复；所有秘密迁入钥匙串、明文遗留清零 | 断网快照入队、联网后补传；按点恢复到干净机器可用 |

## 11. 明确不做的

1. **会话同步引擎**（跨机实时同步）：备份恢复覆盖漫游诉求，同步引擎是过度设计；
2. **知识库 ACL / 分享协作**：家庭/单人多机用 §3.1 三条规则足够；
3. **远程 UI 模块嵌入**（知识库页面由 NAS 出、iframe 进 Agent）：§3.3；
4. **本机跑向量化/嵌入**：重活全在 NAS 知识库服务；
5. **第三、第四个提供者**：等真实需求出现再加，不提前抽象。
