# 轻量知识库产品 · 架构设计文档

> 版本：v0.2（四轮讨论结论整合版）
> 日期：2026-09-10
> 状态：架构基线，替代 v0.1
> 变更摘要：新增数据生命周期、动态解析引擎、存储选型论证、embedding 方案、检索调试台、安全边界、容量规划；修正云端解析额度；调整数据源优先级（RSS/Atom 提前，WebDAV 延后）

---

## 1. 产品定位

一个**轻量级知识库产品**，面向**个人消费级用户、局域网部署**，核心能力对外以 **MCP Server + OpenAPI（REST）+ 官方 Skill** 三种形式提供，主打**向量检索服务**。

### 1.1 目标用户与场景

- 个人用户在本地/局域网部署，无公网服务器、无公网 IP；
- 知识库服务被局域网内各类 Agent 及开源产品（可接入 QQ、微信等公网渠道的网关类产品）调用；
- 不面向企业用户，不做多用户并发写、不做知识库分享协作。

### 1.2 定位决策

| 决策项 | 结论 |
|--------|------|
| 产品形态 | 纯知识库，不做 Agents / 工作流编排 / 文档编辑器 |
| 解析架构 | 可插拔解析服务（云端 / 本地 / 局域网统一路由）+ **逐文件动态引擎选择** |
| 解析产物 | 所有文件统一转为 **Markdown**，向量化只针对 Markdown |
| 图谱与 Wiki | 可拔插增强模块，默认关闭 |
| 数据源 | P0：本地上传、HTML 抓取、RSS/Atom 订阅；延后：WebDAV |
| 图片策略 | 不理解的"位置锚点"方案 |
| 存储 | SQLite 单实现 + 接口抽象 + 预留 PG 后门 |
| embedding | 默认云端免费 API（硅基流动 BGE），本地模型可选 |

### 1.3 参考产品借鉴点与规避点

| 产品 | 借鉴 | 规避 |
|------|------|------|
| WeKnora（腾讯） | 图数据库 + Wiki 生成的产品形态；轻量分层 | 大文件处理不稳定；**一批文件只能绑单一解析引擎**（我们要逐文件动态路由）；图数据库内存开销大 |
| RAGFlow | 多样解析服务配置；**按文件类型的 chunking 预设参数模板** | 整体偏重，链路长 |
| Dify / MaxKB / FastGPT / Notion | 曾用产品，作交互与能力边界参考 | Agents / 编排 / 编辑器不纳入 |

## 2. 总体架构

```
┌───────────────────────── 接入层 ─────────────────────────┐
│  MCP Server (stdio + Streamable HTTP)  │  OpenAPI (REST)  │
│  官方 Skill（封装 API） │  Web 控制台（含检索调试台）        │
└────────────────────────────┬────────────────────────────┘
┌────────────────────────────▼────────────────────────────┐
│                      核心服务层                            │
│  知识库管理 │ 摄入流水线(状态机) │ 检索服务 │ 数据源连接器     │
│  任务调度(asyncio+SQLite 队列) │ Webhook 通知              │
├──────────────────────────────────────────────────────────┤
│                解析插件层（ParserProvider 接口）             │
│  探测(Probe) → 逐文件动态路由                               │
│  ├─ MinerU（云端 API / 本地）— 文字型 PDF 直提、复杂版面     │
│  ├─ PaddleOCR（AI Studio API / 本地）— 扫描件 OCR           │
│  └─ Python 库（pandas/openpyxl/python-docx/markdown-it）   │
├──────────────────────────────────────────────────────────┤
│                      存储层（全部嵌入式）                     │
│  SQLite(元数据+任务状态) │ sqlite-vec(向量) │ FTS5(全文)     │
│  DuckDB(表格结构化副本) │ 本地文件系统(原文+图片+Markdown)   │
│  [可选] 图数据库（图谱模块启用时才部署）                       │
└──────────────────────────────────────────────────────────┘
```

### 2.1 技术栈

| 层 | 选型 | 理由 |
|----|------|------|
| 语言 | **Python** | 解析/ML 生态全在 Python，官方 MCP SDK 有 Python 版 |
| Web 框架 | FastAPI | 异步原生，自动生成 OpenAPI 文档 |
| MCP | 官方 `mcp` Python SDK | stdio + Streamable HTTP 双模式 |
| 元数据/任务 | SQLite | 零依赖单文件，消费级部署友好 |
| 向量 | sqlite-vec（int8 量化，按库分区） | 见第 8 节论证 |
| 全文 | SQLite FTS5 + jieba 分词 | 与元数据同库 |
| 表格 | DuckDB | 嵌入式，支撑结构化查询旁路 |
| 队列 | asyncio + SQLite 任务表 | 不引入 Redis，重启可恢复 |
| 探测/切分 | pypdf + PyMuPDF | 文本层探测、页范围切分 |
| 对象存储 | 本地文件系统（MinIO 可选） | 消费级无需真对象存储 |
| embedding/rerank | OpenAI 兼容 client | 云端/本地同一接口 |
| 控制台前端 | Vue 3 + Vite | 文件树、任务进度、调试台 |
| 打包 | Docker Compose 为主，后续可出 Windows 一键包 | — |

**进程模型：单机 2 个进程**——主服务（API + MCP + 队列 + 控制台静态托管）+ 可选本地解析引擎。无 Redis / PostgreSQL / MinIO 必选依赖。主服务常驻内存约 300–500MB；纯云端解析路线 4GB 内存机器可跑。

## 3. 接入层

### 3.1 三种接入方式（能力等价）

| 接入方式 | 说明 |
|----------|------|
| MCP Server | stdio（本地客户端）+ Streamable HTTP（局域网内其他机器） |
| OpenAPI (REST) | 与 MCP 工具一一对应，共用服务层 |
| 官方 Skill | 预配置好接口与鉴权的 SKILL.md + 脚本，Agent 装上即用 |

**MCP 拟暴露工具**：`list_knowledge_bases` / `create_knowledge_base` / `upload_document` / `add_data_source` / `search` / `get_document_status` / `delete_document`。

### 3.2 工程规范

- **API 版本化**：从第一天起路径带版本（`/api/v1/...`）；
- **幂等键**：上传类接口要求幂等键，防止客户端重试造成重复入库；
- **Webhook**：文档解析完成等异步事件可配置 webhook 通知（轮询 `get_document_status` 之外的推送通道）；
- **鉴权**：API Key 绑定知识库范围（可指定单个/多个库）+ 只读 / 读写两种权限；
- **文件访问**：图片与原文下载返回带过期时间的签名 URL（参考主流产品的鉴权机制）。

### 3.3 检索调试台（Web 控制台内置）

定位：**检索效果的调试工具**，不承担正式对话场景。

- 流程：提问 → 混合检索 → **展示命中 chunks（来源文档、页码、相似度、图片锚点）** → 拼接 prompt → LLM 回答；
- LLM 走 **OpenAI 兼容接口**，用户自填 base_url + key + 模型名，产品不捆绑模型；
- 参数外露可调：top_k、rerank 开关、相似度阈值、图片返回开关；
- 提供"**仅检索**"模式（不调 LLM），用于区分"检索不行"还是"模型不行"；
- 价值：刚录完文件即可验证解析与检索质量，无需配置 MCP 客户端。

## 4. 文档摄入流水线

**核心原则：全程异步 + 状态机化。** 每步可重试、可断点续跑、失败定位到具体步骤。

```
uploaded → probing → parsing → parsed → chunking → chunked → embedding → indexed
                                                                                │
                              （可选增强分支，默认关闭，失败不影响主链路）            │
                              enriching（图谱/Wiki） ──────────→ enriched ────────┘
```

| 状态 | 说明 | 失败处理 |
|------|------|----------|
| `probing` | 探测文件类型、页数、文本层覆盖率 | 重试 |
| `parsing` | 按探测结果动态路由解析引擎 | 指数退避；云端失败可降级本地节点 |
| `chunking` | Markdown 切块 + 图片锚点写入 | 重试，不重解析 |
| `embedding` | 批量向量化 | 按批次重试，断点续跑 |
| `indexed` | 检索可用 | 终态 |

除主链路外还有两个异常终态：`failed`（处理出错，可重试续跑）与 `canceled`
（用户主动叫停，同样可重新摄入）。取消是**协作式**的：接口把文档置为 `canceled`
并把在跑的任务收成 `canceled`，正在执行的摄入在下一个阶段边界发现并停手——
已经发出去的云端解析请求没法中途掐断，但它返回后不会再往下推进。

### 4.1 动态解析引擎（差异化核心能力）

针对 WeKnora"一批文件绑死单一引擎"的问题，**逐文件探测、逐文件路由**：

1. 抽样若干页，计算文本层覆盖率（可提取字符数 / 页面面积）；
2. **文字型 PDF** → MinerU 直提（不经 OCR，速度快一个量级）；
3. **扫描件/图片型 PDF** → OCR 路线（MinerU VLM / PaddleOCR）；
4. **混合型** → 页级路由：有文本层的页直提、无文本层的页 OCR；
5. 探测结果与路由决策写入任务记录，控制台可见"该文件为何走 OCR"。

### 4.2 大文件强制切分

| 文件情况 | 路由 |
|----------|------|
| ≤ 200 页 | MinerU 云端 / PaddleOCR API 均可（按健康检查与剩余额度选路） |
| 200–1000 页 | 优先 PaddleOCR API（单文件上限 1000 页）；走 MinerU 需切分 |
| > 1000 页 | 强制切分（任何渠道都超上限） |

- 切分方式：按页范围切为子任务（如 1000 页 → P1–P5），**流式、顺序**调用解析服务，避免并发打满配额或内存；
- 合并时重映射页码偏移，拼接跨边界的 chunk；
- **UI：文件列表显示为单个文件，点击展开子文件树**；单个子文件失败只需重跑该子文件。

### 4.3 统一 Markdown 产物

- 所有类型解析后统一产出 Markdown，图片以锚点语法内联（`![img](image_id)`）；
- 向量化只针对 Markdown；原文（PDF 等）在文件系统保留一份；
- **下载/取回提供两个选项：Markdown（解析产物）/ PDF（原文件），默认返回 PDF 原件**。

## 5. 检索服务

- **混合检索**：向量召回 + FTS5（BM25）召回，RRF 融合排序；
- **Rerank**：可选，用户自配 rerank 模型（OpenAI 兼容接口，如硅基流动 bge-reranker），不配置则跳过；
- **元数据过滤**：知识库、文件类型、数据源、时间范围；
- **图片上下文返回**：命中 chunk 含图片锚点时附签名 URL / base64；
- **对外边界：MCP/API 只返回检索结果原文，不做任何 LLM 预处理**（注入防护责任在调用方，写入 README 作为产品边界声明）。

### 5.1 Chunking 策略（三模式 + 预设模板）

| 模式 | 说明 |
|------|------|
| 固定长度 | 用户自定义块长与重叠 |
| 语义切块 | 按标题层级/语义边界 |
| 父子切块 | 小块召回、大块返回上下文 |

- 三种模式均支持，由用户选择，块长可调；
- 参考 RAGFlow 按文件类型提供**预设参数模板**（book / paper / manual / FAQ / table 等），用户可覆盖；
- chunk 带稳定 ID + 内容 hash + 标题路径注入（如"第3章 > 3.2节"）。

### 5.2 表格数据双路径

- CSV/Excel 解析后双写入：行文本进向量库（语义检索），结构化表进 DuckDB（精确查询）；
- MVP 先做向量路径 + 保留结构化副本，SQL 查询旁路缓做。

## 6. 数据生命周期

### 6.1 Chunk 级增量更新

- 文档更新（重新上传 / 数据源变更）时，按位置编码对齐新旧 chunk 序列，仅替换变化 chunk 的向量；
- 纯文本类（MD/TXT）精确对齐；PDF 因重解析版面可能漂移，采用"位置对齐 + 相似度兜底"。

### 6.2 删除：级联 + 影响确认

- 删除前返回影响清单（chunk 数、图片数、Wiki 页面、图谱节点数），用户勾选"级联删除"后执行；
- 走异步删除流水线，同步清理：文件系统（原文/图片）、向量、元数据、（可选）图谱；
- **回收站机制**：原文保留 7 天冷备，向量立即删除，防误删全量重跑。

### 6.3 去重

- 文件级内容 hash；上传命中相同 hash 时提醒"检测到相同文件"，仅保留一份。

### 6.4 Embedding 模型规则（重建索引策略）

| 场景 | 规则 |
|------|------|
| 库内已有向量化文件 | **不允许更换模型**；需更换则新建知识库 |
| 更换 endpoint | 允许，但**模型 ID（含版本）必须一致**（如本地 BGE-M3 → 硅基流动 BGE-M3） |
| 维度相同但模型不同 | **禁止**——维度相同不等于向量空间兼容，混用会导致检索静默失效 |

配套：ParseResult、chunk 元数据分层持久化，升级解析器/chunking 策略时可只重跑下游。

## 7. 图片处理策略（位置锚点方案）

| 阶段 | 策略 |
|------|------|
| 解析 | 不做图片理解；记录位置（页码、bbox、前后文锚点），直接利用 MinerU 版面中间产物 |
| 向量化 | 图片不预处理、不入向量库 |
| 存储 | 图片本体存文件系统，chunk 元数据记录 `{ image_id, 段落偏移, page, bbox }` |
| 检索 | 命中含图段落时附图片引用（签名 URL / base64） |
| 使用 | 仅检索返回后由对话模型处理 |

多模态扩展：ParseResult 预留 caption 字段位；音视频预留扩展点，暂不做。

## 8. 存储选型论证（SQLite vs PG）

### 8.1 结论

**SQLite + sqlite-vec + FTS5，单实现 + Repository 接口抽象 + 预留 PG 后门。** 不走双后端并行（30%–50% 永久开发税，小团队不可承受）。

### 8.2 sqlite-vec 压力刻度（1024 维、单库）

| 单库 chunk 量级 | 检索延迟 | 评价 |
|----------------|----------|------|
| < 10 万 | < 50 ms | 无感 |
| 10–50 万 | 50–300 ms | 轻松 ← **目标用户场景（5000 文档 ≈ 20–45 万 chunk）** |
| 50–100 万 | 0.3–1 s | 开始可感，量化+分库可压回 |
| 100–500 万 | 1–5 s | 有压力，考虑迁移 |
| > 500 万 | > 5 s | 超纲 |

### 8.3 配套措施

1. 向量表按知识库分区，检索先按 kb_id 收敛范围；
2. 默认 int8 量化（45 万 × 1024 维 ≈ 450MB）；
3. 定期 `VACUUM` 回收删除空间；
4. **迁移后门**：向量原样搬运（无需重新 embedding），抽象到位时 SQLite → PG 迁移约 1–2 周一次性工作量。

## 9. Embedding 方案

| 项 | 结论 |
|----|------|
| 默认 | 硅基流动免费 BGE API（OpenAI 兼容） |
| 备选 | 本地模型（Qwen3-Embedding-0.6B，CPU 可跑） |
| 节点抽象 | embedding 与解析共用"云端/本地 endpoint"路由抽象 |
| 隐私提示 | 默认云端方案意味着文本分片外发，文档与设置页须明示；隐私敏感用户选本地模型 |

**容量测算（5000 文档）**：首次全量 embedding 约 1–2 亿 token，受免费 API 速率限制需数小时至一两天，异步队列 + 断点续跑兜底；之后日常增量无感。

## 12. 可观测性

- 文件级状态机 + 阶段级进度（如 parsing 3/5 份、embedding 120/480 chunks）；
- 卡住超阈值自动标黄/标红；
- 100 个文件批量上传的顺序执行过程全程可视；
- MinerU token 90 天有效期：配置页显示过期时间，健康检查识别 401 并引导换新。

## 13. 部署形态与运维

| 形态 | 说明 |
|------|------|
| 本地/局域网（主） | Docker Compose 一键起，纯云端解析路线 4GB 内存可跑 |
| 解析节点 | 云端 API ↔ 本地引擎 ↔ 局域网节点，同接口换 endpoint |

- 并发：按用户硬件给出推荐配置表（内存/CPU 档位 → 摄入并发数），文档提供；
- 检索评估体系：缓做；迁移导入工具：不做；检索反馈端点：低成本预留。

## 14. MVP 范围

**做**：MCP（stdio+HTTP）/ REST / 官方 Skill 三接入、上传+HTML+RSS/Atom 数据源、动态解析引擎、大文件切分、异步状态机、混合检索 + 可选 rerank、chunking 三模式与预设、图片位置锚点、检索调试台、级联删除 + 回收站、文件去重、可观测性、API 版本化 + 幂等 + webhook。

**缓做**：WebDAV、图谱/Wiki 增强、表格 SQL 旁路、检索评估体系、本地 embedding 模型包。

**不做**：Agents/编排、文档编辑器、知识库分享协作、数据迁移工具、音视频。
