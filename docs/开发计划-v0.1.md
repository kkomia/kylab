### 1.1 依据文档

| 依据 | 版本 | 本计划引用的关键约束 |

### 1.2 前提假设

1. **人力**：单人全职开发（按 5 人日/周折算）。两人并行方案见 §5.3。
2. **范围**：严格等于架构 §14「做」清单；「缓做」「不做」两类一律不排期、不预留代码分支（仅保留接口扩展点）。
3. **额度**：云端解析（MinerU / PaddleOCR）与 embedding 走免费额度，开发期以 mock 夹具为主，真实 API 仅手工抽样验证（架构 §15）。
4. **环境**：开发机为 Windows；交付形态为 Docker Compose（架构 §13）。当前开发机 **无 docker**，见风险 R9。
5. **节奏**：里程碑内小步提交；每个里程碑合并前跑一次 `code-quality-check` 质检。

## 2. 全局完成定义（DoD）

任一里程碑只有在下列六条全部满足时才允许标记完成：

| 编号 | 条目 | 判定方式 |
|------|------|----------|
| D1 | **可演示**：本里程碑的 Demo 路径端到端跑通 | 按 §3 的「可演示增量」列逐条手工演练 |
| D2 | **测试齐备**：新增功能带测试且镜像同构；涉及的架构承诺项有集成测试 | `pytest` / `pnpm test`，对照 §6.2 映射表 |
| D3 | **门禁全绿**：ruff、emoji 扫描、pytest、eslint、vitest 全通过；CI 绿 | 本地 + CI 双重确认（规范 §5.2「CI 是最终裁判」） |
| D4 | **质检达标**：`code-quality-check` 报告无 P0、无未登记的 P1 | 质检报告归档进里程碑记录 |
| D5 | **文档同步**：接口变更写进 `docs/API-接口规范-*.md`；架构级决策回写架构文档 | 对照 §9 |
| D6 | **纪律零违规**：`api/`、`mcp_server/` 无业务逻辑；`services/` 无 SQL | 人工审查 + 分层检查脚本 |

### 真实语料验证（2026-09-10，眼科医学指南语料 115 份）

用 `F:\下载\24-17年` 下的真实 PDF 语料做了一轮端到端验证，**两条云端通道各自跑通**：

| 样本 | 探测结论 | 解析器 | 结果 |
|------|----------|--------|------|
| 眼轴长度共识（2.6MB） | text / 覆盖 1.00（抽样 5 页 5 页有文本层） | MinerUCloudParser | 119 块 |
| 眼外伤救治商榷（613KB） | text / 覆盖 1.00 | MinerUCloudParser | 8 块 |
| 自造扫描件（文本层剥离） | **scanned / 覆盖 0.00** | MinerUCloudParser（带 OCR） | 8 块 |
| 同上（临时清空 MinerU token） | scanned | **PaddleOCRApiParser** | 8 块 |

**这一轮验证到的**：

- **逐文件动态解析真的在起作用**：同一批 PDF 里，文字型与扫描件分别得到不同处理，
  路由理由（`抽样 N 页，M 页有文本层`）已落进 `parse_results.probe_meta`，
  控制台将来能直接回答"这个文件为什么走了 OCR"；
- **OCR 质量可用**：扫描件经 OCR 后识别出的中文比原文本层还规范
  （自动补了中英之间的空格、全角标点归一），`作者:孙鹏锐,Email:` 这类混排没有粘连；
- **备选通道真的能接管**：清空 MinerU token 后，同一个扫描件由 PaddleOCR 独立解析成功
  （同样的 8 块、同样的正文），证明架构 §4.1「云端失败可降级备选节点」不是纸面承诺；
- **去重生效**：同一份扫描件再传一次被内容 hash 拦下（知识库仍是 3 篇、4 次提交）。

**两点如实记录**：

1. 备选通道当前是"凭据缺失时切换"，**不是"调用失败时切换"**——
   `supports()` 里判的是 token 是否配置；MinerU 在线但返回错误的场景尚未做自动降级
   （那需要路由层捕获 `ParseError` 后重试下一个候选，属于 M6 的收尾项）；
2. 该语料 115 份**全是文字型**（医学期刊 PDF 带完整文本层），没有天然扫描件样本，
   上表里的扫描件是本地用 PyMuPDF 渲染成图后重新打包生成的——结论对这种合成样本成立，
   对真实拍照件（倾斜、阴影、低分辨率）还需要另找样本验证。

**如实记录的另一面**：PaddleOCR 那条"接管成功"是**临时清空 MinerU token** 造出来的——
即"凭据缺失时切换"，不是"调用失败时切换"，两者不是一回事（见下面第 1 点）。
它证明的是备选通道本身能端到端跑通（提交 job → 轮询 → 取 JSONL → 出 Markdown），
**不**证明 MinerU 在线但解析失败时会自动改走它。

**过程中抓到并修掉的两个真实缺陷**（都是"跑通链路"才会暴露的）：

1. **PDF 被纯文本直通接走**：PDF 的头 `%PDF-1.7` 是 ASCII，探测据此判成"文字型"，
   而 `PlainTextParser.supports()` 又接受 `probe.kind == TEXT`，于是切出来的块是原始 PDF 字节流。
   修法两处：探测先按格式分支（PDF 走页级文本层探测），纯文本解析器拒绝二进制容器后缀。
   教训写进注释：**"覆盖率高"只说明不需要 OCR，不等于"能当 txt 读"**。
2. **解析器 `name` 大小写不一致**：云端解析器写成 snake_case，与 `PlainTextParser` 的
   `<引擎><节点>Parser` 约定不一致，而 `parser_name` 会写进 `parse_results` 并在界面显示。
   已在 `parsers/base.py` 写明约定并统一。

**遗留**：解析产出的图片尚未写入对象存储（`ParseResult.image_ids` 已就绪，
`IngestService` 侧的落盘与 Markdown 链接改写还没做）；`documents.page_count` 仍为 null
（探测已经拿到页数，写入链路待补）；备选节点的**失败降级**（而非凭据缺失降级）待 M6 补。

### 快速检索对话 —— 已完成（2026-09-10）

定位是**让用户快速验证"知识库里到底有没有、答得对不对"**的最短链路：

| 产物 | 落点 |
|------|------|
| LLM 客户端 | `services/llm.py`：OpenAI 兼容 `chat/completions`，流式与非流式共用一套构造 |
| 对话编排 | `services/chat.py`：检索 → 提示词 → 作答；`build_messages` 是纯函数，好测 |

**产品边界没有破**（重要）：`/search` 仍然只返回检索原文、不做任何 LLM 加工；
LLM 只出现在对话这一层，并且**强制带引用**——回答必须能回到原文，
否则"验证"这件事本身就不成立。架构 §5 的原文表述在 v0.3 回写时补一句口径说明即可。

**实测（真实凭据、真实链路）**：

1. 设置 `Qwen/Qwen3.5-4B` + 硅基流动 key，`POST /settings/test/llm` 返回"可用（回复：可用）"；
2. 一次性问答：问"儿童近视怎么监测眼轴"→ 回答分点列出测量特点、设备、参考标准与数据应用，
   带 `[1][3]` 引用，6 条出处全部来自《2023年眼轴长度在近视防控管理中的应用专家共识》；
3. 流式问答：`sources`（4 条引用）→ **421 个 delta 块**（打字机效果）→ `done`，引用标题与章节路径正确。

**过程中抓到并修掉的三个真实缺陷**：

1. **推理模型"不回答"**：SiliconFlow 上的 `Qwen/Qwen3.5-4B` 默认先输出 `reasoning_content`，
   `max_tokens` 被吃光后 `content` 为空——表现为"模型没有回答"。
   修法是默认传 `enable_thinking: false`，并把它做成设置项（需要更高质量时再打开并调大长度）。
   设置页的 LLM 连通性测试因此**真发一次最小对话**，专门用来暴露这一类"只回思考不回正文"。
2. **两条 system 消息被 400 拒**：资料原本拼成独立的第二条 system，
   端点返回 `20015 System message must be at the beginning`。
   改为把提示词与资料合并进**唯一**那条 system（`build_messages` 的注释里写明了原因）。
3. **流式第一个事件就把连接打断**：`SourceRef` 是 `slots=True` 的 dataclass，**没有 `__dict__`**，
   用它序列化会抛 `AttributeError` 并截断连接（客户端看到的是 `IncompleteRead`，很难查）。
   改用 pydantic 的 `model_dump()`。这一条已加进 `tests/integration/api/test_chat_api.py`。

**尚未做**：会话持久化（没有 `conversations` 表，历史只在前端内存里）；多轮改写
（当前把历史原样带上，不做指代消解）；引用高亮（回答里的 `[1]` 还没做成可点跳转）。

### 11.1 字号与字体调整系统（用户反馈：「web 字体偏小」）

#### 调研结论（实测本机 DSH 构建产物，非二手资料）

DSH 的字体与字阶（`--dsw-font-*` 令牌，直接从 minified CSS 提取）：

| 项 | DSH 的取值 |
|----|-----------|
| 字体栈 | `-apple-system, BlinkMacSystemFont, "Segoe UI", "PingFang SC", "Hiragino Sans GB", "Microsoft YaHei", "Helvetica Neue", Helvetica, Arial, sans-serif` |
| 正文 | **14px / 24px**，字重 400 |
| 阶梯 | 11 / 12 / 13 / 14 / 16 / 18 / 20 / 24px |
| 代码 | 12px；代码块 11px |

**关键发现：DSH 的正文字号与我们一样是 14px**，所以「偏小」的成因不是基线值，而是
**分布**——DSH 把 11px 只留给代码块，13px 留给表格与流内次要行，正文稳稳占住 14px；
而我们把 `--text-meta-size`(13px) 用于 `font-size:` 达 **43 处**、
`--text-micro-size`(12px) 达 **35 处**（统计口径：`frontend/src` 下 `font-size: var(--text-*)`
的出现数，不含 `base.css` 里的定义行），小字号占满了界面外壳（侧栏、标签、说明、元信息），
正文反倒只是众多字号中的一个，读起来自然整体偏小。

#### 更值得抄的是它的「可调」机制

DSH 用两个变量联动，值得直接借鉴：

```css
--dsh-content-font-size: 14px;                                    /* 用户可调 */
--dsh-content-font-delta: calc(var(--dsh-content-font-size, 14px) - 14px);
/* 正文行高跟着字号一起走 */
--dsw-font-markdown-base: var(--dsh-content-font-size, 14px) / calc(24px + var(--dsh-content-font-delta));
/* 标题整条阶梯一起平移，比例不散 */
--dsw-font-markdown-h1-font-size: calc(21px + var(--dsh-content-font-delta));
/* 次级字号单独推导：设到 14 时是 13，超过则退两档，避免和正文太近 */
--dsh-content-font-size-secondary: min(calc(var(--dsh-content-font-size, 14px) - 1px),
                                      max(13px, calc(var(--dsh-content-font-size, 14px) - 2px)));
```

三个要点：**正文可调**、**行高随字号同步位移**（否则字大了行距会显挤）、
**标题用加法平移而非乘法**（比例不散）。

#### 我方的改造方案

1. **先修正基线分布**（这一步才是解决「偏小」的主因）：
   - `--text-body-size` 14px → **15px**（正文与阅读内容）
   - 新增 `--text-meta-size` 14px、`--text-micro-size` 13px（原 13/12 各升一档）
   - 落回 4px 阶梯：现存的 43 处 meta + 35 处 micro 就近归位，取消 13.5px 这类离阶值
2. **再引入可调层**：`--font-scale`（窗口级）与 `--content-font-size`（阅读区），
   按 DSH 的 delta 写法让行高与标题同步位移；默认档为「中」，可出「小 / 中 / 大 / 更大」四档
3. **设置入口**：外观分组里加字号档位选择，写入 `localStorage`（与主题同一机制，前端本地偏好，
   不进后端 `app_settings`）
4. **硬性约束**：任何档位的 `--text-micro-size` 实际值不得低于 **12px**；
   对比度在最大档下重新审计一遍（大字号下 WCAG 大字阈值降到 3:1，反而更宽松，但需实测确认）

### 11.4 API Key 鉴权 —— 已完成（2026-09-11）

M4 T4.4 落地。它同时封掉了监测报告指出的那条**凭据窃取路径**：无鉴权的
`PATCH /settings` + 可改的 `base_url` = 把用户的 API Key 转发到攻击者服务器。

| 产物 | 落点 |
|------|------|
| 凭据原语 | `core/security.py`：`kylab_sk_` 前缀 + 32 字节随机；只存 SHA-256 摘要 |
| 服务 | `services/api_key.py`：发放 / 校验 / 作用域判定（权限档位与库范围只有一个入口 `check_access`） |
| 请求级鉴权 | `api/auth.py`：控制台令牌与 API Key 统一成 `Caller`；`require_read` / `require_write` / `require_console` |
| 管理端点 | `api/v1/api_keys.py`：`GET/POST/DELETE /api-keys`（**只认控制台令牌**） |
| 首次初始化 | `api/v1/auth.py`：`GET /auth/status`（不鉴权）+ `POST /auth/console-token`（一次性） |
| 迁移 | `_MIGRATION_002`：`api_keys` 增 `key_prefix` 列，供列表分辨"哪把是哪把" |

**三种身份，各管一段**：

| 身份 | 能做什么 | 为什么这样分 |
|------|---------|-------------|
| 控制台令牌 | 全部，含设置页与密钥管理 | 设置页是 embedding/LLM 密钥的落点，且 `base_url` 可改——**外部密钥若能碰它就能截获凭据** |
| API Key（readwrite） | 上传、建库、检索、对话 | 作用域受 `knowledge_base_ids` 限制；列表与检索都会过滤 |
| API Key（readonly） | 只读 | 默认档位：给外部集成发"能删库的钥匙"不该是因为"没填那个字段" |

**默认不开启鉴权**（本机单人开发每次带令牌纯属折磨，且默认开启会让升级后所有客户端
立刻 401）。但"关着"不等于不设防——下面任一条件成立即自动生效：
`KYLAB_AUTH_ENABLED=true`、`KYLAB_CONSOLE_TOKEN` 有值、**库里已存在任何 API Key**。

**用起来才发现的一个死锁（实测踩到并修掉）**：上面第三条自动生效规则 + "设置页只认
控制台令牌"，会让**"凭据关着时建了一把钥匙"把自己锁在门外且无法恢复**。
补了 `POST /auth/console-token`：只在"库里与 .env 都没有令牌"时开放，设过即永久关闭。
响应与测试都钉住了这条恢复路径。

**顺带修掉一个跨零点的真 bug**：仪表盘活跃度按 `stamp.date()`（UTC）分桶，
而窗口用 `date.today()`（本地）——在 UTC+8 每天有 8 小时不重合，这段窗口里
「今天入库」恒显示 0，而库里明明有当天的新文档。改为统一按**本地日历日**归日
（`stats.local_day`）。这个 bug 白天开发时看不到，是跑测试跨零点才暴露的。

**门禁**：后端 **507 通过 / 0 失败**（本轮 +45：19 个服务单测 + 24 个接口单测 +
2 个跨时区用例）；ruff / emoji / 分层通过。前端四门全绿（58 通过）。

**还没做**（均记在上面的收口清单里）：幂等键、签名 URL、提示词注入缓解；
API Key 无有效期（架构未要求，只能"撤销后重发"轮换）。

| 接口 | `POST /knowledge-bases/{id}/documents` 支持 `Idempotency-Key` 头 |
| 维护 | worker 新增空闲维护钩子，**同时**把两个从未被调用的清理接上（见下） |

**四条判定**：键没出现过 → 占住并执行；键出现过且内容相同 → 回放上次响应；
**内容不同 → 409**（这条最容易漏，静默放行会让客户端以为新文件传上去了）；
键出现过但还没跑完 → 409「处理中」（回空会让客户端以为失败又重试）。

**与架构 §3.2 的一处刻意偏差**：架构写"上传类接口**要求**幂等键"，这里做成**可选**。
理由是我们已经有更强的兜底——内容 hash 去重（同一份文件重复上传本来就不会入库两次）。
幂等键补的是 hash 覆盖不到的那段：同键配不同内容的判定，以及"客户端连自己上次传没传
成功都不知道"的回放场景。强制会立刻打断既有前端与所有集成方，而收益只是换一种表达。
所以：**提供则生效，不提供仍受 hash 去重保护**。

**顺带修掉两个"写了却从没跑过"的承诺**：`purge_expired_idempotency_keys` 与
`purge_expired_trash` 写在存储层很久，但**没有任何调用者**——于是"键不会无限增长"
和"原文保留 7 天后不可恢复"实际上都没发生。给 worker 加了空闲维护钩子（一小时一次、
只在没活可干时跑、失败不影响消费），把两件事真正接上。

**过程中抓到的三个真缺陷**（都是写测试才暴露的）：
1. `model_dump()` 留下 `datetime` 对象，落库时抛 `TypeError`，而**抛出点在上传成功之后**
   ——"文件已入库但接口 500"，客户端重试又被幂等层拦成 409。改用 `mode="json"`。
2. 业务中途失败时键留着而响应为空，重试永远拿到"正在处理中"（比报错更糟，像"再等等就好"）。
   补了 `release`，失败即放键。
3. 上面那个 `release` 一开始是空操作：插入时 `_json(None)` 写入的是字符串 `"null"`，
   而不是 SQL `NULL`，所以 `response IS NULL` 永远不成立。改为写真正的 NULL。
